1. 全体像：同じ骨格、kit は「基盤ジェネレータ」として厚い

資料の実践編は次の3層を核にしている。

資料の概念 役割 kit での対応
ハーネス（馬具） 実行前に進路を伝える AGENTS.md / .cursor/rules/*.mdc / 14 Skills / 6段階 workflow
ガードレール（柵） 実行後に逸脱を機械判定 bin/quality-gate * / bin/foundation-gate * / 各種 gate-*.py
フィードバックループ 失敗出力を修正に戻す Advisory ループ（exit 1 → 修正 → 再実行）
構造イメージ
資料: Rules/AGENTS.md → Skills → Subagents → 品質ゲート → Advisory ループ
kit 拡張: 上記に manifest.yaml SoT / tracker・handoff / 6段階 workflow + Step Gate を追加

一致点

資料の3原則（進路を示す / 逸脱を検知 / ループを閉じる）は kit の設計思想とほぼ同型。特に Fowler 派の Guides（事前制御）+ Sensors（事後検証） は、kit の「Rules + Hooks + 品質ゲート」構成とよく対応する。

相違点

資料は「1プロジェクトに最小限のハーネスを育てる」前提。kit は manifest → 生成物 という Meta 層 SoT を持つ 再利用可能な基盤キット。同じ3層モデルの上に、セッション管理・キャンペーン追跡・ADR/GOTCHAS 進化機構が載っている。

2. 5流派と kit の位置づけ

資料第1部（スライド5–11）が整理する5流派に対し、kit は 単一派系のクローンではなく合成設計 である。骨格は Chase 派、実行モデルは Fowler 派、進化運用は Hashimoto 派、アーキテクチャ比喩は Chawla 派 が主成分となる。

結論: kit ≈ Chase 派（全体像）+ Fowler 派（制御ループ）+ Hashimoto 派（失敗進化）+ Chawla 派（OS 層比喩）。Codex 派の大規模自律開発は workflow / 並列 dispatch で部分的に共鳴するが、kit の主目的（manifest SoT から基盤を生成・監査する Meta 層キット）とは重心が異なる。

流派別の近さ（5段階）

順位 流派 代表者 近さ kit との対応
1 Chase 派 Harrison Chase ◎◎◎ モデル以外（Rules / Skills / Hooks / ゲート / オーケストレーション / handoff・tracker / サブエージェント）をすべてハーネス側に配置。「If you're not the model, you're the harness」に最も素直
2 Fowler 派 Birgitta Böckeler ◎◎ Guides = AGENTS.md / rules / Session Protocol。Sensors = bin/quality-gate * / gate-*.py / exit code Advisory ループ。事前制御 + 事後検証の閉ループ
3 Hashimoto 派 Mitchell Hashimoto ◎◎ GOTCHAS 即時記録 → maintenance-gotchas-workflow → Hook 昇格（同一違反3回）。失敗のたびに環境を強くする運用哲学を構造化
4 Chawla 派 Avi Chawla ◎ docs/AGENT_RUNBOOK.md の5層（Context / Constraints / Capabilities / Automation / Delegation）= OS 比喩。コンテキスト・外部状態・ツールを統合する OS 層
5 Codex 派 Ryan Lopopolo ○ 6段階 workflow、worker dispatch、並列 subagent、Step Gate Matrix は本番スケールの故障モード対策寄り。ただし kit は基盤ジェネレータであり、100万行 AI 生成アプリの主戦場とはスコープがずれる

Chase 派ツリーとの対応（スライド6）

Chase 派は「何がハーネスか」の包含関係を定義する流派。kit の全体スコープ定義として最もフィットする。

Chase 派の要素 kit の実装
ツールCursor ツール + bin/*-safe wrapper
オーケストレーションworkflow-orchestrator（6段階 + Step Gate）
メモリtracker-{campaign_id}.md / handoff manifest / turns.jsonl
コンテキストビルダーContext Budget / session-bootstrap / Documentation Navigation
ガードレールquality-gate + guard-git-write.sh
サブエージェントTask ツール + worker dispatch + deep-thinking A/B/C
リトライ／状態管理Advisory ループ（exit 1 → 修正 → 再実行）+ handoff 再開

実行モデルは Fowler 派

Chase 派は分類が主で「どう回すか」までは述べない。kit の 実行モデル として最も近いのは Fowler 派である。

ユーザー要求 → GUIDES（rules/AGENTS.md）→ AGENT → SENSORS（lint/test/gate）→ 成果物
                                    ↑___________自己修正フィードバック___________|

Session Protocol + QUALITY_GATE の Advisory ループは、この閉ループ制御系そのもの。

包含関係の論点（スライド11）：Chase / Chawla 側

観点 包含関係 kit の立ち位置
Chase / Chawla ハーネス ⊃ コンテキスト Context Budget / handoff / tracker をハーネス基盤の一部として設計 → こちら側
Fowler コンテキスト設計 ⊃ ハーネス guides + sensors は採用するが、コンテキスト管理もハーネス内に含める合成

各流派の kit への寄与（合成式）

流派 kit への寄与 主な根拠ファイル
Chase 派 ハーネスの 全体スコープ定義（モデル外のすべて） AGENTS.md / manifest.yaml / Skills 群
Fowler 派 Guides + Sensors による閉ループ制御 docs/QUALITY_GATE.md / rules / workflow-gate
Hashimoto 派 失敗駆動の環境進化 docs/GOTCHAS.md / framework.accd_axes[E]
Chawla 派 OS 層比喩によるレイヤー責務分離 docs/AGENT_RUNBOOK.md §1 5層モデル
Codex 派 並列・本番運用の故障モード対策（部分） workflow-orchestrator / worker dispatch

3. ハーネスの4道具：すべて実装、配分が異なる

資料スライド22の4道具と kit の対応。

道具 資料の位置づけ kit
ルール（常時） AGENTS.md 約50行から開始 AGENTS.md（170行）+ rules 3本 + CLAUDE.md。常時コンテキストは資料推奨より重い
プラン（タスク単位） 着手前に人間合意 .cursor/.tracking/tracker-{campaign_id}.md + session-planning + plan-gate.sh（必須7節を機械検査）
Skills（必要時） 特定手順をオンデマンド読込 14 Skills（workflow-orchestrator, agent-code-review, deep-thinking 等）。Progressive Disclosure で深さを分離
サブエージェント（役割単位） 文脈分離・並列化 Task ツール + workflow の worker dispatch + deep-thinking の A/B/C 並列分析

一致 資料の「左（常時）→ 右（深い）」の使い分けは kit でも採用。Documentation Navigation や step 別ドキュメント（docs/agent-tasks/agent-workflow/）で、全部を AGENTS.md に詰めない設計。

注意 常時ルールの総量は資料の「約50行」より明らかに多い。ただし kit は Meta 層ジェネレータなので、骨格を最初から揃える意図的な厚みがある。

4. ガードレール：「1コマンドの門」は同等、階層は kit の方が深い

資料のモデル

  • フォーマッタ → lint → 型 → ビルド → テストを check 1本に束ねる
  • 人間・AI・CI が同じ合格基準を使う

kit のモデル

  • 入口: bin/quality-gate verify または profile 別 bin/foundation-gate self
  • 内訳: G-GEN / G-BUILD / G-LINT / G-TEST（docs/QUALITY_GATE.md）
  • さらに ドキュメントゲート（G-DOC-ADR, G-DOC-NAMING）、セッションゲート（session-start-gate）、ワークフローゲート（step1〜archive）、完了チェック機械検査（G-TEST-COMP-001/002/003）
観点 資料 kit
成果物への柵 lint / 型 / テスト 同等 + 生成物 drift 検査（G-GEN）
行動への柵 Hooks / 許可リスト guard-git-write.sh（force push deny, gh deny, credential 保護）
合格条件 すべての門が緑 exit code 0（0/1/2 の3段階セマンティクス）
CI 整合 同じ check backend contract 経由で統一

一致 「IDE の赤線は見えない → エージェントが実行できるコマンドで判定」という資料の指摘は、kit の exit code ベース設計と一致。

拡張 資料はアプリ開発向けのシンプルな npm run check 想定。kit は基盤自身の冪等性・設計準拠・タスク完了・アーカイブまでゲート化。

5. 失敗から育てる（Hashimoto 派）：kit は AGENTS.md 1行追加を超えている

資料（スライド7, 23–24）: 逸脱が起きたら AGENTS.md に防止ルールを1行追加。

機構 役割
docs/GOTCHAS.md 失敗事例の即時記録
maintenance-gotchas-workflow Evolve-A: メタ層への再発防止修復
Hook 昇格パス 同一違反3回観測 → Hook へ昇格（manifest.yaml > framework.accd_axes[E]）
docs/DECISIONS.md 設計判断（D-* 次元）の ADR 記録

kit は Hashimoto 派の「失敗駆動で環境を強くする」を、ルール1行追加より構造化している。資料の精神は踏襲しつつ、再発防止を manifest / templates / hooks へ還流させるパイプラインが追加されている。

6. コンテキスト設計：資料の射程を kit が大幅に拡張

資料は「ルールを増やしすぎるとコンテキスト圧迫」と警告し、Skills で深い手順を分離することを推奨。

kit はこれに加えて Context Budget Auto-Handoff を実装（docs/CONTEXT_BUDGET.md）:

  • Yellow / Red 閾値で handoff を促す
  • .cursor/.session/handoff-{session_id}.md によるセッション引き継ぎ
  • tracker-{campaign_id}.md を campaign SoT として維持
  • compact 連動 handoff（Lost in the Middle 対策）

kit 独自 資料の Fowler/Chawla 派（コンテキストもハーネスの一部）に近く、単発タスクのハーネス設計を超えた「長時間自律運用」 のレイヤー。資料単体では触れていない kit の差別化ポイント。

7. セキュリティ：資料の lethal trifecta に kit は具体的実装あり

リスク 資料の対策 kit
間接プロンプトインジェクション 外部コンテンツへの注意 docs-first / 推測禁止（Humble 原則）
秘密情報漏洩 deny 設定で読めなくする Boundaries Never: .env / credential ファイル読取禁止
破壊的操作 Hooks / サンドボックス guard-git-write.sh で force push / 保護ブランチ push / gh pr merge を deny
サプライチェーン 人間承認 Ask First（commit/push/framework 変更）

資料が概念として述べる「行動への柵」は、kit では Hook + Boundaries + bin/*-safe wrapper として具体化されている。

8. 実施順序：思想は逆方向、運用では収束

資料の推奨順序（スライド33）

  1. 素の状態を観察
  2. ルールを約50行から
  3. 柵 + 1コマンドの門
  4. ループを閉じる
  5. 反復が見えてから Skills / サブエージェント
  6. 運用で育て、棚卸し

kit の生成モデル

  • 最初から manifest 経由で Rules / Hooks / Skills / Gates を一括生成
  • 個別プロジェクトでは PO が [要確認] を埋め、運用で GOTCHAS / ADR を育てる
資料 kit
初期投資 最小 → 観察 → 追加 骨格フルセット → 下流で調整
棚卸し 数か月ごとに全体見直し agent-kaizen（18観点の整合性検査）、bin/foundation-gate audit
技術的負債 モデル世代で作り込みが吸収される accd_axes.not_adopted で重い機構を意図的に不採用。ただし kit 自体は厚い

資料の Han Lee 批判（「ハーネスは次世代モデルに溶ける」）に対して、kit は 中核（Boundaries / 品質ゲート / Session Protocol）は残し、作り込み（Finding Code 79 等）は不採用 という明示的な線引きをしている（docs/AGENT_RUNBOOK.md の ACCD 5軸表）。

9. 標準化（Agent Plugins 1.0）との位置

資料スライド13:

  • Skills + MCP は可搬標準化が進む
  • Hooks / Rules / コマンドはクライアント依存 のまま

kit の構成:

  • .cursor/skills/ — Skills 標準と整合
  • .cursor/hooks/ + hooks.json — Cursor 固有
  • AGENTS.md / rules — クライアント横断の de facto 標準だが完全可搬ではない

kit は資料が指摘する「床は標準化、守りは各リポの責任」という現状認識と一致。manifest SoT による再生成は、クライアント差分を吸収する kit 側の回答。

10. 総合評価

強い一致（kit が資料を体現している点）

  1. 3層モデル（ハーネス / ガードレール / ループ）が中核設計
  2. Guides + Sensors（Rules + exit code ゲート）の閉ループ
  3. Skills による Progressive Disclosure（常時ルールを薄く保つ工夫）
  4. 失敗駆動の進化（GOTCHAS / Hook 昇格）
  5. 行動への柵（guard-git-write.sh）
  6. 人間と AI の同一合格基準（quality-gate 統一入口）

kit が資料を超える点

  1. manifest SoT — 生成物の直接編集禁止、冪等再生成
  2. Context Budget / handoff — 長時間セッションの劣化対策
  3. 6段階 workflow + Step Gate Matrix — タスク完走のオーケストレーション
  4. Meta / Domain 2層ドキュメント命名 — ハーネス情報の構造化
  5. ACCD 5軸 — コンテキスト制約の設計フレームワーク
  6. 5流派の合成 — Chase（スコープ）+ Fowler（制御）+ Hashimoto（進化）+ Chawla（OS 比喩）を1キットに統合（§2 参照）

資料とのギャップ・注意点

ギャップ 内容 示唆
初期の軽さ 資料は50行 AGENTS.md から。kit は170行+ 下流プロジェクトでは Domain 層を充実させ、Meta 層は必要最小に保つ運用が有効
1コマンドの単純さ 資料は check 1本。kit は G-* 分割 + workflow ゲート多数 PO 向けには「日常は bin/foundation-gate self だけ」と説明可能
観察ファースト 資料はハーネスなし観察を推奨。kit は骨格先行 新規 adopt 時は kaizen / 素実行で gap を見てから manifest を調整するのが資料流
厚みと負債 kit は Meta 層が厚い 資料の「定期棚卸し」を agent-kaizen + GOTCHAS Evolve-B で運用化

12. 2026 デファクトとの乖離（設計思想）

資料スライド12–14が示す 2026 年の収束方向（3層モデル・Skills/MCP 可搬化・lean harness）と kit を比較した結果。中核思想は整合するが、ミニマル実践デファクトからは意図的に厚い方向へ逸脱している。

結論: kit に「古くて間違った」思想は少ない。ただし 2026 資料の 「薄く・観察から・1コマンド・可搬 Plugin」 からは、基盤ジェネレータとして 厚い・早い・Cursor 固有 な設計へ逸脱している。

整合（2026 標準と一致）

  • 3原則（馬具・柵・ループ）、exit code ゲート、Skills 分離、Hooks 行動制限
  • 人間と AI の同一合格基準（foundation-gate self / quality-gate verify）

逸脱・ギャップ（優先度順）

2026 デファクト kit 性質
観察ファースト → 最小ハーネスから育てる manifest から骨格フルセット一括生成 逸脱 シナリオ差（基盤 seed vs 1チーム育成）
ハーネスは薄く保ち定期棚卸し（Han Lee） Meta 層が厚い（170行 AGENTS.md + 14 Skills + 多層 gate） 逸脱 技術的負債リスクに構造的露出
check 1本（format + lint + types + test） G-* 分割 + workflow step/archive/review ゲート トレードオフ 思想は一致、API は複雑
Agent Plugins 1.0（plugin.json + mcp.json） .cursor/skills/ 個別配置、可搬パッケージ未採用 遅れ Skills/MCP packaging のみ
失敗時 AGENTS.md へ1行追加 GOTCHAS → manifest 再生成 → Hook 昇格 トレードオフ enterprise 向け構造化
ループを Hooks 等で自動化 Advisory ループは AI 規範（exit 0 まで再実行） 弱い ランタイム自動閉ループなし
審査済み Plugin / クラウド隔離 第一方 Skills のみ、Hook 依存 ギャップ 配布・lethal trifecta 対策で不足

先行（標準を上回る）

  • Context Budget / handoff — 長時間セッション劣化対策
  • manifest SoT + 冪等再生成 + drift 検査（G-GEN）
  • Step Gate Matrix — 本番運用向け故障モード対策

下流展開時の示唆

Meta 層を薄く投影、Domain 層充実、check 1本化、Agent Plugins 形式への移行検討。新規 adopt 時は agent-kaizen / 素実行で gap を観察してから manifest を調整するのが資料流に沿う。

反論・精緻化（2026 デファクトへの批判的再評価）

§12 の乖離は「kit が古い」ではなく、ドメイン密度の高い基盤キットに 2026 ミニマル派をそのまま当てはめると不適切 という側面がある。以下は PO 視点の反論に対する客観的・批判的評価。

評価結論: 反論は 概ね妥当。特に可搬 Plugin の限界（script/gate の repo 密着）は資料注記とも整合。ただし「薄く＝ドメインを捨てる」「可搬＝無意味」とまで読むと、資料の Progressive Disclosure / packaging 標準の意図を見落とす。

反論 A：「薄くするとドメイン知識・ガードレールも薄くなり、逸脱リスクが上がる」

観点評価内容
論旨の正しさ 4/5 ドメイン規約・業務 gate はプロジェクト固有で薄くできない。LLM の確率論（資料スライド17）上、一般論だけでは逸脱しやすい
kit との整合 5/5 Meta/Domain 2層、多段 workflow gate は「薄くしすぎると危ない」設計判断の表れ
限界・補足 — 資料の「薄く」は 常時ロード（AGENTS.md） の話。Han Lee 論は 作り込み・回避策 の話で、Domain SoT を薄くしろという意味ではない。Skills + Domain docs なら総ハーネスは厚く保てる

反論 B：「可搬 Plugin は汎用化すると業務に弱い。SKILL.md は可搬しやすいが script は repo 密着」

観点評価内容
論旨の正しさ 5/5 bin/quality-gate / gate-*.py / path 規約 / tech_contract は下流ごとに異なる。Agent Plugins 1.0 も 入れ物だけ 標準化（資料スライド13）
kit との整合 5/5 manifest SoT + 生成物は意図的に repo 固有。cross-repo-knowledge-link は参照可搬であって gate 可搬ではない
限界・補足 — 可搬の対象は 配布・発見・インストール。手順の型（PR レビュー、要求分析）は複数 repo で再利用可能。中身まで universal 化できると期待する方が誤解

3層分離による精緻化（資料・kit・反論の両立）

層1: 常時ロード（AGENTS.md / rules）     → 薄く（資料の「薄く」）
層2: オンデマンド（Skills / Domain docs） → プロジェクト固有で厚く（反論の核心）
層3: 機械検証（gate / script）            → repo 密着・非可搬（反論どおり）
2026 原則資料の意図反論統合解釈
薄く 常時コンテキスト圧迫を避ける ドメインも薄くなる危険 層1だけ薄く。層2–3は厚く
観察から 実在しないルールを増やさない 既存ドメイン規約は最初から存在 新規失敗は観察、既存 SoT は最初から載せる（docs-first）
1コマンド 人間・AI・CI の合格基準統一 backend は repo 依存 入口1本（verify/self）、中身は contract 依存
可搬 Plugin Skills/MCP の packaging script は不可搬 SKILL の型は共有可能、gate script は各 repo
ループ自動化 Hook 等で閉じる 業務 gate は repo 固有 汎用 lint/test は自動化、業務 gate は repo script

批判的総評

  • 強い エンタープライズ / 基盤キット文脈では反論の方が実務に即する。可搬 Plugin の限界指摘は過剰期待への有効な antidote
  • 注意 「薄く＝ドメイン放棄」と読むと反論が強くなりすぎる。資料の Skills 分離を無視しないこと
  • 注意 可搬 Plugin を全面否定すると packaging 標準の配布・発見上の利益を見落とす

一行: 2026 ミニマル・可搬ハーネスをドメイン密度の高い kit にそのまま適用するのは不適切——という反論は客観的に妥当。資料の「薄さ・可搬性」は 常時ロードと packaging に読み替えれば、反論と対立せず両立できる。

13. まとめ

ジュニア・ミドル向け：kit 設計思想をスライドと比べて理解する

ハーネスエンジニアリングに詳しくないエンジニア向けの入口説明。Kinopee 資料（harness-eng.md）の比喩をそのまま使い、kit が何をしているかを対応づける。

30秒で言うと

AI（LLM）だけに任せると、同じ指示でもたまに道を外れる。 だから「事前に進路を教える」「事後に機械でチェックする」「失敗したら直して再実行する」の3つを、コードレビュー文化と同じ感覚で整えたのがハーネスエンジニアリング。kit はその3つを 複数プロジェクトで使い回せる基盤 として最初から一式そろえたもの。

前提：なぜ「指示して祈る」だけでは足りないか（資料スライド17）

通常のプログラムは同じ入力→同じ出力。LLM は確率的で、「テストを実行する」より「テストをスキップする」選択もゼロではない。だから 人間の善意や長いプロンプト1本 だけでは、ミスを完全には防げない。環境（ルール・検査・ループ）で受け止める——これが資料も kit も共有する出発点。

資料の3要素と kit の対応（スライド15–21）

資料の比喩 意味（いつ・何をする） 資料の例 kit での実体
馬具（ハーネス） 走る前に進路を伝える AGENTS.md、Skills、プラン AGENTS.md + .cursor/rules/ + 14 Skills + 追跡ドキュメント（tracker）
柵（ガードレール） 走った後に逸脱を機械判定 lint、型、テストを1コマンドに bin/foundation-gate self / bin/quality-gate verify + 各種 gate-*.py
ループ 失敗出力を修正に戻す テストが赤→直す→再実行 exit code 1 なら修正して再実行（Advisory ループ）。完了宣言前にゲート必須

身近な例：GPS（ハーネス）＋スピードカメラ（ガードレール）＋違反通知を見て曲がり直す（ループ）。AI エージェント版が kit。

資料の4道具と kit（スライド22–27）

資料が教える使い分け
  • ルール — 毎回必要（短く）
  • プラン — タスク開始前
  • Skills — 特定作業のときだけ
  • サブエージェント — 調査・レビューを分離
kit の置き場所
  • ルール — AGENTS.md、.cursor/rules/*.mdc
  • プラン — .cursor/.tracking/tracker-{campaign_id}.md
  • Skills — .cursor/skills/*/SKILL.md（14本）
  • サブエージェント — Task ツール、workflow の worker dispatch

資料は「まずルールを約50行から」（スライド23）。kit は 基盤キット なので最初から骨格が厚い。ただし 詳しい手順は Skills に逃がす 点は同じ。全部を AGENTS.md に書かないのが正解。

「kit は資料より厚い」——混乱しやすい3点を平易に

資料のイメージkit の現実ジュニアが覚えること
小さな AGENTS.md から育てる manifest.yaml から一式を生成 生成物（AGENTS.md 等）を直接編集しない。変えるなら manifest / templates
npm run check 1本 ゲートがいくつかに分かれている 日常は bin/foundation-gate self を覚えればよい（中で lint/test 等をまとめて実行）
失敗したら AGENTS.md に1行追加 GOTCHAS.md 記録 → 必要なら基盤修復 同じミスをしたら GOTCHAS に書く。ルール追加は PO / 基盤担当と相談

kit だけにあるもの（資料スライドにないが、現場で効く）

  • Context Budget / handoff — 長時間チャットで AI が序盤の約束を忘れる問題への対策。Yellow/Red が出たら新チャットへ（docs/CONTEXT_BUDGET.md）
  • 6段階 workflow — 調査→レポート→実装→テスト→PR→完了を Step Gate で区切る。いきなり実装しない
  • Meta / Domain 2層 docs — 大文字（AGENTS.md）= どのプロジェクトでも同じ役割、小文字（docs/spec.md）= このプロジェクト固有の仕様

初めて kit プロジェクトに入ったときの読む順（5ステップ）

  1. AGENTS.md — 全体ルールと Boundaries（push 禁止など）
  2. docs/spec.md など Domain 層 — このプロジェクトの仕様
  3. 進行中タスクがあれば docs/agent-tasks/reports/
  4. 実装後は bin/foundation-gate self（または profile に従う verify）
  5. わからなければ推測で直さず、docs を読むか PO に質問（Humble 原則）

一言でチームに説明するなら

「kit は、AI に 地図（ルール） と 検問所（ゲート） と 直し方（ループ） を最初から配った開発基盤。資料の『馬具・柵・ループ』を、1チーム用の最小構成ではなく、複数プロジェクト向けの標準装備 として厚く作った版。」

一行でまとめると

kit は Kinopee 資料の「馬具・柵・ループ」を、基盤ジェネレータ向けに体系化・機械化した実装 である。

コア思想（事前進路 + 事後検証 + 閉ループ + 失敗から育てる）は一致しているが、kit は SoT 一元化・セッション/handoff・多段ゲート・進化パイプライン まで含む「エンタープライズ向けハーネス基盤」であり、資料が想定する「1チームが50行から育てるミニマルハーネス」より一段上の抽象度と初期コストを持つ。

流派の観点では Chase 派（骨格）+ Fowler 派（制御）+ Hashimoto 派（進化）+ Chawla 派（OS 比喩） の合成。2026 ミニマルデファクトからの乖離と反論による精緻化は §12・§12 反論 参照。
