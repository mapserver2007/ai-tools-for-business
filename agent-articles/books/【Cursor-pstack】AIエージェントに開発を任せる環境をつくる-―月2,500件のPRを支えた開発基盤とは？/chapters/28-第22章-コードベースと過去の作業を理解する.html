この章では、次の4つのSkillを扱います。

  1. /how
  2. /why
  3. /teach
  4. /recall

4つとも、今のコードと過去の作業を調べるためのSkillです。どのSkillを使うかは、知りたいことで決まります。

選び方は次のとおりです。

  • 今どう動いているか（例：実行のキャンセルは、どの関数を通って、どうデータベースを変えるか）・・・ /how
  • なぜその形になったか（例：リトライの上限はなぜ5なのか）・・・ /why
  • その両方を人に分かる説明にしてほしい（例：このPRがリトライをどう変えるのかを、納得できるまで知りたい）・・・ /teach
  • 前回の作業の続きから始める（例：先週のエクスポートの作業はどこまで進み、何が差し戻されたか）・・・ /recall

書き終えた変更が壊しうるものや、差分の弱点を調べるSkillは、第28章で扱います。

この章では、4つのSkillを一覧にしたうえで、1つずつ、使いどき、手順、出力の3つの観点で解説します。原文に依頼例があるSkillには依頼例も示します。

最後に、似ているSkillとPlaybookの使い分けをまとめます。

4つのSkillの一覧

Skill 一言でいうと 主な問い
/how 今のコードの挙動（処理のきっかけ、通る関数、データの流れ）を説明する X はどう動いているか。これはどこに置くべきか
/why コードがその形になった理由を、コミット、PR、チケットなどの記録から調べ、理由ごとに確かさの段階を付けて答える なぜこうなっているのか。なぜYを選んだのか
/teach /how と /why を呼び、その結果を、平易な定義から始める1つの説明にまとめる これを本当に理解したい
/recall 自分のチャット履歴と共有の記録（PR、チケット、本番のエラーなど）から、最近の作業がどこまで進み、何がうまくいかなかったかをまとめ直す どこまでやったか。何が起きていたか

4つは、どれも名前で呼ばれたときだけ動くSkillです。

4つの SKILL.md はどれも、エージェントが会話の内容から自分で選んで動かすことを止める設定（disable-model-invocation: true）を持っています。そのため、4つが動くのは、利用者が名前で呼んだときか、/poteto-mode やほかのSkillが手順の中で名前を指定して呼んだときだけです。

4つを誰が呼ぶかは、次のように分かれます。

  • /how、/why・・・ /poteto-mode が、Playbookの手順に従って呼びます。/how は、節『Non-negotiables』の規則に従っても呼びます。ほかのSkillも、各Skillの手順の中で呼びます（/how は /teach、/architect、/no-comments が、/why は /teach、/recall、/architect、/no-comments が呼ぶ）。利用者が名前で直接呼ぶこともできます。
  • /teach、/recall・・・ /poteto-mode の『Non-negotiables』の規則にも、Playbookの手順にも、ほかのSkillの手順にも出てこないので、利用者が名前で呼んだときだけ動きます。

/how は、変更の前に、コードの挙動を頭の中でたどれるように説明する

/how は、コードの挙動を、サブシステムに新しく加わった上級エンジニアが頭の中で再現できる水準で説明するSkillです。

!

サブシステム・・・ アプリの中で、1つのまとまった機能を受け持つ部分のことです（例：実行のキャンセル、ログイン、決済）。多くの場合、複数のファイルやモジュールにまたがっています。

頭の中で再現できるとは、読んだ人が、処理が何をきっかけに始まり、どのファイルのどの関数を通って、データがどこへ流れるかを、コードを開かずにたどれることです。

説明の目的は、読んだ人が流れをつかむことなので、ソースコードに1行ずつ注釈を付けたような、細かすぎる説明にはしません。

たとえば、実行のキャンセルの仕組みなら、次のような流れを、コードを開かずに説明できる状態です（ファイル名と関数名は説明のための例です）。

使いどき：コードの挙動の説明と、どこに置くかの問い

コードを変える前に、サブシステムの挙動（例：実行のキャンセルが、どの関数を順に通るか）を知りたいとき、または「これはどこに置くべきか」「このレイヤー（例：画面、API、データベースへの読み書きのように、役割ごとに分けたコードの層）で正しいか」のような、コードの置き場所を問うときです。

「なぜその形にしたのか」という動機を問うときは、/how ではなく /why を使います。

手順：事実を集める役と、説明を書く役を分ける

問いが単純なら（例：「関数 X はどう動くか」のように、1つのモジュールで閉じる問い）、explainer（説明役）が1回で調べて説明します。

複数のファイルやサービスにまたがる問いなら（例：サブシステム全体の構成）、エージェントは、問いを2〜4の切り口に分けてexplorer（探索役）を並列に起動し、explainer がその結果を統合します。

切り口とは、同じサブシステムを分けて調べるときの、互いに重ならない部分のことです。たとえば、実行のキャンセルの仕組みなら、「キャンセルの受け付け」「実行の停止」「データベースの更新」のように分けます。

問いが単純か複雑か迷ったら、エージェントは単純な問いとして扱い、explorer を起動せずに explainer だけで調べます。

どちらの道でも、利用者が読む説明を書くのは explainer です。explorer は、説明の材料になる事実を集めるだけです。

explorer は、文章ではなく事実の一覧（見つけたコンポーネント、処理の流れ、読んだファイル、ほかの部分との境界、意外な点）を返します。

人が読む説明は explainer が別に書くので、explorer は読みやすさを気にせず、調べる深さと正確さを優先します。

explorer は、不明点やたどれなかった箇所を作り話で埋めず、「X が Y にどうつながるかは分からなかった」のように、分からなかったことをそのまま書きます。

/how は説明するだけなので、/how のサブエージェントはすべて、ファイルを書き換えない読み取り専用のモードで動きます。

出力：Overview から Gotchas までの5つの見出しで書く

説明の目的は、その領域を知らない人間が、読んだあとに自信を持って作業を始められることです。

そのため explainer は、全体像から細部、作業の入口へと進む次の5つの見出しで書き、該当しない見出しは省きます。例は、「実行のキャンセルの仕組み」を問われた場合です。

  • Overview（概要）・・・ その仕組みが何で、何をし、なぜあるのかを書きます。読み手がここだけ読んで、続きを読むかを決められるようにします（例：キャンセルの仕組みが、利用者の操作から実行の停止までを受け持つこと）。
  • Key Concepts（主要な概念）・・・ 続きを読むのに必要な型やサービスです（例：実行を表す型と、キャンセルを受け付けるサービス）。
  • How It Works（仕組み）・・・ 最も長い部分で、きっかけ、進み方、データの流れを書きます（例：キャンセルの依頼が、どの関数を順に通って、データベースの状態を変えるか）。
  • Where Things Live（置き場所）・・・ どのファイルやディレクトリに何があるかを、短く一覧にします。載せるのは、その領域で作業を始める人が開く必要のあるものだけです（例：キャンセルを受け付ける api/runs.ts と、実行を止める services/runner.ts）。
  • Gotchas（落とし穴）・・・ コードを読んだだけでは気づきにくい点、意外な挙動、今の形になった経緯、間違えやすい点です（例：キャンセルしても、実行中の処理はすぐには止まらず、今の段階を終えてから止まる。そのため、画面に「キャンセル済み」と出た後も、数秒間は処理が続く）。

処理が複数のコンポーネントにまたがるときは、explainer は図も入れます。ただし、図は流れを分かりやすくするためのもので、文章だけで流れが伝わるなら図は省きます。

依頼の例：実際に持っている問いをそのまま聞く

/how は、多くのPlaybookが手順の中で呼びます。代表的なものは次のとおりです。

  • 『Bug fix』（不具合の修正）
  • 『Feature』（機能の追加）
  • 『Refactoring』（振る舞いを変えない構造の整理）

また、/poteto-mode の『Non-negotiables』は、自明でない変更や設計の判断をするとき、「本当に大丈夫か」を確かめるときに、/how を使うと定めています。

Playbookのほかに、/teach、設計を決める /architect（第24章）、差分のコメントを審査させる /no-comments（第32章）も、手順の中で /how を呼びます。

直接呼ぶときは、実際に持っている問いをそのまま聞きます。READMEの例は次のとおりです。

/how do we cancel runs? do we have an n+1 when we look up every run to cancel?
// 実行のキャンセルはどう動いてる？キャンセル対象の実行を1件ずつ引いていて、N+1になっていない？

!

N+1・・・ 一覧を取る1回の問い合わせの後に、項目ごとに1回ずつ問い合わせを追加で行う書き方

たとえば、キャンセルする実行が100件あるとき、アプリはデータベースに、次のように、101回問い合わせます。問い合わせのたびに待ち時間が生じるので、件数が増えるほど処理が遅くなります。

N+1をなくすには、アプリは、IDごとに1回ずつ問い合わせるのをやめ、2回目の問い合わせで100件分のIDをまとめて渡します。データベースは100件分の情報を一度に返すので、問い合わせは次のように合わせて2回で済みます。

同梱ガイドの 03-understand.md は、利用者が「どうせエージェントがコードを読むから」と考えて、そのページで扱うSkill（/how、/why、/teach、/recall）を飛ばさないよう注意しています。

ガイドがこう注意するのは、コードの挙動をたどらないまま編集を始めたエージェントは、最初に見つけたもっともらしい箇所で、根本原因ではなく症状だけを直す対症療法をしがちになるからです。症状だけを直せば、根本原因が残って次の不具合が出ます（第19章）。

また、同じページは、先に /how を使うほうが、その次の不具合に対処するより安く済むと書いています。

/why は、コードが今の形になった理由を、記録で裏づけられるものと推測に分けて答える

/why は、コードがなぜ今の形になったのかを、記録で裏づけられる理由と推測を分けて答えるSkillです。

/how が「どう動くか」に答えるのに対し、/why は「どんな事情や判断がその形を作ったか」に答えます。

/why は、調べても理由が見つからなければ、推測で埋めずに「分からない」と答えます。推測を自信ありげに書くと、利用者はその推測を事実だと思い、その推測に基づいて判断してしまうからです。

使いどき：設計の理由、リグレッション、しきい値の由来を問うとき

「なぜこう動くのか」「なぜYを選んだのか」のように設計の理由を問うときや、リグレッション（以前は動いていた機能が、変更によって動かなくなること）やポストモーテム（障害の後に、原因と再発防止策をまとめる振り返り）、しきい値の由来（例：リトライの上限がなぜ5なのか）を調べるときです。

実行時の挙動（今どう動いているか）を問うなら、/why ではなく /how を使います。

手順：証拠の置き場所ごとに調査役を1体ずつ置き、並列に調べる

/why は、理由の証拠が残っていそうな場所を、次の表の7つのカテゴリに分けます。

カテゴリ MCPの例 特に分かる「なぜ」
ソース管理の履歴 git、gh（GitHubのPRやIssueをターミナルから操作する、GitHub公式のCLI） レビューの中で書かれた、実装時の理由（例：PRの説明）。どの環境でも必ず使える唯一の置き場所なので、常に調べる
課題・チケット管理 Linear、Jira プロダクトやビジネス上の動機（例：顧客の要望で追加した）
長文ドキュメント Notion、Google Docs コードになる前に書かれた設計の理由（例：案Aと案Bを比べた設計書）
リアルタイムのチャット Slack 文書に残らなかった議論
インフラの観測 Datadog タイムアウトやリトライを生んだ実行環境の事情
エラー追跡 Sentry 防御的なコード（例：nullの確認、リトライ）を生んだ例外
プロダクト分析 BigQuery コードの形を決めたプロダクトやデータの事情（例：しきい値の数字がどこから来たか）

エージェントは、まず、利用者のCursorにつながっているMCP（Model Context Protocol。エージェントを外部のツールやデータにつなぐ仕組み）を調べ、それぞれのMCPがどのカテゴリの証拠を読めるかを振り分けます。

たとえば、LinearのMCPがつながっていれば「課題・チケット管理」に、SlackのMCPがつながっていれば「リアルタイムのチャット」に振り分けます。

そのうえで、MCPがつながっているカテゴリごとに、調査役（investigator）を1体ずつ並列に起動します。ソース管理の履歴だけは、MCPがなくても git と gh で読めるので、常に調べます。

エージェントは、調査役を起動する前に、次のようなコマンドで、対象のファイルの行、コミット、PRを集めます。集めた手がかりを全員に渡し、調査役がそれぞれ具体的なコードから調べ始められるようにするためです。

# 対象の行を最後に変えたコミットを表示する
git blame -L <start>,<end> <file>

# PRの説明と議論を表示する
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews

調査役の結果は、synthesizer（統合役）がまとめます。流れは次のとおりです。

調査役は並列で同時に調べ、何も見つからなかった場合は、「見つからなかった」という結果を synthesizer に返します。

synthesizer は、調べなかったカテゴリや、調べても何も見つからなかったカテゴリも、理由付きで記録に残します。「探したが見つからなかった」ことも調査の結果の一つで、記録がなければ、調べていないのか、調べて何もなかったのかを利用者が区別できないからです。

出力：すべての主張を、Direct から Unknown までの確かさの5段階に分ける

コードからは、何をしているかは読めても、なぜあるのかは読めません。理由は、コミットやPR、チケット、チャットのような、不完全な記録の中にしかないからです。

そこで /why は、すべての主張を、どれだけ確かかによって次の5段階に分けて示します。

たとえば、これは、「リトライの上限がなぜ5なのか」を調べた場合です。

段階 意味 例
Direct（直接） 作者が理由を明示的に書いた記録がある コードのコメントに「上流のAPIが6回目以降の再試行を拒むため、5回で止める」と書いてある
Supported（裏づけあり） 明言はないが、複数の間接証拠が一致する 上限を5にしたPRと同じ週のPRやチケットが、どれも同じ障害に触れている
Inferred（推論） 文脈からの妥当な読み。明示的な裏づけはない コードベースのほかの場所でも上限が5なので、チームの慣習に合わせたと思われる
Speculative（推測） 証拠が薄く、ほかの説明も同じくらい成り立つ SLA（約束した応答時間）に合わせた可能性はあるが、SLAの文書には5という値が出てこない
Unknown（不明） 調べたが判明しなかった。何をどこで検索したかを書く チケットを「retry」で検索し、このファイルを変えたPRを6件読んだが、理由は見つからなかった

synthesizer は、「だからXだ」のような言い切りを、DirectとSupportedの主張にだけ使います。言い切りの形は、証拠のある因果関係を主張していると読まれるからです。

たとえば、Direct の主張は「この上限は、上流のAPIが6回目以降の再試行を拒むためにある」と言い切り、出典を添えます。

一方、Inferred の主張は「この上限は、チームの慣習に合わせたものと思われる」のように、推論であることが分かる言い方にします。

利用者が「性能のためだと思うけど」のように問いに仮説を入れていても、/why はその仮説をそのまま認めず、候補の一つとして証拠を独立に確かめます。

poteto氏は『The Complete Guide to pstack』Part 2で、エージェントに頼むときに自分の仮説を先に述べないほうが、間違った方向へ導かずに済む、と書いています。

利用者がこの問いの後にコードを変えるつもりなら、/why は、調べた結果を Preserve / Change / Avoid / Risk（守る、変える、避ける、危険）の制約に変え、変更の計画に渡せるようにします。

たとえば、リトライの上限を変えるつもりで理由を調べた場合、制約は次のようになります。

Preserve: 上流のAPIが拒む回数を超えない（上限の理由として記録がある）
Change:   上限の値をコードに直接書かず、上流のAPIの制限と同じ場所で決める
Avoid:    上限をなくして、成功するまで再試行し続ける
Risk:     上流のAPIの制限が変わっていれば、今の5という値は合わなくなる

このように、調べた結果を4つの制約に分けておけば、変更を計画するときに、守るべき理由を知らずに消してしまうことを防げます。

依頼の例：「誰も理由を書き残していない」も一つの答えになる

/why は、『Investigation』（コードや履歴を読んで答えられる質問に、引用つきで答える）や『Bug fix』のPlaybookから呼ばれます。また、/recall、/teach、/architect（第24章）、/no-comments（第32章）も、手順の中で /why を呼びます。

03-understand.md には、次の依頼例があります。

/why was the retry limit set to five? does the reason still hold?
// リトライ上限はなぜ5にしたの？その理由は今も成り立つ？

同じページは、「誰も理由を書き残していない」という結果も、それ自体が答えだとしています。

理由がどこにも書かれていないと分かれば、利用者は、元の作者に聞くか、これ以上調べないかを決められます。そのため、/why は、理由が見つからなかったという結果も報告します。

/teach は、コードの仕組みと理由を、人が納得できるまで平易に説明する

/teach は、あるコードや変更が何で、どう動き、なぜそう作られているかを、一つの平易な説明にまとめるSkillです。目的は何かを変えることではなく、相手が理解することです。

ちなみに、poteto氏は『The Complete Guide to pstack』Part 2で、自分より賢い相手（エージェント）と働くには、相手に自分に分かる形で言い直してもらうことが大切で、それが /teach の着想になったと書いています。

使いどき：要約ではなく、本当に理解したいとき

要約では足りず、変更やサブシステムを本当に理解したいときです。

手順：/how と /why を呼び出し、その結果を1つの説明にまとめる

調査はやり直さず、/how と /why の結果をまとめる

/teach は、何をどこから説明するかの見当をつけるためにコードを自分で読みますが、調査そのものはやり直さず、/how と /why を実際に呼び出し、その結果を1つの説明にまとめます。

サブシステム全体なら両方を呼び、小さな変更なら、/how・/whyのどちらか一方で、足りることもあります。

/why には、既定で調べる範囲を絞るよう頼む

/teach は、/why を呼ぶとき、既定では調べる範囲を絞るよう頼みます（例：gitと、ほかに1〜2の置き場所だけを調べる）。/why がすべてのカテゴリを調べると時間がかかるので、理由そのものが相手の知りたいことである場合に限って、範囲を広げます。

持ち帰るべき少数の点を決め、平易な定義から目の前のコードへつなぐ

説明するときは、相手が持ち帰るべき少数の点を決め、平易な定義から始めて、目の前のコードに結びつけます。持ち帰るべき点は、相手がなぜ聞いているのか（これから変更するのか、レビューするのか、不具合を調べているのか、など）と、相手がすでに知っていることを、会話から読み取って決めます。

たとえば、「仮想スクロールは、画面に見えている行だけを描画する仕組みです」と一般的な言葉で定義してから、「このアプリでは、長いチャットを開いたときに仮想スクロールを使っています」と目の前のコードにつなぎます。

1〜2文で答えたら止まり、相手の反応を待つ

/teach は、講義ではなく会話にします。小テストを出したり、言い直しを求めたりはせず、1〜2文の最小限の答えを返したら止まって、相手の反応を待ちます。相手が望めば、さらに掘り下げます。

図は1枚に全部を描かず、組み上がる順に描き直す

仕組みの図は、部品を1つずつ追加して描き直します。すべての部品を1枚に描いた図は参照用の資料にはなっても、読み手が仕組みの組み上がる様子を追えないからです。

たとえば、画面からAPI、APIからデータベースへ進む流れなら、次の3枚を順に描きます。

1枚目は、画面からAPIまでです。

2枚目は、1枚目を描き直してデータベースを追加します。

3枚目は、2枚目を描き直して戻りの矢印を追加します。

このように、図を1枚ごとに部品1つだけ増やして描き直せば、読み手は仕組みが組み上がる順番をそのままたどれます。

出力：説明そのものを、要点から平易に返す

返答は作業の報告ではなく、説明そのものです。要点から始め、さらに /how や /why で掘り下げる価値のある論点を添えます。

/teach は、説明のために言い回しを自由に変えてよいのですが、/why の確かさを表す言葉（Direct や Inferred などの段階）は残します。

「〜と思われる」のような断り書きは、言い換えてよい飾りではなく、「記録では裏づけられなかった」という調べて分かったことの一部であるため、/teach は確かさを表す言葉を言い換えずに残します。

依頼の例：「納得させて」と頼む

/teach は利用者が名前で呼ぶSkillです。03-understand.md には、次の依頼例があります。

/teach me how this PR changes retries. convince me it fixes the cause and not the symptom.
// このPRがリトライをどう変えるか教えて。症状ではなく原因を直していると納得させて。

ガイドは「納得させて」（convince me）という頼み方を勧めています。説明が一方的な解説ではなく、反論しながら確かめられる論証になるからです。

実践での使い方は、第40章で扱います。

/recall は、最近の作業の経緯を集め、前回の失敗地点から再開できるようにする

/recall は、作業の開始前や再開前に、最近の作業の経緯（何をして、何を決め、何がうまくいかなかったか）を集め直し、前回の失敗地点から作業を再開できるようにするSkillです。作業が今どこまで進んでいて、次に何をすべきかを短く返します。

使いどき：「どこまでやったか」を聞くとき

作業を始める前や再開する前に、「X での作業を思い出して」「どこまでやったっけ」と聞きたいときです。

手順：チャット履歴と共有の記録を並列に調べる

作業の経緯は2つの記録に分かれて残っているので、/recall は両方を読みます。

  • 自分のチャット履歴・・・ 何をして、何を決めたかが残っています。
  • 共有の記録・・・ 同じコードの周りで起きたことが残っています。たとえば、ユーザーが報告し続けている症状、リリースした後に差し戻された修正、本番で出続けているエラーです。

/recall は、共有の記録を /why の調査役に調べさせます。不具合が長く続いた機能ほど、経緯の大半は自分の履歴ではなく共有の記録に残っているからです。

このとき /recall は、調査役に「なぜこう作られたか」ではなく、「今どういう状態か、何を試してうまくいかなかったか、ユーザーが何を報告し続けているか」を調べさせます。

主エージェントは、検索の前に、期間（既定は直近7日）、話題、ワークスペース（既定は今開いているもの）を決め、その範囲を利用者に述べてから進めます。利用者が思っていた範囲と違えば、その場で直せるようにするためです。

頼まれない限り、主エージェントはほかのプロジェクトの履歴を読みません。

主エージェントは、対象のチャットが1〜2件なら自分で直接探し、それより多ければ、履歴をサブエージェントに並列で読ませます。実際の履歴はサブエージェントの中にとどめ、主エージェントには見つかったことだけを返させます。長い履歴で主エージェントのコンテキストを埋めないためです（第20章）。

主エージェントは、見つかったPRやブランチの実際の状態を、git と gh で確かめます。チャットに残っているのは当時の状態で、その後にマージや差し戻しが起きているかもしれないからです。

利用者が特定の1つのチャットを再開したいだけなら、/recall はその依頼を『Session pickup』Playbookに回します。

出力：Capsule、Threads、Problems、Next move の4つ

出力は、読み手が「作業が全体としてどこまで進んでいて、次に何をするか」をすぐにつかめるように、全体の要約から次の一手へと進む4つの部分で書きます。

  • Capsule（要約）・・・ 最大5項目で、この作業が何で、全体としてどこまで進んでいるか（例：ジョブへの移行はマージ済みで、再試行の問題だけが残っている）を書きます。
  • Threads（作業の単位ごとの状態）・・・ その話題の中で進めてきた作業の単位（例：PR 1本、ブランチ1本）を1行に1つずつ書き、次の表の状態タグを必ず1つ付けます。
  • Problems（繰り返す問題）・・・ 最大5項目で、繰り返し起きている問題を書きます。差し戻された修正も含め、次の試みが前回の失敗地点から始められるようにします。
  • Next move（次の一手）・・・ 最も役立つ次の一手を1つ書きます。

Threads の状態タグは次の6つです。

タグ 意味
[merged #N] PR #N がマージ済み
[open PR #N] PR #N がレビュー待ちなどで開いている
[in flight <branch>] ブランチ上で作業中
[verified, uncommitted] 確かめ済みだが、まだコミットしていない
[reverted #N] PR #N が差し戻された
[planned, not started] 計画したが、まだ始めていない

たとえば、先週のエクスポートの作業について、4つの部分と6つのタグをすべて含む出力は、次のようになります。

Capsule
- CSVエクスポートを、画面の処理から非同期のジョブに移す作業
- ジョブへの移行はマージ済みで、再試行すると同じ行がもう一度書き出される問題が残っている
Threads
- [merged #412] エクスポートをジョブに移す
- [reverted #418] 再試行を追加する（同じ行がもう一度書き出されたため差し戻し）
- [open PR #421] 行のキーで書き込みを冪等にする
- [in flight export-progress] 進み具合を画面に表示する
- [verified, uncommitted] 大きなファイルでのタイムアウトを延ばす
- [planned, not started] 古い同期のエクスポートを消す
Problems
- 再試行すると、1回目の試行で書いた行の後ろに、同じ行がもう一度書き出される。#418 はこれで差し戻された
Next move
- #421 のレビューの指摘に答え、マージする

このように、差し戻された修正とその理由が Problems に残っていれば、次の試みは前回の失敗地点から始められます。

依頼の例：作業の始めに自分で呼ぶ

/recall は、作業を始めるときや再開するときに利用者が名前で呼びます。03-understand.md には、次の依頼例があります。

/recall catch me up on the export work from last week
// 先週のエクスポートの作業について、状況を教えて

新しい作業への引き継ぎ方は第40章で扱います。

/how・/why・/teach・/recall と『Session pickup』は、今持っている問いで選ぶ

それぞれが答える問いは次のとおりです。

  • /how・・・ 「今どう動いているか」
  • /why・・・ 「なぜこの形なのか」
  • /teach・・・ 「本当に理解したい」
  • /recall・・・ 「自分はどこまでやったか」

特定の1つのチャットを続きから進めたいなら『Session pickup』、複数のチャットにまたがるコンテキストを読み込みたいなら /recall を使います。

まとめ

  • 4つのSkill・・・ どれも名前で呼ばれたときだけ動きます。/how、/why は、/poteto-mode がPlaybookの手順に従っても呼びます。
  • /how・・・ 事実を集める役（explorer）と説明を書く役（explainer）を分け、今の挙動を Overview から Gotchas までの5つの見出しで説明します。
  • /why・・・ git、チケット、チャットなど証拠の置き場所ごとに並列に調べ、主張を Direct から Unknown までの5段階に分けます。「だからXだ」と言い切るのは、記録で裏づけられた主張だけです。
  • /teach・・・ /how と /why の結果を束ね、平易な定義から始めて、図を部品1つずつ描き足しながら説明します。
  • /recall・・・ チャット履歴と共有の記録から、Capsule、Threads、Problems、Next move の4つで作業の状況をまとめ、差し戻された修正とその理由を Problems に残します。
  • 使い分け・・・ 今持っている問いで選びます。特定の1つのチャットを続きから進めたいなら『Session pickup』を使います。
