この章では、次の3つのSkillを扱います。

  1. /unslop
  2. /bro
  3. /technical-writing

3つとも、エージェントが書いた文章の品質を保つためのSkillです。3つは、それぞれ次の仕事を受け持ちます。

  • /unslop・・・ エージェントが、自分の書いた文章から、「I hope this helps!（お役に立てば幸いです）」のような決まり文句など、AIらしい癖を取り除きます。
  • /bro・・・ エージェントが、直前の返答を、専門用語を使わずに短く言い直します。
  • /technical-writing・・・ エージェントが、文書の種類（チュートリアルかリファレンスかなど）を先に決めてから、技術文書を書きます。

この章では、まず3つのSkillの対象、誰が直すか、何をきっかけに動くかの違いを確かめます。そのうえで、1つずつ、役割、使いどき、規則や手順、依頼の書き方の4つの観点で解説します。

この章の構成

この章の構成は次のとおりです。

  • 3つのSkillは、対象と、誰が直すかが異なる
  • /unslop は、AIらしい文章の癖を番号付きの規則で取り除く
  • /bro は、分かりにくい返答を、専門用語なしで言い直す
  • /technical-writing は、文書の種類を先に決めてから書かせる
  • まとめ

3つのSkillは、対象と、誰が直すかが異なる

3つのSkillの対象と、誰が直すかを表にまとめると、次のようになります。

Skill 対象 誰が直すか
/unslop エージェントの返答を含む、あらゆる文章 書いたエージェント自身が、規則に沿って直す
/bro エージェントの直前の返答 利用者が、返答が分かりにくいと感じたときに呼び、エージェントが言い直す
/technical-writing ドキュメント、RFC（設計を提案する文書）、README、PR説明、コミットメッセージ 書いたエージェント自身が、4つの層の規範に沿って書き、直す

3つは、名前で呼ばれたときだけ動く

3つの SKILL.md は、どれも disable-model-invocation: true の設定を持っています（第25章）。この設定があるSkillを、エージェントが会話の内容から自分で選んで動かすことはありません。そのため、3つが動くのは、利用者が名前で呼んだときか、/poteto-mode、Playbook、ほかのSkillが手順の中で名前を指定して呼んだときだけです。

/poteto-mode の節『Non-negotiables』（第8章）は、このうち2つのSkillを呼ぶ場面を決めています。あらゆる文章を書くときは /unslop、ドキュメント、RFC（設計を提案する文書）、README、PR説明、コミットメッセージを書くときは /technical-writing を呼びます。

そのため、/poteto-mode で作業していれば、利用者がこの2つを名前で呼ばなくても、エージェントが『Non-negotiables』の規則に従って、この2つを呼びます。

/unslop は、AIらしい文章の癖を番号付きの規則で取り除く

役割：AIらしい文章の癖を規則で取り除く

/unslop は、エージェントが、自分の書いた文章から、AIらしい癖を、規則に沿って削るSkillです。

AIらしい癖とは、AIが書いた文章によく現れ、読み手に「機械が書いた」と気づかせる言い回しや書式のことです。

原文は、この癖を AI tells や AI patterns と呼びます。たとえば、返答の最後に付く決まり文句や、em dash（英文で使う長いダッシュ記号 —）の多用などが該当します。

規則とその例は、どれも英語の文章を対象に書かれていますが、言語に関係なく、共通して文章に適用してほしい規則が大半なので、日本語では使えない、ということはないです。

もちろん、英語で最も効果を発揮するので、やはり英語は "The hottest programming language is English" と言えるでしょう。

使いどき：どんな文章にも常に適用する

/poteto-mode の『Non-negotiables』は、エージェントの返答を含むあらゆる文章にこのSkillを適用するよう定めています。

SKILL.md の説明（description）も、「Must always apply（常に適用すること）」と書いています。ただし、/unslop は disable-model-invocation: true の設定を持つので、エージェントがこの説明を読んで、自分で /unslop を呼ぶことはありません。常に適用されるのは、『Non-negotiables』の規則と、次に見るほかのSkillやPlaybookの手順が、/unslop を呼ぶからです。

/unslop は、文章を書くほかのSkillやPlaybookからも使われる

ほかのSkillやPlaybookも、各手順の中で、自分が書く文章に /unslop を適用するよう定めています。呼ぶ側と、/unslop を適用する文章をまとめると、次のようになります。

呼ぶ側 /unslop を適用する文章
/technical-writing 書いたりレビューしたりするすべての文書
『Opening a PR』『Multi-phase or multi-PR plan』Playbook PRのタイトル、PR説明、コミットの本文、計画書
/teach、/show-me-your-work 説明の返答と、判断の記録
/recall、/blast-radius 利用者に渡す報告
/automate-me 利用者専用のSkillの下書き
『Investigation』Playbook 調べた結果の返答

呼ぶ側ごとの詳細は、次のとおりです。

/technical-writing：AIらしい癖の一覧を、/unslop に任せる

/technical-writing は、AIらしい語彙や埋め草（意味のない語句）などの癖の一覧を自分では持たず、/unslop に任せています。そのため、自分が書いたりレビューしたりするすべての文書に /unslop を適用します。

『Opening a PR』『Multi-phase or multi-PR plan』Playbook：/technical-writing で書いた後に、/unslop を適用する

PRを作る『Opening a PR』Playbook（第14章）は、PRのタイトル、PR説明、コミットの本文を /technical-writing で書いた後に、/unslop を適用するよう定めています。

複数のフェーズやPRにまたがる計画書を書く『Multi-phase or multi-PR plan』Playbook（第16章）も、計画書を /technical-writing で書いた後に、/unslop を適用するよう定めています。

/teach、/show-me-your-work：同僚に話すような言葉で書く

/teach（第22章）は、作業の内容を、人が本当に理解できるよう平易に説明するSkillです。/teach は、すべての返答を、同僚に説明するときのような平易な話し言葉で書くよう定め、その返答に /unslop を適用します。

/show-me-your-work（第29章）は、エージェントの判断とその根拠を、1行に1つずつファイルに記録するSkillです。/show-me-your-work は、判断の記録の各行を、自分のしたことをチームメイトに話すように、AIらしい言い回しや抽象的な専門用語を使わずに書くよう定めています。そのうえで、判断の記録の文にも /unslop を適用するとしています。

/recall、/blast-radius：利用者に渡す報告を書く

/recall（第22章）は、チャットの履歴などから、利用者の最近の作業の状況を組み立て直すSkillです。/blast-radius（第28章）は、変更がほかの場所で壊しうるものを、リリース前に探すSkillです。

2つとも、利用者に渡す報告を、/unslop を通して書きます。/recall の報告は、作業が今どこまで進み、次に何をするかを伝えます。/blast-radius の報告は、変更が壊しうるものと、マージの前に何を確かめるかを伝えます。

/automate-me：利用者専用のSkillの文章を、/unslop で直す

/automate-me（第25章）は、利用者の最近のトランスクリプト（エージェントとの会話の記録）から作業の好みを読み取り、利用者専用のSkill（<利用者の名前>-mode）の下書きを作るSkillです。/automate-me は、その下書きの各行に、/unslop を適用します。

『Investigation』Playbook：調べた結果の返答が、そのまま成果物になる

『Investigation』（第10章）は、コードを変えずに、問いを調べて答えるPlaybookです。このPlaybookは、コードの変更ではなく、出典付きの説明か推奨を返し、その返答を調査の成果物と定めています。

このPlaybookは、手順の最後で、その返答に /unslop を適用します。

規則：AIらしい癖を、7つの分類と固定の番号で示す

SKILL.md の手順は、次の2つだけです。残りの大半は、規則が占めています。

  1. 規則に当てはまる箇所を探す
  2. 意味を保ち、書き手が意図した調子（文調）に合わせて書き直す

規則には番号が付いていて、その番号は、ほかのSkillが規則を指すときに使う固定のIDです。たとえば、/poteto-mode は、「文の途中のつなぎにコロンを使わない」という規則を、「unslop rule 14」のように番号で指しています。

SKILL.md は、規則を消したら、その番号を空けたままにすると定めています。pstack version 0.15.15 の SKILL.md では、1、2、4、6、21の番号が空いています。

!

規則の欠番は、GitHubのソースの表示（Markdown を整形せずに表示する画面）で確かめられます。

規則は28あり、次の7つに分類されています。

分類 何を直すか 規則の番号
Content（内容） 評価だけを付け足す句と、出典の分からない主張 3、5
Language（語彙） AIがよく使う語と、決まった型の言い回し 7〜12
Style（体裁） 記号、太字、見出し、絵文字の使い方 13〜19
Communication artifacts（チャットの名残） チャットで返答するときの決まり文句と、へつらう調子 20、22
Filler（埋め草） 意味のない語句、過剰な予防線、中身のない結び 23〜25
Jargon（専門用語もどき） 専門的に聞こえるだけの比喩の名詞 26
Plain speech（平易な言葉） 感じ（印象）だけを書く文、読み返さないと分からない文、凝った語 27〜33

次に、分類ごとに、すべての規則を挙げます。

前述した通り、原文の規則とその例は、どれも英語の文章を対象にしています。しかし、英語の書式に特有の4つの規則（13、14、17、19）を除けば、ほかの規則は日本語の文章にも当てはまると、本書では考えます。そこで、日本語にも当てはまる規則は、本書で例を日本語に置き換えて示します。英語に特有の4つの規則は、原文の英語の例のまま示します。

Content（内容）

番号 規則 直し方
3 表面的な句 「〜を実現しました」「〜を可能にします」のような、評価だけを付け足す句を、消すか、実際の出典で中身を補う
5 あいまいな出典 「専門家によると」「一般的に言われているように」のような、誰が言ったか分からない書き方をやめ、出典を名指しするか、消す

Language（語彙）

番号 規則 直し方
7 AIらしい語彙 「重要な」「包括的な」「さらに」「〜を活用する」などを多用せず、平易な語に替える
8 「である」の凝った言い方 「〜としての役割を果たす」「〜を誇る」を、「〜である」「〜がある」にする
9 「〜だけでなく、〜も」 「〜だけでなく、〜も」という言い方をやめ、要点をそのまま書く
10 無理に3つ並べる書き方 考えを3つの組に押し込まず、実際の数だけ書く
11 同じものの言い換え 1段落の中で「主人公」「主役」「中心人物」と呼び分けず、1つの語を繰り返す
12 見せかけの範囲 「ドキュメントからテストまで」のように、同じ尺度に乗らないものを「〜から〜まで」でつながず、話題をそのまま並べる

Style（体裁）

番号 規則 直し方
13 em dash の多用 em dash を使わず、ピリオドかカンマにする。括弧、en dash、ハイフンでの代用もしない
14 コロンの多用 コロンは、一覧や例の前にだけ使い、文の途中のつなぎには使わない
15 太字の多用 固有名詞や略語のたびに太字にしない
16 見出し付きの箇条書き 「性能： 性能が向上しました」のように、太字の見出しが同じ行の中身を繰り返す箇条書きを、文章に直す
17 Title Case の見出し 見出しを sentence case で書く
18 飾りの絵文字 見出しや箇条書きから、絵文字を消す
19 曲がった引用符 曲がった引用符を、まっすぐな引用符にする

!

  • em dash・・・ 英文で、挿入句や文の区切りに使う長いダッシュ記号（—）
  • en dash・・・ em dash より短いダッシュ記号。英文で、「1–5」のような範囲を示すのに使う
  • Title Case・・・ 見出しの主な語の頭文字を、すべて大文字にする書き方。例：「Pick The Mode First」
  • sentence case・・・ 見出しを、文と同じく最初の語の頭文字だけ大文字にする書き方。例：「Pick the mode first」
  • 曲がった引用符・・・ 左右で形の異なる引用符（“ ”）。まっすぐな引用符は、左右が同じ形の「"」

Communication artifacts（チャットの名残）

番号 規則 直し方
20 チャットボットの決まり文句 「お役に立てば幸いです」「ほかにもあれば、お知らせください」「承知しました！」のような文を消す
22 へつらう調子 「素晴らしい質問ですね！おっしゃるとおりです！」のような前置きをやめ、直接答える

Filler（埋め草）

番号 規則 直し方
23 埋め草（意味のない語句）の句 「〜という事実があるため」を「〜ため」にする。「〜ということに注意することが重要です」は消す
24 過剰な予防線 「〜という可能性も考えられなくはないかもしれません」を「〜かもしれません」にする
25 中身のない結び 「今後の発展が期待されます。」のような結びをやめ、具体的な計画か事実を書く

Jargon（専門用語もどき）

番号 規則 直し方
26 抽象的な比喩の名詞 「土台」「北極星」「フライホイール」のような比喩を、具体的な語にする。たとえば、「北極星となる指標」を「最も重視する指標」にする

Plain speech（平易な言葉）

番号 規則 直し方
27 感じ（印象）ではなく、何をするかを書く 「読みやすいSQL」「スキーマに沿う型」のような、使ったときの印象を語る言い方を、「.toSQL() は、データベースに送る文字列そのものを返す」「列の名前を変えると、ビルドが失敗する」のような、仕組みか数値を示す文にする
28 詰まった文を短くするか、分ける 読み手が読み返さないと分からない文を、2つに分けるか、文の一部を削る
29 能動態で書く 「クエリは検証されます」を「コンパイラがクエリを検証します」にする
30 副詞を削るか、強い動詞にする 「すばやく動く」を「速い」か、実際の数値にする。「大幅に改善する」は、測った差を書く
31 平易な語を選ぶ 「活用する」「利用する」を「使う」に、「促進する」を「助ける」にする
32 凝った文体をやめる 比喩や飾った言い回しを、文字どおりの言葉にする。たとえば、「回す価値のあるダイヤル」を「変えてみる価値のあるパラメータ」にする
33 詰め込みすぎた文をやめる 動詞を省き、矢印や略語で書いた文を、完全な文に直す。たとえば、「パーサが不正な日付を拒否 → exit 2、書き込みなし」を「パーサは不正な日付を拒否し、終了コード2で終わり、何も書き込まない。」にする

依頼の書き方：直す文章と追加の規則を添えて呼ぶ

同梱ガイドの docs/guide/05-build-and-clean.md は、直す文章と、追加の規則を添えて呼ぶ次の例を挙げています。

/unslop the readme changes, no emdashes
// READMEの変更を unslop して。em dash は使わないで

この依頼では、「the readme changes」が直す文章で、「no emdashes」が追加の規則です。

同じページは、次のような短い依頼でも、エージェントは依頼の意図を読み取り、このSkillで文章を直せると説明しています。

unslop that, tighten it
// それを unslop して、引き締めて

「that」は、直前に書いた文章を指します。

/bro は、分かりにくい返答を、専門用語なしで言い直す

役割：直前の返答を、専門用語なしで言い直す

/bro は、エージェントが直前の返答を専門用語なしで言い直すためのSkillです。本文は3文だけで、pstack で最も短いSkillです。

/unslop との違いは、直す単位です。/unslop は、決まり文句のような、規則に当てはまる箇所だけを直します。一方、/bro は、規則を使わず、直前の返答全体を、平易な言葉で言い直します。

/unslop や /technical-writing と異なり、/poteto-mode も、Playbookも、他のSkillも、手順の中で /bro を呼びません。そのため、/bro は、利用者が名前で呼んだときだけ動きます。

使いどき：返答が詳しいのに、何を言っているのか分からないとき

利用者は、エージェントの返答が技術的には詳しく書かれているのに、何を言っているのか分からないときに、このSkillを使います。

手順：本文の3文が、そのまま指示になる

/bro の本文は、次の3文だけです。

Restate your last message. Stop using jargon and speak coherently. State it more simply and concisely, like one human talking to another.

直前のメッセージを言い直せ。専門用語を使うのをやめ、筋の通った話し方をせよ。人が人に話すように、もっと簡単に、短く言え。

SKILL.md には手順の節がなく、エージェントは、この3文をそのまま指示として受け取ります。

依頼の書き方：「/bro」だけで足りる

同梱ガイドの 10-recipes-and-pitfalls.md は、次の一語だけをプロンプトとして載せています。

/bro

本文の3文がそのまま指示になるので、利用者が言い直し方を書き添える必要はありません。

/technical-writing は、文書の種類を先に決めてから書かせる

役割：技術文書を、層に分けた規範でエージェントに書かせる

/technical-writing は、エージェントが技術文書を書くときに従う規範を、文書全体の種類から一文の書き方までの4つの層に分けて示すSkillです。目標は、疲れたエンジニアが一度読んで理解できる文章です。

poteto氏は『The Complete Guide to pstack』Part 2で、このSkillを作ったきっかけを説明しています。

きっかけは、Cursor社内のデスクトップアプリ用フレームワーク Dune のREADMEを、このSkillなしでエージェントに書かせたことでした。できたREADMEは、チュートリアル、ハウツー、設計の解説、APIリファレンスが一つに混ざり、AIらしい癖のある凝った文章で書かれていて、読みにくいものだったそうです。

使いどき：文書を書くときとレビューするとき

SKILL.md の説明（description）は、ドキュメント、RFC（設計を提案する文書）、README、PR説明、コミットメッセージを書くときと、それらをレビューするときを、使いどきとして挙げています。

ただし、/technical-writing も disable-model-invocation: true の設定を持つので、エージェントがこの説明を読んで、自分で /technical-writing を呼ぶことはありません。こうした場面でこのSkillが使われるのは、『Non-negotiables』の規則が、こうした文書を書くときにはこのSkillを使うよう定めているからです。

Playbookでは、PRを作る『Opening a PR』が、PRのタイトル、PR説明、コミットの本文をこのSkillで書くよう定めています。計画書を作る『Multi-phase or multi-PR plan』も、計画書をこのSkillで書くよう定めています。

規則：4つの層と、層の外の規則

SKILL.md は、4つの層の規範のほかに、層の外の規則も定めています。先に層の外の規則を見てから、4つの層を1つずつ見ていきます。

4つの層より優先する3つの規則

エージェントは、4つの層とは別に、どの層よりも優先して、次の3つの規則を守ります。

  • 取り除いても文の意味が変わらない語は、すべて削ります。たとえば、「In order to」は「to」にします。
  • 短く日常的な語を使います。たとえば、「utilize」ではなく「use」と書きます。
  • 規則を守ると文が悪くなるなら、別の方法で直すか、そのままにします。規則は読み手のためにあり、規則をすべて守っても機械が書いたように読める文は失敗だからです。

名前は、コードベースの名前をそのまま使い、新しい専門用語を作らない

エージェントは、コードベースに実在するシンボル（関数名、型名、変数名など、コードの中で名前を付けたもの）、ファイル、フラグ、コマンドの名前を、言い換えずにそのまま書きます。

また、エージェントは、新しい専門用語も作らず、開発者が口語で使う言葉を使います。たとえば、コードを別の場所に移すことを、「evacuate（避難させる）」ではなく「move（移す）」と書きます。

一方で、「Strangler Fig パターン」のように、決まった設計や進め方に付いていて、すでに広く使われている名前は、エージェントもその名前で書きます。

ただし、エージェントは、その名前が文書で最初に出てきたところに、意味を書き添えます。たとえば、「Strangler Fig パターン（古い仕組みを、少しずつ新しい仕組みに置き換えていく進め方）で移行する」と書きます。

evacuate のような言い換えるべき語は、/unslop の規則26（抽象的な比喩の名詞）が一覧にしています。一覧にない語を見つけたら、エージェントは、/unslop を自分で書き換えず、「その一覧にない語」と「言い換えた語」を一覧に追加する案を、差分つきで返答に書きます。

文の長さを混ぜ、具体的に書く

このSkillは、文の長さと具体性について、次の4つを求めています。

  • 文の長さを意図的に混ぜる・・・ 短い文で要点を示し、長い文で事実をその条件や結果とともに書きます。
  • 文を分けるかどうかは、長さではなく、伝えたいことの数で決める・・・ 「一文に一つのこと」は、「どの文も短くする」という意味ではありません。伝えたいことが二つある文は分けますが、一つだけの文は、長くてもそのまま残します。
  • 解説では、書き手の評価も書く・・・ explanation（解説）では、長所と短所を並べるだけで終わらせず、書き手がそれをどう評価するかも書きます。一方、reference（リファレンス）には評価を書かず、事実だけを書きます。
  • ぼかさず、具体的に書く・・・ 「スキーマの変更は問題を起こしうる」のような当たり障りのない書き方ではなく、「列の名前を変えると、ビルドが失敗する」のように、何が起きるかを書きます。

4つの層の規範をすべて守っても、短く切った文ばかりが並び、具体的なことが何も書かれていなければ、機械が書いたように読めるからです。

PR説明は、1分以内に読める長さにする

エージェントは、PR説明を、レビューする人が1分以内に読める長さにします。そのため、/swarm（第24章）の実行ログ、コミットのSHA（コミットごとに付く、コミットを一意に指す識別子）の一覧、指標の表は、本文に貼らずにリンクします。

4つの層は、文書全体から一文へと細かく見ていく

4つの層は、文書全体から一文の中身へと、順に細かく見ていくための段階です。層ごとに、次の問いを1つずつ受け持ちます。

層 問い 要点
Diátaxis どんな種類の文書か tutorial（チュートリアル）、how-to（ハウツー）、reference（リファレンス）、explanation（解説）のどれか一つにし、混ぜずに分けてリンクする
Google developer style 文が読み手にどう語りかけるか 読み手を「you」と呼び、現在形と命令形で書く。見出しには、何についての節かだけでなく、要点まで書く
STE 一文にどれだけ書くか 一文には、伝えたいことを一つだけ書く。同じ動作は、文書の中でずっと同じ語で書く
Global English 二通りに読める文がないか 「it」や「this」が何を指すか、読み手が迷わないように書く。同じものは、文書の中でずっと同じ名前で呼ぶ

!

  • Diátaxis・・・ 技術文書を、tutorial（チュートリアル）、how-to（ハウツー）、reference（リファレンス）、explanation（解説）の4つの種類に分けて書く考え方
  • Google developer style・・・ Googleの開発者向け文書のスタイルガイド
  • STE・・・ Simplified Technical English。使う語と文の形を制限した、技術文書のための英語の規格
  • Global English・・・ Kohl の『The Global English Style Guide』が示す、英語を母語としない読み手や翻訳者、エージェントにも一通りに読める英文の書き方

表の各層を、原文の例で1つずつ見ていきます。

Diátaxis：文書の種類を先に決める

最初の層（Diátaxis）で、文書の種類を先に決めます。種類が混ざった文書は、この章の『役割：技術文書を、層に分けた規範でエージェントに書かせる』で見た Dune のREADMEのように読みにくくなるからです。

種類は、「行動のための文書か、理解のための文書か」と「学習のための文書か、仕事のための文書か」の2つの問いで決まります。

学習のため 仕事のため
行動のため tutorial how-to
理解のため explanation reference

SKILL.md は、4つの種類を次のように説明しています。

  • tutorial（チュートリアル）・・・ 初めて使う人が、ハンズオン（手を動かして）で、実際に何かを作りながら覚えるための文書です。最初に完成するものを示し、手順ごとに、「画面や出力に何が表示されるはずか」を書きます。
  • how-to（ハウツー）・・・ すでに使い慣れた人が、目の前の問題を解決するための手順書です。基本の説明は省き、やることだけを順に書きます。
  • reference（リファレンス）・・・ 必要なときに引いて、正確な事実を確かめるための文書です。仕様や設定項目を並べ、手順や書き手の意見は入れません。
  • explanation（解説）・・・ 仕組みや設計が「なぜそうなっているのか」を理解するための文書です。設計の判断、経緯、制約、他の案を書きます。書き手の意見を書くのは、この文書だけです。

Dune のREADMEのように4つの種類を一つに混ぜた文書なら、エージェントは4つの文書に分け、互いにリンクします。

ただし、PR説明とコミットメッセージには、エージェントはこの層を適用せず、残りの3つの層だけを適用します。

!

残りの3つの層（Google developer style、STE、Global English）は、英語の文章の書き方を主に扱います。英語以外で文書を書く読者は、次の3つの節を読み飛ばすことを推奨します。

Google developer style：読み手に語りかける

エージェントは、読み手を「you」と呼び、指示は「Click Submit.」のような命令形で書きます。

また、エージェントは、条件を指示の前に置き、「To delete the document, click Delete.」（ドキュメントを削除するには、Delete をクリックする）のように書きます。条件が先にあれば、読み手は自分に関係のない指示を読み飛ばせるからです。

さらに、エージェントは、見出しに、「何についての節か」だけでなく、「その節の要点」まで書きます。

たとえば、「Modes（モード）」のように「何についての節か」だけを示す見出しではなく、「Pick the mode first（最初にモードを選ぶ）」のように、読み手が「何をすればよいか」まで分かる見出しにします。
ここでのモードは、Diátaxis の文書の種類のことです。

STE：一文には、伝えたいことを一つだけ書く

エージェントは、一文に一つの指示だけを書きます。ここでの指示とは、「Install the component.（部品をインストールする）」のように、読み手に何かをさせる文です。

また、エージェントは、長い文を2つに分けます。目安は、指示なら約20語、それ以外の文なら約25語です。この語の数は、英語の単語の数です。

文章を書く時、エージェントは、英語の冠詞「the」や「a」を省きません。たとえば、「Remove backup file」は二通りに読めますが、「Remove the backup file（そのバックアップファイルを消す）」なら一通りにしか読めません。

!

  • 冠詞・・・ 英語で、名詞の前に付ける「the」「a」などの語。日本語にはない
  • 「Remove backup file」が二通りに読める理由・・・ 原文は、どの二通りかまでは書いていない。本書では、次のように読めると考える。冠詞がないと、「backup file」を1つの名詞（バックアップファイル）として読み、「バックアップファイルを消す」と取ることも、backup（バックアップ）と file を切り離し、file を動詞（保管する）として「バックアップを消して、保管する」と取ることもできる。「the」があれば、「the backup file」がひとまとまりの名詞だと決まる

さらに、エージェントは、同じ動作を、文書の中でずっと同じ語で書きます。ある箇所で「start（始める）」と書いたなら、別の箇所で「initiate（開始する）」と言い換えません。

Global English：二通りに読める文をなくす

エージェントは、「only」や「not」を、それが修飾する語のすぐ隣に置きます。「only fails on growth（増えたときに、失敗するだけ）」と「fails only on growth（増えたときだけ、失敗する）」のように、置く場所で意味が変わるからです。

また、エージェントは、一つのものを、どこでも一つの名前で呼びます。一つの仕組みを「the gate」「the ratchet」「the budget check」と呼び分ける文書は、読み手に3つのものがあると思わせてしまいます。

例）1段落を、規則に沿って書き直す

SKILL.md は、書き直しの例を1つ載せています。直す前の段落は、次のとおりです。

Configuration of the proto import ratchet budget script parameters is performed via budget.json. Note that it's important to remember that running with --write, which updates the committed budget to reflect the current count, should only be done when lowering it. If exceeded, CI fails.

proto import ratchet budget script のパラメータの設定は、budget.json を介して行われる。--write を付けて実行すること（コミットされた予算を現在の数に合わせて更新する）は、予算を下げるときにだけ行うべきだと覚えておくことが重要である点に注意。超えると、CI が失敗する。

直した後の段落は、次のとおりです。

budget.mjs reads the committed budget from budget.json and counts the files that import protos. If the count exceeds the budget, CI fails. Run budget.mjs --write only to lower the budget.

budget.mjs は、コミットされた予算を budget.json から読み、protoをインポートしているファイルを数える。数が予算を超えると、CI が失敗する。budget.mjs --write は、予算を下げるときにだけ実行する。

2つの段落を比べると、次の点が変わっています。

  • 「proto import ratchet budget script」という名詞の連なりをやめ、実在するファイル名 budget.mjs と budget.json で書いている
  • 「is performed via」という受け身をやめ、budget.mjs を主語にして、何をするかを書いている
  • 「Note that it's important to remember that」のような、意味のない語句を削っている
  • 比喩の「ratchet」を使っていない。ratchet は一方向にしか回らない歯車のことで、ここでは「減ることしかない上限」の比喩として使われていた
  • 「should only be done」という受け身の注意を、「Run budget.mjs --write only to lower the budget.」という命令形の指示にしている
