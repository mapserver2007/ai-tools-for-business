第5章 自動化は、信頼の土台の上に築く

自動化は、成果物を検証でき、作業手順が定まり、過去の判断がコードベースに残ってはじめて機能します。

poteto氏が講演で、4つのテーマの最後に自動化を置いたのはこのためです。

この章では、自動化を最後に置く理由、どの仕事から自動化してよいのか、土台がそろったときに何を自動化できるのか、そして自動化したあと人間に何が残るのかを、順に解説します。

この章の構成

この章の構成は次のとおりです。

  • なぜ自動化を最後に置くのか
  • どの仕事から自動化してよいのか
  • 土台がそろったとき、何を自動化できるのか
  • 自動化したあと、人間には何が残るのか
  • まとめ：自動化は、信頼と記憶の上に最後に積む

なぜ自動化を最後に置くのか

自動化を最後に置く理由は、以下の2つです。

  1. 土台がないまま自動化すると、成果ではなく、確認できない成果物や繰り返す失敗が増えるから
  2. エージェントの能力だけでは品質が安定せず、能力を発揮できる環境が先に必要だから

土台のない自動化は、確認できない成果物を増やす

1つ目の理由から見ていきます。講演は、土台が欠けたまま自動化すると何が起きるかを、欠けている土台ごとに次のように説明しています。

欠けている土台 自動化すると起きること
仕事を信頼できない（第2章、第3章） 正しいか確認できない成果物が増える
過去の判断が残っていない（第4章） 同じ失敗を何度も繰り返す
複数の実装方法が無秩序に残っている（第4章） 望ましくないパターンを大量に作る

どれも、土台の欠陥がもともと持っていた問題を、自動化がそのまま大量に増やしてしまう、というものです。そのため、自動化は3つの土台を整えたあと、最後の段階に置きます。

ミシュランの厨房には、料理人の腕だけでなく手順と道具が必要

2つ目の理由は、ミシュランの厨房のたとえで説明されています。

講演では、エージェント、開発ツール、検証、自動化を組み合わせて、ソフトウェアの変更を作り続ける仕組みを「ソフトウェア工場」と呼んでいます。そして同じ仕組みを「ミシュランの厨房」にもたとえています。

高品質な料理を安定して出す厨房には、優れた料理人がいるだけでは足りません。以下の仕組みも必要です。

  • 調理手順
  • 道具
  • 材料の管理
  • 衛生基準
  • 役割分担
  • 品質確認の仕組み

エージェントによる開発も同じで、エージェントの能力だけに期待するのではなく、エージェントが安全に能力を発揮できる環境を設計しなければなりません。

第2〜4章で見た、検証の道具、作業手順、コードベースという記憶は、この環境に当たります。

どの仕事から自動化してよいのか

自動化してよいのは、以下の5つの条件をすべて満たした仕事です。
どの条件も、本書のこれまでの章で扱っています。

自動化の前に整える条件 本書で扱った章
成果物を直接検証できる 第2章、第3章（方法1）
高品質な作業手順が定義されている 第3章（方法2）
過去の判断がコードベースに残っている 第4章
推奨される実装方法が明確になっている 第4章（舗装された一本の道）
望ましくない実装を自動的に止められる 第3章（教訓を仕組みに残す）、第4章

土台がそろったとき、何を自動化できるのか

土台が整うと、ユーザーから届いた不具合報告を受けて、エージェントが再現を試みるところまで自動化できます。検証スキルとFeature Mapが十分に整えば、修正まで進める構想もあります。

講演が描く最終形は、前の節の条件を整えたうえで、複数のエージェントやツールを組み合わせ、変更を続けて実装し、検証し、本番へ届ける仕組みです。次に、そのための構成要素と、報告の自動再現という例を順に見ていきます。

構成要素は、条件を整えたうえで組み合わせる

この仕組みを作る要素として、講演では以下の4つが挙げられています。どれも、前の節の条件を整えたうえで組み合わせるものです。

  • Grok Bot・・・ AI Botアプリ。pstackをプラグインとして入れて使える
  • Cloud Agents・・・ Cursorのクラウドインフラ（仮想環境）上で動くエージェント
  • automations・・・ 予定した時刻や、イベントが起きたときに処理を動かす仕組み
  • Agent SDK・・・ エージェントをプログラムから呼び出すための開発キット

『The Complete Guide to pstack』Part 1は、このうちの3つの使い方を、次のように説明しています。

  • Cloud Agents・・・ エージェントごとに専用の実際のコンピュータで動き、依存関係を入れ、アプリを動かし、動画やスクリーンショットを撮れる
  • Grok Bot・・・ Bot自身に作業させるのではなく、Cloud Agentsを起動させる。Botの手が空き、作業の細かいやり取り（コードを読む、コマンドを実行するなど）でBotのコンテキストウィンドウを埋めずに済むので、Botは Cloud Agents を管理し監督するまとめ役として使う
  • Grok Botのroutines、Cursor Automations・・・ 検証スキルに満足できたら、ここに組み込んで、予定した時刻やイベントをきっかけに実行させる

報告の自動再現は、土台の出来がそのまま結果に出る

報告の自動再現は、自動化の出来が土台の質で決まることがよく分かる例です。

『The Complete Guide to pstack』Part 1は、自動化の例として、次の使い方を挙げています。

  1. ユーザーのフィードバックを流しているSlackや、社内のフィードバック用チャンネルをBotに聞かせる
  2. 報告が届くたびに、Cloud Agentsで自動的に再現を試みさせる
  3. 検証スキルとFeature Mapが十分に良ければ、自動で修正まで進めることも考えられる

3つ目には、「検証スキルとFeature Mapが十分に良ければ」という条件が付いています。この条件から、自動化をどこまで進められるかは、アプリを操作して確かめる道具（第3章）と、機能ごとの使い方と確かめ方をまとめた記憶（Feature Map、第4章）の出来で決まると読むことができます。

自動化したあと、人間には何が残るのか

人間には、方針を決めることと、最終的な責任を持つことが残ります。

エージェントは、明確な手順と制約が用意された環境の中で作業します。その環境が十分に整っていれば、人間が常に隣で見張る必要はなく、席を外している間もエージェントは一定の品質で仕事を続けられます。

pstackの入口 /poteto-mode の節『Autonomy』は、人間とエージェントの線引きを具体的に書いています。この節では、取り消せる作業は人間に確認せずに進め、共有ブランチへのforce-push、デプロイ、データの削除、顧客へのメッセージのような取り消せない書き込みの前では、必ず人間を待つ、と定めています（第38章）。

この線引きの考え方は、原則『Never Block on the Human』として第20章で扱います。

同じ線引きは、個々のPlaybookにも書かれています。PRをマージ可能な状態まで運ぶ『Babysit』Playbook（playbooks/babysit.md）は、自分ではマージしません。人間がはっきりマージを頼んだときは、マージを受け持つ『Shipping』Playbookに回します。同梱ガイドは、すべてのチェックが通っていても自分ではマージしない理由を、マージは別の判断だからだと説明しています。

講演は、さらに先の見通しにも触れています。コードの正しさを形式的に検証できるコードベースに近づけば、エージェントの成果物への信頼はより強くなり、いずれは人間によるコードレビューそのものが、通常業務ではなく例外的な作業になるかもしれない、と述べられています。

まとめ：自動化は、信頼と記憶の上に最後に積む

  • なぜ自動化を最後に置くのか・・・ 土台がないまま自動化すると、確認できない成果物、繰り返す失敗、望ましくないパターンが増えるからです。また、講演がミシュランの厨房にたとえるように、エージェントの能力だけでなく、能力を発揮できる環境が必要だからです。
  • どの仕事から自動化してよいのか・・・ 本書で整理した5つの条件（直接検証できる、手順がある、判断が残っている、推奨される実装方法が明確、望ましくない実装を自動で止められる）をすべて満たした仕事からです。
  • 何を自動化できるのか・・・ ユーザーから届いた不具合報告の再現までを自動化できます。検証スキルとFeature Mapが十分に整えば、修正まで進める構想もあります。Grok Bot、Cloud Agents、automations、Agent SDKは、条件を整えたうえで組み合わせます。
  • 人間に何が残るのか・・・ 方針を決めることと、最終的な責任です。/poteto-mode は、取り消せない操作の前で必ず止まるよう定めています。

第1部では、pstackの具体的な部品にはあまり触れずに、講演の4つのテーマ（信頼、信頼を高める方法、記憶としてのコードベース、自動化）に沿って、任せられる条件を見てきました。第2部では、pstackがこれらを Skill、Playbook、Principle という部品でどう実現しているかを見ていきます。
