この章では、次の3つのSkillを扱います。

  1. /architect
  2. /arena
  3. /swarm

3つは、どれも複数のサブエージェントを並列に動かします。3つが異なるのは、並列に動かして何を得たいかです。

3つの違いは次のとおりです。

  • /architect・・・ エージェントが、実装の前に、型とモジュールの境界（例：インポートの処理を、1つの関数として公開するか、読み込み、検証、保存の3つの関数として公開するか）を決めます。そのために、複数のモデルに設計案を作らせて比べます。得たいのは、実装が従う一つの設計です。
  • /arena・・・ エージェントが、同じ課題（例：キャッシュキーの形式を決める）を複数のサブエージェントに別々に解かせ、最も良い案を土台にして、ほかの案の良いところを組み込みます。得たいのは、一つの最良の成果物です。
  • /swarm・・・ エージェントが、仕事（例：packages/ 以下の全パッケージのチェック）を複数のエージェントに分担させるか、同じ課題で競わせ、結果を一つの報告にまとめます。得たいのは、漏れのない確認か、速い答えです。

この章では、3つのSkillを誰が呼ぶのかを確かめたうえで、1つずつ、役割、使いどき、手順の3つの観点で解説します。原文に依頼例があるSkillには依頼例も示します。

最後に、並列の3つのSkillの使い分けを整理します。

3つのSkillは、/poteto-mode が規則とPlaybookの手順に従って呼ぶ

/architect、/arena、/swarm は、/poteto-mode が『Non-negotiables』の規則やPlaybookの手順に従って呼びます。

Skill 一言でいうと 並列の使い方
/architect 呼び出し側の使い方、型、モジュールの形を実装の前に決める 内部で /arena を使い、複数の設計案を比べる
/arena 同じ課題をN個の候補（課題を解くサブエージェント）に解かせ、最も良い候補を土台に選び、ほかの候補の良い部分を移植する 全員が同じ課題に取り組む
/swarm N体のWorkers（並列に動く複数のエージェント）を分担か競争で動かし、一つの報告にまとめる 別々の範囲を受け持つか、同じ課題で競う

3つを誰が呼ぶかは、次のとおりです。

  • /architect、/arena、/swarm・・・ /poteto-mode が、節『Non-negotiables』の規則と、Playbookの手順に従って呼びます。ほかのSkillも、各Skillの手順の中で呼びます（/architect は /figure-it-out と /no-comments が、/arena は /architect と /blast-radius が呼ぶ）。利用者が名前で直接呼ぶこともできます。

/architect は、呼び出し側の使い方から型を決め、骨組みが間違っていたら捨てる

役割：設計を、文章ではなくコードの骨組みで決める

/architect は、関数の境界をまたぐコードを書く前に、型、関数のシグネチャ（関数の名前、引数、戻り値の型）、モジュールの境界を、関数の中身を書かない骨組み（not implemented）で描くSkillです。

!

骨組み・・・ 型、関数のシグネチャ（関数の名前、引数、戻り値の型）、モジュールの境界だけを書き、関数の中身は throw new Error("not implemented") のような仮の本体にしておくコード（以下の例の ImportOptions・ImportResult・importRows）。not implemented は「まだ実装していない」という意味で、仮の本体は、呼ばれるとこのエラーを投げるだけで、処理は何もしない

たとえば、インポートの処理の骨組みを考えてみましょう。

呼び出し側の使い方を先に書き、そこから型とシグネチャを決めると、次のようになります。

// 呼び出し側の使い方：これを先に書き、ここから型を決める
async function onImportClick(file: File) {
  const result = await importRows(file, { onError: "skip" });
  console.log(`${result.imported}件を取り込み、${result.skipped}件を飛ばしました`);
}

// 骨組み：型とシグネチャだけを書き、中身は書かない
// onError は、不正な行があったときに、その行を飛ばすか（skip）、取り込みを止めるか（stop）
type ImportOptions = { onError: "skip" | "stop" };
type ImportResult = { imported: number; skipped: number };

export async function importRows(file: File, options: ImportOptions): Promise<ImportResult> {
  throw new Error("not implemented");
}

中身はまだなくても、呼び出し側が importRows を1回呼べば取り込めることと、戻り値で取り込んだ件数と飛ばした件数が分かることは、骨組みだけで読み取れます。

エージェントが骨組みを先に作るのは、骨組みが、実装が守るべき「契約」（実装は骨組みの型とシグネチャのとおりに書く、という約束）になるからです。

骨組みがあれば、実装が型から外れたことや、型の検査をすり抜ける逃げ道（any や、第18章で見たキャスト（as User のように、値の型を決めつける書き方））が必要になったことが、骨組みとの差分として目に見えます。

たとえば、骨組みでは importRows(file, options) だったのに、実装の途中で3つ目の引数が必要になれば、シグネチャの変更が差分に現れます。

エージェントは、こうしたずれを、実装の中で黙って整合させて片付けずに表に出し、骨組みが間違っていたのか、要件を見落としていたのか、実装が必要以上のことをしているのかを問い直します。このようなずれは、設計か要件か実装のどこかに誤りがあることを示しているからです。

/architect は、骨組みを1つの案で決めず、複数のモデルに作らせた案を統合して決めます。そのうえで骨組みに沿って中身を埋め、骨組みが間違っていると分かったら、骨組みを捨てて設計し直します。

poteto氏は『The Complete Guide to pstack』Part 2で、計画はコードで行うほうがはるかに効果的だと書き、その手段として、/poteto-mode でのプロトタイプ作りと /architect を挙げています。

使いどき：関数の境界をまたぐコードを書く前

/poteto-mode の節『Non-negotiables』（第8章）は、関数の境界をまたぐコードには /architect を使うと定めています。

Playbookも、この決まりに沿って /architect を手順に組み込んでいます。『Feature』（機能の追加）は、手順2で必ず /architect を呼びます。『Bug fix』（不具合の修正）、『Refactoring』（リファクタリング）、『Perf issue』（性能の改善）は、変更が関数の境界をまたぐときに /architect を呼びます。

たとえば、新しい関数を作り、それを別のファイルの関数から呼ぶ変更は、関数の境界をまたぎます。一方、1つの関数の中の計算を直すだけの変更のように、1つの関数の中で閉じる変更には、/architect は必要ありません。

また、ほかのSkillでは、/figure-it-out（第23章）が、後戻りできない設計の判断で /architect を呼びます。/no-comments（第32章）も、コメントの指摘を直すのにコードの新しい形が必要なときに、/architect を一度だけ呼びます。

手順：Ground から Scrap まで、5つの Phase で進む

Phase 名前 内容
A Ground（土台を固める） /how（第22章）で、新しいコードが関わる仕組みを調べる。関係するファイル名を挙げるだけでは調べたことにならないので、/how が求めるとおり、処理の流れをたどった結果を残す。設計が、どのモジュールが何を受け持つかやレイヤーを変えるなら、/why で今の形になった理由も調べ、その理由を設計の制約にする
B Sketch（骨組みを描く） /arena で複数の設計案を作らせ、比べて統合する
C Agree（合意する） 既定では人の確認を挟まずに実装へ進む。利用者が求めたときだけ、設計を見せて承認を待つ
D Implement（実装する） 骨組みの not implemented の仮の本体を、実際のコードに置き換える
E Scrap（捨てる） 骨組みに合わない回避策や逸脱が実装で繰り返し出たら、骨組みを捨てて設計し直す

Phase B：構造の異なる案を2つ以上比べる

エージェントは、最初の案で十分に見えても、構造の異なる設計を少なくとも2つ作らせてから統合します。難しい設計を1回だけ作らせると、その設計は、モデルが最初に思いついた形に固まってしまうからです（同梱ガイドの 04-design.md）。

エージェントが比べるのは、1つの形の中の部分的な手直しではなく、形そのものが異なる案です。

たとえば、importRows の引数の名前だけを変えた案は、同じ形の手直しにすぎません。1つの関数だけを公開する案と、読み込み、検証、保存を別々の関数として公開する案なら、形そのものが異なります。

Phase B のこのやり方は、第17章の原則『Exhaust the Design Space』を具体化したものです。

/arena が起動する各候補（設計案を1つずつ作るサブエージェント）は、10項目の指示に従って設計案を作ります。ここでは、そのうち主な5つを紹介します。

1. 呼び出し側の使い方を先に書き、そこから型を決める

候補は、型を書く前に、その型を使う呼び出し箇所のコードを先に書きます。呼び出し側がどう使いたいかが、設計が満たすべき仕様だからです。

使い方と型が食い違ったら、候補は、型のほうを直して使い方に合わせます。

たとえば、骨組みの例で使用したコードでは、先に onImportClick の中で importRows(file, { onError: "skip" }) という呼び出しを書き、その書き方に合わせて ImportOptions と ImportResult の型を決めました。

// 呼び出し側の使い方：これを先に書き、ここから型を決める
async function onImportClick(file: File) {
  const result = await importRows(file, { onError: "skip" });
  console.log(`${result.imported}件を取り込み、${result.skipped}件を飛ばしました`);
}

// 骨組み：型とシグネチャだけを書き、中身は書かない
// onError は、不正な行があったときに、その行を飛ばすか（skip）、取り込みを止めるか（stop）
type ImportOptions = { onError: "skip" | "stop" };
type ImportResult = { imported: number; skipped: number };

export async function importRows(file: File, options: ImportOptions): Promise<ImportResult> {
  throw new Error("not implemented");
}
2. よく行う読み書きに合うデータ構造を先に決める

候補は、ロジックを書く前に、よく行う読み書き（例：IDでユーザーを1人引く）に合うデータ構造を決めます。

候補は、その読み書きを、決めたデータ構造でどう処理するかを1つずつたどって確かめます。たどった結果、「後で索引やキャッシュを追加すればよい」という答えになるなら、そのデータ構造は間違っています。

たとえば、IDでユーザーを引く処理が多いのに、ユーザーを配列で持つケースを見てみましょう。

配列で持つと、IDで引くたびに配列を先頭から探すことになります。IDで引く処理をこの構造でたどると、「後でIDからの索引を追加すればよい」という答えになるので、配列という構造は間違っています。そこで、候補は最初から、IDをキーにした表（マップ）で持つ構造を選びます。

type User = { id: string; name: string };
// 探したいユーザーのID
declare const id: string;

// 前：IDで引くたびに、配列を先頭から探す
const userList: User[] = [];
const found = userList.find((u) => u.id === id);

// 後：IDをキーにした表で持ち、IDから直接引く
const usersById = new Map<string, User>();
const user = usersById.get(id);

このように、向いているデータ構造はよく行う読み書きで変わるので、候補は、実装の前に、その読み書きに合った構造を選びます。

3. 公開する関数を少なくし、処理はその裏に隠す

候補は、外に公開する関数や型（公開インターフェース）を少なく小さくし、多くの処理をその裏に隠します。こうすることで、呼び出し側が知る必要のあることが減るからです。

公開するものが少ないのに、裏に多くの処理を隠しているインターフェースを、「深いインターフェース」と呼びます。

たとえば、インポートの処理の公開インターフェースを2通りに書くと、次のようになります。

// 深い：公開するのは1つの関数だけで、読み込み、検証、保存はその裏に隠す
type DeepImporter = {
  importRows(file: File, options: ImportOptions): Promise<ImportResult>;
};

// 浅い：3つの関数を公開し、呼び出し側がそれらを正しい順番で呼ぶ必要がある
type ShallowImporter = {
  loadRows(file: File): string[][];
  validateRows(rows: string[][]): string[][];
  saveRows(rows: string[][]): Promise<void>;
};

DeepImporter なら、呼び出し側は importRows を1回呼ぶだけで取り込めます。ShallowImporter では、呼び出し側が3つの関数を正しい順番で呼ばなければなりません。

4. 常に成り立つべき条件は、できるだけ型で表す

候補は、不変条件を、まず型で表します。型で表せないときは実行時のチェックで表し、それもできないときだけコメントで書きます。

たとえば、「発送済みの注文は、必ず追跡番号を持つ」という不変条件を3通りで書くと、次のようになります。

// 型で表す：shipped の注文は、trackingNo を持つ形しか書けない
type Order =
  | { state: "paid" }
  | { state: "shipped"; trackingNo: string };

// 実行時のチェック：型では防げず、動かしたときに初めて見つかる
type LooseOrder = { state: "paid" | "shipped"; trackingNo?: string };

function assertTrackingNo(order: LooseOrder): void {
  if (order.state === "shipped" && !order.trackingNo) {
    throw new Error("発送済みなのに追跡番号がありません");
  }
}

// コメント：守られるかどうかは、コメントを読んだ人次第
type CommentedOrder = {
  state: "paid" | "shipped";
  // state が "shipped" のときは、必ず trackingNo を入れること
  trackingNo?: string;
};

型で表せば、不変条件を破るコードを書いた時点でコンパイラが知らせてくれます。そのため、候補は、不変条件をできるだけ型で表します。

5. 外から入る値は入口で一度だけ検証し、内側では確かめ直さない

候補は、外から値が入る場所（境界。例：ファイルやAPIのレスポンスを受け取る関数）で、値を一度だけ検証し、検証した値に型を付けます。内側のコードは、型の付いた値を確かめ直さずに使います。入口で一度確かめておけば、内側で同じ確認を何度も書かずに済むからです。

たとえば、インポートの処理なら、importRows がファイルの各行を読んだ直後に、IDが空でないかを確かめます。内側の保存の処理は、確かめ終えた行だけを受け取るので、IDが空かどうかを確かめ直しません。

この指示は、第18章の原則『Boundary Discipline』に従ったものです。

設計に理由書を付け、退けた別案とその理由を書く

各候補は、設計に1ページの理由書を付けます。理由書では、呼び出し側から見た使い方（Usage）を型より先に書き、退けた別案とその理由を必ず書きます。

候補は、別案を比べるときに、実装が簡単かどうかだけでなく、呼び出し側に見せる複雑さと、内側に隠す複雑さで比べます。たとえば、DeepImporter と ShallowImporter なら、呼び出し側が知る必要のある関数は1つと3つなので、DeepImporter のほうが、呼び出し側に見せる複雑さが小さくなります。

統合する前に、8つの危険信号で点検する

エージェントは、候補を統合する前に、すべての候補を、危険信号の一覧（references/design-red-flags.md）で点検します。危険信号とは、エージェントが見つけたら、その設計を直すか、退ける理由になる構造上の特徴です。

点検するときは、次の前提に立ちます。

Assume the next contributor is an agent that sees only the files it opened, copies the nearest example, and takes the shortest path that compiles. Prefer the design where a change that looks right from one file is right for the whole repo.

次にコードを変更するのは、自分が開いたファイルしか見ず、いちばん近くにある例をまね、コンパイルが通る最短の道を選ぶエージェントだと想定せよ。1つのファイルだけを見て正しく見える変更が、リポジトリ全体にとっても正しくなる設計を選べ。

つまり、この前提は、次にコードを変えるエージェントがリポジトリ全体を見ていなくても、正しい変更しかできないような設計を選ぶ、ということを意味します。同じ前提は、/correct（第35章）にも書かれています。

8つの危険信号は、次のとおりです。

  • 浅いモジュール・・・ 公開する関数や型が多いのに、その裏に隠す処理が少ないモジュールです。
  • 情報の漏れ・・・ 本来は1つのモジュールの中だけで決めておけばよいこと（例：データをどんな形で持つか）を、ほかのモジュールも前提にして書かれている状態です。その決めごとを変えると、前提にしているモジュールをすべて一緒に直す必要があります。
  • 順番による分割・・・ 処理を実行する順番（読み込む→検証する→保存する）どおりに、モジュールを分けた構造です。順番どおりに分けると、どのモジュールも同じデータの形を受け渡しするので、その形を前提にするモジュールが増えます。原文は、同じデータを扱う処理は、実行するタイミングが異なっても1つのモジュールにまとめるよう勧めています。
  • 素通しのメソッド・・・ 受け取った引数を、同じ形のまま別のメソッドへ渡すだけのメソッドです。
  • 持ち主が複数いる（原文では Split ownership）・・・ 複数のモジュールが、同じ状態を書き換えたり、それぞれが自分の写しを持ったりしている状態です。
  • 1つの作業に2つのやり方（原文では Two ways to do one task）・・・ 同じ作業に、2つ以上のやり方が用意されている状態です。
  • 外から import できる内部実装（原文では Importable internals）・・・ モジュールの内部実装（外に公開するつもりのない関数や型など）を、外から import できる状態です。
  • 手動で同期する一覧（原文では Hand-synced list）・・・ 2か所以上に同じ項目の一覧があり、項目を足すにはすべての一覧を編集する必要がある状態です。

ここからは、前半の4つと後半の4つに分けて見ていきます。

まず、前半の4つです。たとえば、インポートの処理で、前半の4つの危険信号をすべて含む骨組みは、次のようになります。

// load.ts：CSVを読み、各行を文字列の配列にする（浅いモジュール）
export function loadRows(file: File): string[][] {
  throw new Error("not implemented");
}

// validate.ts：0列目がIDであることを前提に、IDが空の行を除く（浅いモジュール・情報の漏れ）
export function validateRows(rows: string[][]): string[][] {
  throw new Error("not implemented");
}

// save.ts：0列目がIDであることを前提に、IDをキーにして保存する（浅いモジュール・情報の漏れ）
export function saveRows(rows: string[][]): Promise<void> {
  throw new Error("not implemented");
}

// importer.ts
export class Importer {
  // 受け取った rows を、同じ形のまま saveRows へ渡すだけ（素通しのメソッド）
  save(rows: string[][]): Promise<void> {
    return saveRows(rows);
  }
}

// 呼び出し側：3つを正しい順番で呼ばないと取り込めない（順番による分割）
async function onImportClick(file: File) {
  const rows = validateRows(loadRows(file));
  await new Importer().save(rows);
}

このコードでは、4つの危険信号が次のように現れています。

  • 浅いモジュール・・・ 3つのファイル（load.ts・validate.ts・save.ts）は関数を1つずつ公開していますが、どの関数も、読むだけ、行を除くだけ、保存するだけという小さな作業しかしていません。公開している関数の数に比べて、裏に隠している処理が少ないので、浅いモジュールです。その結果、1回の取り込みを終えるには、呼び出し側が3つの関数を自分で組み合わせて呼ぶ必要があります。原文も、1つの操作のために呼び出し側が複数の関数を組み合わせることを、浅いモジュールの兆候に挙げています。
  • 情報の漏れ・・・ validate.ts と save.ts は、どちらも「各行は文字列の配列で、0列目（配列の先頭の要素）がID」という前提で書かれています。たとえば、CSVの列の並びが変わり、IDが2列目に移ったとします。すると、validate.ts と save.ts の両方を同時に直さなければなりません。
  • 順番による分割・・・ ファイルを、処理の順番どおりに「読み込む」（load.ts）、「検証する」（validate.ts）、「保存する」（save.ts）の3つに分けています。3つのファイルは、行のデータを順に手渡ししていくので、3つとも「各行は文字列の配列」という同じ形を知っていなければなりません。そのため、行の形を変えると、3つのファイルすべてを直すことになります。
  • 素通しのメソッド・・・ Importer.save は、受け取った rows を同じ形のまま saveRows へ渡すだけで、何も隠していません。

このように、決めごとが複数のモジュールに散らばると、変えるたびに直す場所が増えるので、決めごとは1つのモジュールの内側に閉じ込める必要があります。

前に示した importRows(file, options) の骨組みなら、呼び出し側は1つの関数を呼ぶだけで済みます。行の表し方や、どの列がIDかという決めごとは、importRows のモジュールの内側に閉じ込められます。

次に、後半の4つです。どれも、上の前提に書かれたエージェントの次の3つの性質のせいで起きる間違いを扱っています。

  • 自分が開いたファイルしか見ない
  • いちばん近くにある例をまねる
  • コンパイルが通る最短の道を選ぶ

後半の4つは、importRows の骨組みを使っていても、その周りのコードで起こりえます。ここからは、取り込みの処理を例に、1つずつ見ていきます。

持ち主が複数いる

取り込んだ行数を、2つのファイルがそれぞれ数えています。

// importer/progress.ts：取り込んだ行数を数える
export let importedCount = 0;
export function onRowImported() {
  importedCount += 1;
}

// ui/ProgressBar.ts：画面に出す行数を、画面の側でも別に数えている
let shownCount = 0;
export function onRowShown() {
  shownCount += 1;
}

エージェントに「取り込みを中止したら、行数を0に戻して」と頼んだとします。エージェントは、開いた progress.ts に importedCount = 0 を足して終えます。ProgressBar.ts は開いていないので、shownCount は0に戻りません。その結果、画面には、中止する前の行数が出たままになります。

直し方は、行数の持ち主を1つにすることです。たとえば、ProgressBar.ts は自分では数えず、progress.ts の importedCount を読むだけにします。

 // ui/ProgressBar.ts
-let shownCount = 0;
-export function onRowShown() {
-  shownCount += 1;
-}
+// 自分では数えず、progress.ts の importedCount を読むだけにする
+import { importedCount } from "../importer/progress";

こうすれば、行数を0に戻す処理は progress.ts に足すだけで済み、画面の行数も一緒に0に戻ります。

1つの作業に2つのやり方

取り込みの入口が2つあります。

// importer/import.ts：ファイルから取り込む入口
export function importRows(file: File, options: ImportOptions): Promise<void> {
  throw new Error("not implemented");
}

// importer/import.ts：文字列から取り込む、古い入口。中身は importRows とほぼ同じ
export function importText(text: string): Promise<void> {
  throw new Error("not implemented");
}

エージェントは、新しい画面に取り込みの機能を付けるとき、近くにある既存の画面のコードをまねます。その画面が importText を使っていれば、新しい画面も importText を使います。こうして、どちらの入口も呼び出し元が増え続けます。取り込みの不具合を直すときには、2つの入口の両方を直す必要が出てきます。

直し方は、入口を importRows の1つに絞ることです。importText の呼び出し元を importRows に移し、同じ変更の中で importText を消します。

 // importer/import.ts
 export function importRows(file: File, options: ImportOptions): Promise<void> {
   throw new Error("not implemented");
 }
-
-export function importText(text: string): Promise<void> {
-  throw new Error("not implemented");
-}

 // importText を呼んでいた画面（例：ui/PastePage.ts）
-await importText(text);
+await importRows(new File([text], "pasted.csv"), options);

外から import できる内部実装

取り込みの内側だけで使うつもりの関数が、export されています。

// importer/parse.ts：取り込みの内側だけで使うつもりの、CSVを解析する関数
export function parseCsv(text: string): string[][] {
  throw new Error("not implemented");
}

エージェントに「取り込む前に、CSVの中身を画面に表示して」と頼んだとします。エージェントは、すでに export されている parseCsv を、プレビュー画面から直接 import します。取り込みのモジュールに表示用の入口を足すより、そのほうが早く、コンパイルも通るからです。

// ui/PreviewPage.ts：取り込みの内側の関数を、直接 import している
import { parseCsv } from "../importer/parse";

その結果、parseCsv は、取り込みのモジュールのインターフェース（外から使ってよい関数や型）の一部になってしまいます。あとで parseCsv の戻り値の形を変えると、プレビュー画面も壊れます。

直し方は、parseCsv をモジュールの外から届かないようにし、外から import するとビルドが失敗するようにすることです。たとえば、ESLint のルールで、importer の外から内部のファイルを import することを禁じます。

 // eslint.config.js
 rules: {
+  "no-restricted-imports": ["error", {
+    patterns: [{
+      group: ["**/importer/*", "!**/importer/index"],
+      message: "importer の内部は import できません。importer/index から使ってください。",
+    }],
+  }],
 },

CIで ESLint を実行していれば、PreviewPage.ts のような import は、CIで失敗します。エージェントは、失敗したメッセージを読んで、importer/index が公開している関数を使うように直します。

手動で同期する一覧

同じ列の一覧が、2つのファイルにあります。

// importer/columns.ts：取り込める列の一覧
export const COLUMNS = ["id", "name", "email"];

// ui/columnLabels.ts：画面に出す列名の一覧。同じ3つの列を、別に書き並べている
export const COLUMN_LABELS = { id: "ID", name: "名前", email: "メールアドレス" };

エージェントに「電話番号の列を足して」と頼んだとします。エージェントは、開いた columns.ts の COLUMNS に "phone" を足して終えます。COLUMN_LABELS は更新されないので、画面には電話番号の列名が出ません。

直し方は、一覧を1つにし、ほかの一覧はそこから作ることです。たとえば、列の名前と画面に出す名前を1つの一覧にまとめ、画面に出す列名の一覧は、そこから作ります。

 // importer/columns.ts：列の名前と、画面に出す名前を、1つの一覧で持つ
-export const COLUMNS = ["id", "name", "email"];
+export const COLUMNS = [
+  { key: "id", label: "ID" },
+  { key: "name", label: "名前" },
+  { key: "email", label: "メールアドレス" },
+] as const;

 // ui/columnLabels.ts：自分では書き並べず、COLUMNS から作る
-export const COLUMN_LABELS = { id: "ID", name: "名前", email: "メールアドレス" };
+import { COLUMNS } from "../importer/columns";
+export const COLUMN_LABELS = Object.fromEntries(COLUMNS.map((c) => [c.key, c.label]));

こうすれば、電話番号の列を足すときは、COLUMNS に1行足すだけで済みます。

どうしても1つにできない一覧は、一覧どうしが食い違ったらビルドが失敗するようにします。

Phase C：既定では人の確認を挟まずに実装へ進む

既定では、エージェントは人の確認を挟まずに実装へ進みます。

エージェントが人の返事を待たずに進め、人が後から方針を修正するのは、原則『Never Block on the Human』（第20章）と同じ考え方です。

人が設計の形に異議を唱えたら、エージェントはその異議を Phase A の新しい材料として扱い、調べ直して Phase B をやり直します。

実装の前に設計の弱点を厳しく問いただしたいときは、エージェントは、統合した骨組みに第28章の /interrogate をかけます。

Phase E：骨組みを捨てる判断

エージェントは、骨組みを捨てるかどうかを、1回きりの出来事ではなく、繰り返し現れるパターンで判断します。

兆候は、たとえば次のようなものです。

  1. 同じ形の回避策が、無関係なコードに繰り返し現れる（例：importRows を呼ぶ別々の画面が、どれも呼ぶ前に同じ前処理を自分で書いている）
  2. コンパイルを通すために、any やキャストのような逃げ道が必要になる
  3. 呼び出し側が、共通の関数や型の内部の決まりを知らないと、それを使えない（例：importRows を呼ぶ前に、呼び出し側が必ず別の初期化の関数を呼んでおかなければならない）
  4. 骨組みからの同じ形の逸脱が、別々の箇所で2回以上起きる（例：骨組みにない引数の追加が、2つの関数で別々に必要になる）

たとえば、4つの兆候をすべて含む実装は、次のようになります。

type Row = { id: string; name: string };

// 取り込みに使うデータベースの接続を、先に作っておく関数
declare function initImporter(): Promise<void>;

// 骨組みでは parseRows(text: string): Row[] だった
// 兆候4：実装で、骨組みになかった tenantId（どの契約者のデータか）の引数が必要になった
declare function parseRows(text: string, tenantId: string): Row[];

// 骨組みでは saveRows(rows: Row[]): Promise<void> だった
// 兆候4：実装で、骨組みになかった tenantId（どの契約者のデータか）の引数が必要になった
declare function saveRows(rows: Row[], tenantId: string): Promise<void>;

// 設定画面
async function onUploadFromSettings(file: File) {
  // 兆候3：これを先に呼ばないと、importRows が失敗する。この決まりは、importRows の型からは読み取れない
  await initImporter();

  // 兆候1：importRows を呼ぶ前に、CSVの1行目（見出しの行）を自分で取り除いている
  const lines = (await file.text()).split("\n");
  const body = new File([lines.slice(1).join("\n")], file.name);

  // 兆候2：骨組みの ImportResult にない reasons（飛ばした行の理由）を読むために、any にしている
  const result = (await importRows(body, { onError: "skip" })) as any;
  console.log(result.reasons);
}

// ダッシュボード：設定画面とは無関係の画面なのに、兆候1の前処理と、兆候3の初期化を同じように書いている
async function onUploadFromDashboard(file: File) {
  // 兆候3の初期化
  await initImporter();
  // 兆候1の前処理
  const lines = (await file.text()).split("\n");
  const body = new File([lines.slice(1).join("\n")], file.name);
  await importRows(body, { onError: "stop" });
}

まれな入力や状況（エッジケース）への対応がいくつか必要になるだけでは、設計全体を否定する理由になりません。また、扱うデータそのものが入り組んでいるせいで分岐が増えるのも、骨組みを捨てる理由になりません。

たとえば、国ごとに住所の書き方が異なるせいで分岐が増えるのは、データが入り組んでいるからで、設計が間違っているからではありません。

骨組みを捨てるとき、エージェントは、それまでに作ったものに /how をかけ直して仕組みを調べ直します。そのうえで、古い骨組みに修正を継ぎ足すのではなく、実装で分かった新しい制約を最初からの前提として、Phase B から設計し直します。

また、エージェントは、新しい骨組みに何かを追加する前に、まず不要なもの（例：使われなくなった関数や、重複した検証）を削ります。不要なものを先に削る手順は、原則『Subtract Before You Add』（第17章）に従ったものです。そのため、新しい骨組みは、機能を追加し始める前の時点で、古い骨組みより小さくなります。

依頼の書き方：「一番気にしていること」を添える

同梱ガイドの 04-design.md には、次の依頼例があります。

/architect design the import pipeline before writing any code. i care most about how callers use it.
// コードを書く前に、インポートの処理の流れを設計して。一番気にしているのは、呼び出し側がどう使うか。

Phase C で確認を挟みたいときは、利用者は次のように頼みます。

/architect with checkpoint. stop and show me before implementing.
// 確認を挟んで。実装の前に止まって、設計を見せて。

使い方から設計を考える実践と、設計を見直す実践は、第41章と第42章で扱います。

/arena は、一つの最良の成果物のために複数の候補を競わせる

役割：同じ課題をN個の候補に解かせる

候補とは設計案を1つずつ作るサブエージェントのことです。
/arenaは、複数の候補に課題を解かせ、最良の成果物を選び、ほかの成果物の良い考えを最良のものに取り込むSkillです。

使いどき：後から直すと高くつく成果物

利用者やエージェントは、キャッシュキーの形式のように、1回だけ作らせると最初に思いついた形に決まってしまいそうで、しかも後から変えると高くつく成果物に /arena を使います。

/poteto-mode の作業の中で /arena を呼ぶ場面は、主に2つです。

1つは、/architect が Phase B で複数の設計案を作らせるときです。
もう1つは、『Feature』Playbookの手順4で、実装に複数の妥当な形がありうるとき（たとえば、エラーの扱い方やテストの構成に、複数の妥当な書き方があるとき）に、主エージェントがコーディングを /arena の候補に任せるときです。

/arena は、PlaybookやほかのSkillからも呼ばれる

/arena を呼ぶPlaybookとSkillは、どれも、1つのモデルに1回だけ作らせた答えでは偏りや見落としが残る場面で /arena を使います。呼ぶ側ごとの場面と理由は、次のとおりです。

/architect：設計案を1つだけで決めない

/architect は、Phase B で /arena を呼び、複数のモデルに設計案を作らせます。難しい設計を1回だけ作らせると、その設計は、モデルが最初に思いついた形に固まってしまうからです（この章の『Phase B：構造の異なる案を2つ以上比べる』）。

『Eval』Playbook：Skillの変更の効果を、複数のモデルと目隠しの採点で測る

『Eval』は、Skillやプロンプトの変更が、エージェントの行動をどう変えるかを測るPlaybookです（第13章）。

『Eval』では/arenaを直接、呼び出すわけではありませんが、/arenaの手順どおりに作業を進めるように定義されています。

『Eval』では、変更を入れた環境で、同じ依頼を複数のモデルに別々に解かせます。そのうえで、どのモデルの出力かを伏せたまま、別のモデルに採点させます。
つまり、複数の候補に同じ課題を解かせ、別のモデルに採点させる進め方は、/arena と同じということです。

『Orchestrate』Playbook：後戻りできない判断を、作業を動かし始める前に比べる

『Orchestrate』は、何日も続き、多数のPRとサブエージェントが動くプロジェクトを管理するPlaybookです（第16章）。

『Orchestrate』は、最初の手順（Frame）で、意見の分かれる作業の分け方や、後戻りできない判断を、最初の作業単位を試しに動かす前に /arena にかけます。後戻りできない判断は、プロジェクトが動き出した後では直せないからです。

/blast-radius：大きな変更の影響を、複数のモデルに調べさせる

/blast-radius（第28章）は、大きな変更や影響の広い変更を調べるときに、/arena で複数のモデルに同じ問いを投げ、その答えを統合します。/blast-radius の SKILL.md によれば、モデルが異なれば、見つける不具合も異なるからです。

手順：Frame から Verify まで、6つの Phase で進む

Phase 名前 内容
A Frame（課題を定める） 各候補が作る成果物と、3〜6個の採点基準を決め、候補ごとに別の出力先を割り当てる。出力先を分けるのは、候補同士が互いの成果物を上書きしないようにするため
B Fan out（一斉に起動する） N個のサブエージェントを同時に起動する。既定では、Opus と Grok で1体ずつ、合わせて2体
C Cross-judge（別のモデルが採点する） 全候補が書き終えてから、判定役（cross-judge）のモデルに採点させる。判定役には、できるだけ、主エージェント（候補を起動した元のエージェント）とは別の系統のモデルを選ぶ
D Pick（土台を選ぶ） 主エージェントが全候補を最後まで読んで採点基準ごとに採点し、判定役が勧める土台と比較して土台を決める。一致すれば選択の裏づけになる。食い違えば、主エージェントと判定役のどちらかに偏りがあるか、採点基準があいまいだったと疑う
E Graft（移植する） 負けた候補から価値のある部分を探し、機械的に貼り付けず、土台の設計に合うように書き直して組み込む。成果物が1つの考え方で一貫している必要があるため
F Verify（確かめる） 統合した成果物が実際に機能するかを、ほかの成果物と同じ厳しさで、原則『Prove It Works』（第19章）に従って確かめる

6つの Phase の流れは次のとおりです。

判定役は、全候補が書き終えてから起動する

判定役の採点と、主エージェントが全候補を読む作業は、全候補が書き終えてから並行して進みます。主エージェントは、候補がまだ書いている途中で判定役を起動しません。

候補には、作る成果物を明記した同じプロンプトを渡し、採点基準は見せない

全候補は同じプロンプトを受け取るので、各候補が何を作るかは、プロンプトに書いた内容だけで決まります。そのため、主エージェントは Phase A で、各候補が作る成果物（例：キャッシュキーの形式の案と、その理由）をプロンプトに明記します。

採点基準は、主エージェントが Phase D で土台を選ぶときに使うものなので、主エージェントは候補に採点基準を見せず、課題だけを見せます。

土台には、最も機能を追加しやすい候補を選ぶ

主エージェントは、将来の保守担当者が、不変条件を壊さずに最も機能を追加しやすい候補を、土台に選びます。

全候補が同じ形にたどり着いたら、主エージェントは、別々に解いた候補の答えが一致したことを強い裏づけとみなし、移植をせずにその形を採ります。

候補の形が大きく食い違ったら、課題を定め直す

候補の形が大きく食い違ったら、主エージェントは、課題の定め方が足りなかったと判断し、Phase A に戻って課題を定め直してやり直します。

たとえば、候補ごとにキャッシュキーの形式がすべて異なるとき、主エージェントは、各候補から少しずつ取った中間の形式を作ることはしません。中間の形式は、どの候補の考え方とも一貫しない形になるからです。

最後に、統合した成果物と統合メモを返す

主エージェントが最後に返すのは、統合した成果物1つと、短い統合メモです。統合メモに書く内容は次のとおりです。

  • 土台に選んだ候補と、選んだ理由（判定役の結論を含む）
  • ほかの候補から取り込んだ部分と、それぞれがどの候補から来たか
  • 検討したが取り込まなかった部分と、その理由
  • 成果物を出せずに途中で抜けた候補（あれば）。主エージェントは、抜けた候補を除いた残りの候補で統合を進め、抜けたことをメモに残します
  • 統合した成果物を、Phase F（Verify）で実際に動かして確かめた結果

依頼の書き方：候補の数を指定する

04-design.md には、候補数を指定する例があります。

/arena this, 5 candidates. the cache key format is expensive to change later.
// これを候補5つで。キャッシュキーの形式は後から変えると高くつく。

同梱ガイドの 10-recipes-and-pitfalls.md は、後から変えると高くつく決定の前に、今の設計についてセカンドオピニオンを頼む使い方も挙げています。

この使い方では、主エージェントは、利用者とエージェントが今進めている設計を候補の一つとして、ほかの候補と比べます。

ask /arena for a second opinion on this thread and our approach
// このスレッドと、私たちの進め方について、/arena でセカンドオピニオンを出して

/swarm は、網羅と競争のために仕事をWorkersに分け、結果を一つの報告にする

役割：Cloud Agentsを並列に動かす

/swarm は、クラウド上でN体のエージェント（Workers）を同時に動かし、結果を集めて一つの報告を返すSkillです。/arena が「一つの最良の答え」を作るのに対し、/swarm は「漏れのない確認」か「速い答え」を作ります。

poteto氏は『The Complete Guide to pstack』Part 1で、多数の Cloud Agents（Cursorのクラウド上で動くエージェント）で検証スキルを実行し、十分なサンプル数で性能の改善を確かめたり、アプリをファジングしたりする使い方を挙げています。

!

ファジング・・・ ランダムな入力や壊れた入力を大量に与えて、不具合を探すテスト

使いどき：網羅、競争、関門、探索の分割

使いどきは次のとおりです。

  • 網羅・・・ 主エージェントが、複数の範囲をWorkersに割り振り、漏れなく確かめます（例：packages/ 以下のすべてのパッケージを確かめる）。
  • 競争・・・ 主エージェントが、同じ課題を複数のWorkersに競わせます（例：同じ不具合の再現を複数のWorkersで試す）。
  • gauntlet（関門）・・・ 主エージェントが、1つの変更に検証を何本も並べ、変更がすべての検証に通ることを求めます（例は次の囲みで示します）。
  • 探索の分割・・・ 主エージェントが、探す場所を複数に分け、各Workersに1か所ずつ調べさせます（例：不具合の原因を探すとき、疑わしいモジュール1つ1つに対して1体ずつWorkerを割り振って調べさせる）。

!

gauntlet（関門）は、pstackのファイルに定義のある言葉ではありません。英語の gauntlet は、次々と課される試練をくぐり抜けることを指します。

pstackでの使われ方は、同梱ガイドの 04-design.md にある「gauntlet lanes」（関門の担当）という書き方と、/swarm を使うPlaybookから読み取れます。

たとえば、Playbook『Multi-phase or multi-PR plan』（第16章）が作る計画書では、PRがレビューに出せる状態になったときと、その後に変更をpushするたびに、その時点のPRの最新のコミットに対して、次の担当を /swarm で並列に走らせ、すべてが PASS のときだけ合格とします。

  • テストやlintなどのチェックを、その最新のコミットで実行し直す担当1つ
  • 実際の画面やCLIで確かめる担当10個
  • 性能を測る担当1つ
  • 差分と実行の記録を読み、PRの説明を疑って点検する担当2つ以上

/poteto-mode は、節『Non-negotiables』で、仕事を並列に分ける場面（網羅、競争、関門、探索の分割）では /swarm を使うと定めています。特に、第16章で見た、多数のPRを検証しながら進めるPlaybookは、PRをマージしてよいかの判定に /swarm を使います。

たとえば『Autopilot-full』（PRごとの担当者が、作るところからマージまでを受け持つ手順書）では、コーディネーターエージェント（作業全体を管理するエージェント）が、独立した検証者を /swarm で並列に動かし、その結果を一つの判定にまとめます。各PRの担当者は、問題なしの判定が出るまで、PRをマージしません。

手順：Frame から Report まで、4つの Phase で進む

/swarm は、次の4つの Phase で進みます。

  1. Frame・・・ 主エージェントが、終了条件（何が成り立てば完了かを、確かめられる形で書いた条件）と、返すべき報告を定めます。形（次の表の分担、競争、混合）とWorkersの数も決めます。Workersの数は、利用者が依頼で指定すればその数にし、指定がなければ形から決めます。
  2. Fan out・・・ 主エージェントが、全Workersをクラウドで同時に起動します。Workersはそれぞれ PASS（合格）、ISSUES（問題あり）、BLOCKED（確かめられなかった）のどれかを、証拠（例：確かめたコミットのSHA（コミットを識別する値）と、チェックの出力）付きで報告します。
  3. Aggregate・・・ 主エージェントが結果を集めます。競争なら、Frame で宣言しておいた選び方の規則を当てはめて、結果を選びます。
  4. Report・・・ 主エージェントが、結果の表、証拠付きの問題、結果が得られなかった範囲（空白）と途中で抜けたWorkers（脱落）を、一つの報告にまとめます。

Frame で選ぶ形は、次の3つです。

形 内容
分担（partition） 仕事を重ならない範囲に分け、Workersがそれぞれ1つを受け持つ（例：パッケージごとに1体）
競争（race） N体のWorkersに同じ指示を与えて競わせる（例：同じ不具合の再現を複数のWorkersで試す）
混合 分担と競争を組み合わせる（範囲ごとに複数のWorkersを競わせる）

競争と混合の形では、主エージェントが、「最初に合格したものを採る」（first pass）、「全員を順位付けする」（rank all）、「最も良いものを採る」（best-of）のどれを選び方の規則にするかを、起動する前に宣言します。

主エージェントは、指示で求めた記録がない結果は捨てます。記録とは、たとえば、確かめたコミットのSHA（コミットごとに付く、コミットを一意に指すID）や、何回測るかなどの計測の方法です。そして、記録のない結果を出したWorkerが受け持っていた仕事を、新しく起動したWorkerに一度だけやり直させます。どのコミットをどう確かめたかが分からない結果は、今のコードに当てはまるかを判断できないからです。

2回目も記録が欠けたら、主エージェントはその範囲を空白として記録します。空白は合格と数えません。

たとえば10体のうち9体が PASS で1体が欠ければ、報告は「9件合格」ではなく「9件合格、1件空白」になります。

依頼の書き方：確かめ方、形と数、返すものを一文ずつ書く

READMEと同梱ガイドには、次の依頼例があります。

/swarm check every package under packages/ against its check.sh. one worker per package. one report.
// packages/ 以下の全パッケージを、それぞれの check.sh で確かめて。1パッケージに1体。報告は1つ。

この依頼は、確かめ方（check.sh）、形と数（1パッケージに1体）、返すもの（報告は1つ）を、一文ずつ書いています。この3つは、主エージェントが Frame で決める内容に該当するので、依頼に書いておけば、主エージェントはその指定に沿って Frame を組み立てます。

並列の3つのSkillは、得たいものと、変更の大きさや戻しにくさで使い分ける

使い分けは次のとおりです。

  • 関数の境界をまたぐ変更を設計したい（例：新しい関数を作り、別のファイルの関数から呼ぶ）・・・ 内部で /arena を使う /architect
  • 最後に一つの成果物がほしい（例：キャッシュキーの形式を1つに決める）・・・ /arena
  • 多くの範囲を確かめた結果を、一つの表にまとめたい（例：packages/ 以下の全パッケージのチェック結果）・・・ /swarm

設計の手間は、変更の大きさと戻しにくさで決める

すべての変更に設計作業が必要なわけではありません。04-design.md は、次の目安を示しています。

状況 使うもの
小さく完成した変更で、不安がある /interrogate だけ
関数の境界をまたぐ、または所有（どのモジュールが責任を持つか）を移す変更 /architect（内部で /arena も使う）
命名やアルゴリズムのような単独の判断 /arena を直接
範囲ごとの網羅的なチェック、並列のチェック、選び方の規則を宣言した競争 /swarm
意見が分かれ、元に戻すのが高くつく設計 /architect の後に /interrogate

/poteto-mode は、この目安を自分で当てはめ、関数の境界をまたぐ作業では、頼まれなくても /architect を呼びます。そのため、利用者がこれらのSkillを直接呼ぶのは、既定より念入りに、または手短に確かめたいときです。

/arena と /swarm は、得たいものが異なる

項目 /arena /swarm
目的 一つの最良の成果物を作る 網羅するか、競争で速く答えを出す
各サブエージェントへの指示 全員に同じ課題 分担なら別々の範囲、競争なら同じ指示
結果のまとめ方 土台を選び、負けた候補の良い部分を、土台の設計に合わせて書き直して移植する 表にまとめる。競争なら宣言した規則で選ぶ
出力 統合した成果物1つと統合メモ チャットの中の一つの報告

利用者が網羅のために /arena を使うのは、よくある取り違えです（10-recipes-and-pitfalls.md）。/arena は全候補に同じ課題を与えるので、別々の範囲を確かめることにはならないからです。

網羅には、利用者は、範囲を分けて結果を一つの報告にまとめる /swarm を使います。/swarm は、/arena のように土台を選んで移植する手順を踏みません。

まとめ

  • 3つのSkillの分担・・・ /architect、/arena、/swarm は、/poteto-mode が『Non-negotiables』の規則やPlaybookの手順に従って呼びます。
  • /architect・・・ 関数の境界をまたぐコードの前に、呼び出し側の使い方から型を導き、関数の中身を書かない骨組みを作ります。同じ形の回避策や型の逃げ道（any やキャスト）が繰り返し出たら、骨組みを捨てて設計し直します。
  • /arena・・・ 後から直すと高くつく成果物（例：キャッシュキーの形式）を複数のモデルに解かせ、最も良い候補を土台に選び、ほかの候補の良い部分を土台の設計に合わせて書き直して移植します。
  • /swarm・・・ 網羅（例：全パッケージのチェック）や競争のためにWorkersを並列に動かし、一つの報告にまとめます。確かめたコミットなどの記録が、Workerを1回起動し直しても欠けた範囲は、合格と数えず空白として報告します。
  • 並列の3つの使い分け・・・ 関数の境界をまたぐ変更なら /architect、一つの成果物なら /arena、網羅した結果の表なら /swarm です。
