この章では、/no-comments を扱います。

/no-comments は、エージェントが、レビューの前に、差分のコメントを、そのコメントを書いていない別のエージェント（Comment Sicko）に審査させるSkillです。Comment Sicko は、プロジェクト自身のコードの意外な挙動（例：保存する関数が確認メールも送る）を説明するコメントを消し、その関数を、直すべき箇所として報告します。元のエージェントは、コメントがなくても挙動が分かるよう、関数名を変えたり関数を分けたりしてコードを直します。外部のライブラリなど、自分たちでは変えられないものに強いられた挙動を説明するコメントは、消さずに残します。

/no-comments は、第30章から続く、コードの品質を保つ3つのSkillの3つ目です。/no-comments で、コードを書いたエージェントの代わりにコメントを確かめるのは、コメントを書いていない Comment Sicko です。

/no-comments が審査する対象は、差分の中のコメントと、lint や型チェックの抑制指示（eslint-disable、@ts-ignore など）です。

!

  • 抑制指示・・・ lint や型チェックが出す警告を、その箇所だけ止めるために、コードに書く指示
  • Comment Sicko・・・ pstack に同梱された、コメントを審査して消すサブエージェント（第8章）
  • /no-comments が Comment Sicko を起動し、その報告を受けて、/no-comments がコードを直す

この章では、/no-comments を、役割、使いどき、規則と手順、依頼の書き方の4つの観点で解説します。

役割：コメントを書いていないエージェント（Comment Sicko）に、そのコメントを審査させる

/no-comments は、レビューの前にコメントを取り除くSkillです。

このSkillは、Comment Sicko（第8章）を起動し、Comment Sicko の指摘のうち受け入れたものを直します。また、コメントが主張する制約（例：「文言を変えないこと」）を、テストなどのコードで表す案を出します。

このSkillは、自分たちのコードの意外な挙動を説明するコメントを、コードを直すべき箇所の印として扱います。そうした挙動は、名前を変えたり関数を切り出したりすれば、文章で説明しなくてもコードを読めば分かる形に直せるからです。
※ 「意外な挙動を説明するコメント」については『保存する関数が確認メールも送る例で、コメントを関数名に置き換える』で後述します。

コメントの審査を別のエージェントに任せる理由を、同梱ガイドの docs/guide/05-build-and-clean.md は次のように説明しています。

Comments need their own pass, and not from the agent that wrote them. An author defends its comments the way you'd defend yours.

コメントには専用の点検が必要で、書いたエージェント以外が行うべきだ。書き手は、あなたが自分のコメントを守るのと同じように、自分のコメントを守ってしまう。

エージェントが自分の書いたコメントを点検すると、自分のコメントを守ろうとして、不要なコメントでも残してしまいます。そのため、コメントの審査は、コメントを書いていない Comment Sicko が行います。

使いどき：レビューの前に、差分を対象に呼ぶ

/no-comments は disable-model-invocation: true の設定を持つので（第25章）、エージェントが会話の内容から /no-comments を選んで動かすことはありません。このSkillを動かすのは、名前で呼ぶ利用者と、/poteto-mode の規則やPlaybookの手順です。

/poteto-mode の節『Non-negotiables』（第8章）の規則や、PRを開くときの『Opening a PR』Playbookなどが、レビューの前に /no-comments を呼ぶよう定めています。

/no-comments が見る範囲は、呼び出し側が渡したファイルか差分です。渡されなければ、ベースブランチ（既定は main）との差分を、まだコミットしていない変更も含めて見ます。

/no-comments と、似た掃除をするほかの2つのSkillは、対象によって次のように分担しています。

  • コードの中の不要物・・・ /deslop が、処理を説明するだけのコメント、根拠のない防御的なチェック、使われなくなった互換性のための経路などを取り除きます。/deslop は cursor-team-kit に同梱されていて、pstackには含まれません。
  • 文章の癖・・・ /unslop（第33章）が、READMEやPR説明などの文章から、AIらしい癖を取り除きます。
  • コメント・・・ /no-comments が、コメントを書いていないエージェントにコメントを審査させます。

/no-comments は、PRを作るPlaybookからも呼ばれる

/no-comments を呼ぶPlaybookは、どれも、PRをレビューや検証に出す前に、差分からコメントを取り除いておくために /no-comments を使います。呼ぶ側ごとの場面と理由は、次のとおりです。

『Opening a PR』：レビューの前に、未完成に見える差分を片付ける

『Opening a PR』は、PRを開くPlaybookで、他のすべてのPlaybookの最後に呼ばれます。このPlaybookは、レビューの前に /no-comments を実行するよう定めています。PRを開くサブエージェントも、/no-comments を実行してから、PRのURLを投稿します。

同梱ガイドの 05-build-and-clean.md は、差分のCleanup（片付け）を省略できない理由として、処理を説明するだけのコメントや、防御のための不要なコードが残った差分は、レビューする人には未完成に見えることを挙げています。同ページは、残った不要なコードが、次の不具合が潜む場所になるとも書いています。

『Autopilot-full』『Autopilot-stack』：コードを確定させてから、検証に渡す

『Autopilot-full』と『Autopilot-stack』（第16章）では、PRごとの担当者（PR1本の変更を最初から最後まで受け持つクラウドエージェント）が、/deslop と /no-comments を済ませ、マージするコードが最終の形になってから、そのコミットのSHA（コミットごとに付く、コミットを一意に指す識別子）を報告します。その後で、担当者自身による検証とCIが、/swarm（第24章）による独立した検証と並行して進みます。

『Multi-phase or multi-PR plan』：計画書のチェックリストに入れる

『Multi-phase or multi-PR plan』（第16章）が作る計画書は、PRごとの担当者が1項目ずつ実行し、運用者（計画の実行開始を指示し、証拠を点検する人）が証拠を見て確かめるチェックリストです。計画書のひな形には、すべてのPRに共通する項目として、「コミットの前に毎回 /deslop を、レビューの前に /no-comments を実行する」が入っています。

規則と手順：Comment Sicko の指摘を審査する

Comment Sicko はコメントを審査して消し、アプリのコードは書き換えない

Comment Sicko（agents/comment-sicko.md）は、コメントを消し、直すべきコードを報告するだけで、アプリのコードは書き換えません。

Comment Sicko の定義は、「常軌を逸したコメント嫌い」という誇張した口調で書かれています。ただし、残してよいコメントの規則は厳密です。

Comment Sicko が残すコメントは次の5種類だけで、迷ったら消します。

  • 法務・ライセンスのヘッダー
  • 自分たちでは変えられない外部の依存やプラットフォームに強いられた、自明でない挙動の説明
  • // prettier-ignore（コード整形ツール Prettier に、直後のコードを整形させない指示）と、ルール自体が誤っている、細かすぎる、またはスタイルだけを扱うlintルールの抑制
  • 公開APIの契約を定義するドキュメントコメント
  • コードでは表せない制約を説明する issue や RFC（設計を提案する文書） へのリンク

意外な挙動の説明や、重要なlintルールの抑制は消し、MUST KILL として挙げる

Comment Sicko は、自分たちのコードの意外な挙動を説明するコメントを消し、その挙動を持つシンボル（関数や変数、型などの名前）を、報告の中で MUST KILL として挙げます。MUST KILL は、改名、切り出し、型付け、設計のやり直しなどで、文章で説明しなくても挙動が分かるように直すことを求める指摘です。

実際に起きうる不具合を見つけるlintルールや、正しさや安全を守るlintルールを、抑制指示（eslint-disable、@ts-ignore、@ts-expect-error など）で止めている場合も、Comment Sicko はその抑制指示を消し、lintの警告の原因になっているシンボルを MUST KILL として挙げます。

保存する関数が確認メールも送る例で、コメントを関数名に置き換える

自分たちのコードの意外な挙動を説明するコメントの例を見てみましょう。

保存する関数が、実は確認メールも送るケースです。

type User = { name: string; email: string };

// 前：自分たちの関数の意外な挙動を、コメントで説明している
// 注意：この関数は、保存に加えて確認メールも送る
function saveUser(user: User) { /* ... */ }

type User = { name: string; email: string };

// 後：2つの仕事を、名前で分かる2つの関数に切り出す
function saveUser(user: User) { /* ... */ }
function sendConfirmationMail(user: User) { /* ... */ }

前のコメントは、外部の依存に強いられた挙動ではなく、自分たちのコードの意外な挙動を説明しています。そのため、Comment Sicko は、このコメントを消し、saveUser を MUST KILL として挙げます。

Comment Sicko 自身はコードを直しません。/no-comments が、後の例のように2つの関数に切り出せば、コメントがなくても、どちらの関数が何をするかが名前で分かります。

このように、自分たちのコードの意外な挙動をコメントで説明しているなら、コメントを消し、挙動が名前で分かる形にコードを直す必要があります。

/no-comments は、Comment Sicko の報告をそのまま受け入れずに審査する

/no-comments は、Comment Sicko の報告と、Comment Sicko が加えた変更を、そのまま受け入れません。次の3つの段階で審査します。

  1. 誤りのある報告を却下し、1回だけやり直させる
  2. 根拠の書かれていない注意書きへの判断は、/how か /why で確かめてから受け入れる
  3. 直すのに新しいコードの形が必要なら、/architect で形を決めてから直す

1. 誤りのある報告を却下し、1回だけやり直させる

Comment Sicko の報告や変更には、次のような誤りが混じることがあります。

  • 渡した範囲の外への指摘・・・ /no-comments が審査を頼んだファイルや差分の外にある、コードについての指摘
  • アプリのコードの書き換え・・・ Comment Sicko はコメントしか変えてはいけないのに、アプリのコードまで書き換えた変更
  • 残してよいコメントの削除・・・ 『Comment Sicko はコメントを審査して消し、アプリのコードは書き換えない』で挙げた、残してよい5種類に当たるコメントを消した変更
  • MUST KILL の理由の誤り・・・ MUST KILL として挙げたシンボルについて、直すべき理由として書いた内容が、実際のコードと合っていない指摘（例：確認メールを送っていない関数を、「確認メールも送る」として挙げる）
  • 意図したコードへの誤った指摘・・・ 意図して書き、残すと決めたコードを、直すべきものとして挙げた指摘

こうした誤りのある報告を見つけたら、/no-comments は、Comment Sicko の変更を元に戻し、何が誤っていたかを伝えて、Comment Sicko にもう一度だけ審査させます。2回目の報告にも誤りがあれば、/no-comments は、その問題を未解決として報告し、/no-comments の実行を失敗として終えます。

2. 根拠の書かれていない注意書きへの判断は、/how か /why で確かめてから受け入れる

コードには、「IMPORTANT」や「do not remove（消さないこと）」のように、理由が書かれていない短い注意書きのコメントがあります。

Comment Sicko がこうしたコメントを「消す」または「残す」と判断していたら、/no-comments は、その判断を受け入れる前に、コメントが付いているシンボルに /how か /why（どちらも第22章）を実行します。/how でコードの今の仕組みを、/why でコードがその形になった理由を調べ、注意書きの主張が今も正しいかを確かめるためです。

たとえば、次のような注意書きです。

declare function sleep(ms: number): Promise<void>;
declare function saveDraft(): Promise<void>;

async function onClose(): Promise<void> {
  // IMPORTANT: do not remove
  await sleep(100);
  await saveDraft();
}

/why で調べた結果、この待ち時間が、すでに直った古いライブラリの不具合を避けるためのものだと分かれば、注意書きの主張はもう正しくありません。この場合、/no-comments は、Comment Sicko の「消す」という判断を受け入れます。

調べても判断がつかないときは、/no-comments は、コメントを消します。

3. 直すのに新しいコードの形が必要なら、/architect で形を決めてから直す

受け入れた指摘のうち、使われていない処理を消す、不要な引数を外す、本来使うべきAPIを使うといった小さな直しは、/no-comments がそのまま直します。

関数の分け方や型の作り方など、コードの新しい形を決めないと直せない指摘があれば、/no-comments は、受け入れた指摘をまとめて /architect（第24章）に一度だけ渡し、形を決めてもらいます。/architect は形を決めるところで止まり、実際にコードを直すのは /no-comments です。

受け入れた指摘は根本原因から直す

/no-comments は、審査で受け入れた指摘を、根本原因から直します（第19章の原則『Fix Root Causes』）。

たとえば、Comment Sicko が、回避策（不具合の原因を直さずに、症状だけを避けるコード）の理由を説明するコメントを消したなら、/no-comments は、回避策のコードも消し、回避策が必要になった根本原因のほうを直します。

ただし、/no-comments は、渡された範囲の外のコードを直しません。根本原因が範囲の外にあれば、範囲の中でできる最小の修正だけを行い、残りは未解決として報告します。

制約を主張するコメントは、コードで守らせる方法を提案し、承認を待つ

制約を主張するコメントとは、「do not remove（消さないこと）」「do not change wording（文言を変えないこと）」「talk to X before changing（変える前にXに相談すること）」のように書かれたコメントです。

/no-comments は、こうしたコメントについて、その制約を、コメントではなくコードで守らせる方法を1つ提案し、利用者の承認を待ちます。方法の候補は次の4つで、/no-comments は、渡された範囲の中で最も手間の少ないものを選びます。

  • 型・・・ 制約に反するコードを、コンパイルエラーにする
  • 実行時チェック・・・ 制約に反したら、実行時にエラーを出す
  • テスト・・・ 制約に反したら、テストが失敗する
  • lint・・・ 制約に反するコードを、lint が警告する

たとえば、「文言を変えないこと」というコメントなら、/no-comments は、その文言が変わると失敗するテストを書く案を出します。そのテストがあれば、コメントがなくても制約が守られます。

// 前：制約をコメントだけで主張している
// 文言を変えないこと
function stockLabel(count: number): string {
  return count === 0 ? "在庫切れです" : `残り${count}点`;
}

// テストを1件登録する
declare function test(name: string, fn: () => void): void;
// 値を確かめる
declare function expect(value: unknown): { toBe(expected: unknown): void };

// 後：制約をテストで表し、コメントを消す
function stockLabel(count: number): string {
  return count === 0 ? "在庫切れです" : `残り${count}点`;
}

test("在庫が0のときの文言は「在庫切れです」から変わらない", () => {
  expect(stockLabel(0)).toBe("在庫切れです");
});

このように、コメントが制約を主張しているなら、その制約をテストなどのコードで表す必要があります。

利用者が承認すれば、/no-comments は制約をコードで表してからコメントを消します。承認しなければ、コメントは消したうえで、その制約を未解決として報告します。
