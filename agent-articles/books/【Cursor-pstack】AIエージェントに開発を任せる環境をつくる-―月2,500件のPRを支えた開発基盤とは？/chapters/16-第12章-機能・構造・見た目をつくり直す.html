この章では、次の4つのPlaybookを扱います。

  1. Feature
  2. Refactoring
  3. Prototype
  4. Visual parity

4つとも、コードに手を入れるPlaybookです。違いは、振る舞いの扱い方です。振る舞いとは、コマンドの出力や画面の表示のように、ユーザーが実際に受け取る結果のことです。

扱い方の違いは次のとおりです。

  • 振る舞いを追加するか、変える
  • 振る舞いを変えずに、構造だけを直す
  • 振る舞いを試して設計を決め、コードは捨てる
  • 見た目をピクセル単位でそろえる

どのPlaybookを使うときも、依頼には何を変えてはいけないかを書きます。同梱ガイドの実装のページ（docs/guide/05-build-and-clean.md）も、Featureの依頼には、振る舞いと、変えてはいけないものを書くよう勧めています。

この章では、4つの違い、それぞれの使い方、依頼の書き方を順に解説します。

この章の構成

この章の構成は次のとおりです。

4つのPlaybookは、振る舞いを追加するか、保つか、試すか、見た目をそろえるかで選ぶ

4つのPlaybookは、振る舞いをどう扱うかで分かれます。何を変えてはいけないか、何に責任を持つか、どう検証するかも、それに合わせて変わります。

項目 『Feature』 『Refactoring』 『Prototype』 『Visual parity』
振る舞い 追加する、変える 変えない 試す（本番には入れない） 見た目を変えない
責任を持つもの 設計 契約（今の振る舞い） 設計判断（コードではない） ピクセル単位の同一性
検証 変更が現れる場所で実際に動かして確かめる 本物の成果物で、変更前と振る舞いが同じことを証明する 各案を観察で比べる 画像差分がゼロ

4つの間には受け渡しもあります。『Prototype』は比較して決めた設計案を『Feature』に渡します。『Refactoring』は、途中で見つかった足りない機能や本物のバグを別の作業に切り出し、先に構造の変更を出します。設計ごと作り直す場合は、作り直しだと明示して『Feature』へ回します。

『Feature』は、データの形を決めてから、実装を任せてレビューする

『Feature』は、新しい機能で扱うデータの形（データの項目や型）を先に決め、それをもとに機能を実装するPlaybookです。主エージェントは設計に責任を持ち、コードを書く作業は別のエージェントに任せます。

要点は2つです。

  • 書き始める前にデータの形を決める・・・ 原則『Model the Domain』（第18章）は、構造は書くときに選べば低コストで済むが、後から取り戻そうとするとリファクタリングに見えて先送りされがちだ、と説明しています。
  • コードを書く人と、その差分をレビューする人を分ける・・・ コードを書く作業はサブエージェントに任せ、主エージェントはその差分をレビューします（手順4）。

手順：設計を決め、実装を任せ、検証してからPRを作る

手順は8つです。

  1. 影響するサブシステムに /how（コードの仕組みを説明するSkill、第22章）をかける
  2. /architect（コードより先に設計を描くSkill、第24章）で、型やモジュール構成の案を並列に探る
  3. スループット・チェックポイントを書く（以下の表を参照）
  4. コードを書く作業をサブエージェントに任せる
  5. 変更が現れる環境（画面ならブラウザ、コマンドならCLI）で検証する
  6. 小さく順序立ったコミットにrebaseする（原則『Sequence Work into Verifiable Units』、第19章）
  7. 設計に異論があるなら、複数のモデルのレビュアーが変更を問いただす /interrogate（第28章）をかけてから進める
  8. PRを作る手順を定めた『Opening a PR』を実行する（第14章）

!

rebase・・・ Gitの操作で、コミットを別の土台の上に積み直すこと。コミットの順序を並べ替えたり、複数のコミットを1つにまとめたりするのにも使う

手順3のスループット・チェックポイントは、作業を「どう並列に分けられるか」を検討した結果を、TODOリストに記録する際の4つの項目です。

!

TODOリスト・・・ エージェントが作業の始めに作る、その作業でやることの一覧（計画）です。Cursorでは、チャットの画面に表示されます。利用者は、この一覧を見て、エージェントがどの手順を進め、どの手順を飛ばしたか（skip: <理由>）を確かめられます
（同梱ガイド 01-setup.md）。

複数手順の自明でない作業では、『Feature』以外でもこの手順を書くよう求められています。

項目 書くこと
先に済ませる手順 並列に進める前に通すべき関門
独立した作業の流れ コンフリクトが起こらない作業（ファイルやレイヤーが重ならない作業）は並列にできる
共有される可変の状態 既定は、変更対象を分け、同じものを同時に書き換えないようにし、共有をなくすこと（原則『Separate Before Serializing Shared State』）
最小で安全な分け方 安全に分けられる作業単位を書く。1人で進めるほうがよければ、その理由を書く

4項目のうち、今回の作業に当てはまらないものも削らず、n/a: <理由> と理由を書きます。これで、検討した結果不要としたのか、項目を見落としたのかを区別できます。

手順4の実装では、ファイルのパス、データの形、成功の基準を指定して、feature用に設定したモデル（第6章で触れた /setup-pstack で変えられます）のサブエージェントに任せます。実装に複数の妥当な形があり得るなら、同じ課題に複数の候補を並列に作らせて良いところを組み合わせる /arena（第24章）を通します。

この委任は必須で、skip: <理由> で省くことも、「最小の変更」を求める原則『Laziness Protocol』で覆すこともできません。得たいのは行数の節約ではなく、レビューの分離だからです。

実装を任されたサブエージェントが、さらに別のサブエージェントを起動できない場合は、その実装サブエージェントがコードを書きます。依頼元のエージェントが差分をレビューするため、実装とレビューの担当は分かれたままです。

依頼の書き方：振る舞いと、変えてはいけないものを書く

同梱ガイドの例は、次のとおりです。

/poteto-mode add a --json flag. text output stays byte-identical. verify both forms.
// --json フラグを足して。テキスト出力はバイト単位で同じまま。両方の形を確かめて。

『Refactoring』は、今の振る舞いを固定してから構造を動かす

『Refactoring』は、名前の変更、抽出、重複の除去、移動のように、振る舞いを保ったまま構造だけを変えるPlaybookです。

主エージェントが責任を持つのは「契約」、つまり今の振る舞いです。構造は変えても、今の振る舞いは変えません。

構造だけでなく設計ごと作り直すことも許容されますが、その場合は作り直しだと明示し『Feature』へ回します。

手順：振る舞いを固定し、不要なコードを消してから動かし、同等性を確かめる

手順は8つです。

  1. 振る舞いの契約を固定する
  2. 欠けている構造に名前をつける
  3. 目標の形に名前をつける
  4. 追加する前に消す
  5. 小さな歩幅で動かす
  6. 振る舞いが変わっていないことを、本物の成果物で証明する
  7. 残す価値があるかを確かめる
  8. 小さく順序立ったコミットにrebaseする

ここからは、各手順を1つずつ見ていきます。

!

  • スナップショットテスト・・・ 出力を一度ファイルに保存しておき、以降の実行結果をそれと比べて変化を検出するテスト

1. 振る舞いの契約を固定する

構造を動かす前に、今の振る舞いを担保する特性テスト（今の出力をそのまま正解として記録するテスト）、スナップショットテスト、新旧の出力を比べる仕組みなどを書く。型チェックやlintが通るだけでは、振る舞いを固定したことにはならないためである。

2. 欠けている構造に名前をつける

この手順は、原則『Model the Domain』（第18章）に当たる。

3. 目標の形に名前をつける

モジュールの分け方、データ型、関数同士の呼び出し関係を決める。目標の形が関数の境界をまたぐなら /architect で探る。

4. 追加する前に消す

デッドコード（使われていないコード）や、呼び出し元が1か所しかない関数（Wrapper）は、その処理を呼び出し元にまとめるなどし、不要なコードを消してから、新しい構成を入れる（原則『Subtract Before You Add』）。

5. 小さな歩幅で動かす

一つずつ、手順1で固定したテストや比較が通る状態を保つ。APIの形を変えるなら、APIの呼び出し元をすべて新しいAPIに移し、古いAPIを同じ一連の変更の中で消す（原則『Migrate Callers Then Delete Legacy APIs』、第18章）。

6. 振る舞いが変わっていないことを、本物の成果物で証明する

コンパイルやbuildが通るだけでは、振る舞いが変わっていないことの証明にならない（原則『Prove It Works』）。

7. 残す価値があるかを確かめる

差分が読み手の負荷を下げていなければ取り消す（原則『Minimize Reader Load』、第17章）。

8. 小さく順序立ったコミットにrebaseする

コードを消す引き算の実装、構造の作り直し、後続のclean upの順にコミットし、『Opening a PR』を実行する。

依頼の書き方：構造を動かす前に今の出力を記録させる

同梱ガイドの例は、次のとおりです。

/poteto-mode move parsing into one module, zero behavior change. record the current output first and prove it's unchanged after.
// パースを1つのモジュールに移して。振る舞いの変化はゼロ。先に今の出力を記録して、後で変わっていないことを証明して。

「先に今の出力を記録して」が手順1に、「後で変わっていないことを証明して」が手順6に該当します。

『Prototype』は、捨てる前提のコードで設計を低コストで決める

『Prototype』は、捨てる前提のプロトタイプを作り、観察した結果で設計の判断を下すPlaybookです。

主エージェントが責任を持つのは設計判断で、コードではありません。本番の実装は『Feature』で行います。

捨てる前提なので、原則『Laziness Protocol』の「最小の変更」と、検証の基準の2つが逆転する唯一のPlaybookとされています。

磨くより速さを優先し、コードの品質は問わず、頼まれていない案も出します。検証の基準は「変更が正しい」ことの証明ではなく、「決めたいことを観察する」ことに変わります。

手順：何を決めるのかをはっきりさせたうえで、プロトタイプを作り、比較する

手順は6つです。

  1. プロトタイプで何を決めるのかをはっきりさせる
  2. 方針がまだ決まっていないなら参考例を集める
  3. 本番のソースから離れた作業用ディレクトリで作る
  4. 代替案は同じ画面で切り替えて比べられるようにする
  5. 各案を実際に動かして比べる
  6. 比較結果として代替案、トレードオフ、推奨を示す

ここからは、各手順を1つずつ見ていきます。

1. プロトタイプで何を決めるのかをはっきりさせる

決めるのは、見た目や操作なら「どのレイアウトにするか」「どの操作方法にするか」「画面の要素をどれくらい詰めて並べるか」、動かして観察すればどれが良いかがわかる選択なら「どの挙動にするか」「どのタイミングにするか」「どの方法にするか」だ。決めることがないならプロトタイプを作らず、『Feature』へ回す。

2. 方針がまだ決まっていないなら参考例を集める

似た機能や画面の例を利用者に見せ、プロトタイプを作り始める前に、どんな見た目や操作にするか選んでもらう。すでに決まっていれば省略する。

3. 本番のソースから離れた作業用ディレクトリで作る

本番用のフレームワーク、テスト、抽象化は持ち込まず、問いを確かめるための最小限のコードだけ用意する。

4. 代替案は同じ画面で切り替えて比べられるようにする

各案にラベルをつけ、ボタンやキー操作で切り替える（原則『Exhaust the Design Space』、第17章）。

5. 各案を実際に動かして比べる

画面の見た目ならスクリーンショット、処理時間なら計測値を記録し、手順1ではっきりさせたことを決めるための材料を集める。

6. 比較結果として代替案、トレードオフ、推奨を示す

各案の違いと採用した場合の長所・短所を説明し、推奨案を伝える。採用する案が決まったら、その方針を『Feature』に引き継ぐ。

依頼の書き方：「比べたいので2つ作って」と書く

pstackのREADMEの例は、次のとおりです。

/poteto-mode build two prototypes of the markdown renderer so we can compare. spawn an agent for each.
// 比べられるように、markdownレンダラーのプロトタイプを2つ作って。それぞれにエージェントを立てて。

「モックを作って」「このレイアウトを試して」のような言い回しも、このPlaybookへの合図です。

『Visual parity』は、基準の見た目（ベースライン）を仕様として画像差分ゼロを目指す

『Visual parity』は、2つの実装を一致させるときや、スタイリングの仕組みを移行するときに、UIの見た目をピクセル単位で同一に保つPlaybookです。

ベースラインには手を触れず、同一であることは画像差分で確かめます。

合否は目視ではなく、差分がゼロかどうかで決まります。ただし、ベースラインそのものがおかしく見えたときは、エージェントはベースラインを直さず、止まって利用者に聞きます（手順2）。

手順：部品ごとに画像差分ゼロまで回す

手順は5つです。

  1. 移行の前に、比較基準（ベースライン）を作る
  2. 差分を通すための近道を禁じる
  3. 部品を1つずつ移す
  4. 各部品をベースラインと画像差分で比べる
  5. 部品ごと、または安全なまとまりごとに『Opening a PR』を実行する

ここからは、各手順を1つずつ見ていきます。

!

  • worktree・・・ Gitの機能で、1つのリポジトリから複数の作業ディレクトリを作り、別々のブランチを同時に扱えるようにするもの

1. 移行の前に、比較基準（ベースライン）を作る

移行前の部品を、さまざまな状態（通常、ホバー、無効など）で自動的にスクリーンショットする仕組みを作る。このスクリーンショットが、移行後の見た目と比較する基準になる。

2. 差分を通すための近道を禁じる

ハーネス（手順1のスクリーンショットを撮って比べる仕組み）を変えない、ベースラインを改ざんしない、差分を通すために部品の構造を組み替えない。ベースラインがおかしく見えたら、止まって利用者に聞く。

3. 部品を1つずつ移す

部品を1つずつ新しい実装やスタイリング方式に置き換える。worktreeを分けて並列に進め、共有の基本部品は最初に移す。

4. 各部品をベースラインと画像差分で比べる

比較差分がゼロになるまで /loop（エージェントを繰り返し起こし直すCursor組み込みのコマンド、第15章）で回す。

5. 部品ごと、または安全なまとまりごとに『Opening a PR』を実行する

依頼の書き方：「2枚目の画像が正しい」とベースラインを伝える

READMEの例は、次のとおりです。

/poteto-mode the row spacing is too tall when this flag is on. the second image is correct. repro and fix until it matches.
// このフラグがオンのとき、行間が高すぎる。2枚目の画像が正しい。再現して、一致するまで直して。

「2枚目の画像が正しい」が、どちらの見た目をベースラインにするかを伝える一文です。これがなければ、エージェントはどちらに合わせるかを推測するしかありません。

依頼には「何を変えてはいけないか」を書く

4つのどれに頼むときも、依頼には「何を変えてはいけないか」を書きます。

依頼で伝えたいこと 依頼の言葉の例 振り分け先
新しい振る舞いが欲しい。既存の出力は変えない 「テキスト出力はバイト単位で同じまま」 『Feature』
構造だけ整えたい 「振る舞いの変化はゼロ。先に今の出力を記録して」 『Refactoring』
どの設計がよいか決めたい 「比べられるように、プロトタイプを2つ作って」 『Prototype』
見た目を寸分違わずそろえたい 「2枚目の画像が正しい。一致するまで直して」 『Visual parity』

依頼に書いた一文は、作業が終わったかを確かめる基準になります。たとえば「テキスト出力はバイト単位で同じまま」と書けば、テキスト出力が変更前とバイト単位で同じであることが、完了の条件の1つになります。

まとめ

  • 4つの分かれ方・・・ 『Feature』は設計、『Refactoring』は契約、『Prototype』は設計判断、『Visual parity』はピクセル単位の同一性に責任を持ちます。
  • Feature・・・ データの形を決め、スループット・チェックポイントを書き、実装は必ず別のエージェントに任せます。
  • Refactoring・・・ 今の振る舞いをテストなどで固定し、不要なコードを消してから構造を動かし、本物の成果物で振る舞いが変わっていないことを証明します。
  • Prototype・・・ 「最小の変更」と検証の基準が逆転します。案を低コストで作って観察で比べ、決まった方向を『Feature』に渡します。
  • Visual parity・・・ ベースラインに手を触れず、部品ごとに画像差分がゼロになるまで回します。
  • 依頼の書き方・・・ 「何を変えてはいけないか」を書くと、それが完了の検査になります。

次の第13章では、Skillを書く『Authoring or modifying a skill』と、変更の効果を確かめる『Eval』を扱います。
