この章では、次の5つの原則を扱います。

  1. Prove It Works
  2. Fix Root Causes
  3. Sequence Work into Verifiable Units
  4. Test Behavior, Not Implementation
  5. Explain the Number

5件はVerification（検証）のグループの原則で、どれもエージェントが何を確かめたら、作業を完了と言えるかを決めます。同梱ガイドのページ docs/guide/08-principles.md は、5件を「何をもって証明とするか」を決める原則とまとめています。

5件を使うと、エージェントは、次のように動作します。

  • 「ビルドが通った」で終わりにせず、書き出したファイルを開いて、実際に書かれた行を確かめる
  • エラーを消すだけの対処（例：値が null なら処理を飛ばすチェックを足す）をせず、なぜエラーが起きたのかを突き止めて、その原因を直す
  • 作業を小さな単位に分け、単位を1つ終えるたびにテストを実行し、通ってから次の単位へ進む
  • テストでは、コードがどの関数を呼んだかではなく、コードに具体的な入力を渡したときに実際に返ってくる値を、期待値と比較する
  • 「30%速くなった」などの数値を報告する前に「何がその数値を頭打ちにしているか」を突き止め、エラーやキャッシュなど別のものを測定していないかを確かめる

この章では、5原則を、第17章と同じく、ルールと発火条件の観点で1件ずつ解説し、最後に、重複行の依頼で原則がどう使われるかを示します。

重複行の依頼とは、はじめにで紹介した次の依頼で、利用者が「再試行が実行の途中に入ると、エクスポートが重複した行を書き出す」という不具合をエージェントに直してもらうものです。

/poteto-mode the export writes duplicate rows when a retry lands mid-run. repro first, then fix and verify.
// 再試行が実行の途中に入ると、エクスポートが重複した行を書き出す。まず再現して、それから直して、確かめて。

本章の依頼例も、第17章と同じく、原則名を入れた一行の指示にしています。原則名を書かなくても、作業が発火条件に当てはまればエージェントが原則を自分で読んで適用することは、第17章の前提で見たとおりです。

!

本章で原則の依頼例を載せているのは、5件のうち『Prove It Works』の1件だけです。

本書では、依頼例を、pstackの同梱ガイド、README、poteto氏のポストに記載があるものだけにとどめるものとします。原文に依頼例がない原則について本書で依頼例を作ると、pstackが想定していない使い方を示してしまうおそれがあるためです。

5原則の一覧

Principle 一文の結論
『Prove It Works』 作業の結果を、代理指標ではなく本物を直接見て確かめる
『Fix Root Causes』 不具合の症状（表に出たエラーなど）を隠すのではなく、その症状を起こした根本原因を直す

!

代理指標（原文では proxy）・・・ 本来確かめたいものの代わりに見る、間接的な手がかり

たとえば、「ファイルの更新時刻が新しいから、中身も正しく書き換わったはずだ」「ビルドが通ったから、機能も動くはずだ」と判断するときの更新時刻やビルドの成功が、代理指標にあたります。

『Prove It Works』は、作業の結果を代理指標ではなく本物を直接見て確かめる

原則『Prove It Works』は、エージェントが完了を宣言する前に、実際に動くアプリ、書き出されたファイル、画面に出た値そのものを、自分で確かめるよう求めます。

この原則の中心は、原文の冒頭にある次の一文です。この一文は第2章でも引用しました。

Verify every task output by checking the real thing directly. Do not infer from proxies, self-reports, or "it compiles."

すべての作業結果を、本物を直接確かめて検証する。代理指標、自己申告、「コンパイルが通った」から推測しない。

原則がこれを求めるのは、確かめていない作業は、正しく見えても実際には間違っていることがあるからです。

エージェントには、次のような間接的な確認のほうが、本物を直接見るより手軽に見えます。どれも、機能を動かさずに済むからです。

  • ファイルの更新時刻（「更新時刻が新しいから、書き出しは成功したはずだ」）
  • 出力が新しいかどうか（「今回の実行で書き出されたものに見えるから、正しいはずだ」）
  • エージェントの自己申告（「直しました」という報告）
  • 保存済みのスクリーンショット（前に撮った画面の写し）

しかし、間違った推測をもとに作業を進めると、本物を確かめるよりはるかに大きなコストがかかります。

たとえば、エージェントが、更新時刻だけを見て「書き出しは成功した」と報告し、実際にはファイルに重複した行が入っていたケースでは、利用者が後で重複に気づき、どの作業から壊れていたのかを調べ直すことになります。

このように、本物を確かめずに完了を宣言すると後から手間が大きく増えるので、完了の前に本物を直接確かめる必要があります。

ルール：実際に動かした結果と実際の値を読む

本物を見るとは、エージェントが機能を実際に動かし、実際の値を読む、ということです。主なルールは次のとおりです。

機能は実際に動かして確かめる

エージェントは、「ビルドが通った」「エージェントがそう報告した」で終わらせず、機能を実際に動かして結果を見ます。ビルドの成功が示すのは、コンパイルできたことだけだからです。

たとえば、ボタンを押すと商品がカートに入る機能なら、エージェントは実際にボタンを押し、カートに商品が入ったことを画面で確かめます。

プログラムが動いているかは、直接確かめる

エージェントは、サーバーのようなプログラムが動いているかどうかを、ログファイルのような、プログラムが残した別の情報から推測しません。

たとえば、エージェントは、「ログファイルが最近更新されているから、サーバーは動いているはずだ」とは判断せず、サーバーに実際にアクセスして応答が返ることを確かめます。ログは、サーバーが止まる直前に書かれたものかもしれないからです。

保存された写しではなく、実際の値を読む

エージェントは、キャッシュされた値や、元の値から作られた別の表示ではなく、実際の値を読みます。

たとえば、画面に出る金額が正しいかを確かめるなら、エージェントは、前に撮ったスクリーンショットではなく、今の画面に出ている金額を読みます。前に撮ったスクリーンショットは、元の値が変わった後も古いままのことがあるからです。

確認に失敗したら、システムより先に確かめ方を疑う

確認の結果がおかしいとき、エージェントは、システムが壊れていると決めつける前に、自分の確かめ方が間違っていないかを疑います。

たとえば、画面に新しい値が出ないなら、エージェントは、古い画面を開いたままにしていないか、別の環境のサーバーを見ていないかを先に確かめます。確かめ方が間違っていると、正しく動いているシステムを直そうとしてしまうからです。

確認はスクリプトにして残す

原則によれば、いちばん強い証拠は、一度きりの目視ではなく、同じ比較を何度でも再実行できるスクリプトです。

スクリプトは何度実行しても同じ比較をするので、レビューする人は、エージェントの言葉を信じる代わりに、同じ確認を自分で再実行し、同じ結果になるかを確かめられます。

そこで、エージェントは、可能ならスクリプトを書いて実行し、その出力をレビューする人が見える場所に残します。

たとえば、書き出したファイルの中身を、期待する内容と比べるスクリプトは、次のようになります。

// check-export.ts：書き出したファイルの行を、期待する行と比べる
import { readFileSync } from "node:fs";

const actual = readFileSync("out/export.csv", "utf8").trim().split("\n");
const expected = ["a", "b", "c"];

if (JSON.stringify(actual) !== JSON.stringify(expected)) {
  console.error("NG", { actual, expected });
  process.exit(1);
}
console.log("OK", actual.length);

書き出したファイルが a、b、c の3行なら、OK 3 と出ます。

行が重複して a、b、a、b、c になっていれば、NG と両方の中身が出るので、レビューする人も、どこがずれているかを自分で見られます。

ただし、エージェントは、スクリプトとその出力を、普段はレビューする人に見える場所に残すだけにし、コミットには含めません。

コミットに含めるのは、大きな移植や移行のように、後から作業の跡を監査できる必要がある、大きな作業や複雑な作業のときだけです。

発火条件

作業を終えた後、完了を宣言する前です。

依頼の例：ビルドログではなく、本物の出力を求める

同梱ガイドの docs/guide/10-recipes-and-pitfalls.md は、ビルドが通ったことだけを根拠に成功を報告することを、よくある落とし穴として挙げています。ビルドの成功が示すのは、コンパイルできたことだけだからです。

同じページは、脇道にそれた実行を引き戻す一行の依頼の1つとして、次の依頼を載せています。ビルドログではなく本物の出力を求める依頼なので、エージェントがビルドが通っただけで成功を報告したときに使えます。

apply prove it works. show me the real output, not the build log.
// prove it works を適用して。ビルドログではなく、本物の出力を見せて。

『Fix Root Causes』は、不具合の症状ではなく原因を直す

原則『Fix Root Causes』は、エージェントがデバッグするとき、エラーを消す最短の変更で止めず、なぜ起きたかを根本原因（root cause）までたどり、原因のある場所で直すよう求めます。

原則がこれを求めるのは、症状への対処（回避策）が積み重なるからです。

回避策では本当のバグが残るので、そのバグが別の症状を出すたびに、回避策がまた一つ増えます。回避策が増えるほど、読み手はシステムの動きを理解しにくくなります。

また、回避策が残ると、エージェントがそれを正しい実装例としてコンテキストにしてしまい、間違ったコピーが量産され、コードベースが記憶として機能しなくもなります（第4章）。

原因を直すほうが最初は時間がかかりますが、デバッグにかかる時間の合計は減ります。また、以降のすべてのタスクにも、複利で効果が出てきます。

ルール：症状を隠すガードを追加せず、原因を直す

主なルールは次のとおりです。

先に不具合を再現する

エージェントは、直す前に、不具合が起きる状況を自分で作り、実際に起きることを確かめます。

たとえば、「保存ボタンを2回続けて押すとエラーになる」という報告なら、エージェントは、まず自分で2回押してエラーを出します。再現できないまま直すと、直ったかどうかを確かめられないからです。

根本原因に当たるまで「なぜ」を問う

エージェントは、根本原因に当たるまで「なぜ」を問い続けます。

たとえば、先の保存ボタンの例で見てみましょう。エージェントは、次のように問います。

  1. なぜエラーになるのか → 保存が2回走るから
  2. なぜ保存が2回走るのか → 1回押した後も、ボタンが押せる状態のままだから
  3. なぜボタンが押せる状態のままなのか → 保存している間、ボタンを押せなくする処理がないから

3つ目の答えが原因なので、エージェントは、保存している間はボタンを押せなくするように直します。

1つ目の答えで止めると、エージェントは「2回目の保存を無視する」処理を追加するだけで終わり、ボタンが押せるままになっている、という根本原因は残ります。

このように、途中で「なぜ」を問うのをやめると症状を直すだけの対症療法になるため、根本原因に当たるまで「なぜ」を問い続ける必要があります。

ガードで症状を隠さない

エージェントは、ガードを追加して症状を隠すことはしません。

!

ガード・・・ 問題が起きそうな値のときに、残りの処理を止めたり飛ばしたりする短いチェック（例：関数の先頭に置く if (user === null) return;）

たとえば、値が null のときに落ちる処理に「null なら何もしない」というガードを追加すれば、クラッシュは消えますが、なぜ値が null になったのかは分からないままです。

そのため、エージェントは、ガードを追加せず、値が null になる原因を直します。ガードは症状を隠すだけで、本当のバグは残るからです。

長い言い訳のコメントが必要なら、コードを直す

回避策を正当化するのに段落一つ分のコメントが必要なら、コードが間違っています。直すべきはコメントではなく、コードです。

たとえば、重複行の不具合に対して、次のような修正が追加されていたら、回避策である可能性が高いといえます。

type Row = { id: string };
declare function writeRow(row: Row): void; // 1行をファイルに書く

const writtenIds = new Set<string>();

function writeRowOnce(row: Row) {
  // 再試行が入ると、書き終えたはずの行がもう一度届くことがある。
  // なぜもう一度届くのかは分かっていない。
  // そこで、書き終えた行の ID を覚えておき、同じ ID の行が届いたら書かずに捨てる。
  // こうすれば、重複した行は書き出されなくなる。
  if (writtenIds.has(row.id)) return;
  writeRow(row);
  writtenIds.add(row.id);
}

この修正で重複した行は書き出されなくなりますが、コメントは、なぜ同じ行がもう一度届くのかに答えていません。

エージェントは、このようなコメントとコードを書く前に、なぜ同じ行がもう一度届くのかを問います。

このように、修正を正当化するのに長いコメントが必要なら、コメントを書くのではなく、コードを直す必要があります。

一か所だけでなく、同じパターンの箇所をすべて直す

エージェントは、原因と同じパターンのコードを探し（grepで探索）、見つかった箇所をすべて直します。

たとえば、ある画面で「1回押した後もボタンが押せる」ことが原因なら、エージェントは、ほかの画面のボタンにも同じ書き方がないかを探します。一件だけ直すと、同じバグがほかの箇所に残るからです。

行き詰まったら、推測せずに計測する

行き詰まったとき、エージェントは、推測で直さず、ログを追加したり実際のエラーメッセージを読んだりして、何が起きているかを確かめます。推測で直すと、推測が外れたときに、回避策が一つ増えるだけだからです。

「再起動したら動かなくなった」という不具合では、エージェントは、コードより先に、再起動しても消えずに残る古い状態（原文では stale persistent state）を疑います。たとえば、次のようなものです。

  • 設定ファイル
  • キャッシュ
  • ロックファイル
  • ファイルに保存した処理の途中の状態

処理の途中の状態を保存したファイルを消すと動くようになったなら、原因はそのファイルに残っていた古い状態です。

この場合、エージェントは、ファイルを消して終わりにせず、ファイルから読み込んだ状態が今のコードの想定する形かを確かめる処理（状態の検証）を、修正として優先します。ファイルを消すだけでは、次に古い状態が残ったときに、また動かなくなるからです。

たとえば、以前のコードが途中の状態を { step: 3 } の形で保存し、今のコードは { lastRowId: "b" } の形を想定しているケースでは、状態の検証は次のようになります。

// 今のコードが想定する、途中の状態の形
// 古い { step: 3 } の形は、下の loadState で弾く
type SavedState = { lastRowId: string };

// 保存ファイルから読み込んだ値が、SavedState の形かを確かめる
function loadState(raw: unknown): SavedState | null {
  if (
    typeof raw === "object" &&
    raw !== null &&
    "lastRowId" in raw &&
    typeof raw.lastRowId === "string"
  ) {
    return { lastRowId: raw.lastRowId };
  }
  // { step: 3 } のような古い形の状態は使わず、最初からやり直す
  return null;
}

このように、前の実行が残した状態で動くかどうかが変わるなら、読み込んだ状態を検証する必要があります。

発火条件

デバッグするときです。

『Sequence Work into Verifiable Units』は、作業を確かめられる小さな単位に分けて進む

原則『Sequence Work into Verifiable Units』は、エージェントが作業を小さな単位に分け、単位を一つ終えるたびにテストなどのチェックを実行し、チェックがすべて通ってから、次の単位へ進むよう求めます。

たとえば、50個のファイルにまたがる名前の変更なら、エージェントは、1つのパッケージの名前を変えたらそのパッケージのテストを実行し、通ってから次のパッケージへ進みます。

原則がこれを求めるのは、単位ごとに確かめれば、壊れた箇所を、原因になった単位の段階で見つけられるからです。

たとえば、上の名前の変更で、10個のパッケージをまとめて変えてからテストが落ちたなら、エージェントは10個の変更のどれが原因かを探す必要があります。しかも、そのときにはもう、壊れた状態の上にさらに作業を重ねてしまっています。

1つずつ確かめていれば、テストが落ちたときに見るのは、直前に変えた1つのパッケージだけです。

このように、まとめて確かめる変更が多いほど原因を探す範囲が広がるので、変更を1つ入れるたびに確かめる必要があります。

ルール：一単位ずつ確かめて進め、コミットは正しさを示す順に並べる

作業の進め方のルールは次のとおりです。

一つ変えたら、一度確かめる

エージェントは、正常と分かっている状態から始め、変更を一つ入れ、チェックを実行してから次へ進みます。上の名前の変更の例なら、パッケージ1つが一単位です。

チェックが落ちたとき、エージェントが直すのは、直前に入れた1つの変更だけです。そのため、原因を探す範囲が広がりません。

エージェントは、編集を自動で行う道具（第17章の『Build the Lever』で作るようなもの）を使う場合も、単位ごとのチェックを省きません。道具を使えば、単位ごとのチェックの手間はほとんどかからないからです。

始める前に、きれいなtrunkの上にrebaseする

エージェントは、作業を始める前に、ブランチを、余計な変更のない最新のtrunk（マージ先の本流のブランチ）の上にrebase（ブランチのコミットを、別のコミットの上に付け直すgitの操作）しておきます。

そうすれば、どのチェックの結果も、最新のtrunkという本当の基準（原文では baseline）と比べたものになります。

古いtrunkや、ほかの変更が混ざったブランチの上で作業すると、チェックが落ちたときに、自分の変更が原因なのか、元々あったものが原因なのかを区別できません。

コミットは、正しさを示す順に並べる

エージェントは、コミットとPRを、レビューする人がコミットを順に追うだけで、変更が正しいことを確かめられる順番に並べます。基本の形は「失敗するテストが先、その上に修正」という順です。

この順に並べると、レビューする人はテストが落ちてから通るまでを自分の目で確かめられます。

コミットの並び（下が先）

修正のコミット          ← ここでテストが通る
   ↑
失敗するテストのコミット  ← ここでテストが落ちる
   ↑
trunk

原則は、ほかにも次の3つの並べ方を挙げています。

  • 構成を組み替えるコミットの前に、不要なコードを消すコミットを置きます。たとえば、使われていない関数を消してから、残ったファイルの構成を組み替えます。
  • 改善のコミットの前に、改善前の計測値を記録するコミットを置きます。たとえば、処理を速くする変更の前に、今の処理時間を記録します。
  • 機能を作るコミットの前に、その機能を載せる土台だけを作るコミットを置きます。たとえば、新しい画面の中身を作る前に、空の画面とそこへの経路だけを追加します。

エージェントは、どのコミットも単独で取り込める形にし、コミットの並び全体が、変更が正しいことを順に示す説明として読めるようにします。

発火条件

複数の段階がある作業（一括の修正、移行、似た編集の連続）をするときと、コミットやPRを並べる順番を決めるときです。

『Test Behavior, Not Implementation』は、実装ではなく振る舞いをテストする

原則『Test Behavior, Not Implementation』は、テストとは、コードを、そのコードを使う側と同じ方法で呼び、使う側が観察できる結果を、テストに直接書いた期待値と比べるものだ、と定めます。

!

  • 振る舞い（Behavior）・・・ コードを使う側から見える動きや結果（関数が返す値や、保存されたデータなど）
  • 実装（Implementation）・・・ コードの中でどの関数をどう呼んでいるかといった内部の作り
  • テストに直接書いた期待値（原文では literal expected value）・・・ コードで計算せず、値そのものを書いた期待値（以下の例の "hello-world"）

たとえば、文字列をURL向けの形に変える関数 slugify のテストを2通りに書くと、次のようになります（テストランナーは Vitest を想定）。

// 文字列をURL向けの形に変える
declare function slugify(text: string): string; 

// 実装をテストする：slugify が内部で toLowerCase を呼んだかを見る
const spy = vi.spyOn(String.prototype, "toLowerCase");
slugify("Hello, World!");
expect(spy).toHaveBeenCalled();

// 振る舞いをテストする：使う側と同じく slugify を呼び、結果を直接書いた期待値と比べる
expect(slugify("Hello, World!")).toBe("hello-world");

前者は、slugify が toLowerCase を呼んでさえいれば、結果が "hello-world" でなくても通ります。後者は、結果が "hello-world" でなければ落ちます。

原則がこう定めるのは、コードがどの関数を呼んだかを確かめるテストや、コードの中の定数を書き写しただけのテストは、コードにバグがあっても落ちないからです。

こうしたテストは、使う側と同じ呼び方も、観察できる結果との比較も、どちらもしていません。そのため、CIの時間とレビューする人の注意を使うだけで、バグを何も見つけません。

また、定数を書き写しただけのテストは、誰かがその定数を意図して編集したときにも落ちるので、その編集を妨げます。

たとえば、「1ページに表示する件数」の設定値が 20 のとき、テストでも 20 と書いて、設定値が 20 であることを比べるケースを考えてみましょう。

表示件数を30件に変えたくて設定値を 30 に書き換えると、表示は30件で正しく動いているのに、テストは 20 を期待しているので落ちます。テストを通すには、テストの 20 も 30 に書き換えるしかありません。

このように、定数の値を書き写しただけのテストは、定数を正しく変えただけで落ちるので、正しい編集を妨げます。

ルール：「全部undefinedでも通るか」の一問で、何も確かめていないテストを見分ける

エージェントは、テストを残す前に、一つの問いでそのテストを判定します。「テストがimportする関数が、すべて undefined を返すだけだったとしても、このテストは通るか」という問いです。

通るなら、そのテストは振る舞いを何も観察しておらず、本物のコードが壊れていても落ちません。その場合、エージェントは、アサーションを書き直すか、テストを消します。

!

  • アサーション・・・ テストの中で、結果が期待どおりかを確かめる文（expect(slugify("Hello, World!")).toBe("hello-world"); など）
  • モック・・・ テストのために本物の代わりに置く偽の部品（vi.fn() で作った偽の関数など）

この問いで通ってしまうテストは、主に次の5つの形です。

確かめ方が弱い

アサーションがない、または toBeDefined（値が undefined でないことだけを確かめる）のように、ほぼ何でも通る確かめ方しかしていないテストです。

たとえば、先の slugify のテストで expect(slugify("Hello, World!")).toBeDefined() と書くと、このテストは、slugify が "hello-world" ではなく "xyz" を返しても通ります。

// 文字列をURL向けの形に変える
declare function slugify(text: string): string; 

// 弱い：slugify が "xyz" を返しても通る
expect(slugify("Hello, World!")).toBeDefined();

// 強い："hello-world" 以外を返せば落ちる
expect(slugify("Hello, World!")).toBe("hello-world");

呼ばれたかどうかだけを見る

モックが呼ばれたこと（toHaveBeenCalled）や、結果が空であること（toEqual([])）だけを確かめるテストです。

たとえば、名前で会員を探す関数 findUsers のテストが expect(findUsers("存在しない名前")).toEqual([]) だけなら、このテストは、findUsers が、どんな名前にも常に空の配列を返す壊れた実装でも通ります。

type User = { name: string };
declare function findUsers(name: string): User[]; // 名前で会員を探す

// 空の配列になることだけを見ている。常に [] を返す壊れた実装でも通る
expect(findUsers("存在しない名前")).toEqual([]);

期待値をテスト対象から作る

期待値を、テストしているコード自身で計算するテストです。

たとえば、合計金額を計算する関数 calcTotal に、数量を掛け忘れるバグがあるケースを見てみましょう。100円の商品を2個買うと、本当は 200 を返すべきところで、100 を返してしまいます。

前のテストは、期待値の側も同じ calcTotal で計算しているので、calcTotal がどんな間違った値を返しても、左と右が必ず同じ値になり、通ってしまいます。

type Item = { price: number; quantity: number };
// 合計金額を計算する（数量を掛け忘れるバグがある）
declare function calcTotal(items: Item[]): number; 

const items = [{ price: 100, quantity: 2 }];

// 前：期待値も calcTotal で計算している。左も右も 100 になるので通ってしまう
expect(calcTotal(items)).toBe(calcTotal(items));

// 後：期待値をテストに直接書く。100 は 200 と違うので落ちる
expect(calcTotal(items)).toBe(200);

定数を書き写しただけ

コードの中の定数や設定値、プロンプトの文字列を、テストでもう一度書いて比べるだけのテストです。

たとえば、エージェントが一度に使える道具の数の上限を、コードの中で 8 と決めているケースだと、コードの中で LIMITS.maxTools に書いた 8 を、テストでもう一度書いているだけです。

// コード：道具の数の上限を 8 と決めている
const LIMITS = { maxTools: 8 };

// テスト：コードに書いた 8 を、テストでもう一度書いているだけ
expect(LIMITS.maxTools).toBe(8);

テストが用意したデータを見るだけ

テストの準備で自分で作ったデータを読んで確かめるだけで、テスト対象のコードを一度も呼ばないテストです。

it("keeps the user name", () => {
  const user = { name: "taro" }; // テストが自分で作ったデータ
  expect(user.name).toBe("taro"); // テスト対象のコードを一度も呼んでいない
});

書き直し方

対象のコードを具体的な入力で呼び、直接書いた期待値と比べる

テストを書き直すとき、エージェントは、テストの中で対象のコードを具体的な入力1つで呼び、出てきた値か観察できる変化（データが保存されたなど）を、直接書いた期待値と比べます。

たとえば、先の slugify なら、expect(slugify("Hello, World!")).toBe("hello-world") のように書きます。

起きないことを確かめるときは、別の入力で起きることも確かめる

何かが起きないことを確かめたいときは、エージェントは、同じテストの中で、別の入力では起きることも確かめます。

たとえば、先の findUsers なら、次のように、見つかる名前での結果も同じテストで比べます。

type User = { name: string };
declare function findUsers(name: string): User[]; // 名前で会員を探す

expect(findUsers("存在しない名前")).toEqual([]);
expect(findUsers("taro")).toEqual([{ name: "taro" }]);

常に空の配列を返す壊れた実装では、2つ目のアサーションで落ちます。

定数は、値を書き写さず、その定数を読み込んで動く処理を確かめる

定数の場合は、エージェントは、値を言い直す代わりに、その定数を読み込んで動く処理を、入力1つで確かめます。

たとえば、先の「1ページに表示する件数」なら、次のように書き直します。

// 1ページに表示する件数の設定値（今は 20）
declare const PAGE_SIZE: number; 
// 配列をページごとに分ける。pageSize を省くと PAGE_SIZE を使う
declare function paginate<T>(items: T[], pageSize?: number): T[][];

// 前：設定値を書き写しただけ。設定値を 30 に変えると落ちる
expect(PAGE_SIZE).toBe(20);

// 後：ページに分ける処理を、入力1つで確かめる
expect(paginate(["a", "b", "c"], 2)).toEqual([["a", "b"], ["c"]]);

後のテストは、ページに分ける処理が壊れれば落ちますが、設定値を 30 に書き換えても落ちません。

確かめ方が見つからないテストは消す

こうした確かめ方が見つからないなら、エージェントはテストを消します。

モックは、呼ばれたことではなく、受け取った中身を確かめる

モックを使うこと自体は問題ありません。ただし、エージェントは、テストで、モックが呼ばれたことではなく、モックが受け取った中身か、呼び出した後の状態を確かめます。

たとえば、メールを送る部品をモックにしたなら、エージェントは、「送信が呼ばれた」ではなく、「正しい宛先と本文が渡された」ことを確かめます。呼ばれたことだけを確かめるテストは、渡した中身が間違っていても通ってしまうからです。

type Mailer = { send: (mail: { to: string; body: string }) => void };
// 会員を登録し、登録のお礼のメールを mailer で送る
declare function registerUser(mailer: Mailer, user: { email: string }): Promise<void>;

// 前：送信が呼ばれたことだけを見る。宛先や本文が間違っていても通る
it("sends a welcome mail", async () => {
  const mailer = { send: vi.fn() };
  await registerUser(mailer, { email: "taro@example.com" });
  expect(mailer.send).toHaveBeenCalled();
});

// 後：モックが受け取った宛先と本文を、直接書いた期待値と比べる
it("sends a welcome mail", async () => {
  const mailer = { send: vi.fn() };
  await registerUser(mailer, { email: "taro@example.com" });
  expect(mailer.send).toHaveBeenCalledWith({
    to: "taro@example.com",
    body: "ご登録ありがとうございます",
  });
});

このテストコードでは、registerUser が宛先を空のまま送ってしまうバグがあっても、前のテストは通ります。後のテストは、宛先が taro@example.com ではないので落ちます。

発火条件

テストを書くとき、変えるとき、残すかどうかを決めるときです。

例：再試行のテストを振る舞いで書く

『呼ばれたかどうかだけを見る』テストと、その書き直し方を、重複行の依頼で見てみましょう。重複行の依頼は、冒頭で示した次の依頼です。

/poteto-mode the export writes duplicate rows when a retry lands mid-run. repro first, then fix and verify.
// 再試行が実行の途中に入ると、エクスポートが重複した行を書き出す。まず再現して、それから直して、確かめて。

この依頼を受けたエージェントが、再試行のテストを書くケースです。

次のテストは、exportWithRetry が db.query を呼びさえすれば、行を正しく書かなくても通ります。

type Db = { query: (...args: unknown[]) => unknown };
type InMemoryDb = Db & { rows: (table: string) => { source_row_id: string }[] };

// 元の行 input をエクスポートし、途中で失敗したら再試行する
declare function exportWithRetry(
  db: Db,
  input: string[],
  options?: { failAfterRows?: number },
): Promise<void>;
 // テスト用に、メモリ上で動くDBを作る
declare function createInMemoryDb(): InMemoryDb;
// 元の行（a、b、c の3行）
declare const input: string[]; 

// 悪いテスト。モックが呼ばれたことしか見ていない
it("writes rows on retry", async () => {
  const db = { query: vi.fn() };
  await exportWithRetry(db, input);
  expect(db.query).toHaveBeenCalled();
});

次のテストは、使う側が観察できる結果、つまり実際に書き出された行を、テストに直接書いた期待値 ["a", "b", "c"] と比べます。

// 振る舞いを確かめるテスト
it("writes each source row once when a retry lands mid-run", async () => {
  const db = createInMemoryDb();
  await exportWithRetry(db, input, { failAfterRows: 2 });
  expect(db.rows("export_rows").map((r) => r.source_row_id)).toEqual(["a", "b", "c"]);
});

failAfterRows: 2 は、2行を書いた後で1回失敗させ、実行の途中に再試行を入らせる指定です。

再試行が1行目から書き直す実装では、書き出される行は次のように変わります。

最初に書いた a、b の後ろに、再試行で1行目から書き直した a、b、c が続くので、実際の行は ["a", "b", "a", "b", "c"] になります。この行は、期待値の ["a", "b", "c"] と合わないので、このテストは落ちます。

このように、テストが不具合を捕まえられるかは何を比べるかで決まるので、観察できる結果を、直接書いた期待値と比べる必要があります。

『Explain the Number』は、測った数値が何を測ったものかを説明できるまで、その数値を信じない

『Explain the Number』は、測った数値が、報告で主張している内容を本当に表しているかを確かめる原則です。

性能を測ると、「エクスポートが30%速くなった」のような数値が出ます。この原則は、こうした数値を、「このシステムは、これだけ速い（遅い）」という主張として扱います。主張である以上、信じる前に、「本当にそう言えるかを確かめる必要がある」というのが、この原則の考え方です。原文は、冒頭で次のように書いています。

A measured number is a claim about a system. Before you trust it, report it, or act on it, find what limits it and rule out that it measured something else.

測った数値は、システムについての主張である。その数値を信じたり、報告したり、その数値をもとに作業したりする前に、何がその数値を頭打ちにしているかを突き止め、その数値が別のものを測った可能性を消せ。

「システムについての主張」とは、先ほどの「このシステムは、これだけ速い（遅い）」という主張のことです。

pstackは、この原則が必要な理由として、うまくいかなかった実行も、それらしい数値を出力することを挙げています。「うまくいかなかった実行」はたとえば、以下のようなものです。

  • リクエストが失敗していた
  • キャッシュが効いて、本来の処理をスキップしていた
  • 測りたかったコードが、一度も実行されていなかった
  • 比べる2つ（例：変更前と変更後）のうち、片方だけが、本番と同じように調整されず、既定の設定のまま動いていた
  • 実行するたびに、結果が大きくばらついていた

こうした実行も、問題がなさそうな数値を出します。そのため、数値だけを見ても、実行がうまくいかなかったことには気づけません。

そのうえで、原文は次のように続けています。

If you cannot say why the number is not twice as good, you do not know what you measured.

その数値がなぜ2倍にならないのかを説明できないなら、自分が何を測ったのかを分かっていない。

「なぜ2倍にならないのか」とは、「何が、これ以上の改善を止めているのか」という問いです。たとえば、30%速くなったなら、なぜその2倍の60%ではなく、30%で止まったのかを問います。その理由を説明できないなら、測った数値が何を表しているのかも、分かっていないことになります。

ルール：頭打ちの原因を挙げ、ほかに測っていたかもしれないものを証拠で消す

原文のルールは、次の3つです。

「なぜ2倍にならないのか」を問う

エージェントは、数値を頭打ちにしている原因の名前を挙げます。原因になるのは、CPUのコアのような資源か、コードの経路（1つの処理が通る、関数の呼び出しの流れ。例：リクエストを受け取る → JSONを解析する → データベースに書き込む）です。原文は、この頭打ちの原因を limiter と呼びます。

limiter の例として、原文は次の5つを挙げています。

!

  • CPUのコア・・・ CPUの中で、実際に計算をする部分。1つのコアは、一度に1つの処理しか実行できない。たとえば、処理が1つのコアだけで動いていると、ほかのコアが空いていても、そのコアの速さが上限になる
  • ロック・・・ 複数の処理が同じデータを同時に書き換えないように、一度に1つの処理だけに使わせる仕組み。ロックを待つ処理が多いと、処理は順番待ちになる
  • ディスク・・・ データを保存する装置。1秒あたりに読み書きできる量に上限がある
  • ネットワーク・・・ 別のコンピューターとデータをやり取りする経路。1秒あたりに送れる量（帯域）に上限がある
  • 負荷をかける側のツール・・・ 大量のリクエストを送る、性能測定のためのツール。このツールのほうが先に限界に達すると、測りたいシステムではなく、このツールの性能を測ることになる

limiter を突き止めるときは、実際に動かして記録した、次の2つのデータを使います。

  • プロファイル・・・ 処理を実行している間に、どの関数にどれだけ時間がかかったかを記録したもの
  • システムのカウンター・・・ OSが数えている数値（例：CPUの使用率、ディスクの読み書きの量、ネットワークで送った量）

エージェントは、こうしたデータから時間のかかっている箇所を見つけ、その箇所がソースコードのどこにあたるかまでたどります。コードを読んで「ここが遅そうだ」と推測しただけのものは、limiter として認めません。推測では、その箇所が実際に頭打ちを起こしているかが分からないからです。

ほかに測っていたかもしれないものを並べ、1つずつ証拠で消す

エージェントは、その数値が、測りたかった処理（例：エクスポート）ではなく、別の何かを測っていた可能性を並べ、1つずつ証拠で消します。よくある候補は、次の5つです。

  • エラー
  • 例：リクエストが失敗し、エラーの応答がすぐに返ってきていただけ
  • スキップされた処理や、キャッシュされた処理
  • 例：2回目以降の実行は、保存済みの結果を返していただけ
  • 比べる2つのうち、片方だけが、本番と同じように調整されていない
  • 例：変更後のコードは本番と同じ設定で動かしたが、変更前のコードは既定の設定のまま動いていた
  • 実行ごとのばらつき
  • 例：たまたま速かった1回の結果を見ていた
  • 処理全体に占める割合が小さく、速くしても全体はほとんど変わらない部分
  • 例：リクエスト全体の時間の1%しか使っていない関数を、2倍速くした

証拠を、数値と一緒に残す

エージェントは、読み手が、その数値の主張を確かめられるようにするため、実行の回数、ばらつき、limiter を、メモかリンクした成果物に置きます。

性能の数値には /benchmark-checklist を使い、評価の結果にも同じ問いを当てはめる

性能の数値については、この原則は、第27章の /benchmark-checklist の手順をすべて実行するよう求めています。

評価（eval）の結果にも、同じ問いを当てはめます。評価とは、AIのモデルやエージェントに同じ課題を何度も解かせ、その出来を採点することです。課題を解かせる1回1回を、試行と呼びます。たとえば、「プロンプトを変えたら、課題の正答率が60%から75%に上がった」という数値が、評価の結果です。

ここでいう「同じ問い」とは、ここまでに見た「その数値は、別の何かを測っていないか」という問いです。評価の結果では、次の3つを問います。

  • すべての実行が、課題をこなしたか
  • 例：正答率が上がったのは、一部の試行がエラーで途中で終わり、簡単な課題だけが採点されたからではないか
  • 差は、試行やモデルをまたいでも保たれるか
  • 例：60%から75%への差は、もう一度試しても、別のモデルで試しても出るか。たまたまの1回ではないか
  • そのシナリオ（評価で解かせる課題の設定）に、意味があるか
  • 例：採点に使った課題は、ユーザーが実際に頼む作業に近いか。誰も頼まない課題で正答率が上がっても、意味は薄い

この原則を飛ばした印

次のいずれかに当てはまれば、エージェントはこの原則を飛ばしたと判定されます。

  • 数値の裏づけとなる証拠に、実行の回数、ばらつき、名前の付いた limiter のいずれかがない
  • 例：「30%速くなった」とだけ書かれていて、何回測ったのか、結果がどれだけ揺れたのか、何が頭打ちの原因なのかが書かれていない報告
  • 処理全体において、変更によって短くなった時間が、変更した部分の実行時間よりも長い
  • 例：変更前は実行に1秒しかかかっていなかった関数を速くしただけなのに、処理全体が3秒短くなった、という結果

2つ目のような結果は、本来ありえません。変更した関数を丸ごと消したとしても、処理全体で短くなる時間は、最大で「その関数の実行にかかっていた1秒」だからです。このような結果が出たら、キャッシュやエラーなど、別のものを測っていた可能性があります。

『Prove It Works』は出力が本物かを、『Explain the Number』は数値の意味を確かめる

原文は、この原則を、『Prove It Works』と次のように区別しています。

  • 『Prove It Works』は、出力が本物かを確かめる
  • 『Explain the Number』は、測った数値が、報告で主張している内容を本当に表しているかを確かめる

たとえば、エクスポートを速くしたという作業なら、『Prove It Works』は、書き出されたファイルに正しい行が入っているかを確かめます。一方、『Explain the Number』は、「30%速くなった」という数値が、本当にエクスポートの速さを測ったものかを確かめます。

発火条件

測った数値を、信じたり、報告したり、その数値をもとに作業したりする前です。測った数値の例として、原文は次の5つを挙げています。

!

  • 高速化・・・ 変更によって、処理が速くなること（例：エクスポートが30%速くなった）
  • 性能の低下・・・ 変更によって、処理が遅くなること。原文では regression
  • スループット・・・ 一定の時間に処理できる量（例：1秒あたりに処理できるリクエストの数）
  • レイテンシ・・・ 1つの処理を頼んでから、結果が返ってくるまでの時間（例：APIの応答時間）
  • 評価の結果・・・ 評価（eval）で得た、課題の正答率などの数値

重複行の依頼では、『Fix Root Causes』と『Prove It Works』が『Bug fix』Playbookの各手順で使われる

冒頭で示した重複行の依頼を、もう一度示します。

/poteto-mode the export writes duplicate rows when a retry lands mid-run. repro first, then fix and verify.
// 再試行が実行の途中に入ると、エクスポートが重複した行を書き出す。まず再現して、それから直して、確かめて。

この依頼では、第11章で見た『Bug fix』Playbookの手順の中で、主に2つの原則が当てはまると、本書では読みます。

依頼文のうち、「まず再現して」は『Fix Root Causes』に、「確かめて」は『Prove It Works』に当たります。

『Bug fix』の手順 使う原則と、判断がどう変わるか
1. 自分で再現する 『Fix Root Causes』。再試行が途中に入る条件を作り、重複が起きるまで条件を絞り込む。修正は再現してから書く
2. 二分探索で原因を絞る 『Fix Root Causes』。原因の候補を挙げ、疑う範囲を半分ずつ狭めながら、ログを追加して、候補を1つずつ確かめる
3. 修正を計画する 『Fix Root Causes』。書き出した後で重複行を消す処理は、重複が起きる原因を直していないので、症状への対処になる。書き込みを冪等にするなら、第18章の『Make Operations Idempotent』の3つの問いで書き込みの設計を確かめる
4. 同じ環境と操作で確かめる 『Prove It Works』。ユニットテストが通ったことではなく、元の再現が通ることと、実際に書き出された行を確かめる
5. 失敗する再現を先にコミットする 『Sequence Work into Verifiable Units』。テストが落ちる状態から通る状態への変化をGitの履歴に残す
返答 『Prove It Works』。根本原因と修正を書き、再現の手順が直す前は失敗し、直した後は通ることを示す出力を貼る

手順2で、エージェントが確かめる原因の候補は、たとえば次の3つです。

  • キュー（処理を待つ作業の列）が、同じ仕事を2回渡している
  • 再試行が、書き終えた行の次からではなく、すでに書いた行からやり直している
  • 書き込みが冪等でない（第18章）
  • 冪等・・・同じ操作を何度実行しても、1回だけ実行したときと同じ結果になる性質

まとめ

  • 『Prove It Works』は、「コンパイルが通った」「エージェントがそう言った」を証拠と認めず、本物の成果物（書き出されたファイルや、動いている画面）を直接見ます。
  • 『Fix Root Causes』は、不具合を再現してから原因に当たるまで「なぜ」を問い、ガードで症状を隠さずに原因を直します。
  • 『Sequence Work into Verifiable Units』は、小さな単位ごとにテストなどのチェックが通ることを確かめ、失敗する再現のコミットを修正のコミットより前に並べます。
  • 『Test Behavior, Not Implementation』は、「全部undefinedでも通るか」の一問で、バグを何も見つけられないテストを見分けます。
  • 『Explain the Number』は、測った数値を頭打ちにしている原因を挙げ、エラーやキャッシュなど、別のものを測った可能性を証拠で消してから、その数値を信じます。
  • 重複行の依頼では、『Bug fix』の再現から修正の計画までに『Fix Root Causes』が、確認と返答に『Prove It Works』が使われます。
