この章では、/tdd を扱います。

/tdd は、エージェントが、不具合を直す前に、その不具合があるうちは失敗するテストを先に書くためのSkillです。たとえば、「再試行すると、通知が2通届く」という不具合なら、エージェントは「通知は1通だけ届く」ことを確かめるテストを書きます。このテストは、直す前は失敗し、直した後に通ります。

/tdd は、第30章から続く、コードの品質を保つ3つのSkillの2つ目です。/tdd で、コードを書いたエージェントの代わりに修正を確かめるのは、修正前に失敗し、修正後に通る回帰テストです。

この章では、/tdd を、役割、使いどき、手順、依頼の書き方の4つの観点で解説します。

この章の構成

この章の構成は次のとおりです。

  • 役割：不具合を直す前に、壊れた挙動をテストで再現する
  • 使いどき：利用者がTDDを頼んだときか、手軽に書けるテストの当てがあるときだけ
  • 手順：直す前に「正しい理由で失敗する」ことを確かめる
  • 依頼の書き方：コマンドだけで足りる

役割：不具合を直す前に、壊れた挙動をテストで再現する

/tdd は、不具合を直す前に回帰テスト（直した不具合が再び起きていないかを確かめるテスト）を一つ書き、そのテストが修正前に失敗し、修正後に通ることを確かめるSkillです。

名前はTDD（テスト駆動開発）ですが、SKILL.md の題が「TDD Bug Fix」であるとおり、新機能の設計をテストから進める手引きではなく、不具合の修正だけを扱うSkillです。

/tdd は、テストを必ず先に書くことは求めません。エージェントがテストを先に書くのは、利用者が頼んだときか、手軽に書けるテストの当てがあるときだけです。

使いどき：利用者がTDDを頼んだときか、手軽に書けるテストの当てがあるときだけ

/tdd は disable-model-invocation: true の設定を持つので（第25章）、エージェントが会話の内容から /tdd を選んで動かすことはありません。

/tdd を動かすのは、名前で呼ぶ利用者と、/poteto-mode です。README は、/poteto-mode が、手順の中で必要になったときに /tdd を実行すると説明しています。

SKILL.md の説明（description）は、/tdd を使うのを次のケースだけに絞っています。

  • 利用者がTDD、失敗するテスト、回帰テストのどれかの実装を依頼したとき
  • 不具合を手元ですぐ実行できるテストで確かめられると分かっているとき

逆に言えば、以下のケースではエージェントは新しいテストを追加しません。

  • テストの経路がはっきりしないとき
  • 手間がかかるとき
  • 多くの部品を組み合わせないとテストを書けないとき
  • 頼まれていないとき

「手軽に書けるテストの当てがある」というのは、たとえば、不具合のあるコードにすでに単体テストがあり、そこへテストを1つ追加すれば済む場合などです。

大がかりな準備が要るなら、テストを追加せず、最も近い確認手段に切り替える

前述した「手間がかかるとき」と「多くの部品を組み合わせないとテストを書けないとき」は、具体的には、テストを書くのに次のようなものが必要になるときです。

  • 広い範囲にわたって新しく用意する、テストを動かすための仕組み（ハーネス）
  • 実装が少し変わるだけで合わなくなる、壊れやすいモック
  • 実行に時間のかかるE2Eテスト（アプリ全体を、ユーザーの操作どおりに通して確かめるテスト）の基盤
  • 本番にしかない状態（例：本番のデータベースにだけあるデータ）
  • あいまいな再現の手順
  • 不具合と関係のない、テスト用データ（フィクスチャ）の大がかりな変更

こうしたものが必要なときは、エージェントは新しいテストを追加せず、最も近い確認手段（スクリプトや手動の再現コマンドなど）に切り替えます。

このような場合に、エージェントがテストを追加しないのは、こうした準備をして無理に書いたテストは、直ったことの証拠として弱いからです。

たとえば、壊れやすいモックを使って通したテストは、本物の部品の代わりにモックを確かめているだけなので、本物のコマンドを実行して確かめるより、直ったことを示す力が弱くなります（同梱ガイドの docs/guide/10-recipes-and-pitfalls.md）。

『Bug fix』Playbookは、手軽なテストの当てがあるときだけ /tdd を参照する

/poteto-mode も /tdd を使います。不具合修正の進め方を定めた『Bug fix』Playbookは、手順5で、不具合を再現するコミット（修正前のコードでは失敗するテストなど）を、Gitの履歴の上で、修正のコミットより前に置くよう求めています。そのうえで、手軽なテストの当てがあるときに、/tdd を参照しています。

ただし、このPlaybookも、テストに手間がかかるとき、多くの部品を組み合わせないとテストを書けないとき、テストの書き方がはっきりしないときは、/tdd を飛ばすよう定めています。

手順：直す前に「正しい理由で失敗する」ことを確かめる

6段の手順で、修正前の失敗から修正後の成功までを確かめる

/tddの手順は6段です。

  1. 不具合を理解する・・・ エージェントは、意図した挙動、現在の挙動、不具合を起こす最小の再現（最も短い操作や入力）を特定します。
  2. 最も狭い範囲で確かめられるテストを選ぶ・・・ エージェントは、不具合のあるコードにすでに使われているテストの中から、不具合の箇所を最も狭い範囲で確かめられるテストを選びます。手軽に使えるテストが見つからなければ、この手順をこなすためだけに、新しくテストを一から作ることはしません。
  3. 失敗するテストを先に書く・・・ エージェントは、この不具合を見つけられる最小のテストを1つ追加します。テストの期待値には、本来あるべき挙動を書きます。たとえば、通知が2通届く不具合なら、今のコードが2通送るからといって、期待値を2にはせず、1にします。
  4. 修正前にテストを実行する・・・ エージェントは、テストが、意図した理由（不具合そのもの）で失敗することを確かめます。
  5. 不具合を直す・・・ エージェントは、テストではないアプリ本体のコードに、意図した挙動を満たす最小の変更を入れます。そのとき、周りのコードが前提にしている約束（関数の引数や戻り値の形など）は崩しません。
  6. 回帰テストを再実行する・・・ エージェントは、テストが通ることを確かめます。

手軽なテストが見つからないときと、修正前のテストが意図した理由で失敗しなかったときの分かれ道を図にすると、次のようになります。

修正前の実行で、不具合のせいで失敗しているかを見分ける

手順4で修正前にテストを実行するのは、テストが不具合のせいで失敗しているのか、別の理由で失敗しているのかを見分けるためです。

別の理由（関数名の書き間違いなど）で失敗しているテストは、不具合があってもなくても失敗します。そのため、この失敗は、そのテストが不具合を見つけられることの証拠になりません。

また、修正前に通ってしまうテストも、不具合を検出できていないので、エージェントはテストのほうを直します。

例）通知が2通届く不具合で、正しい理由の失敗と別の理由の失敗を比べる

たとえば、「再試行すると、通知が2通届く」という不具合を直すケースで、手順4の修正前の実行を見てみましょう。

テストは、「再試行しても、通知は1通だけ届く」という意図した挙動を確かめます。

declare function test(name: string, fn: () => void): void;
declare function expect<T>(actual: T): { toBe(expected: T): void };
// 確かめたい関数：通知を送り、失敗したら再試行する。送った通知の一覧を返す
declare function sendWithRetry(message: string): string[];

// 正しい理由で失敗するテスト：修正前は「1のはずが2だった」で失敗する
test("再試行しても、通知は1通だけ届く", () => {
  const sent = sendWithRetry("注文を受け付けました");
  expect(sent.length).toBe(1);
});

// 別の理由で失敗するテスト：関数名を書き間違えているので、不具合と関係なく失敗する
test("再試行しても、通知は1通だけ届く", () => {
  const sent = sendAndRetry("注文を受け付けました");
  expect(sent.length).toBe(1);
});

このように、修正前のテストが不具合とは別の理由で失敗しているなら、エージェントは、実装を直す前に、テストのほうを直す必要があります。

テストが書けないときも、実行できる確認に置き換える

テストを書くのが現実的でないときは、エージェントは、テストを、スクリプト、手動の再現コマンド、ブラウザ自動化、ログに期待した行が出たかの確認などの、実行できる確認に置き換えます。

エージェントは、テストを書かない場合も、確認そのものは省きません。確認を省くと、直ったことを示す証拠が何も残らないからです。

最後の報告には、結果だけでなく修正前後の証拠を書く

エージェントは、最後の報告に、修正前にどのテスト（または確認）がどう失敗したかと、修正後に通った実行を書きます。修正前の失敗を示せなかったなら、その理由と、代わりに使った確認を書きます。

エージェントは、結果だけでなく、その証拠を報告します。「直りました」という結果だけでは、報告を読む人が、本当に直ったのかを確かめられないからです。

悪いテストを追加するくらいなら、新しいテストは追加しない

/tdd は、悪いテストを追加するくらいなら、新しいテストは追加しないという立場を取ります。

悪いテストとは、モックばかりを確かめるテストや、今の実装の細部を固定するテストなどです（第19章の原則『Test Behavior, Not Implementation』）。モックばかりを確かめるテストは本物の挙動を確かめておらず、実装の細部を固定するテストは、挙動を変えない書き換えでも壊れます。

2種類の悪いテストと良いテストを、通知が2通届く不具合の例で比べると、次のようになります。

declare function test(name: string, fn: () => void): void;
declare function expect<T>(actual: T): { toBe(expected: T): void };
type Transport = { send(message: string): void };
// 確かめたい関数：通知を送り、失敗したら再試行する。送った通知の一覧を返す
declare function sendWithRetry(message: string, transport?: Transport): string[];
// 送信の部品の偽物（モック）。send が呼ばれた回数を数える
declare const mockTransport: Transport & { calls: number };
// 関数の内部で使っている、再試行の回数を数える変数
declare const retryState: { attempts: number };

// 悪いテスト1（モックばかりを確かめる）：偽物の send が呼ばれた回数しか見ておらず、
// 実際に届いた通知の数を確かめていない
test("送信の部品を1回呼ぶ", () => {
  sendWithRetry("注文を受け付けました", mockTransport);
  expect(mockTransport.calls).toBe(1);
});

// 悪いテスト2（実装の細部を固定する）：内部の変数の値に頼るので、
// 届く通知の数を変えない書き換え（例：変数名の変更など）でも壊れる
test("再試行の回数が1回になる", () => {
  sendWithRetry("注文を受け付けました");
  expect(retryState.attempts).toBe(1);
});

// 良いテスト：外から見える挙動（届いた通知の数）を確かめる
test("再試行しても、通知は1通だけ届く", () => {
  const sent = sendWithRetry("注文を受け付けました");
  expect(sent.length).toBe(1);
});

エージェントは、テストを意図した挙動に合わせます。間違った実装に合わせてテストを変えることはしません。また、期待する挙動そのものが本当に変わり、その理由がはっきりしている場合を除き、既存のアサーション（expect(sent.length).toBe(1) のような、結果が期待どおりかを判定する記述）を弱めません。

declare const sent: string[];
declare function expect<T>(actual: T): {
  toBe(expected: T): void;
  toBeGreaterThanOrEqual(expected: number): void;
};

// 前：意図した挙動（通知は1通だけ届く）を確かめる
expect(sent.length).toBe(1);

// 後（してはいけない書き換え）：2通届く間違った実装でも通るよう、アサーションを弱めた
expect(sent.length).toBeGreaterThanOrEqual(1);

依頼の書き方：コマンドだけで足りる

直したい不具合を確かめる手軽なテストが書けて、その不具合について会話ですでに話していれば、利用者の依頼はコマンドだけで足ります（docs/guide/05-build-and-clean.md）。

/tdd implement
// /tdd で実装して

手軽に書けるテストがあるときだけ /tdd を使ってほしいなら、docs/guide/10-recipes-and-pitfalls.md にある次の依頼のように、条件を付けて書きます。

/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.
// まず二重書き込みを再現して。手軽なテストの経路があれば /tdd で。それから直して、再実行して。

「if there's a cheap test path」（手軽なテストの経路があれば）という条件が付いているので、手軽なテストがなければ、エージェントは /tdd を飛ばして、最も近い確認手段を使えます。

まとめ

  • 確かめる役・・・ 修正前に失敗し、修正後に通る回帰テストが、修正を確かめます。
  • 使いどき・・・ 利用者が頼んだときか、手軽に書けるテストの当てがあるときだけ、失敗するテストを修正より先に書きます。
  • 手順・・・ 修正前にテストを実行し、不具合のせいで失敗することを確かめてから直します。

次の第32章では、コードの品質を保つ3つのSkillの3つ目として、差分のコメントを、書いた本人ではないエージェントに審査させる /no-comments を扱います。
