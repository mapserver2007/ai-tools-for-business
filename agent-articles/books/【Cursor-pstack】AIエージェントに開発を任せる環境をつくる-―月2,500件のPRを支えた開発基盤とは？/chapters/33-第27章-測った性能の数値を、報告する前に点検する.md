# 第27章 測った性能の数値を、報告する前に点検する

この章では、[`/benchmark-checklist`](https://github.com/cursor/plugins/blob/main/pstack/skills/benchmark-checklist/SKILL.md) を扱います。

`/benchmark-checklist` は、エージェントが性能を測って出した数値（例：「30%速くなった」）を、報告する前や、その数値をもとに作業する前に、7つの質問で点検するSkillです。

前の[第26章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/03ebca)の検証スキルは、アプリが正しく動くかを、実際に動かして確かめるものでした。この章の `/benchmark-checklist` が確かめるのは、動きではなく数値です。性能を測った数値が、報告で主張している内容を本当に表しているかを確かめます。

poteto氏は、pstack の `0.15.9` を告知する[ポスト](https://x.com/poteto/status/2106542593656111276)で、このSkillを、性能分析で知られる Brendan Gregg氏のベンチマークのチェックリスト（ブログ記事『[Evaluating the Evaluation: A Benchmarking Checklist](https://www.brendangregg.com/blog/2018-06-30/benchmarking-checklist.html)』）をもとにしたSkillと紹介しています。

この章では、`/benchmark-checklist` を、役割、使いどき、手順、依頼の書き方の4つの観点で解説し、あわせて、性能を扱うPlaybookとの関係を見ます。

## この章の構成

この章の構成は次のとおりです。

- 役割：測った数値が、「本当に知りたかった処理の速さを表しているか」を確かめる
- 使いどき：性能を測って数値を出したとき
- 手順：測る前に準備し、7つの質問に答えてから、結論を先に報告する
- `/benchmark-checklist` は、『Perf issue』と『Hillclimb』の数値を点検する
- 依頼の書き方：`/benchmark-checklist` の後に、点検したい数値と、その数値をどこで使うかを書く
- まとめ

## 役割：測った数値が、「本当に知りたかった処理の速さを表しているか」を確かめる

`/benchmark-checklist` は、**数値が出たかどうかではなく、その数値が、本当に知りたかった処理の速さを表しているかどうか**を確かめます。

[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)の原則『[**Explain the Number**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-explain-the-number/SKILL.md)』は、このSkillが必要な理由を、次のように書いています。

> A run that went wrong still prints a plausible number. Requests that failed, a cache that skipped the work, code that never ran, a side left on default settings, and run-to-run noise all produce results that look fine.
>
> うまくいかなかった実行も、それらしい数値を出力する。リクエストが失敗した。キャッシュが本来の処理をスキップした。コードが一度も実行されなかった。比べる2つのうち、片方が既定の設定のまま動いていた。実行するたびに結果がばらついた。これらは、どれも問題がなさそうな結果を生む。

たとえば、APIの応答時間を測って、「30%速くなった」という結果が出たとします。ところが、変更後のコードがリクエストの多くをエラーで返していたなら、速くなったのは、エラーの応答がすぐに返ってきたからかもしれません。この場合、数値が表しているのは、APIの処理の速さではなく、エラーが返ってくる速さです。数値だけを見ても、この違いは分かりません。

そのため、`/benchmark-checklist` は、**7つの質問のどれにも、コードを読んだうえでの推測ではなく、実際に動かして得た記録で答える**よう求めています。

なお、『Explain the Number』と、同じ第19章の原則『[**Prove It Works**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)』は、確かめる対象が異なります。

- 『Prove It Works』は、作業の結果（例：書き出されたファイル）が本物かを確かめる
- 『Explain the Number』は、測った数値が、報告で主張している内容を本当に表しているかを確かめる

## 使いどき：性能を測って数値を出したとき

`/benchmark-checklist` を使うのは、エージェントが性能を測って数値を出す場面で、次の4つです。

- PRの変更前と変更後で、速さを比べたとき
- 変更によって性能が落ちたと、エージェントが主張するとき
- 『Hillclimb』Playbook（1つの指標を、変更と計測の繰り返しで改善するPlaybook。[第11章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42)）で、変更の効果を、毎回同じ条件で測るための仕組み（測定ハーネス）を作ったとき
- ライブラリや設定の選択肢のうち、どれを採用するかを、測った結果で決めるとき
  - 例：JSONを解析するライブラリAとBのどちらを使うか
  - 例：データベースへの同時接続の数を、10にするか50にするか

`/benchmark-checklist` は `disable-model-invocation: true` の設定を持つので（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）、エージェントが会話の内容から自分でこのSkillを選ぶことはありません。このSkillを動かすのは、次の3つです。

- **利用者**・・・ `/benchmark-checklist` と名前で呼びます。
- **`/poteto-mode`（[第38章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f8911)）**・・・ 次のときに、このSkillを使うよう定めています。使うのは、数値を報告する前や、数値をもとに作業する前です。
  - ベンチマーク（性能を測るためのプログラムや手順）を実行するとき
  - 自分で性能を測るとき
  - 自分で測った結果をもとに、性能について報告するとき（「速くなった」「遅くなった」など）
- **『Perf issue』と『Hillclimb』（[第11章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42)）**・・・ 遅さを測って直す『Perf issue』と、1つの指標をループで改善する『Hillclimb』は、手順の中でこのSkillを使います。詳しくは、この章の[『/benchmark-checklist は、『Perf issue』と『Hillclimb』の数値を点検する』](#%2Fbenchmark-checklist-%E3%81%AF%E3%80%81%E3%80%8Eperf-issue%E3%80%8F%E3%81%A8%E3%80%8Ehillclimb%E3%80%8F%E3%81%AE%E6%95%B0%E5%80%A4%E3%82%92%E7%82%B9%E6%A4%9C%E3%81%99%E3%82%8B)で見ます。

### 頼まれたのが大まかな見積もりなら、実行は1回でよい

利用者が大まかな見積もりを手早く出すよう頼んだときは、実行は1回のみ行います。ただし、この場合もエージェントは、[手順2](#2.-7%E3%81%A4%E3%81%AE%E8%B3%AA%E5%95%8F%E3%81%AB%E3%80%81%E5%AE%9F%E9%9A%9B%E3%81%AB%E5%8B%95%E3%81%8B%E3%81%97%E3%81%A6%E5%BE%97%E3%81%9F%E8%A8%98%E9%8C%B2%E3%81%A7%E7%AD%94%E3%81%88%E3%82%8B)で答える7つの質問のうち、**次の2つは必ず確かめ**、1回の実行の結果であることを報告に書きます。

- エラーが出ていないか
- 作業は本当に行われたか

残りの5つの質問は、その実行の結果に不審な点があるときだけ確かめます。

一方で、**ライブラリや設定の選択肢から1つを選ぶための計測（例：ライブラリAとBのどちらを使うかを決めるための計測）は、大まかな見積もりとして扱いません**。選んだものが、そのまま採用されるからです。

## 手順：測る前に準備し、7つの質問に答えてから、結論を先に報告する

手順は次のとおりです。

1. 測る前に、「報告したい結論」を書き出し、計測のスクリプト（性能を測るために実行するプログラム）とマシン（計測に使うコンピューター）を確かめる
2. 7つの質問に、実際に動かして得た記録で答える
3. 結論を先に報告する

ここからは、各手順を1つずつ見ていきます。

### 1. 測る前に、「報告したい結論」を書き出し、計測のスクリプトとマシンを確かめる

エージェントは、何かを実行する前に、次の3つをします。

- **「報告したい結論」を、報告で使う言葉のまま書き出す**・・・ 「報告したい結論」とは、測り終えたときに、報告に書くつもりの1文です。たとえば、次のような1文です。**この後の7つの質問は、この1文が正しいかを試すためのもの**です。

  > export is 30% faster at p50 on the 60k-row dataset
  >
  > 6万行のデータセットで、エクスポートが p50（測った値を小さい順に並べたときの真ん中の値）で30%速い
- **計測のスクリプトを読む**・・・ 計測のスクリプトが、何の時間を測り、何を数え、何を無視しているかを書き留めます。
- **計測に使うマシンの負荷を確かめる**・・・ 計測に使うマシンで、ほかの処理が多く動いている（負荷が高い）と、測った数値がその影響を受けます。そこで、`uptime` でマシンの負荷の平均（load average）を、`nproc` でCPUのコア数を確かめます。負荷が高ければ、何が動いているかを調べます。その処理を止められないときは、比較対象（変更前と変更後のように、比べる2つのもの）を交互に実行して、どちらも同じ影響の中で測られるようにし、そのことを報告に書きます。

!

- **`uptime`**・・・ マシンがどれくらい混んでいるか（負荷の平均）を表示するコマンド
- **負荷の平均（load average）**・・・ マシンで、同時に動こうとしている処理の数の平均。この数が、CPUのコア（CPUの中で、実際に計算をする部分。1つのコアは、一度に1つの処理しか実行できない）の数より大きければ、処理が順番待ちになっている。たとえば、コアが4つのマシンで負荷の平均が8なら、いつも4つの処理が順番を待っている
- **`nproc`**・・・ マシンのCPUのコアの数を表示するコマンド

### 2. 7つの質問に、実際に動かして得た記録で答える

エージェントは、次の7つの質問に答えます。答えには、プロファイラ（処理の実行中に、どの関数にどれだけ時間がかかったかを記録する道具）の記録やエラーの数のような、実際に動かして得た記録を使います。

| # | 質問 | 確かめること |
| --- | --- | --- |
| 1 | Why not double?（なぜ2倍にならないのか） | 結果を頭打ちにしている原因を挙げられるか |
| 2 | Was it tuned?（調整したか） | 比較対象を、どれも本番と同じように動かしたか |
| 3 | Did it break limits?（限界を超えていないか） | 結果が、ディスク、ネットワーク、CPUの限界の範囲に収まっているか |
| 4 | Did it error?（エラーが出ていないか） | 失敗を数えたか。出力が正しいか |
| 5 | Does it reproduce?（再現するか） | 何度測っても、同じ差が出るか（例：5回測って、5回とも変更後のほうが速いか） |
| 6 | Does it matter?（意味のある差か） | ユーザーが待つ時間全体で見ても、意味のある差か（例：関数が2倍速くなっても、ユーザーが画面で待つ時間がほとんど変わらないなら、意味は小さい） |
| 7 | Did it even happen?（作業は本当に行われたか） | 時間を測っている間に、測りたかった処理が実際に行われたか（例：エクスポートなら、ファイルが本当に書き出されたか） |

!

- **CPU**・・・ コンピューターの中で、計算をする装置
- **CPUのコア**・・・ CPUの中で、実際に計算をする部分。1つのコアは、一度に1つの処理しか実行できない。コアが4つあれば、同時に4つの処理を実行できる
- **ディスク**・・・ データを保存する装置。1秒あたりに読み書きできるデータの量に上限がある
- **ネットワーク**・・・ 別のコンピューターとデータをやり取りする経路。1秒あたりに送れるデータの量に上限がある

ここからは、手順1の結論「6万行のデータセットで、エクスポートが p50 で30%速い」を例に、各質問を1つずつ見ていきます。

#### 質問1 なぜ2倍にならないのか：結果を頭打ちにしている原因を突き止める

「なぜ2倍にならないのか」は、「何が、これ以上の改善を止めているのか」を問う質問です。

エージェントは、結果を頭打ちにしている原因を挙げます。このような原因を **limiter** と呼びます。limiter の例（CPUのコア、ロック、ディスクなど）は、[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)の原則『Explain the Number』の節で説明しています。

limiter を探すときは、次の道具を使います。

- **プロセスごとのCPU使用率**（`top`、`pidstat`）
- **実行環境ごとのプロファイラ**（`node --cpu-prof`、`py-spy`、`perf`）
- **I/O待ち**
- **システムコールの回数**（Linux の `strace -c`）

!

- **プロセス**・・・ 実行中のプログラム。1つのアプリが、複数のプロセスで動くこともある
- **I/O待ち**・・・ CPUが、ディスク（データを保存する装置）やネットワーク（別のコンピューターとデータをやり取りする経路）の読み書きが終わるのを待っている時間
- **システムコール**・・・ プログラムが、ファイルの読み書きなどをOSに頼むときの呼び出し

ただし、プロファイラのような記録の道具は、処理そのものを遅くします。そのため、**limiter を探すための実行は、報告に使う実行とは別扱いにします**。

エージェントは、見つけた時間のかかる箇所が、ソースコードのどこにあたるかまで突き止めます。

負荷をかける側のツール（大量のリクエストを送る、性能測定のためのツール）も見ます。このツールが先に限界に達していれば、測ったのは、測りたかったシステムではなく、そのツールの性能になるからです。

変更しても数値が動かなかったときも、limiter がその理由を説明します。そのため、エージェントは、limiter を見つける前に、**その変更を「役に立たないもの」と決めつけません**。

エクスポートの例なら、エージェントは、「1コアでの JSON の解析が頭打ちになっている」のように、30%で止まっている理由を、プロファイラの記録から挙げます。

#### 質問2 調整したか：比較対象を、どれも本番と同じように動かす

エージェントは、比較対象を、どれも本番と同じように動かします。たとえば、次の6つを本番とそろえます。

- ビルドの種類（本番と同じリリースビルドを使う）
- フラグと環境変数
- バッチとトランザクションの設定
- コネクションプール
- キャッシュの状態（本番と同じく、warm cache（データがすでにたまっているキャッシュ）で測るか、cold cache（データがまだ入っていない、空のキャッシュ）で測るか）
- 使うソフトウェアのバージョンと、使うデータ

!

- **リリースビルド**・・・ 本番で動かすために作ったプログラム。開発中に使うデバッグ用のビルドより、速く動くように作られている
- **フラグ**・・・ 機能のオンとオフなどを切り替える設定
- **環境変数**・・・ プログラムの外から渡す設定の値（例：接続するデータベースの場所）
- **バッチ**・・・ 複数の処理をまとめて実行する単位。たとえば、1行ずつ書き込むか、1000行ずつまとめて書き込むか
- **トランザクション**・・・ 複数のデータベースの操作を、1つのまとまりとして確定する仕組み。どの単位で確定するかで、速さが大きく変わる
- **コネクションプール**・・・ データベースへの接続を作っておき、使い回す仕組み。接続の数の上限が、速さに影響する

比較対象の片方だけが、本番とは異なる設定で動いていたなら、**比べたのは実装の違いではなく、設定の違い**です。

limiter が設定だった場合は、その設定で動いていた比較対象が、調整されていないということです。たとえば、次のようなものが limiter なら、その比較対象は調整されていません。

- 1行書き込むたびに、データベースへの変更を確定する（コミットする）設定
- デバッグ用のビルド
- インデックス（データベースで、検索を速くするための索引）の付け忘れ

エージェントは、調整されていなかった比較対象を調整し、測り直してから、どちらが優れているかを決めます。**調整できないなら、その実行からは、どちらが優れているかを決めません**。

たとえば、データベースに6万行を書き込む処理で、ライブラリAとBを比べたとします。

- **調整できる場合**・・・ 測ると、Bのほうが3倍遅かったとします。limiter を調べると、Bは1行書き込むたびにコミットしていました。これは、Bそのものの遅さではなく、Bの設定が原因です。エージェントは、Bを1000行ごとにまとめてコミットする設定に変えて測り直し、そのうえで、AとBのどちらが速いかを決めます。
- **調整できない場合**・・・ Bに、まとめてコミットする設定がそもそも見つからないなどで、Bを調整できないとします。このときエージェントは、この実行の結果だけで「Aのほうが速い」とは決めません。報告の結論は「結論が出ない」とし、Bを調整できなかったことを書きます。

このとき、「今の設定のままなら、Aのほうが速い」と、主張の範囲を狭めて報告しても、問題は解決しません。

利用者が知りたいのは、AとBのどちらを採用するかです。利用者がBを採用すれば、Bの設定は、利用者が自由に調整できます。上の例なら、利用者は、Bを1000行ごとにコミットする設定にして使えます。そのため、調整していない今の設定でAとBを比べた結果は、どちらを採用するかを決める材料になりません。

エクスポートの例なら、変更前のコードだけがデバッグ用のビルドで動いていた場合、30%の差は、変更の効果ではなく、ビルドの違いかもしれません。

#### 質問3 限界を超えていないか：計算して確かめる

エージェントは、結果が、マシンの限界を超えていないかを、次の3つの式で確かめます。**どれかの式が成り立たない結果は、ありえない結果**です。

!

- **スループット**・・・ 1秒あたりに処理した量。読み書きなら、1秒あたりに読み書きしたデータの量（バイト数）。操作なら、1秒あたりにこなした操作の回数
- **帯域**・・・ ディスクやネットワークが、1秒あたりに読み書きできるデータの量の上限
- **CPU時間**・・・ CPUのコアが、実際にその処理の計算に使った時間

**① 読み書きしたデータの量が、ディスクやネットワークの上限を超えていないか**

```
読み書きのスループット（バイト/秒） ≦ ディスクやネットワークの帯域（バイト/秒）
```

1秒あたりに読み書きしたデータの量は、ディスクやネットワークが1秒あたりに運べる量を超えられません。たとえば、帯域が 100 MB/秒 のディスクから、1秒で 500 MB を読んだという結果は、ありえません。

**② 使ったCPUの時間が、コアの数を超えていないか**

```
操作のスループット（回/秒） × 1回の操作のCPU時間（秒） ≦ 使えるCPUのコアの数
```

左辺は、1秒の間に、いくつのコアが計算し続ける必要があるかを表します。たとえば、1秒に1万回の操作をこなし、1回の操作にCPU時間を0.5ミリ秒使うなら、左辺は 10000 × 0.0005 = 5 です。つまり、5つのコアが1秒間ずっと計算し続ける必要があります。コアが4つのマシンでこの結果が出たなら、その結果はありえません。

**③ 短くなった時間が、変更した部分にかかっていた時間を超えていないか**

```
処理全体で短くなった時間 ≦ 変更した部分の、変更前の実行時間
```

変更した部分を丸ごと取り除いても、処理全体で短くなる時間は、その部分にかかっていた時間までです。たとえば、実行時間の10%を占める部分を丸ごと取り除くと、100かかっていた時間は90になります。速さは 100 ÷ 90 で、最大でも約1.11倍（約11%速い）にしかなりません。

**限界を超えた結果は、測りたかった処理以外のものを測った印**です。たとえば、次のようなものを測っていた可能性があります。

- キャッシュ
- 何もしない処理
- 不具合

エクスポートの例なら、変更した部分がエクスポート全体の時間の10%しか使っていなかったのに、全体が30%速くなったなら、その結果は限界を超えています。

#### 質問4 エラーが出ていないか：失敗を数え、出力が正しいかを確かめる

エージェントは、失敗の数と、成功以外の応答の数を数えます。**出力についても、あるかどうかだけでなく、正しいかどうかを確かめます**。

エラーを数えるのは、エラーが成功とは違う動きをするからです。拒否の応答はたいてい速く返り、タイムアウトや再試行は遅くなります。そのため、エラーが混ざると、数値は実際より速くも遅くも見えます。

計測のスクリプトがエラーを数えていなければ、エージェントは、エラーを数える処理を追加します。

エクスポートの例なら、エージェントは、書き出したファイルに6万行がそろっているか、各行の中身が正しいかを確かめます。

#### 質問5 再現するか：比較対象を交互に5回以上測る

エージェントは、それぞれの比較対象を少なくとも5回実行し、A、B、A、B のように交互に実行します。交互にするのは、次の4つが、片方の比較対象だけを有利にしないためです。

- ウォームアップ
- 遅延初期化
- キャッシュ
- ドリフト

!

- **ウォームアップ**・・・ 最初の数回の実行が、準備が整っていない（例：使うデータが、まだメモリに読み込まれていない）せいで、遅くなること。Aを先にまとめて実行すると、Aだけがこの遅さの影響を受ける
- **遅延初期化**・・・ 必要になるまで、準備を後回しにする仕組み。最初にその機能を使った実行だけが、準備の分だけ遅くなる
- **キャッシュ**・・・ 一度使ったデータを手元に取っておき、次から速く返す仕組み。先に実行した側が作ったキャッシュを、後から実行した側が使えてしまう
- **ドリフト**・・・ 時間とともにマシンの状態（例：ほかの処理の量、CPUの温度）が変わり、測る時刻によって速さが変わること。Aを午前に、Bを午後にまとめて測ると、AとBの差に、時刻による差が混ざる

報告には、中央値と範囲（最小値から最大値まで）を書きます。

**比較対象どうしの差が、同じ比較対象を何度か測ったときの揺れより小さければ、「測れるほどの差はない」とします**。たとえば、変更前の5回が 40〜46 ms、変更後の5回が 39〜45 ms で、中央値の差が 1 ms だったとします。このとき、変更をしていなくても、同じコードを測るだけで、結果は 6 ms ほど上下しています。そのため、変更後のほうが 1 ms 速かったのが、変更の効果なのか、たまたま速い回が多かっただけなのかが分かりません。

差があるかどうかの判断が際どいときは、順位和検定という統計の方法か、測定ハーネスが持つ統計の機能を使って判断します。何度も測った結果から、差がたまたまのものかを判断する機能を持つハーネスもあります。たとえば、ベンチマークのツール [hyperfine](https://github.com/sharkdp/hyperfine) は、2つのコマンドを何度も実行し、「AはBより 1.23 ± 0.05 倍速い」のように、差を誤差の幅とともに示します。

順位和検定とは

変更前と変更後の値をすべてまとめて小さい順に並べ、どちらかの値が上位（速い側）に偏っているかを見て、差があるかを判断する方法です。

たとえば、変更前の5回が 40、41、42、43、44 ms、変更後の5回が 33、34、35、36、37 ms なら、速い順の上位5つは、すべて変更後の値です。このように偏りが大きいほど、たまたまの揺れではない差だと判断できます。

エクスポートの例なら、変更前と変更後を交互に5回ずつ実行し、30%の差が、5回の結果の揺れよりはっきり大きいかを確かめます。

#### 質問6 意味のある差か：処理全体の中での割合を出す

エージェントは、関数1つのような小さな範囲を測った結果（マイクロベンチマークの結果）を出したら、あわせて、ユーザーが待つ処理全体（end-to-end）も測ります。

処理全体は、本番に近い条件で測ります。

- **データの量**・・・ 例：テスト用の10行ではなく、本番と同じ6万行
- **同時実行の数**・・・ 例：同時に操作するユーザーが1人ではなく、本番と同じくらいの人数

そして、**小さな範囲の結果を、処理全体に占める割合として報告します**。たとえば、リクエストの時間の1%を占める補助の関数は、どれだけ速くしても、リクエスト全体を最大1%しか速くできません。

エクスポートの例なら、エクスポートの関数だけを測った結果に加えて、ユーザーがボタンを押してからファイルを受け取るまでの時間も測ります。そのうえで、30%の改善が、その時間の何%にあたるかを報告します。

#### 質問7 作業は本当に行われたか：時間を測っている間に、作業が行われたことを確かめる

エージェントは、時間を測っている間に、作業が実際に行われたことを確かめます。たとえば、次の4つです。

- リクエストがサーバーに届いたか
- 行が書き込まれたか
- データが読み込まれたか
- コードがその結果を使ったか

作業が行われたことを確かめるのは、**作業が行われていなくても、時間だけは測れてしまうコードがあるから**です。

たとえば、エクスポートの関数を変更して、行を1つずつ作るジェネレーター（値を1つずつ作り出す関数）を返すようにしたとします。ジェネレーターは、誰かが値を取り出すまで、中の処理を動かしません。計測のスクリプトが、この関数を呼ぶ時間だけを測ると、記録されるのは、ジェネレーターを返すまでのごく短い時間です。6万行を作る処理は、まだ1行も動いていません。

図にすると、次のようになります。

```
変更前：時間を測る範囲の中で、6万行を作る

  計測開始 ──[ 6万行を作る（500 ms） ]── 計測終了   → 記録：500 ms

変更後：時間を測る範囲の中では、ジェネレーターを返すだけ

  計測開始 ──[ ジェネレーターを返す（0.1 ms） ]── 計測終了   → 記録：0.1 ms
                                                      │
                                                      └→ 後で値を取り出したときに、
                                                         はじめて6万行を作る（測っていない）
```

その結果、「変更前は 500 ms かかっていたエクスポートが、変更後は 0.1 ms になった」という数値が出ます。しかし、0.1 ms は、ジェネレーターを返すまでの時間で、エクスポートの時間ではありません。測りたかったエクスポートの作業が、時間を測っている間に行われていないからです。速くなったと報告すれば、嘘の報告になります。

そのため、エージェントは、時間を測っている間に作業が行われたことを確かめます。行われていなければ、値をすべて取り出す、await する（処理が終わるのを待つ）などして、作業が時間を測る範囲の中で行われるようにしてから、測り直します。

直した後の流れを図にすると、次のようになります。

```
直した後：値をすべて取り出すまでを、時間を測る範囲に入れる

  計測開始 ──[ ジェネレーターを返す → 値をすべて取り出す（6万行を作る） ]── 計測終了
                                                                              → 記録：エクスポートの時間
```

計測のスクリプトでは、たとえば次のように直します。

```
 const start = performance.now();
-const rows = exportRows(data); // ジェネレーターを返すだけで、6万行はまだ作られていない
+const rows = Array.from(exportRows(data)); // 値をすべて取り出すので、ここで6万行が作られる
 const elapsed = performance.now() - start;
+
+// 作業が本当に行われたことを確かめる
+if (rows.length !== 60000) {
+  throw new Error(`行の数が合いません：${rows.length}`);
+}
```

Promise（後で終わる処理を表す値）を返す関数も同じです。await しなければ、処理が終わる前に、時間を測り終えてしまいます。

```
 const start = performance.now();
-exportToFile(data); // await していないので、書き出しが終わる前に次の行へ進む
+await exportToFile(data); // 書き出しが終わるのを待ってから、次の行へ進む
 const elapsed = performance.now() - start;
```

こうした「作業が行われていなくても、時間だけは測れてしまうコード」の代表例が、遅延評価のコードです。たとえば、次の3つがあります。

- 誰も値を取り出さないジェネレーター
- 誰も await しない Promise
- JITが、使われないと判断して、計算ごと捨ててしまえる結果

!

- **遅延評価**・・・ 結果が必要になるまで、計算を後回しにする仕組み
- **ジェネレーター**・・・ 値を1つずつ作り出す関数。値を取り出されたときに、はじめて次の値を作る
- **Promise と await**・・・ Promise は、後で終わる処理を表す値。await は、その処理が終わるのを待つ書き方。await しなければ、処理が終わる前に次へ進む
- **JIT**・・・ 実行中に、コードを機械語に変換する仕組み。結果が使われていない計算を、丸ごと省くことがある

タイムアウトも同じです。処理が終わる前に打ち切られても、打ち切るまでの時間は記録されます。

エクスポートの例なら、エージェントは、時間を測っている間に、ファイルが実際に書き出されたことを確かめます。

### 3. 結論を先に報告する

エージェントは、次の4つを守って報告します。

- **結論を先に書く**・・・ 結論は、次のいずれかです。

  - 速くなった
  - 遅くなった
  - 測れるほどの差はない
  - 結論が出ない
- **数値には、単位、実行の回数、範囲、limiter を添える**・・・ たとえば、次のように書きます。

  > p50 41 ms → 33 ms, median of 7 runs per side, range 32 to 35 ms after, bound by JSON parsing on one core.
  >
  > p50 が 41 ms から 33 ms に。比較対象ごとに7回実行した中央値で、変更後の範囲は 32〜35 ms。1コアでの JSON の解析が頭打ちの原因。
- **確かめられなかったことがあれば、結論を「結論が出ない」とする**・・・ 次のいずれかに当てはまるときは、結論を「結論が出ない（inconclusive）」とし、何が足りないかを書きます。

  - 差があると主張するのに、limiter を挙げられない
  - 比較対象の片方を、調整しないまま動かした
  - 「エラーが出ていないか」と「作業は本当に行われたか」の2つの質問を確かめられなかった
- **PRの本文に書く数値は1つにする**・・・ 『[**Opening a PR**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)』Playbook（PRの作り方を定めたPlaybook。[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)）に従い、**PRの本文には、主な数値を1つだけ書きます**。各実行の結果、範囲、limiter の証拠は、リンクした成果物か、メモのファイルに置きます。

## `/benchmark-checklist` は、『Perf issue』と『Hillclimb』の数値を点検する

`/benchmark-checklist` は、性能を扱う2つのPlaybook（[第11章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42)）の中で、数値を点検する役を受け持ちます。

| Playbook | Playbookがすること | `/benchmark-checklist` の役割 |
| --- | --- | --- |
| 『[**Perf issue**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/perf-issue.md)』 | 遅さの原因を見つけて直す | Playbookが修正を計画する前に、基準となる計測結果（ベースライン）を点検する。その後に出る数値も、すべて点検する |
| 『[**Hillclimb**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/hillclimb.md)』 | 1つの指標を良くするために、1つの変更と1回の計測を繰り返す | 測定ハーネス（変更の効果を、毎回同じ条件で測るための仕組み）を固定する前に、その測定ハーネスを点検する |

『Perf issue』では、直し方の候補を、[2つ目の手順](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42#%E6%89%8B%E9%A0%86%EF%BC%9A%E3%83%99%E3%83%BC%E3%82%B9%E3%83%A9%E3%82%A4%E3%83%B3%E3%81%AE%E3%83%88%E3%83%AC%E3%83%BC%E3%82%B9%E3%81%AB%E5%A7%8B%E3%81%BE%E3%82%8B6%E3%81%A4%E3%81%AE%E6%89%8B%E9%A0%86)（`/how` でコードの仕組みを調べ、仮説の根拠にする）で使う performance mantras（直し方の候補を、安いものから順に並べた7つの指針）から考えます。

『Hillclimb』では、変更と計測を何度も繰り返し、そのたびに変更を残すか戻すかを決めます。そのたびに、エラーが出ていないかと、作業が行われたかを別に調べるのは手間がかかります。

そこで、固定する測定ハーネスに、計測の結果と一緒に、エラーの数と、行った作業の数（例：書き出した行の数）も出力させます。そうすれば、変更を残すか戻すかを決めるたびに、追加の手間なしで、質問4「エラーが出ていないか」と質問7「作業は本当に行われたか」を確かめられます。

## 依頼の書き方：`/benchmark-checklist` の後に、点検したい数値と、その数値をどこで使うかを書く

同梱ガイドの[`06-verify-and-ship.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md)は、**数値を報告したり、その数値をもとに作業したりする前に**、次のように入力するよう勧めています。

```
/benchmark-checklist vet the export speedup before it goes in the pr
// PRに書く前に、エクスポートが速くなったという数値を点検して
```

同ページでは、**利用者が自分でこのSkillを実行するのは、次の2つのとき**だと説明しています。`/poteto-mode` は、『Perf issue』と『Hillclimb』の手順の中では、このSkillを自分で実行するからです。

- 『Perf issue』や『Hillclimb』を使わずに、何かを測ったとき
- ほかの人が出した数値が、信じられないほど良く見えるとき

同梱ガイドの[`10-recipes-and-pitfalls.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md)も、次の例を挙げています。

```
/benchmark-checklist vet this 40% speedup before it goes in the pr description
// PRの説明に書く前に、この40%の高速化を点検して
```

どちらの依頼でも、返ってくるのは、「速くなった」「遅くなった」「測れるほどの差はない」「結論が出ない」のいずれかの結論と、実行の回数、範囲、limiter です。

## まとめ

- **役割**・・・ 測った性能の数値が、本当に知りたかった処理の速さを表しているかを、7つの質問で点検します。答えには、コードを読んだうえでの推測ではなく、実際に動かして得た記録を使います。
- **使いどき**・・・ 次の4つのときに使います。

  - PRの変更前後で、速さを比べたとき
  - 変更によって性能が落ちたと、エージェントが主張するとき
  - 『Hillclimb』で測定ハーネスを作ったとき
  - ライブラリや設定のうち、どれを採用するかを、測った結果で決めるとき

  大まかな見積もりなら、実行は1回のみ行います。ただし、選択肢から1つを選ぶための計測は、大まかな見積もりとして扱いません。
- **手順**・・・ 測る前に、報告に書くつもりの結論（例：「エクスポートが p50 で30%速い」）を書き出します。そのうえで、7つの質問に答え、結論を先に報告します。limiter を挙げられないときなどは、結論を「結論が出ない」とします。
- **依頼の書き方**・・・ `/benchmark-checklist` の後に、点検したい数値と、その数値をどこで使うか（例：PRの説明）を書きます。

次の[第28章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)では、書き終えた変更が壊しうるものと、差分の弱点を確かめる2つのSkillを扱います。見ていくのは、[`/blast-radius`](https://github.com/cursor/plugins/blob/main/pstack/skills/blast-radius/SKILL.md)、[`/interrogate`](https://github.com/cursor/plugins/blob/main/pstack/skills/interrogate/SKILL.md)です。
