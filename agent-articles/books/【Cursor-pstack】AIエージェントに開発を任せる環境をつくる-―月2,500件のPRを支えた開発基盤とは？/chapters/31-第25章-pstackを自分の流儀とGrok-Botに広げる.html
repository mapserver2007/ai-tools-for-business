この章では、次の2つのSkillを扱います。

  1. /automate-me
  2. /make-bot-ui

2つは、どちらも、pstackを利用者の環境に合わせて広げるSkillです。それぞれの用途は次のとおりです。

  • /automate-me・・・ エージェントが、利用者のチャットの履歴から利用者の流儀（例：「段落は短く。選択肢を比べるときは表にする。」）を読み取り、その流儀を書いた、/poteto-mode のような利用者専用の mode のSkillを作ります。
  • /make-bot-ui・・・ エージェントが、利用者がボタンを押すと、pstackを入れられるAI Botアプリ Grok Bot（第5章）の処理が起動するWebページを作ります。

この章では、2つのSkillを誰が呼ぶのかを確かめたうえで、1つずつ、役割、使いどき、手順の3つの観点で解説します。原文に依頼例があるSkillには依頼例も示します。

この章の構成

この章の構成は次のとおりです。

  • 2つのSkillは、利用者が名前で呼んだときだけ動く
  • /automate-me は、チャットの履歴から利用者の仕事の進め方を読み取り、利用者専用のSkillにする
  • /make-bot-ui は、送信キーを外に出さずに、Grok Bot をボタンで起動するページを作る
  • まとめ

2つのSkillは、利用者が名前で呼んだときだけ動く

Skill 一言でいうと
/automate-me 利用者のチャットの履歴から、利用者専用の -mode Skillを作る
/make-bot-ui ボタンを押すと、webhook（URLへのHTTPリクエスト）で Grok Bot の処理を起動するページを作る

2つの SKILL.md は、どちらも、エージェントが会話の内容から自分で選んで動かすことを止める設定（disable-model-invocation: true）を持っています。また、/poteto-mode も、Playbookも、手順の中でこの2つを呼びません。そのため、2つは、利用者が名前で呼んだときだけ動きます。

/automate-me は、チャットの履歴から利用者の仕事の進め方を読み取り、利用者専用のSkillにする

役割：利用者の流儀を、履歴と質問から利用者専用のSkillにする

/automate-me は、利用者の仕事の流儀を、エージェントが従うSkillに変えるSkillです。出力は、その利用者に合わせた -mode という接尾辞を付けた1つのSkillです（例：jay-mode）。

利用者は、自分の流儀を説明する必要はありません。エージェントが、利用者が実際に何度も求めてきたことを、チャットの履歴から読み取ります。

たとえば、利用者が「返答はもっと短くしてください」と何度もエージェントに言い直していれば、エージェントは「返答は短く」を利用者の流儀として読み取ります。履歴に出てこない意図は、エージェントが利用者に質問して補います。

使いどき：利用者が、自分の好みや働き方を Skill にしたいとき

pstackの/poteto-modeや他のSkillでも、すべてのユースケースに対応することはできません。
そこで、利用者は、自分の好みや働き方に合うSkillを作りたいときに、このSkillを名前で呼びます。

「コミットメッセージの書き方」のような1つの作業の手順だけを残したいときは、利用者は、このSkillではなく、Skillのファイルを書くための Cursor 組み込みのSkill create-skill だけを使います。1つの作業の手順は、働き方全体をまとめる仕事の流儀のためのSkillではなく、普通のSkillとして書けば足りるからです。

手順：履歴を読み、利用者に聞き、下書きを磨いてからPRを開く

  1. 履歴を読む・・・ エージェントは、今のワークスペースの直近2〜4週間のトランスクリプト（チャットの記録）を、たとえば3つの期間に区切り、並列のサブエージェントに読ませます。読むのは今のワークスペースの記録だけで、ほかのプロジェクトの個人的なチャットまで読まないようになっています。2つ以上の期間で見つかったパターンだけを確度が高いとみなし、1つの期間にしか出てこないパターンは、通常は捨てます。1度だけ言われて、別の場面では逆のことを言われた、というような好みは、流儀ではなく雑音だからです。
  2. 利用者に直接聞く・・・ エージェントは、履歴にまだ出てきていない意図を補うため、選択式の質問を1〜2問と、自由記述の質問を1問だけ聞きます。選択式にするのは、利用者が一から文章を書かずに済むようにするためです。
  3. 下書きする・・・ エージェントは、create-skill で .cursor/skills/<handle>-mode/SKILL.md に下書きを書きます。<handle> には、利用者の名前や、利用者が選んだ識別子が入ります。
  4. 磨く・・・ エージェントは、下書きに、AIらしい文章の癖を取り除く /unslop（第33章）をかけ、本人らしく読めるかを利用者と確かめます。
  5. 取り込む・・・ エージェントは、worktree（1つのリポジトリから、作業用のコピーを複数作るgitの機能。第18章）で作業してPRを開きます。main に直接 push はしません。

既存の mode のSkillがあれば、エージェントは、前回の編集以降の履歴だけを読んで、そのSkillを更新します。

エージェントは、利用者にエージェントの既定の振る舞いと異なる具体的な規則があるときだけ、Skillに節を作り、「明確に伝える」のような一般論は書きません。一般論はエージェントの振る舞いを変えないので、書いても読む手間が増えるだけだからです。

たとえば、「段落は短く。選択肢を比べるときは表にする。箇条書きは項目が本当に並列なときだけ。」のような規則なら、節を作ります。

依頼の書き方：コマンドだけで始められる

同梱ガイドの 09-make-it-yours.md によると、利用者は、次のようにコマンドだけを打てば始められます。利用者の流儀は、エージェントが履歴から読み取るので、利用者が説明を書き添える必要はありません。

/automate-me

同じページは、働き方が変わったときに、既存の mode のSkillを更新する依頼も載せています。

/automate-me update my mode skill with everything since its last edit
// 前回の編集以降のすべてを使って、私の mode のSkillを更新して

/make-bot-ui は、送信キーを外に出さずに、Grok Bot をボタンで起動するページを作る

役割：秘密の値をエージェントに見せずに、Botを起動する仕組みを組み立てる

/make-bot-ui は、利用者がクリックするページを作り、そのボタンで Grok Bot を webhook 経由で起動する仕組みを組み立てるSkillです。

使いどき：Grok Bot のルーティンを、webhook でボタンから起動したいとき

利用者は、Grok Bot を webhook で起動するページ（ボタンやダッシュボード）を作りたいときに、このSkillを使います。そのページのために送信キーを提出するときや、ページを Tailscale で公開するときも、このSkillを使います。

!

Tailscale・・・ 利用者が持つ端末（パソコンやスマートフォンなど）同士を、インターネットに公開せずにつなぐ非公開のネットワークを作るサービス。このネットワークを tailnet と呼び、tailnet に入っている端末からだけ、そのネットワーク上のページを開ける

Grok Bot はAI Botアプリで、pstack をプラグインとして入れられます（第5章）。Grok Bot には、ルーティンを登録できるため、スケジュールやイベントをトリガーに動作させることができます。

!

webhook・・・ 指定したURLにHTTPリクエストを送ることで、別のシステムにイベントを知らせ、処理を起動する仕組み（例：GitHubへのpushをきっかけに、指定したURLへ通知を送る）

/make-bot-ui が扱うのは、webhook をきっかけに起動するルーティンです。ボタンを押してから Grok Bot の処理が始まるまでに、次の3つが順に動きます。

  1. 利用者がブラウザでページのボタンを押すと、ページは、Botと同じコンピューターで動く小さなサーバー（以下、ローカルのサーバー）に、ボタンに対応するJSON（例：{"action": "summarize-today"}）を送ります。
  2. ローカルのサーバーは、受け取ったJSONに送信キーを付けて、ルーティンの webhook URL（そのルーティンを外から起動するための専用のURL）に送ります。
  3. webhook URL にJSONが届くと、Botのルーティンが起動し、そのJSONを入力として処理を始めます。

ページが webhook URL に直接送らず、間にローカルのサーバーを挟むのは、送信キーをブラウザに渡さないためです。理由は、この後の手順の説明で見ます。

手順：ルーティンを作り、ページを置いて、tailnet で公開する

  1. ルーティンを作る・・・ エージェントは、webhook で起動するルーティンを作り、POSTの本文を信頼できないデータとして扱うようプロンプトに書きます。webhook URL に届く本文は外から送られてくるので、本文に「これまでの指示を無視して」のような指示の文が紛れ込んでいても、Botがその文に従わないようにするためです。
  2. URLを取ってもらう・・・ エージェントは、利用者に、Routines（Botのルーティンの一覧）からルーティンを開き、webhook URL をコピーしてもらいます。原文は、webhook URL はチャットに貼ってもらってよいとしています。一方、次の手順の送信キーは、チャットに貼ってもらいません。
  3. 送信キーを受け取る・・・ 送信キーは、webhook を呼ぶ正当な送り手であることを示す秘密の値です。エージェントは、送信キーをチャットでは受け取らず、秘密の値を入力する専用のカードで利用者に提出してもらいます。提出されたキーの値はエージェントには見えず、エージェントは値を見ないまま、その値をサーバーの設定に書き込みます。
  4. ページを置く・・・ エージェントは、ページとローカルのサーバーを、Botと同じコンピューターに置きます。ページのボタンはローカルのサーバーにPOSTし、そのサーバーが送信キーを付けて webhook にPOSTします。
  5. tailnet に載せる・・・ エージェントは、Tailscale で、インターネットに公開せずに、利用者の端末からページを開けるようにします。
  6. 起動を受け取る・・・ Botは受け取ったJSONを、指示ではなく外部のデータとして扱います。

エージェントは、送信キーをサーバーにだけ置き、ブラウザやチャットには出しません。キーを知っていれば、誰でもそのルーティンを起動できてしまうからです。

ブラウザから直接 webhook を呼ぶと、ページのコードにキーを書くことになり、ページを開いた人なら誰でもキーを読めてしまいます。そのため、ボタンは必ずローカルのサーバーを通して webhook を呼びます。

また、秘密の値をチャットに出さないという同じ方針で、エージェントは Tailscale の認証情報も利用者に聞きません。代わりにログインURLを渡し、利用者自身にブラウザで端末を承認してもらいます。

まとめ

  • 2つのSkillの呼び方・・・ /automate-me と /make-bot-ui は、利用者が名前で呼んだときだけ動きます。
  • /automate-me・・・ チャットの履歴と利用者への質問から、利用者の流儀を書いた利用者専用の -mode Skillを作ります。
  • /make-bot-ui・・・ 送信キーをチャットにもブラウザにも出さずに、ボタンで Grok Bot を起動するページを作ります。
