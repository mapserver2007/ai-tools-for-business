第34章 作業の学びを振り返り、反映する

この章では、/reflect を扱います。

/reflect は、作業の会話から次の作業でも使える学びを取り出し、利用者が承認したものだけを、既存のSkillに追記するなどして、学びを残すSkillです。

学びを取り出すのは、会話を3つの視点で読むサブエージェント（レビュー役）と、その結果をまとめるサブエージェント（合成役）です。Skillに残すかどうかは、利用者が決めます。

この章では、/reflect を、役割、使いどき、手順、依頼の書き方の4つの観点で解説します。

この章の構成

この章の構成は次のとおりです。

  • 役割：会話から長く通用する学びを絞り込む
  • 使いどき：学びのあった作業の直後に、利用者が /reflect を呼んだとき
  • 手順：3つの視点から集めた学びを、承認を得てから適用する
  • 依頼の書き方：何が起きたかと、何を残したいかを書く
  • まとめ

役割：会話から長く通用する学びを絞り込む

利用者の訂正から得た教訓を会話の中だけで終わらせず、コードベース、lintなどの自動検証、Skillなどに残す考え方は、第3章で扱いました。/reflect は、このうちSkillに残す部分を受け持ちます。

ただし、第21章の原則『Encode Lessons in Structure』が言うとおり、文章の指示は見落とされやすいものです。Skillに一文追加しても、次のエージェントがその一文に気づかなければ、何も変わりません。

そのため、このSkillの手順のうち、手順3から手順5までの3つは、学びを増やすためではなく、絞り込むためのものとして、本書では扱います。

  • 合成役は、今後のエージェントの行動を変えない学びを退けます。
  • エージェントは、lint やスクリプトで強制できる学びを、Skillの文章にせず、チームが使う課題管理のツールに登録する項目（Backlog）に回します。
  • 利用者は、残った学びのうち、Skillに残すものを選びます。

絞り込むことで、次のエージェントの行動を、実際に変える学びだけがSkillに残ります。

使いどき：学びのあった作業の直後に、利用者が /reflect を呼んだとき

同梱ガイドの docs/guide/09-make-it-yours.md は、学びのあった作業の直後に /reflect を呼ぶよう勧めています。/reflect の SKILL.md では、このSkillの使いどきを、利用者が「reflect」か「/reflect」と言ったときと定めています。

一方で、以下のようなケースではエージェントはこのSkillを使用しません。

  • 些細な会話のとき
  • 会話が本題から外れているとき
  • エージェントが既存のSkillどおりに正しく作業したとき

既存のSkillどおりに正しく進められた会話から得られる学びは、すでにそのSkillの内容が正しいものである証拠だからです。

また、エージェントは、一度きりの出来事を学びとして扱いません。

なお、このSkillは disable-model-invocation: true の設定を持つので（第25章）、エージェントが「reflect」という言葉を読んで、自分でこのSkillを選ぶことはありません。このSkillを動かすには、利用者が /reflect と名前で呼びます。

手順：3つの視点から集めた学びを、承認を得てから適用する

手順は次のとおりです。

  1. トランスクリプトを見つける・・・ エージェントが、今の会話のトランスクリプト（エージェントとの会話の記録）のファイルを探します。探すのは、今のワークスペースの agent-transcripts/ ディレクトリだけです。ほかのプロジェクトのディレクトリまで探すと、無関係なプロジェクトの非公開の会話を読んでしまうからです。見つからなければ、会話の要約を書き、ファイルの代わりにレビュー役に渡します。
  2. 3つの視点のレビュー役を同時に起動する・・・ エージェントが、判断（Judgment）、道具（Tooling）、発散（Divergent）の3つの視点で会話を読むレビュー役を、同時に起動します。既定のモデルは、判断と発散が claude-opus-5-5-xhigh、道具が grok-4.7-xhigh-fast で、/setup-pstack で変えられます（第36章）。それぞれの視点が探す学びは、この節の『3つの視点のレビュー役は、それぞれ別の種類の学びを探す』で説明します。
  3. 合成役が仕分ける・・・ 合成役が、3体のレビュー役が挙げた学びの候補を、Accepted（採用）、Rejected（却下）、Backlog の3つに分けます。
  4. lint やスクリプトで強制できるものを Backlog に回す・・・ エージェントは、Accepted のうち、lint のルール、スクリプト、メタデータのフラグ、実行時のチェックで強制できるものを、Skillの文章にせず Backlog に移します。文章の指示は読み手が気づいて守らなければ効きませんが、lint やスクリプトは、読み手が気づかなくても、決まりを守らせることができるからです。
  5. 利用者の承認を得てから、Skillの編集を適用する・・・ エージェントが、合成役の仕分けの結果をすべて利用者に見せ、利用者が、Accepted のうち、どれを適用するかを選びます。利用者は、「どのSkillに入れるか」という振り分け先を変えることもできます。エージェントは、利用者が選んだ編集だけを適用します。なお、承認を待つのは Accepted だけで、Backlog の項目は、エージェントが承認を待たずに課題管理のツールに登録します。
  6. 利用者へ短く報告する・・・ エージェントが、適用した編集、新しく作ったSkill、Backlog に回したもの、却下したもの（却下の理由を添える）を1行ずつ並べます。

手順2から手順5までの流れを図にすると、次のようになります。

Skillを編集するのは、Accepted に残り、利用者が承認した学びだけです。

3つの視点のレビュー役は、それぞれ別の種類の学びを探す

3つの視点と、それぞれが探す学びは次のとおりです。

  • 判断（Judgment）・・・ 個別の出来事の背後にある、長く通用する原則を探します。たとえば、利用者から受けた訂正の背後にある原則です。
  • 道具（Tooling）・・・ 次のエージェントが調べ直すことになる、ツール、コマンド、パス、フラグといった具体的な情報を探します。たとえば、エージェントが手探りで見つけたコマンドのフラグや、失敗した実行を手元で再現する方法などです。また、利用者が手で渡した情報のうち、エージェントがMCP（エージェントを外部のツールやデータにつなぐ仕組み）で自分で取得できたものも挙げます。たとえば、利用者が会話に貼り付けたチケットのIDなどが該当します。
  • 発散（Divergent）・・・ ほかの2つの視点が見落とすものを探します。たとえば、間違った理由でうまくいった判断や、テストがたまたま通っただけで残った判断、エージェントが飛ばした検証などです。

3体のレビュー役は、どれも、学び1つごとに、次の3つを返します。

  • 原則・・・ 次の作業でも通用する学びを、1文で書いたもの
  • 根拠・・・ その学びが出てきた、会話の中の場面
  • 振り分け先・・・ 学びを入れる先のSkill

振り分け先にできるのは、その会話で実際に使ったSkillだけです。使えば役立ったのに使われなかったSkillは、その説明（description）を直す提案にします。どちらにも当てはまらない学びは、レビュー役が捨てます。

合成役は、8つの基準で学びを絞り込む

合成役への指示は、references/synthesizer.md に書かれています。この指示によると、合成役は、学びの候補の1つ1つに、次の8つの基準を当てはめます。

基準 何を確かめるか
Durability（長持ち） ファイルのパスやツールのバージョンが変わった6か月後も、正しいか
Specificity（具体性） 別の作業にも使えるほど広く、使う場面が分かるほど具体的か
Existing-skill-first（既存のSkillが先） 新しいSkillを作らず、既存のSkillへの追加で済まないか
Convergence（重なり） 複数のレビュー役が挙げたか
Decision-changing（行動が変わる） その学びを書くと、次のエージェントが取る行動が変わるか
Structural-mechanism check（仕組みで守れるか） lint やスクリプトで守らせられないか
Skill-was-used（使ったSkillか） その会話で実際に使ったSkillに追加する学びか
Already-covered（書いてあるか） 追加する先のSkillに、同じことがすでに書かれていないか

たとえば、合成役への指示は、捨てる学びの例として、次の1行を挙げています。

linter at SHA bd91aa7 uses chars/4 heuristic

コミット bd91aa7 の時点の linter は、文字数を4で割る目安を使っている

bd91aa7 は、SHA（コミットごとに付く、コミットを一意に指す識別子）です。この1行は、「コミット bd91aa7 の時点のコードでは、linter がこう動いていた」という事実にすぎません。後のコミットで linter が書き換えられれば、この事実は正しくなくなります。

そのため、合成役は、Durability の基準に照らして採用しません。

Skillの編集は、利用者の明示の承認を得てから適用する

Skillの変更は、組織の今後のすべてのエージェントに影響します。そのため、エージェントは、Skillの編集を自動では適用せず、利用者の明示の承認を待ちます。

利用者が承認した編集を、エージェントは、編集の大きさに応じて次のように適用します。

  • 1行の追加や、古い事実の訂正などの小さな編集・・・ エージェントが、自分で直接編集します。
  • 新しい節の追加など、10行を超えるような大きな編集・・・ Cursor に組み込みの create-skill（Skillを書くためのSkill）に任せ、下書き、試し、直しを繰り返させます。
  • Skillはあるのに、使うべき場面で使われなかった場合・・・ create-skill に、そのSkillの説明（description）を直させます。
  • 既存のSkillに、追加する先がない場合・・・ create-skill に、新しいSkillを作らせます。

SKILL.md の検証ツールがある環境では、エージェントは、編集したSkillすべてにそのツールを実行してから、作業を終えます。

同梱ガイドは、利用者に、今後のエージェントの判断を変える提案だけを承認するよう勧めています。同ページでは、「一度だけ起きた変わった出来事は、たまたまの出来事であって、決まりではない」とも書いています。

!

SKILL.md の検証ツールの例

SKILL.md の検証ツールは、主に、先頭の設定欄（frontmatter）の書き方が正しいかを確かめるツールです。たとえば、次のものがあります。

  • skills-ref validate・・・ Agent Skills の仕様を公開しているリポジトリにある、参照用のライブラリのコマンドです。skills-ref validate path/to/skill のように、Skillのディレクトリを指定して実行します
  • quick_validate.py・・・ Anthropic の anthropics/skills リポジトリにある、Skillを作るためのSkill（skill-creator）に付いているスクリプトです。SKILL.md があるか、frontmatter が正しい YAML か、name と description があるか、許されていない項目がないかを確かめます

なお、pstack 自身は、SKILL.md のスクリプトとしての検証ツールを同梱していません。
そのため、pstackでは、検証ツールがない環境でも、Skillを書く『Authoring or modifying a skill』Playbook（第13章）が、検証ツールとしての役割を果たしています。

このPlaybookでは、frontmatter に name と description があるか、参照しているファイルがあるか、ほかのSkillへのリンクがたどれるかを確かめるよう定めています。

依頼の書き方：何が起きたかと、何を残したいかを書く

同梱ガイドは、学びのあった作業の直後に送る、次の依頼例を挙げています。

/reflect that took way too long. capture what we learned so the next run doesn't repeat it.
// 時間がかかりすぎた。次の実行で繰り返さないよう、学んだことを残して。

この依頼では、利用者は、何が起きたか（時間がかかりすぎた）と、何を残したいか（次の実行で同じことを繰り返さないための学び）を書いています。

まとめ

  • 学びの集め方・・・ 判断、道具、発散の3つの視点で集めた学びを、6か月後も正しいかなどの基準で絞り込みます。
  • Backlog・・・ lint やスクリプトで強制できる学びは、Skillの文章にせず、チームの課題管理のツールに回します。
  • 学びの残し方・・・ 利用者の承認を得てから、すでにあるSkillの SKILL.md に書き足したり、書き直したりします。

次の第35章では、エージェントが繰り返す間違いを、文章ではなくリポジトリの仕組みで起こせなくする /correct を扱います。
