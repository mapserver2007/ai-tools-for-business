# 第10章 問題を調べ、再現する

この章では、次の3つのPlaybookを扱います。

1. [Investigation](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)
2. [Runtime forensics](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/runtime-forensics.md)
3. [Trace forensics](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/trace-forensics.md)

3つとも、調べて答えを出すためのPlaybookで、コードは変えません。**成果物は修正ではなく、根拠を示した答えか診断**です。

どのPlaybookを使うかは、調査に使える情報や証拠で決まります。ソースコードと履歴を読めば答えられるのか、動いているプロセスを計測できるのか、取得されたプロファイルやダンプ（実行中の状態を記録したファイル）を調べるのかによって、使い分けます。

この章では、3つに共通する決まりと、それぞれの使い方を順に解説します。

## この章の構成

この章の構成は次のとおりです。

- 3つのPlaybookはコードを変えず、調査に使える情報や証拠で選ぶ
- 『Investigation』は、コードや履歴を読んで答えられる質問に、引用つきで答える
- 『Runtime forensics』は、ソースからの推測をやめて生きたプロセスを計測する
- 『Trace forensics』は、プログラムを再実行せず、渡された成果物を問い合わせできる形にして読む
- まとめ

## 3つのPlaybookはコードを変えず、調査に使える情報や証拠で選ぶ

冒頭で述べたように、3つのPlaybookは、**調査に使える情報や証拠で使い分けます**。

選び方は次のとおりです。

- **コードや履歴を読めば答えられる質問がある**・・・ 『**Investigation**』
- **不具合や遅延などが今も起きていて、動いているプロセスを自分で計測できる**・・・ 『**Runtime forensics**』
- **事後に渡されたプロファイルやダンプ（実行中の状態を記録したファイル）だけがある**・・・ 『**Trace forensics**』

| 項目 | 『**Investigation**』 | 『**Runtime forensics**』 | 『**Trace forensics**』 |
| --- | --- | --- | --- |
| 証拠 | ソースコードと履歴 | 動いているプロセスから取った計測 | 事後に渡された成果物（cpuprofile、spindump、heap snapshotなど） |
| プログラムの再実行 | しない | しない（動いているプロセスに計測を差し込み、仮説を確かめる） | しない |
| 次の行き先 | 利用者に戻し、『[**Bug fix**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)』か『[**Feature**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/feature.md)』へ | 『**Bug fix**』か『[**Perf issue**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/perf-issue.md)』へ | 『**Bug fix**』か『**Perf issue**』へ |

同じ「遅い」という相談でも、生きたプロセスを測れるのか、受け取ったファイルしかないのかで、選ぶPlaybookが異なります。また、証拠の種類ごとに「やってよいこと」も異なります。

『**Runtime forensics**』では、動いているプロセスにログや計測のコードを差し込んで確かめることが許容されています。一方『**Trace forensics**』では、受け取ったプロファイルやダンプを読むだけで、**プログラムを再実行して取り直すことは禁じられています**。

## 『Investigation』は、コードや履歴を読んで答えられる質問に、引用つきで答える

### 役割：コードや履歴を読んで答えが出る質問に答える

『**Investigation**』は、「Xはどう動くか」「Yはなぜこう作られたか」「Zは本当に大丈夫か」「XとYのどちらにすべきか」のような、**ソースコードや変更の履歴を読むだけで答えが出る質問に答えるPlaybook**です。

成果物は引用つきの説明か推奨です。PRを作らず、PRをマージできる状態まで見守る作業（『[**Babysit**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/babysit.md)』。[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)）もしません。途中でコード変更が必要だと分かったら、自分で直し始めずに利用者に戻します。

### 手順：出力の形まで決める4つの手順

1. 質問を `/how`（コードの仕組みや置き場所を説明するSkill）に通す。「なぜ」を問う質問なら、設計の理由や経緯を引用つきで調べる `/why` にも通す（どちらも[第22章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746)）
2. スループット・チェックポイントは「該当なし」の1行にする
3. `/how` と同じ5つの見出し（概要、主要な概念、仕組み、場所、注意点）で書く。選択肢の比較なら、トレードオフの表をつけた推奨を書く
4. 返答に `/unslop`（AIが書きがちな言い回しを削るSkill）をかける（[第33章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)）

!

- **TODOリスト**・・・ エージェントが作業の始めに作る、その作業でやることの一覧（計画）です。Cursorでは、チャットの画面に表示されます。利用者は、この一覧を見て、エージェントがどの手順を進め、どの手順を飛ばしたか（`skip: <理由>`）を確かめられます（同梱ガイド [`01-setup.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/01-setup.md)）。
- **スループット・チェックポイント**・・・ 作業を「どう並列に分けられるか」を検討した結果を、TODOリストに記録する際の4つの項目です。4項目は、次のとおりです。

  - 先に済ませる手順
  - 独立した作業の流れ
  - 共有される可変の状態
  - 最小で安全な分け方

  複数の手順がある自明でない作業では、どのPlaybookでも、これを書くよう求められています（詳しくは[第12章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/f1e85b)）。

  調べるだけでコードを変えない『**Investigation**』には分担する作業がないので、4項目を書かず「該当なし」の1行で済まされます。

「本当に大丈夫か」と聞かれたら、**相手の見立てにそのまま同意せず、理由を添えて自分の判断を書き**、前提が間違っていれば、その点も指摘します。

### 依頼の書き方：「新しいタスク」「まだコードは変えないで」と書く

依頼に「新しいタスク」と「まだコードは変えないで」を書くと、Playbookが選び直され、コードを変えない制約がかかります。同梱ガイド（[docs/guide/02-poteto-mode.md](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/02-poteto-mode.md)）の例は、次のとおりです。

```
/poteto-mode new task. figure out why the cache entry survives logout. don't change any code yet.
// 新しいタスク。ログアウト後もキャッシュのエントリが残る理由を突き止めて。まだコードは変えないで。
```

返答の形を依頼の側で指定しておく手もあります。『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)では、次の例が記載されています。

```
/poteto-mode investigate why background workers periodically fail with timeout errors. give me a breakdown of what we know, what data you used, and your best hypotheses.
// バックグラウンドのワーカーがときどきタイムアウトのエラーで失敗する理由を調べて。分かっていること、使ったデータ、有力な仮説を分けて示して。
```

この頼み方は、`/poteto-mode` の節『[Writing the reply](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#writing-the-reply)』の規定と同じ区別を求めています。**すべての主張に、証拠か、測定した・推論した・推測のどれかのラベルを同じ文の中で添える**、という規定です。依頼の側でもこの区別を求めておくと、返答のどの文が確かめた事実で、どの文が推測なのかを見分けられます。

## 『Runtime forensics』は、ソースからの推測をやめて生きたプロセスを計測する

### 役割：実行時の症状を、生きたプロセスの計測から診断する

『**Runtime forensics**』は、メモリリーク、アイドル中のCPU空転、表示の乱れといった実行時の症状を、ソースからの推測ではなく、**動いているプロセスの計測から診断する**Playbookです。

ソースを読めば、原因と考えられる経路は分かります。しかし実行時の症状では、どの経路が実際に走っているかが問題になります。実際に走っている経路は、動いているプロセスを計測して確かめます。

### 手順：信号を取る、証拠へ絞る、仕組みを証明する、ソースに対応づける

1. **ライブの信号を取る**
   - 症状に合ったcontrol系Skillを使い、CPUプロファイル、ヒープスナップショット、CDP（Chrome DevTools Protocol）のトレースを取得する
   - control系Skillはpstackに同梱されておらず、[`cursor-team-kit`](https://github.com/cursor/plugins/tree/main/cursor-team-kit) の `control-ui` と `control-cli` を指す
2. **決定的な証拠まで絞り込む**
   - ホットパス（実行時間の大半を使っている経路）上の関数、リークしたオブジェクトの保持チェーン、入力がないのに回り続けるループを探す
   - 大きな成果物はサブエージェントに解析させる（原則『[**Guard the Context Window**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-guard-the-context-window/SKILL.md)』、[第20章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/c155cc)）
3. **信じる前に仕組みを証明する**
   - 仮説が示す、症状を起こしている仕組みを確かめる
   - 確かめ方は、実行中のプロセスに計測のコードを差し込むか、再起動せずに動いているコードを直接書き換える（ホットフィックス）
4. **ソースに対応づける**
   - 原因の箇所を、ソースコードのファイル、シンボル（関数名などの名前）、該当する行までたどる

頼まれない限り修正は加えず、原因が分かったら『**Bug fix**』か『**Perf issue**』に渡します。

!

- **CPUプロファイル**・・・ 一定時間に、どの処理がCPUを使っていたかの記録
- **CDPトレース**・・・ Chrome DevTools Protocolを使って記録した、ブラウザ内の処理のログ。JavaScriptの実行や画面のレイアウト、描画などを調べられる
- **ヒープスナップショット**・・・ ある時点で、アプリがメモリに保持しているデータと、その参照関係を記録したもので、メモリリークの調査などに使う

## 『Trace forensics』は、プログラムを再実行せず、渡された成果物を問い合わせできる形にして読む

### 役割：取得済みの成果物を読むことに徹する

『**Trace forensics**』は、利用者の環境で取られたCPUプロファイル、spindump、ヒープスナップショットなど、事後に渡された成果物を、**再実行せずに読んで原因を診断する**Playbookです。

!

- **spindump**・・・ 応答しなくなったアプリの処理状態を調べる、macOSの診断レポート

『**Runtime forensics**』との違いは、取得がすでに済んでいることです。成果物は固定されたデータなので、読むことに徹します。ツールも、Playbookをどの環境でも使えるように、DevToolsやtrace解析ツール（パーサー）のような汎用的なものに限定します。

### 手順：成果物を読み込む、形を整える、原因へ絞る、ソースコードの位置を特定する

1. **形式を見分けて読み込む**
   - 大きな成果物はサブエージェントで解析する
2. **問い合わせできる形に変換する**
   - traceやヒープスナップショットをsqliteに流し込み、読む前に問い合わせできる形にする
3. **原因へ絞り込む**
   - 最も時間を使っているフレーム、リークの保持チェーン、止まっているスレッドを探す
4. **ソースコードの位置を特定する**
   - 最も時間を使っているフレームが、ソースコードのどのファイルの、どの関数の、何行目に当たるかを、成果物に含まれるシンボル情報を手がかりに特定する
   - この位置が分からない間は、どのコードが原因かを言えないので、診断はまだ終わっていないものとして扱う
   - 位置が分からないときは、シンボル情報を解決するか、成果物にシンボル情報が含まれていないことを明示する
5. **対になる取得があれば突き合わせる**
   - 修正の前と後のように、比べられる2つの成果物があれば差分を取る
   - 比較がなければ、所見を「成果物が支持する最も強い仮説」と書き、確定した原因とはしない
6. **引用つきの診断を返す**
   - 頼まれない限り修正はせず、『**Bug fix**』か『**Perf issue**』に渡す

!

- **フレーム**・・・ 処理の呼び出し履歴に記録される、関数の位置
- **保持チェーン**・・・ データがメモリから解放されずに残る原因となる、参照のつながり
- **スレッド**・・・ プログラム内で処理を進める流れの一つ

## まとめ

- **共通点と選び方**・・・ 3つのPlaybookは、どれもコードを変えずに答えや診断を返します。コードや履歴を読めば答えられる質問か、今も動いているプロセスを計測できるか、取得された成果物しかないか、の3つで選びます。
- **Investigation**・・・ `/how` と `/why` で答え、5つの見出しか比較表つきの推奨で返します。コード変更が必要なら利用者に戻します。
- **Runtime forensics**・・・ ソースからの推測をやめ、生きたプロセスを計測し、仕組みを証明してからソース位置を示します。
- **Trace forensics**・・・ プログラムを再実行せず、渡された成果物を問い合わせできる形にして、原因のあるソースコードの位置まで特定します。比較できる成果物がなければ「最も強い仮説」を書きます。

次の[第11章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42)では、診断を受け取って実際に直す側の3つのPlaybook、『**Bug fix**』、『**Perf issue**』、『[**Hillclimb**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/hillclimb.md)』を、「何を直したいか」という観点から見ていきます。
