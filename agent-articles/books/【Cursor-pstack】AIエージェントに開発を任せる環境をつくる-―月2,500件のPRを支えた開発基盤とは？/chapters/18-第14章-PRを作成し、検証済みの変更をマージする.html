この章では、次の3つのPlaybookを扱います。

  1. Opening a PR
  2. Babysit
  3. Shipping

3つとも、変更を trunk（PRのマージ先になる本流のブランチ）に取り込むまでを受け持つPlaybookで、それぞれが担当する段階は次の3つです。

  • PRを作る
  • PRを merge-ready（マージできる状態）まで運ぶ
  • 検証済みのPRだけを trunk に取り込む

どのPlaybookを使うかは、PRが今どの段にあるかで決まります。まだPRがないのか、PRはあるがマージできる状態になっていないのか、マージできる状態のPRを trunk に取り込みたいのかによって、使い分けます。

この章では、3つのPlaybookのつながり、それぞれの手順と要点を順に解説します。

3つのPlaybookは「PRを作る、マージ可能にし、trunk に取り込む」の順につながる

冒頭で述べたそれぞれの担当領域は、「PRを作る」「緑（CIのチェックがすべて通った状態）にする」「trunk に取り込む」の順に並び、それぞれ、どこで終わるかが決まっています。

段階 Playbook 終わる地点
作る 『Opening a PR』 PRのURLを返す
緑にする 『Babysit』 merge-ready
取り込む 『Shipping』 ルートから続く検証済みのPRがマージされる

!

  • フォージ・・・ この章では、PRを管理するサービスと、それを操作するCLIをまとめて「フォージ」と呼びます。既定は GitHub CLI（gh）です。
  • trunk・・・ PRのマージ先になる本流のブランチです。多くのリポジトリでは main です。
  • スタック・・・ 親子関係でつながったPRの列です。最前線のPR（ルート）だけが trunk を向きます（形は次の節の図）。
  • マージの最前線・・・ スタックの中で、まだマージされていないPRのうち、次にマージするPRです。
  • merge-ready・・・ CIのチェックがすべて通っている、未解決のレビューがない、コンフリクトがない、とフォージが判断している状態です。

それぞれ、依頼の言葉も異なります。以下は同梱ガイドの検証のページ（docs/guide/06-verify-and-ship.md）にある例です。

/poteto-mode babysit this pr. get it green.
// このPRを babysit して。緑にして。

/poteto-mode land the stack.
// スタックを trunk に取り込んで。

PRを開いただけでは『Babysit』は始まりません。

「緑にして」と頼めば『Babysit』が、「スタックを取り込んで」と頼めば『Shipping』が動きます。

『Opening a PR』は、PRを小さく、読みやすく、すぐレビューできる形で作る

『Opening a PR』は、変更をPRにするときの作法を決めるPlaybookです。

手順はこれまで見てきたPlaybookと異なり番号付きではなく、見出しごとに規則をまとめています。主な規則は次のとおりです。

  • Worktree・・・ 作業は main から切った git worktree で行います。
  • Commits・・・ PRを開く前に、小さく順序立てたコミットへrebaseを使用してまとめ直します。各コミットを、単独でマージできる「将来のPR」として扱います。
  • PRs・・・ 差分に対して、コミットの前に /deslop（cursor-team-kit にある、AIが書きがちな余計なコードを削るSkill）、レビューの前に /no-comments（不要なコメントを削るSkill）を実行します。タイトル、説明、コミット本文は、技術文書の書き方の基準を定めた /technical-writing で書き、AIが書きがちな言い回しを削る /unslop をかけます（第33章）。
  • Titles・・・ fix(pstack): retarget opening-a-pr babysit trigger のような、Conventional Commits の形式で書きます。
  • Forge・・・ 作成からマージまで、同じフォージを使い続けます。
  • Built-in PR tool・・・ 実行環境に組み込みのPRツール（例：Cursorのクラウドで動くエージェントが持つ、PRを作るためのツール）があれば、PRの作成、編集、マージ先の変更、レビュー可能な状態への切り替えは、フォージのCLI（GitHub CLI の gh コマンドなど、PRを管理するサービスを操作するコマンドラインのツール）ではなく、そのツールで行います。CLIで作ったPRは、そのツールが管理する対象に入らないからです。原文は、その例にPRの説明を挙げています。そのツールで作ったPRなら、後から別に起動したエージェントも、そのツールを使ってPRの説明を書き直せます。CLIで作ったPRの説明は、そのツールでは書き直せません。
  • Size and stacks・・・ 大きなPRを1つ作るより、狭いPRを5つ作るほうを選び、小さなPRはスタックとして積みます。
  • Readiness・・・ PRはドラフトではなく、レビュー可能な状態で開きます。組み込みのPRツールは既定でドラフトにすることがあるので、そのツールでPRを作るたびに draft: false（ドラフトにしない、という指定）を付けます。

!

  • git worktree・・・ 1つのリポジトリから、別のブランチを取り出した作業ディレクトリを追加で作るgitの機能（例：main の作業ディレクトリを残したまま、修正用のブランチを別のディレクトリで開く）
  • rebase・・・ コミットを別のコミットの上に付け直し、履歴を並べ直すgitの操作
  • Conventional Commits・・・ fix: や feat: のような、変更の種類を表す接頭辞を付けてコミットメッセージを書く規約

スタックは次のような形で、子のPRは、親のブランチをベースに向けます。

main  ← trunk
 └─ PR #1 (base: main) ← ルートのPRだけが trunk を向く
     └─ PR #2 (base: PR #1 のブランチ)
         └─ PR #3 (base: PR #2 のブランチ)

PRの本文は「Briefing」として書く

このPlaybookの要点は、本文の規則の最初の一文です。

The PR body is a briefing, not the lab notebook.

PRの本文はブリーフィングであって、実験ノートではない。

作業中に試したことや経過は書き連ねず、差分を手元に持つレビュアーが変更を承認できるか判断するために必要な情報だけを書きます。

このPlaybookは、レビュアーが1分以内に、次の4つを分かるように書くよう求めています。

  • 変更が存在する理由
  • 変更が扱わないこと
  • 変更が壊しうるもの
  • 変更が動くことを、どう証明したか

そのため、本文は、識別子（parseUser や src/date.ts のような、関数名、型名、ファイルのパスなどのコード上の名前）をあまり使わない、短く簡単な文で書き、長い段落を続けて書くことはしません。

各節は太字の書き出しではなく、見出し（##）の下に置き、節どうしの区切りを、分かりやすくします。節は次の順に並べ、書くことがない節は省きます。

節 書くこと
## Why 問題と、採用した方法を、短い文1〜3つで書く
## What changed 変更を、短い箇条書き1〜3つで書く。実際の関数名や型名（シンボル）、ファイルのパスは、変更の内容を説明するのに、その名前が欠かせない場合だけ書く
## Scope このPRで扱う範囲と、扱わない範囲を、対にして必ず書く。短い項目1〜3つで書く（扱わない範囲の例：別のPRで行う関連の作業や、PRを作った人が認識しているものの、このPRでは対応しない不足。不足の例は「検索画面は作ったが、検索結果の並べ替えには、まだ対応していない」など）
## Tradeoffs 検討したが採用しなかった案のうち、レビュアーが「なぜこの案にしなかったのか」と聞きそうなものだけを書く。ほかに検討した案がなければ、この節は省く
## Blast Radius（影響範囲） この変更の影響を受ける人や機能と、それがなぜ安全か、または危ないかを、1〜2文で書く
## Verification 実際に実行した経路と結果を、箇条書き1〜3つで書く。性能の変更なら、主な数値を1つ、単位付きの before → after の形で書く（例：p50 41 ms → 33 ms）

PRを開いても、Babysitは始めない

エージェントはPRを開いたら、PRのURLを報告して、残りの作業を続けます。

PRごとに『Babysit』を回すと、そのたびに作業が中断されます。さらに、後の作業でコミットを書き換えると、そのPRで回したCIのチェックが無駄になり、新しいコミットでやり直すことになります。

例外は、第16章で扱う『Autopilot-full』（PRのキューをエージェントが自律的にマージまで運ぶPlaybook）と『Autopilot-stack』（同じ進め方で、マージせずに1本のスタックを作るPlaybook）で、PRを1つずつ受け持つエージェント（オーナー）です。オーナーへの指示に『Babysit』のループが含まれているので、オーナーは担当するPRを開いたあとも、続けて merge-ready（Autopilot-stackでは STACK-READY）まで運びます。

依頼の書き方：小さく順序立てたコミットと、説明に書く証拠を求める

同梱ガイドの依頼例は、コミットを小さく順序立てることと、証拠をPRの説明に書くことを求めています。

/poteto-mode open the pr. small ordered commits, evidence in the description.
// PRを開いて。コミットは小さく順序立てて、証拠はPRの説明に書いて。

『Babysit』は、未マージの最前線のPRから順に問題を片付け、merge-ready にする

『Babysit』は、コンフリクト、レビューのスレッド、CIの失敗を片付け、PRやスタックを merge-ready まで運ぶPlaybookです。人間の判断が必要なところまで来たら止まります。

Cursorには、PRの状態を見守る組み込みの /autopilot Skill（以前の名称は babysit）もあり、同じような依頼の言葉で呼び出されることがあります。そのため /poteto-mode は、PRの状態に関する依頼をすべてこのPlaybookに回すと明記しています。対象になる依頼の例は次のとおりです。

  • 「このPRを見ていて」
  • 「緑にして」
  • 「Bugbotのコメントに対応して」
  • 「PR X の様子を見て」

!

Bugbot・・・ Cursorが提供する、PRを自動でレビューする機能。PRが作られたり更新されたりすると、差分を読み、不具合やセキュリティの問題の疑いを、PRのレビューコメントとして書き込む

手順：最前線のPRから順に問題を片付ける

主な手順は次のとおりです。

  1. モードを宣言する・・・ どこまで作業するかを表すモードを、状態を確かめる前に決める。既定は drive で、小さなPRやドキュメントだけのPRは check にする（各モードについては以下の表を参照）
  2. 最前線だけに集中する・・・ 未マージの最前線のPRだけを直し、その上のPRには手を出さない
  3. 1つのスタックを担当するエージェントは1体にする
  4. スタックの構成（PRの親子関係）を変えない・・・ rebase、ベースの付け替え、force-pushはしない。rebaseが必要なら、ブランチの持ち主に報告する
  5. コンフリクト、レビューのスレッド、CIの順に片付ける・・・ 判明している修正は1回のpushにまとめ、チェックの再実行を1回で済ませる。コンフリクトだけは自分で解決せず、どのブランチにrebaseが必要かを報告して止まる
  6. フォージの判定を信じる・・・ 「ready」は、CIのチェックがすべて通っていることではなく、フォージがマージできると認めている状態を指す。GitHubでは同梱のスクリプト watch-pr でPRの状態を取得する
  7. CIの失敗は、再実行の前に分類する・・・ 再実行はフレーク（コードと関係なく、ときどき失敗するテスト）やインフラの問題のときだけにし、差分自身のコードで失敗したときだけコミットで直す
  8. Bugbotのコメントをトリアージする
  9. 人間の判断が必要なところで止まる

!

  • force-push・・・ リモートのブランチの履歴を、手元の履歴で強制的に上書きするpush
  • トリアージ・・・ 対応が必要か、どう対応するかを決めるために、項目を振り分けること（例：直す、却下する、質問する）
モード 何をするか 対応する依頼
drive merge-ready になるまで、状態の確認と修正を繰り返す 「緑にして」「マージできる状態にして」
background ほかの作業を止めずに、PRの状態をトリアージする 計画がまだ実行中のとき
threads-only レビューコメントに答えるだけ 「Bugbotのコメントに対応して」
check 状態を1回確認して報告する 「X の様子を見て」「緑になった？」

Bugbotのコメントは、fix、dismiss、askに分ける

手順8では、Bugbotなどのコメントを、対応する前に3つに分けます。基準は references/bugbot-triage.md にあります。

  • fix・・・ 正しさ、セキュリティ、データ損失などに関わりそうなら、問題のコードを含むPRのうち、最も先にマージされるPRで直し、スレッドを解決します。
  • dismiss・・・ 記録済みの危険の少ないパターンに当てはまり、指摘された懸念が該当しないとコードで証明できる場合、短い理由を返信して解決します。
  • ask・・・ 指摘が新しい種類のもの、深刻度が高いもの、あいまいなものなら、推測せずに利用者に尋ねます。

Bugbotの指摘は、まずコードで確かめます。誤検知かどうか判断できないときは、推測せずに利用者に確認します。確認の手間より、本物のバグを誤って退ける損失のほうが大きいからです。

レビューコメントは検証すべき主張であり、そのまま従う指示ではないので、指摘を消すことだけを目的にコードを変えず、問題を確かめた場合にのみ修正します。

merge-ready でも、マージはしない

手順9のマージの規則は次のとおりです。

Babysitting never authorizes merging. Only an explicit request to merge, land, ship, or merge when ready does.

babysitはマージを許可しない。許可するのは、マージする、取り込む（land）、出す（ship）、準備ができたらマージする、という明示的な依頼だけである。

merge-ready に達しても、エージェントは報告して止まります。マージを頼まれたら『Shipping』に回します。

merge-ready に達したら、その回に行ったコメントの振り分けを見直し、チームで役立つdismissのパターン（記録済みの危険の少ないパターン）があれば、references/bugbot-triage.md への追加を別のPRで提案します。

要点は「最前線だけ」の規則

『Babysit』では、次にマージするPRの問題を優先して修正します。

後続のPRに付いたレビューコメントも読み、対応事項をまとめますが、その修正で先にマージするPRのチェックをやり直すことになる場合は、後続のPRの修正を後回しにします。

たとえばPR #1 のCIが失敗しているときにPR #3 にレビューコメントが付いても、まずPR #1 のCIを通します。スタックは下から順にしかマージできないので、今マージを進められるのは最前線だけです。

また、上のPRへの指摘を、来るたびに直してpushすると、そのたびにチェックが再実行されます。そのため、上のPRへの指摘は貯めておき、最前線の修正と同じ1回のpushにまとめて直します。

依頼の書き方：「緑にして」と頼み、状態だけなら小さく頼む

merge-ready まで運んでほしいときは、「緑にして」と頼みます。章の冒頭で示した依頼を、もう一度示します。

/poteto-mode babysit this pr. get it green.
// このPRを babysit して。緑にして。

状態だけを知りたいときは、小さく頼みます。次の依頼なら、ループを始めずに check で答えます。

/poteto-mode check on pr 123. anything outstanding?
// PR 123 の状態を確認して。残っていることはある？

『Shipping』は、別のエージェントの検証を通ったPRの範囲だけを trunk に取り込む

『Shipping』は、CIが通ったスタックをtrunk（PRのマージ先になる本流のブランチ）に取り込むよう頼まれたときに使うPlaybookです。各PRを独立に検証し、ルートから続く検証済みの範囲だけを1つずつマージします。/poteto-mode はこのPlaybookを「Green is not safe.」（CIが通っていても安全とは言えない）と要約しています。

要点は「安全」の定義

Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.

安全とは、そのコードを書いていないエージェントによる判定のことだ。CIが通ったことは判定ではなく、承認するボットのレビューも判定ではない。

第2章の「信頼するのはエージェントではなく成果物」を、マージの直前の確認にも当てはめ、誰が確かめるかまで決めた定義となっています。

手順：各PRを検証し、連続した範囲を決め、1つずつ trunk に取り込む

手順は6つです。

  1. すべてのPRを独立に検証する
  2. ルートから続く、連続した検証済みの範囲だけを取り込む
  3. 判定が今もそのパッチ（変更差分）を表しているか確かめる
  4. 最前線のPRだけを準備し、1つずつマージする
  5. マージのたびに計算し直し、最前線がマージされるまで状態を監視する
  6. 上限で止まる

ここからは、各手順を1つずつ見ていきます。

!

  • git patch-id・・・ コミットの差分の中身から識別子を計算するgitのコマンド。コミットのIDが変わっても、差分が同じなら同じ値になる

1. すべてのPRを独立に検証する

PRごとにサブエージェントを1体ずつ割り当て、親のブランチとPRの最新のコミットを実際の画面やコマンドで比べさせる。結果は PASS、PASS+NOTES（注記つきの合格）、FAIL のいずれか。

2. ルートから続く、連続した検証済みの範囲だけを取り込む

手順2の「連続した範囲」は、次のように決まります。

PR #4  PASS      ← 検証済みだが、下に未検証がある
PR #3  (未検証)  ← ここで連続が切れる
PR #2  PASS
PR #1  PASS      ← 最前線
main

つまり、取り込んでよいのは PR #1 と #2 だけです。

PR #4をマージするには、前提となる未検証のPR #3を検証してからマージする必要があり、#3の検証を飛ばすと、未検証の変更まで trunk に入ってしまうことになります。

3. 判定が今もそのパッチ（変更差分）を表しているか確かめる

rebaseでコミットのID（SHA）が変わっても、差分の中身が同じかを git patch-id で比べる。中身が変わっていれば検証し直す。

4. 最前線のPRだけを準備し、1つずつマージする

準備は、必要なら最前線のPRを最新の trunk にrebaseし、そのPRのベースを trunk に付け替えることを指す。1つマージされてから次を準備する。

5. マージのたびに計算し直し、最前線がマージされるまで状態を監視する

1つマージされるたびに、新しく最前線になったPRのベース、チェック、patch-idを調べ直す。自動マージを予約していても、それをスタックが安全である証拠とは見なさない。

6. 上限で止まる

上限は、検証済みの連続したPRの一番上のPR（手順2の図ではPR #2）。そこまでマージしたら、何が取り込まれたか、次の未検証のPRはどれかを報告して終わる。

依頼の書き方：「スタックを取り込んで」と頼む

章の冒頭で示した依頼を、もう一度示します。

/poteto-mode land the stack.
// スタックを trunk に取り込んで。

まとめ

  • 3つのPlaybookのつながり・・・ 『Opening a PR』はPRを作成し、『Babysit』はマージ可能な状態まで整え、『Shipping』は検証を通ったPRを trunk（PRのマージ先になる本流のブランチ）へマージします。
  • Opening a PR・・・ 小さく順序立てたコミットと差分を絞ったPRを作り、本文は「ブリーフィング」として短く書きます。PRを開いても『Babysit』は始めません。
  • Babysit・・・ モードを宣言し、最前線だけを見て merge-ready まで運びます。Bugbotのコメントは fix、dismiss、ask に分けます。
  • Shipping・・・ 「安全」をコードを書いていないエージェントの判定と定義し、ルートから連続した検証済みの範囲だけを1つずつマージします。
  • BabysitとShippingの違い・・・ 2つのうち、マージするのは明示的な依頼を受けた『Shipping』だけです（『Autopilot-full』など第16章のPlaybookには別の決まりがあります）。
