この章では、次の2つのSkillを扱います。

  1. /create-verification-skill
  2. /maintain-verification-skill

2つとも、エージェントが実際にアプリを動かして、自分の仕事を確かめられるようにするためのSkillです。2つは、それぞれ次の仕事を受け持ちます。

  • /create-verification-skill・・・ エージェントがアプリを起動し、実際のユーザーと同じように操作して、スクリーンショットなどの証拠を取るための手順を、プロジェクトに作ります。
  • /maintain-verification-skill・・・ /create-verification-skill が作った手順に書かれた機能や操作が、今のアプリと食い違っていないかを、エージェントが定期的に点検し、ずれを直します。

/create-verification-skill は、実際のユーザーのように、アプリを動かして確かめるために、検証スキル（原文では verification skill）を作ります。検証スキルは、エージェントが作業中のアプリを起動し、操作し、証拠（スクリーンショット、ターミナルの出力、ログなど）を取るための、プロジェクト専用のSkillです（第3章）。

2つのうち、利用者が最初に使うのは、検証スキルを作る /create-verification-skill です。

この章では、2つの分担、2つを誰が呼ぶか、検証スキルから始める理由を確かめたうえで、1つずつ、役割、使いどき、手順、依頼の書き方の4つの観点で解説します。

この章の構成

この章の構成は次のとおりです。

  • 2つのSkillが受け持つ仕事
  • /create-verification-skill は、アプリをユーザーと同じ経路で動かす手段を作る
  • /maintain-verification-skill は、Feature Map と今のアプリのずれを定期的に直す
  • まとめ

2つのSkillが受け持つ仕事

2つのSkillの役割と成果物を表にまとめると、次のようになります。

Skill 役割 成果物
/create-verification-skill アプリを起動・操作して証拠（スクリーンショットなど）を残す手順を、プロジェクトに作る .cursor/skills/verify-<app>/（検証スキルと Feature Map）
/maintain-verification-skill 検証スキルと Feature Map を、今のアプリに合わせ続ける アプリを動かして確かめた修正をまとめたPR（1本まで）、または報告だけ

Feature Map は、アプリの機能ごとに、何ができるか、ユーザーがその機能にどうたどり着くか、検証スキルでどう操作し、どんな結果を確かめられるかをまとめた文書です（第4章）。

/create-verification-skill と /maintain-verification-skill は、第19章の原則『Prove It Works』が求める「実際に機能を動かして確かめる」ことを、どの作業でもできるよう、確かめる手段をプロジェクトに作り、保ち続けるSkillです。

2つは、利用者か /setup-pstack が名前で呼んだときだけ動く

2つの SKILL.md は、どちらも disable-model-invocation: true の設定を持っています（第25章）。この設定があるSkillを、エージェントが会話の内容から自分で選んで動かすことはありません。そのため、2つが動くのは、利用者が名前で呼んだときか、ほかのSkillが手順の中で名前を指定して呼んだときだけです。

2つを誰が呼ぶかは、次のとおりです。

  • /create-verification-skill・・・ 利用者が名前で呼びます。また、/setup-pstack は、最後の手順で、アプリを動かして確かめる手段がプロジェクトにないと分かると生成を提案し、利用者が受け入れればこのSkillを呼びます。
  • /maintain-verification-skill・・・ 利用者が名前で呼んだときだけ動きます。

最初に検証スキルを作るのは、エージェントが自分の仕事を確かめられるようにするため

利用者が検証スキルを最初に用意するのは、エージェントが自分の仕事を確かめられないと、どれだけ多くの仕事をエージェントに任せても、最後は人間が1つずつ確かめることになり、人間が作業の流れを止める存在（ボトルネック）になるからです。

人間がボトルネックになってしまうと、一日中エージェントの面倒を見ることになります。検証スキルがあれば、エージェントは自分でアプリを動かして確かめ、成功するまで作業を続けられます。利用者は、エージェントが確かめ終えた結果だけを見れば済みます。

poteto氏も、『The Complete Guide to pstack』Part 1とPart 2で、この考えを繰り返し述べています。

特に、Part 1では、検証スキルがあれば、ほかのSkillや、自動で動く仕組みにも、アプリの確認を任せられると述べています。このように、poteto氏は、検証スキルを、他のSkillや定期的な作業のための土台と位置づけています。

ちなみに、Part 1が挙げる例は、次の2つです。

  • /swarm（第24章）が、多数のクラウドエージェントに検証スキルを実行させ、性能の改善を十分な回数で確かめる。
  • Grok Bot のルーティン（第25章）が、Slackに届いたユーザーの報告を受け取るたびに、クラウドエージェントに検証スキルでその不具合を再現させる。

/create-verification-skill は、アプリをユーザーと同じ経路で動かす手段を作る

役割：実際のアプリを動かして挙動を証明する手段を、プロジェクトに作る

/create-verification-skill は、プロジェクト専用の検証スキルを .cursor/skills/verify-<app>/ に生成するSkillです。エージェントは、生成された検証スキルを使って、実際のアプリを起動し、ユーザーと同じように操作して、証拠を残せるようになります。

エージェントは、生成する検証スキルを、人間ではなく、ほかのエージェントが読むものとして書きます。読み手は、そのアプリを一度も見たことがなく、作業の途中で予備知識なしにこの検証スキルを開くエージェントだからです。そのため、エージェントは、読み手が推測しなくて済むよう、このリポジトリで実際に使うコマンドやセレクタ（画面の要素を指す書き方）を、検証スキルにそのまま書きます。

検証スキルができれば、利用者が「アプリで確かめて」と頼むだけで、どのエージェントも、アプリの起動や操作の方法を利用者から教わらずに確かめられるようになります（docs/guide/06-verify-and-ship.md）。

使いどき：アプリの挙動を、スクリプトで確かめる手段がないとき

利用者がこのSkillを使うのは、アプリの挙動を、スクリプトで繰り返し確かめる手段がプロジェクトにないときです。

たとえば、ブラウザを自動で操作して画面を確かめるスクリプトも、CLIを実行して出力を確かめるスクリプトも、まだプロジェクトにない場合です。

pstack が使うモデルを設定する /setup-pstack も、最後の手順で、アプリを動かして確かめる手段（verify-* のSkillや、既存のハーネス）がプロジェクトになければ、一度だけ生成を提案し、利用者が受け入れれば /create-verification-skill を呼びます（第36章）。

手順：リポジトリを調べて検証スキルを書き、一度実行してから渡す

手順1：アプリの動かし方を、利用者に聞く前にリポジトリから調べる

エージェントは、最初の手順で、アプリの動かし方を、利用者に聞く前にリポジトリのコードや設定から調べます（原文では、この調査を「面談（interview）」と呼んでいます）。

エージェントが利用者に聞くのは、コードベースから観察できないことだけです。コードを読めば分かることまで利用者に聞くと、利用者の手間が増え、返事を待つ間は作業も止まってしまうからです。

エージェントは、次の5つの問いに、コードベースから答えます。5つの問いは、検証スキルに書く中身（何をどう起動し、どう操作し、何を証拠に残すか）を集めるためのものです。

観点 問い
Surface（ユーザーが触れるもの） ユーザーは実際に何に触れるか（Web UI、CLI、API など）
Run（起動） アプリはローカルでどう起動するか（package の scripts、Makefile、READMEのクイックスタートなど、リポジトリ自身の開発用コマンドを優先する）
Drive（操作） エージェントはどうやってプログラムから操作できるか。Playwright や Cypress のテスト、curl で呼べるエンドポイントなど、リポジトリにすでにある仕組みを先に探す。なければ、CDP、PTY や tmux、素の HTTP といった汎用の手段を選ぶ
Observe（観察） どんな証拠を残せるか（スクリーンショット、ターミナルの記録、応答の本文、ログ、終了コード、データベースの状態など）
Isolate（分離） アプリのインスタンスを2つ、ポートやデータのディレクトリを分けて並べて動かせるか

!

  • Playwright・Cypress・・・ ブラウザを自動で操作してテストするツール
  • CDP・・・ ブラウザの開発者ツールと同じ機能をプログラムから使う仕組み。WebアプリやElectron（デスクトップアプリを構築するためのフレームワーク）アプリでは、エージェントはCDPでブラウザにつなぎ、クリックや文字の入力を送って、画面の状態を読み取る
  • PTY・・・ 疑似端末（pseudo terminal）。本物の端末の代わりにプログラムが用意する端末で、その中で動くアプリからは、人が端末を使っているのと同じに見える
  • tmux・・・ 1つのターミナル画面上で、複数のセッションやウィンドウ、分割画面（ペイン）を管理できる端末多重化ソフトウェア（Terminal Multiplexer）。外からコマンドで、セッションにキー入力を送ったり、画面に表示された内容を取り出したりもできる
  • CLIやTUIでは、エージェントは、PTYやtmuxのセッションの中でアプリを起動し、キー入力を送って、画面に表示された文字を読み取る
  • 素の HTTP・・・ 画面を通さず、curl などでHTTPのリクエストをアプリに直接送り、返ってきた応答を確かめること
  • インスタンス・・・ 起動中のアプリ1つ1つを指す。たとえば、同じWebアプリをポート3000と3001で1つずつ起動すれば、インスタンスは2つとなる

2つのインスタンスを並べて動かせないなら、エージェントは、そのことを検証スキルに書き、1つのインスタンスを2体のエージェントで同時に操作しないよう指示します。利用者が使っているインスタンスをエージェントが同時に操作すると、利用者が作業中のセッションを壊すおそれがあるからです。

リポジトリのコードが今の状態で、ビルドか起動のどちらかができないなら、エージェントは、検証スキルを生成する前に、ビルドと起動ができるように直すか、何が足りないかを正確に報告します。ビルドも起動もできない状態を前提に書いた検証スキルは、読んだエージェントに間違った手順を伝えてしまうからです。

手順2：SKILL.md の6つの見出しを書く

エージェントは、生成する SKILL.md に、次の6つの見出しを置きます。アプリを一度も見ていない次のエージェントが、起動から片付けまでを順に進められるようにするためです。

エージェントは、中身を手順1の調査で見つけた事実だけで書き、プレースホルダー（後で埋めるための仮の文字列）を残しません。アプリを知らない次のエージェントには、仮の文字列を正しい値に置き換えることができないからです。

プレースホルダが残った書き方と、調査で見つけた事実で書いた書き方を比べると、次のようになります。

<!-- プレースホルダが残っている：次のエージェントは、何を実行し、何をクリックすればよいか分からない -->
起動：`<起動コマンド>` を実行し、`http://localhost:<PORT>` が応答したら準備完了
操作：`TODO: 送信ボタンのセレクタ` をクリックする

<!-- 調査で見つけた事実で書いている：次のエージェントは、そのまま実行できる -->
起動：`pnpm dev` を実行し、`http://localhost:5173` が応答したら準備完了
操作：`getByRole('button', { name: '送信' })` をクリックする
見出し 中身
Launch（起動） 起動するコマンド、アプリの「準備ができたこと」を判断する方法（特定のログの1行が出る、ポートが応答するなど）、停止方法
Doctor（診断） 「このインスタンスを操作して確かめる意味があるか」を確かめる、読み取りだけのチェック（プロセスが動いているか、ビルドが正しいか、そのポートを使っているのが自分の起動したインスタンスか、認証が有効かなどを見る）
Drive（操作） このリポジトリの実際のセレクタやコマンドを使った操作手順。画面の座標やTabキーでフォーカスが移る順番ではなく、ARIAラベルや data 属性のような変わりにくい目印を使う
Evidence（証拠） 証明のために何を残し、どこに置くか
Cleanup（片付け） この実行が作ったインスタンスの片付け方。証拠は消さない
Helpers（補助スクリプト） 同梱するスクリプトの呼び方

!

ARIAラベル・・・ 画面の読み上げ用に、ボタンなどの要素へ付ける名前

Drive の「変わりにくい目印」を、Playwright のコードで比べると、次のようになります。

declare const page: {
  mouse: { click(x: number, y: number): Promise<void> };
  getByRole(role: "button", options: { name: string }): { click(): Promise<void> };
  locator(selector: string): { click(): Promise<void> };
};

// 前：画面の座標で押す。ボタンの位置が変わると、別の場所を押してしまう
async function saveByPosition() {
  await page.mouse.click(640, 410);
}

// 後：ARIAラベルで押す。ボタンの位置が変わっても、同じボタンを押せる
async function saveByLabel() {
  await page.getByRole("button", { name: "保存" }).click();
}

// 後：data 属性で押す。ボタンの位置が変わっても、同じボタンを押せる
async function saveByDataAttribute() {
  await page.locator('[data-testid="save"]').click();
}

Evidence には、証明の基準も書きます。基準には、次のようなものがあります。

  • テスト専用の近道ではなく、ユーザーが通る実際の経路を操作する
  • 画面だけでなく、副作用（書かれたファイル、追加された行、送られたメッセージなど）も確かめる

テスト専用の近道とは、たとえば、内部の値を直接書き換える関数や、テストのためだけに用意したエンドポイントです。エージェントが近道で確かめても、ユーザーが通る経路（実際のアプリの挙動）が正しく動くことの証明にはなりません。

手順3：Feature Map の最初の版を作る

エージェントは、生成する検証スキルに Feature Map も付けます。

Feature Map は、ユーザー向けの機能ごとに1つずつ作る機能ファイルと、それらをまとめる目次の features/README.md からなります。エージェントは、最初は、主な機能を3〜5件ほど見つけ、機能ごとに機能ファイルを作ります。

エージェントは、主な機能を、次の4つから探します。

  • ルート・・・ Webアプリの画面ごとに決まっているURLのパス（例：/settings）。
  • コマンド・・・ CLIが受け付けるコマンドやサブコマンド（例：git commit の commit）。
  • メニュー・・・ アプリの画面に並ぶメニューの項目
  • ドキュメント・・・ README や使い方の説明など、アプリの機能を説明した文書

機能ファイルの中身と、Feature Map を記憶として育てる考え方は、第39章で扱います。

The map is the repo's maintained verification source; a proof that drives one convenient entry point is incomplete when the map lists others.

Map は、リポジトリで保守される検証の正本である。Map がほかの入口も挙げているとき、都合のよい入口を一つだけ操作した証明は不完全である。

ここでいう入口は、ユーザーがその機能にたどり着く方法のことです（ボタン、キー操作、コマンドなど）。

Feature Map が一つの機能に複数の入口を挙げているなら、エージェントは、すべての入口を確かめて初めて、その機能が動くことを証明できます。この決まりによって、Feature Map は、どの入口まで確かめれば証明になるかを決める一覧にもなります。

たとえば、この決まりを、同梱の Feature Map の例に当てはめてみましょう。この例の、メモの検索機能の機能ファイル search.md には、ユーザーが検索機能にたどり着く方法が、次のように書かれています。

How to get to it (user POV)

  • Choose the Search button in the browser toolbar.
  • Press / in the browser while focus is outside an editable field.
  • Run notes search <query> in a terminal.

機能へのたどり着き方（ユーザーの視点）

  • ブラウザのツールバーの Search ボタンを選ぶ。
  • ブラウザで、編集できる欄の外にフォーカスがあるときに / キーを押す。
  • ターミナルで notes search <query> を実行する。

この例では、メモの検索機能に、ツールバーの Search ボタン、/ キー、ターミナルの notes search <query> の3つの入口があります。この機能を、エージェントが Search ボタンで確かめただけでは、証明として足りません。残りの2つの入口も確かめて、初めて証明になります。

このように、Feature Map が一つの機能に複数の入口を挙げているなら、エージェントは、すべての入口を確かめる必要があります。

手順4：生成した検証スキルを一度最後まで実行する

エージェントは、生成した検証スキルを利用者に手渡す前に、その検証スキルに書いた指示どおり一度最後まで実行します。操作する機能は一つで足ります。残りの機能は、Feature Map を使って後の実行で確かめられるからです。

実行の流れを図にすると、次のようになります。

エージェントは、失敗した回でも片付けを実行するので、失敗した試行が起動したプロセスや、使っていたポートは残りません。

また、エージェントは、片付けの後に証拠が残っていなければ、その実行を不合格とします。片付けが証拠まで消してしまうと、証明が何も残らないからです。

さらに、エージェントは、生成した検証スキルを、一度も実行していないうちは、成果物ではなく下書きとして扱います。書いた手順に誤りがあっても、実行するまでは見つからないからです。

たとえば、Launch に書いたポート番号が間違っていても、実行しなければ気づけません。

最後に、エージェントは、Feature Map を保守する /maintain-verification-skill を利用者に案内します。

依頼の書き方：コマンドだけで始められる

docs/guide/06-verify-and-ship.md によると、利用者は、次のようにコマンドだけを打てば Feature Mapと検証スキルの作成を開始できます。エージェントはアプリの動かし方をリポジトリから調べるので、利用者が前もって説明を用意する必要はありません。

/create-verification-skill

検証スキルを実際に作って育てる流れは、第39章で扱います。

/maintain-verification-skill は、Feature Map と今のアプリのずれを定期的に直す

役割：検証スキルと Feature Map を、今のアプリと食い違わないよう保つ

/maintain-verification-skill は、検証スキルと Feature Map が今のアプリと食い違っていないかを点検し、ずれを直すSkillです。

A feature map rots the moment the app changes.

アプリが変わった瞬間から、Feature Map は古くなり始める。

アプリが変わると、その時点から、Feature Map の記述は実際のアプリと合わなくなり始めます。そのため、Feature Map は作った後もメンテナンスし続ける必要があり、そのメンテナンスを受け持つのがこのSkillです。

使いどき：アプリが変わった後に、定期的に使う

利用者がこのSkillを使うのは、アプリが変わって、Feature Map の記述と今のアプリがずれたときです。

poteto氏は、『The Complete Guide to pstack』Part 1で、少なくとも1日1回の実行を勧めています。エージェントがアプリを操作するための情報を、いつも最新に保つためです。

同梱ガイドの06-verify-and-ship.mdも、実行し忘れないように、少なくとも1日1回、可能であれば、決まった時刻にSkillを自動で実行する仕組み（原文では scheduled automation）を使うよう勧めています。

そのため、本書でも少なくとも1日1回の実行と、Routineなどで、このSkillの実行を自動化することを推奨します。

手順：ソースコードは並列に読み、アプリの操作は主エージェントだけが行う

プロダクトのコードは編集せず、退行は Feature Map を直さずに報告する

エージェントが編集してよいのは、検証スキル自身のディレクトリ（SKILL.md、features/、検証スキルが持つスクリプト）だけです。

エージェントは、点検中にプロダクトのコードを編集しません。アプリが Feature Map に書かれたとおりに動かないときは、その食い違いが Feature Map の書き誤りなのか、プロダクトの退行（以前は動いていた機能が壊れること）なのかを見分けます。書き誤りなら Feature Map を直し、退行なら利用者に報告します。

エージェントが退行を Feature Map の修正で済ませないのは、プロダクトが壊れているのに Feature Map の記述を今の挙動に合わせてしまうと、壊れていること自体が隠れてしまうからです。

7段の手順で、索引の整備からPRにするかの判断までを進める

手順は次のとおりです。

  1. 対象を探す・・・ 主エージェントは、点検する検証スキル（通常は .cursor/skills/verify-*/）を探します。見つからなければ止まり、/create-verification-skill を案内します。
  2. 索引を整える・・・ 主エージェントは、Feature Map の目次（README）と機能ファイルを見比べ、欠けた項目やリンク切れを直します。
  3. ソースコードを読む・・・ 主エージェントは、機能ファイルごとに、読み取りだけを行うサブエージェントを並列に起動します。各サブエージェントは、Feature Map の説明と今のソースコード間で、ずれている疑いのある箇所を、根拠となるソースコードの場所とともに返します。
  4. 突き合わせる・・・ 主エージェントは、手順3で挙がったずれている疑いのある箇所のうち、いくつかを実際に確かめます。また、最近の変更の中から、Feature Map に記載がない機能を探します。
  5. 実際に操作する・・・ 主エージェントは、ソースコードに問題が見つからなくても、すべての機能を少なくとも一度操作します。
  6. 仕分ける・・・ 主エージェントは、見つけた問題を、この後の『見つけた問題は3種類に仕分け、結果は3つのどれか一つで示す』の表の3種類に分けます。
  7. PRにするか止めるか決める・・・ 実際に操作して確かめた修正があれば、主エージェントは、変更したファイルを読み直してから1本のPRにまとめます。直すものがないときや、確認を終えられなかったときは、主エージェントはPRを作らず、結果と確かめた範囲を報告します。

手順3でサブエージェントがずれを見つけなかった機能も、主エージェントは、手順5で実際に操作します。ソースコードを読んだだけでは、アプリが Feature Map の説明どおりに動くことを証明できないからです。証明するには、実際にアプリを動かして確かめる必要があります（第19章の原則『Prove It Works』）。

複数のエージェントが同じアプリを操作すると、証拠が信用できなくなる

サブエージェントがソースコードを並列に読んでも、互いの作業に干渉しません。一方、複数のエージェントが同じアプリを同時に操作すると、状態が混ざり、証拠が信用できなくなります。

たとえば、一方のエージェントが開いた画面を、もう一方のエージェントが閉じてしまうと、撮ったスクリーンショットがどちらの操作の結果なのか分からなくなります。そのため、アプリの操作は、主エージェント1体だけが受け持ちます。

手順3から手順5までの分担を図にすると、次のようになります。

主エージェントは、操作の間に3つの決まりを守る

主エージェントは、手順5で操作している間、途中でどんな失敗が起きても、次の3つを守ります。

  • インスタンスが予想外の挙動を示したら、次に操作する前に Doctor のチェックを実行し、まだ操作できる状態かを確かめ直します。

    Doctor（診断）・・・ 「このインスタンスを操作して確かめる意味があるか」を確かめる、読み取りだけのチェック（プロセスが動いているか、ビルドが正しいか、そのポートを使っているのが自分の起動したインスタンスか、認証が有効かなどを見る）

  • 取得した証拠は、Cleanup（片付け）で消さずに残します。

    Cleanup（片付け）・・・ この実行が作ったインスタンスの片付け方。証拠は消さない

  • 操作のために起動したものは、残さずにCleanup（片付け）します。

見つけた問題は3種類に仕分け、結果は3つのどれか一つで示す

問題の仕分けは次の3種類です。

種類 対応
ドキュメントのずれ（ユーザーから見た機能の説明が誤っている、または欠けている） Feature Map を直す
ハーネスの欠落（アプリは正しく動くのに、検証スキルの操作手順やスクリプトでは操作できない） 操作手順やスクリプトを直す
プロダクトの欠陥（アプリの挙動そのものが壊れている） 利用者のために記録する。このPRでは直さない

結果は、直すものがない clean、確かめた修正を1本のPRにまとめる changed、確認を終えられなかった blocked のどれか一つです。

まとめ

  • /create-verification-skill・・・ アプリの起動や操作の方法を、利用者に聞く前にリポジトリのコードや設定から調べて、検証スキルと Feature Map を生成します。起動から片付けまでを一度最後まで実行し、片付けの後も証拠が残ることを確かめてから手渡します。
  • Feature Map・・・ アプリの機能ごとに、何ができるか、ユーザーがどうたどり着くか、検証スキルでどう操作し、どんな結果を確かめられるかをまとめた文書です。
  • /maintain-verification-skill・・・ 検証スキルのディレクトリだけを編集し、プロダクトの退行は直さずに報告します。すべての機能を少なくとも一度実際に操作し、直すものがない clean、確かめた修正を1本のPRにまとめる changed、確認を終えられなかった blocked のどれか一つで終えます。
