この章では、次の3つのPlaybookを扱います。

  1. Bug fix
  2. Perf issue
  3. Hillclimb

3つとも、コードを直すためのPlaybookです。直すときは、プログラムを実際に動かして得た出力、ログ、計測（実行時の証拠）を根拠にします。

どのPlaybookを使うかは、何を直したいかで決まります。結果そのものが間違っているのか、動作に誤りはないが処理が遅いのか、一つの数値を目標まで繰り返し押し上げたいのかによって、使い分けます。

この章では、3つに共通する決まりと、それぞれの使い方を順に解説します。

この章の構成

この章の構成は次のとおりです。

  • 3つのPlaybookは実行時の証拠をもとに直し、何を直したいかで選ぶ
  • 『Bug fix』は、不具合を再現してから、証拠で必要と確かめた最小限の変更で直す
  • 『Perf issue』は、修正前の測定から始め、修正後の測定で改善を示す
  • 『Hillclimb』は、一つの指標を「1つの変更、1回の測定、採用か取り消し」の繰り返しで改善する
  • まとめ

3つのPlaybookは実行時の証拠をもとに直し、何を直したいかで選ぶ

3つのPlaybookは、実行時の証拠で裏づけられない変更は残さないという決まりを共有し、次のように選び分けます。

  • 利用者が受け取る結果そのものが間違っている・・・ 『Bug fix』
  • 動作に誤りはないが処理が遅く、パフォーマンスを1回の修正で改善したい・・・ 『Perf issue』
  • 一つの数値を目標まで繰り返し押し上げたい・・・ 『Hillclimb』
項目 『Bug fix』 『Perf issue』 『Hillclimb』
出発点 不具合を自分で再現する ベースライン（修正前の基準）のトレースを取る 結果を左右する条件と対象の仕組みを把握し、指標と停止条件を決める
回数 一度の修正 一度の修正 停止条件を満たすまでループ
返答の中心 失敗から成功に変わった再現の出力 ベースライン、修正後、差分 指標の開始時と終了時の値、採用した変更と取り消した変更の数

原因だけ知りたく、修正は必要ないなら、第10章の『Runtime forensics』か『Trace forensics』を選びます。

3つとも、実装はサブエージェントに任せ、主エージェントは修正の計画と差分のレビューに回ります。

『Bug fix』は、不具合を再現してから、証拠で必要と確かめた最小限の変更で直す

役割：不具合を再現して根本原因を突き止める

『Bug fix』は、報告された不具合を再現して根本原因を突き止め、実行時の証拠で必要だと確かめた、最小限の変更だけを入れるPlaybookです。

「効くかもしれない」という念のための対策は、まだ確かめていない仮説であって修正ではないので、変更は入れません。実行時の証拠が仮説を否定したら、その仮説に基づいて入れた変更は戻します。

講演では、場当たり的な回避策を残すと、次のエージェントがそれを正しい実装例としてコピーしてしまう、と述べられています（第4章）。本書では、否定された仮説に基づく変更を戻す規則は、こうした回避策がコードに残り、次のエージェントに真似されるのを防ぐものだと読みます。

手順：再現、二分探索、計画、検証、コミット、PRの6つの手順

  1. 自分で再現する - 症状が現れる場所に合ったcontrol系Skill（cursor-team-kit の control-ui か control-cli）を使う - 利用者に再現を頼むのは、そのSkillでは操作できない具体的な理由があり、操作できるところまで自分で進めたあとに限定する - すぐに再現しないときは、不具合のきっかけを人工的に作る、不具合が起きやすい条件に絞る、計測のコードを入れる、のいずれかで、不具合が起きるまで試す
  2. 原因を二分探索する - 原因の仮説を並べ、残っている候補を最も大きく減らせる確かめ方から順に試して、一つに絞る - 仮説の候補は、影響するサブシステムの仕組みを /how で説明させ、以前は動いていたものが壊れた経緯を /why で履歴から調べさせて集める（どちらも第22章） - プログラムの状態が分からなければ計測やログを追加し、推測はしない - 次に進む前に、最後に残った仮説が示す仕組みを実行時の証拠で確かめる
  3. 修正を計画する - 修正が関数の境界をまたぐなら、先に /architect（型やモジュール構成をコードより先に設計するSkill、第24章）を使う - 実装は、範囲を具体的に絞ってサブエージェントに任せる
  4. 症状が出たのと同じ画面やコマンドで検証する - 元の再現の手順が、今度は成功することを確かめる - 別の画面やコマンドで確かめた場合や、確かめても結論が出なかった場合は、合格としない - 単体テストが示すのは個々の処理の振る舞いで、不具合がなくなったことではない。そのため、単体テストに合格しただけでは直ったと判断しない
  5. 不具合を再現するテストを、修正より先にコミットする - 修正前は失敗するテストを先にコミットし、その上に修正を重ねる - 手元で手軽に実行できるテストが書けるなら、失敗するテストを先に書いて進める /tdd（第31章）に従う - テストの作成に手間がかかる、複数のサービスをつないだ環境に大きく依存する、何を確かめるテストかが不明確、のいずれかに該当するなら、この手順は省ける
  6. PRを作る手順を定めた『Opening a PR』を実行する（第14章）

返答に書く項目は次のとおりです。

  • 何が壊れていたか
  • 根本原因
  • 修正
  • 検証の方法

あわせて、失敗してから成功に変わった再現の出力を、要約せずそのまま貼ります。

本書では、手順とPrincipleの対応を次のように読みます。原則『Fix Root Causes』は手順1から3に、原則『Prove It Works』は手順4と返答に、原則『Sequence Work into Verifiable Units』は手順5に対応します（第19章）。このうち、Playbookの原文が名前を挙げているのは、手順5の『Sequence Work into Verifiable Units』だけです。

依頼の書き方：「まず再現して」と書く

依頼には「まず再現して」と書き、テストを求めるなら「手軽に書けるテストがあれば」と条件をつけます。同梱ガイド（docs/guide/10-recipes-and-pitfalls.md）の例は、次のとおりです。

/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.
// まず重複書き込みを再現して。手軽に書けるテストがあれば /tdd で進めて。それから直して、もう一度流して。

壊れやすいモック（本物の部品の代わりに使う偽の部品）でテストを無理に作るより、本物のコマンドを実行するほうが、直ったことを正確に示せます。手順5で、テストの作成に手間がかかるなら省略できるとしているのは、このためです。

『Perf issue』は、修正前の測定から始め、修正後の測定で改善を示す

役割：遅さを測って直す

『Perf issue』は、実際に測った遅さについてトレース（処理ごとの実行時間などを記録したもの）を取り、ベースラインと比べて改善するPlaybookです。測る代わりにソースを読んで済ませることを禁じ、すべての修正を測定に結びつけます。

手順：ベースラインのトレースに始まる6つの手順

  1. ベースラインのトレースを取る・・・ 症状に合ったcontrol系Skillを使う。ベースラインと、その後に出る数値はすべて、/benchmark-checklist（第27章）で点検する
  2. /how でコードの仕組みを調べ、仮説の根拠にする・・・ 実際に動かして測る前に、「これ以上は速くならない」と決めつけない。直し方は、7つの performance mantras（直し方の候補を、安いものから順に並べた7つの指針）を、上から順に試す
  3. トレースから修正を計画する・・・ 実装はサブエージェントに任せ、差分をレビューし、修正後のトレースを取る
  4. 修正前後のトレースを解析して比べる・・・ トレースをsqliteに取り込むなどして差分を取る。別の画面やコマンドで測った場合や、測っても結論が出なかった場合は、合格としない
  5. PRに測定の結果を引用する
  6. 『Opening a PR』を実行する

返答に含める4項目は次のとおりです。

  • ベースラインの数値
  • 修正後の数値
  • 差分
  • 成果物のパス

どれも実際に測らなければ書けないので、返答の形そのものが「測らずに済ませる」ことを防いでいます。

手順2の performance mantras は、次の7つです。エージェントは、上から順に、安いものから試します。

  1. Don't do it. Stop work whose result nothing uses rather than cheapening it.
  2. Do it, but don't do it again.
  3. Do it less.
  4. Do it later.
  5. Do it when they're not looking.
  6. Do it concurrently.
  7. Do it cheaper.
  8. やらない。誰も結果を使わない作業は、軽くするのではなく、やめる。
  9. やる。ただし、二度はやらない。
  10. 減らす。
  11. 後でやる。
  12. ユーザーが見ていないときにやる。
  13. 並行してやる。
  14. 安くやる。

7つの mantra が、それぞれどんな直し方を指すかは、次のとおりです。各例は、本書で付けたものです。

mantra どんな直し方か 例
1. やらない 誰も結果を使わない処理を、やめる 画面に表示しない項目まで、毎回計算している処理をやめる
2. やる。ただし、二度はやらない 一度出した結果を保存して、使い回す リクエストのたびに設定ファイルを読み直すのをやめ、1回読んだ結果を使い回す
3. 減らす 処理する量を減らす 1万件すべてではなく、画面に表示する50件だけを取得する
4. 後でやる 必要になるまで、処理を後回しにする 起動時にすべての画面を準備せず、開かれた画面だけを準備する
5. ユーザーが見ていないときにやる ユーザーが待っていない時間に、処理を済ませておく ユーザーが操作していない間に、次に開かれそうな画面のデータを読み込んでおく
6. 並行してやる 互いを待つ必要のない処理を、同時に進める 3つのAPIを1つずつ順に呼ばず、同時に呼ぶ
7. 安くやる 同じ処理を、より速い方法で行う 全件を1件ずつ調べる検索を、インデックス（検索を速くするための索引）を使う検索に変える

上から順に試し、目標に届いた時点で、残りの mantra は試さずに止めます。たとえば、誰も結果を使わない計算をやめるだけで目標に届いたなら、ほかの計算を速くする工夫は試しません。

依頼の書き方：「遅い気がする」ではなく測った数値を書く

依頼には、「遅い気がする」ではなく、測った数値を書きます。同梱ガイド（docs/guide/05-build-and-clean.md）の例は、次のとおりです。

/poteto-mode startup takes 1.8s on this fixture. trace it, fix the measured cause, show me before and after.
// このフィクスチャ（計測に使う決まった入力）で起動に1.8秒かかる。トレースして、測った原因を直して、前後を見せて。

改善の確かさまで求めたいときは、検証スキル（アプリを利用者と同じように操作して確かめるSkill、第3章）を /swarm で並列に走らせて改善を確かめるよう、依頼に含めます。『The Complete Guide to pstack』Part 1の例は、次のとおりです。

spawn a cloud agent to use /poteto-mode to improve the initial loading time of our app. first use /control-app to take a trace of the status quo, and identify opportunities for improvement. then do a targeted fix and use /control-app + a /swarm to confirm the win
// クラウドエージェントを起動して、/poteto-mode でアプリの初回読み込み時間を改善させて。まず /control-app で現状のトレースを取り、改善の余地を見つけて。それから狙いを絞って直し、/control-app と /swarm で改善を確かめて。

/control-app は、記事で作った検証スキルの呼び名です（第39章）。/swarm（第24章）は、並列でWorkers（複数のエージェント）を走らせて1つの報告にまとめるSkillです。多数のエージェントに検証スキルを実行させるので、十分なサンプル数で改善を確かめられます。1回の計測のばらつきを、改善と取り違えないためです。

『Hillclimb』は、一つの指標を「1つの変更、1回の測定、採用か取り消し」の繰り返しで改善する

役割：一つの指標を目標までループで改善する

『Hillclimb』は、一つの指標を目標に向けてループで継続的に改善するPlaybookです。一度きりの修正は『Bug fix』か『Perf issue』の担当です。

中心の規律は「one change, one measurement, keep or revert」、つまり1つの変更、1回の測定、採用か取り消しです。試していない変更を積み重ねず、コードを読んだだけで改善したと主張しません（原則『Prove It Works』）。

手順：1回に1つの仮説でループする8つの手順

  1. 指標を選ぶ前に、結果を左右する条件と対象の仕組みを把握する - 対象に /how をかけ、指標の値を左右する現実的な条件（データ量、履歴、状態、並行度）を挙げる - ユーザーの不満を再現するケースを選ぶ - 指標1つと停止条件を決める - 停止条件は、「ベースラインより50%以上よく、かつ10回以上試す」のように、目標と試行回数の下限をセットにする。下限を設けるのは、序盤にたまたま良い結果が出ただけで終わらせないため
  2. 測定ハーネスを作り、違いを見分けられることを確かめてから固定する - 目標のケースが症状を再現し、症状の出ない易しいケースと測定値で区別できることを確かめる - 確かめたら、測定方法を固定する。固定とは、測る対象のケース、指標、測定のコマンドを、以降のループの間は変えないことを指す - 固定する前に、/benchmark-checklist（第27章）で測定ハーネスを点検し、測定ハーネスにエラーの数と、行った作業の数を出力させる - 固定したあとは、決まった1つのコマンドで指標を出せるようにし、1回ではなく複数回の中央値をとる - 変更を入れる前に、ベースラインの指標と、回帰ゲート（通り続けなければならない必須のテスト）がすべて通った結果を記録しておく（原則『Build the Lever』、第17章）
  3. 判断の記録を開く - 判断の記録を残す /show-me-your-work（第29章）で decision.tsv を作る - decision.tsv は、試すたびに、仮説、変更、前後の数値、採用か取り消しかを1行ずつ書く表 - 次の試行の前に読み返す
  4. 仮説は、手順1で把握した仕組みに基づいて立てる - 「Xが最初の描画を遅らせているので、起動時の処理から外す」のように、具体的な仕組みを仮説として立てる - 「何かをメモ化してみる」のような仮説は認められない - 指標が性能なら、仮説を、『Perf issue』の手順2の performance mantras の順に並べる。借りるのは並べる順番だけで、「目標に届いた時点で、残りの mantra は試さずに止める」という『Perf issue』の止め方は借りない
  5. 1回に1つの仮説でループする - 変更はサブエージェントに渡す（原則『Guard the Context Window』） - 独立した仮説が複数あれば、worktreeごとの並列のサブエージェントに配る（原則『Separate Before Serializing Shared State』） - 手順2で固定したハーネスで変更の前後を測る - 採用するのは、指標の改善が偶然とは言えないほどはっきりしていて、回帰ゲートがすべて通ったときだけ - それ以外は変更を丸ごと取り消す - 採用でも取り消しでも、decision.tsv の行は必ず書く - 無人で走らせるなら、長いタスクを止まらずに完了まで運ぶ『Autonomous run』（第15章）から、時間やイベントをきっかけにエージェントを起こし直す仕組みだけを借りる。停止条件は、手順1で決めたものに従う
  6. 改善が止まっても、すぐには終わらせない - 取り消しが続いたら、仮説の系統（取り組み方の種類）を切り替える、惜しかった案を組み合わせる、より大胆な案を試す、などをしてから結論する - 指標は良くなっても振る舞いを壊す変更は取り消す - 指標を保ったままコードを単純にする変更は残す（原則『Laziness Protocol』）
  7. 停止条件を満たすか、残りの案の効果が手間に見合わなくなったら止める - 停止条件を緩めて満たしたことにはしない - 低コストで試せる仮説が残っているうちはやめない - 行き詰まったら空回りせずに報告する
  8. 『Opening a PR』を実行する - 採用したコミットを、入った順に積み重ねる

!

「偶然とは言えないほどはっきりした改善」とは

たとえば処理時間を測り、コードを変えなくても100ミリ秒前後で数ミリ秒揺れるとします。変更後に80ミリ秒前後まで下がれば、揺れ幅を超えた改善と判断できます。一方、数ミリ秒しか変わらなければ、測定の揺れかもしれず、改善とは言い切れません。

手順2で1回ではなく複数回の中央値をとるのも、この揺れの影響を小さくするためです。

!

  • ハーネス・・・ 計測やテストを、毎回同じ条件で走らせるための仕組み
  • メモ化・・・ 関数の計算結果を入力ごとに保存しておき、同じ入力で呼ばれたときに保存した結果を返す手法
  • worktree・・・ Gitの機能で、1つのリポジトリから複数の作業ディレクトリを作り、別々のブランチを同時に扱えるようにするもの

依頼の書き方：指標、目標、試行回数の下限の3点を渡す

同梱ガイド（docs/guide/05-build-and-clean.md）によれば、指標、目標、試行回数の下限を渡せば、『Hillclimb』は測定方法を固定したハーネスを使い、1回に1つの仮説を試す流れを繰り返します。

まとめ

  • 共通の規律と選び方・・・ 3つのPlaybookは、入れる変更のすべてに実行時の証拠という根拠があること、という規律を共有しています。振る舞いの誤りなら『Bug fix』、処理の遅さを1回の修正で改善するなら『Perf issue』、一つの指標を目標まで繰り返し改善するなら『Hillclimb』を選びます。
  • Bug fix・・・ 自分で再現し、原因の仮説を二分探索で一つに絞り込んでから直します。返答には失敗から成功に変わった出力をそのまま貼ります。
  • Perf issue・・・ ベースラインのトレースから始め、/benchmark-checklist で数値を点検しながら、7つの performance mantras を安い順に試し、修正前後の数値で改善を示します。
  • Hillclimb・・・ /benchmark-checklist で点検してから測定方法を固定したハーネスを作り、目標と試行回数の下限を組にした停止条件のもとで「1つの変更、1回の測定、採用か取り消し」を繰り返します。

次の第12章では、振る舞いを「追加する」「保つ」「試す」、見た目を「そろえる」Playbook、『Feature』、『Refactoring』、『Prototype』、『Visual parity』の4つを、「何を変えてはいけないか」という観点から見ていきます。
