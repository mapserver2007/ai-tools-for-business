この章では、次の4つのPlaybookを扱います。

  1. Autonomous run
  2. Pause safely
  3. Session pickup
  4. Worktree and simulator cleanup

4つとも、1つの長い作業をエージェントに任せるためのPlaybookです。役割は次のとおりです。

  • 1つのタスクを、止めずに最後まで進める
  • 途中で止めて、別のエージェントが再開する
  • 作業のあとで、不要なworktreeなどを片付ける

!

  • worktree・・・ gitの機能で、1つのリポジトリから複数の作業ディレクトリを作り、別々のブランチを同時にチェックアウトできるようにするもの

同梱ガイドの夜間作業のページ（docs/guide/07-overnight.md）は、寝ている間に作業を任せられる条件を3つ挙げています。3つの条件は次のとおりです。

  • 確かめられる終了条件
  • 分離したworktree
  • 朝に監査する判断記録

たとえば「古い呼び出し元がゼロ」は確かめられる終了条件ですが、「4時間作業して」はこの条件には入りません。

この章では、4つのPlaybookを役割で整理したうえで、それぞれの使いどころ、手順、要点を順に解説します。

4つのPlaybookは、1つの長い作業を「続ける、止めて再開する、片付ける」で分担する

この章の4つのPlaybookは、次の表の3つの役割に分かれます。

役割 Playbook 責任を持つもの
1つのタスクを止めずに最後まで進める 『Autonomous run』 終了条件
止めて、再開する 『Pause safely』 再開できる状態で止めること
止めて、再開する 『Session pickup』 前の作業のどこから再開するか
後片付け 『Worktree and simulator cleanup』 ディスク容量を取り戻すことと、消してよいかを削除前に確かめること

章全体に出てくる道具

この章のPlaybookには、次の道具が繰り返し出てきます。

  • /loop・・・ 決まった間隔や、CIの完了などのイベントでエージェントを起動する、Cursor組み込みのコマンドです。
  • decisions.tsv・・・ /show-me-your-work（第29章）が書く判断記録で、1行に1つの判断を書きます。

長い作業や席を外す作業では、/show-me-your-work で判断を記録します。朝の確認では、夜の作業をすべて読み直すのではなく、この記録（decisions.tsv）で判断を監査します。

『Autonomous run』は、終了条件を先に決め、それが満たされるまで止まらずに作業を続ける

『Autonomous run』は、「終わるまで回して」「/loop で X まで回して」のような依頼で、長いタスクを止まらずに完了まで運ぶPlaybookです。

6つの手順

手順は次のとおりです。

  1. 終了条件を決める
  2. エージェントの起こし方を決める
  3. 証拠を元に必要な変更を一つずつ行い、結果を確かめる
  4. 途中で見つけたことは自分で片付ける
  5. 毎回、/show-me-your-work で判断を記録する
  6. 終了条件が満たされたら止まる

ここからは、各手順を1つずつ見ていきます。

1. 終了条件を決める

「テストが通る」「N個のPRがすべてマージされた」のような形で、最初の繰り返しの前に終了条件を書く。

2. エージェントの起こし方を決める

/loop を使って決める。CIの完了、マージなど、待つべきイベントがあるなら、そのイベントを監視し、エージェントを起こす監視役のサブエージェントを付け、予備として長い間隔の定期的な起動も用意する。待つべきイベントがないなら、結果を確かめ直す価値が出るころに合わせた一定の間隔で起動する。

3. 証拠を元に必要な変更を一つずつ行い、結果を確かめる

証拠をもとに必要最小限の変更をする。変更後、最初に決めた終了条件に近づいたかを確かめ、近づいていればコミットし、近づいていなければ変更を取り消す（原則『Sequence Work into Verifiable Units』、第19章）。

4. 途中で見つけたことは自分で片付ける

関連するバグや不安定な検証はエージェントが自分で直し、本筋から外れた修正は別のPRにする。人間に判断を求めるのは、元に戻せない操作、実験では決められない判断、本当の行き詰まりだけ。

5. 毎回、/show-me-your-work で判断を記録する

反復のたびに、何を変えたかと、終了条件に近づいたかを、1行ずつ記録する。

6. 終了条件が満たされたら止まる

条件を満たしていなければ、別の方法を試す。条件を下げて完了とはせず、本当に進められなくなった場合は、その状況を報告する。

返答に書く項目

返答に書く項目は次のとおりです。

  • 終了条件
  • ループ回数
  • 最終的に残した変更と、試しても条件に近づかず元に戻した変更
  • 最後の条件の状態

要点は、終了条件を確かめられる述語にすること

述語とは条件のことで、満たされたかどうかを、真か偽かで判定できるものです。

冒頭で述べたように、時間の長さは終了条件になりません。「4時間作業して」では確かめるものがなく、朝に残るのは4時間分の動きだけです。同梱ガイドの落とし穴のページ（docs/guide/10-recipes-and-pitfalls.md）も、「もっと良くして」のようなあいまいな条件を失敗例に挙げています。そのため、エージェントは手順1で条件を決め、手順6で止まるまで同じ条件を守ります。

『Pause safely』は、何も知らないエージェントが再開できる区切りで作業を止める

『Pause safely』は、止めるよう指示されたとき、Cursorを再起動するとき、会話のコンパクション（入りきらない分の会話を要約して詰める処理）が迫っているときに使うPlaybookです。何も知らないエージェントでも再開できる状態で止めます。明示的な指示でだけ動き、「続けて」「止まらないで」と言われたら止まりません。

4つの手順

  1. 安全な区切りで止まる・・・ 今の最小単位の手順を終えるか元に戻し、新しいことは始めない
  2. 止まるために元に戻せない操作をしない・・・ すでにPRを出している場合を除き、PRも作らずpushもしない
  3. 作業を消えない形にする・・・ コミットしていない編集を、wip: で始まる一つのコミットにまとめる
  4. 再開用のメモを、コンテキストの外に書く・・・ 意図、進み具合、次の手順、注意点を書く。/show-me-your-work の記録があれば、重複させずにそれを指す

返答に書く項目は次のとおりです。

  • ループのどこにいるか
  • ファイルやコミットに記録されている情報と、まだ会話（チャット）のコンテキストにしか残っていない作業の状況・意図・注意点など
  • 作ったコミット
  • 再開時の最初の行動

要点は「エージェントの頭の中にしかないもの」を外に出すこと

エージェントのコンテキストは、コンパクションやセッションの終わりで消えます。エージェントが返答で「ディスクにあるもの（ファイルやコミットに記録されている情報）」と「頭の中にしかないもの（作業の状況・意図・注意点）」を分けて書くので、何をファイルやコミットに移し損ねたかが見えます。

wip: コミットは編集途中のコードを、再開メモはコードに書けない意図や注意点を、ディスクに残します。第4章の「コードベースは記憶である」を、一つの作業の単位で実行する手順と読むことができます。

『Session pickup』は、前のエージェントの記録を信じて作業の続きから始める

『Session pickup』は、前のエージェントが途中まで進めた作業を、トランスクリプト（エージェントとの会話の記録）、Cloud AgentsのURL、pushされたブランチから引き継ぐPlaybookです。『Pause safely』と対になっています。

特定の一つの作業を引き継ぐなら『Session pickup』、複数のチャットからコンテキストを集めるなら /recall（第22章）を使います。

5つの手順

  1. 前の記録を探す - 探す先は、作業中のワークスペースのトランスクリプト、Cloud AgentsのURL、pushされたブランチのどれか - 長いトランスクリプトはサブエージェントに読ませ、要約だけを主スレッド（サブエージェントを呼び出す元の会話）に置く（原則『Guard the Context Window』、第20章）
  2. 作業の状態を組み立て直す - 作業中のブランチ、すでに入った変更（git log やベースとの git diff で確かめる）、残っているTODO、下された判断を把握する
  3. 済んだことと残りを比べる - 計画したことと済んだことを比べてどこから再開するかを特定し、終わった作業を繰り返さない
  4. 残りの作業を、内容に合うPlaybookに引き渡す - ここから先は、作業内容に合うPlaybookが引き継ぐ
  5. 引き継いだ主張を実物で確かめる - 前のエージェントの「成功した」という自己申告は証明とせず、引き継いだ変更を実際に確かめる（原則『Prove It Works』、第19章）

返答に書く項目は次のとおりです。

  • 前のエージェントがどこで止まったか
  • 引き継いだものと、やり直したもの
  • 再開地点
  • 結果

要点は、前の記録を信頼できる入力として扱うこと

再開したエージェントは、前の記録を自分で導き直さずに、そのまま入力として使います。

Playbookは、前の記録を使って済んだ作業と残っている作業を見分け、残っているところから再開するよう求めています。

たとえば、前のエージェントが不具合を再現し、操作手順や画面・ログを残していれば、次のエージェントは同じ操作をやり直さず、その記録を読んで原因調査や修正から再開します。

依頼の書き方：判断ログを読み、済んだ作業の続きから始めるよう頼む

同梱ガイドの依頼例は、ブランチの引き継ぎを頼み、判断ログを読んで何が済んでいるかを把握することと、終わった作業をやり直さないことを求めています。

/poteto-mode take over this branch. read the decision log, figure out what's done, and continue from there. don't redo finished work.
// このブランチを引き継いで。判断ログを読み、何が済んでいるかを把握して、そこから続けて。終わった作業はやり直さないで。

『Worktree and simulator cleanup』は、worktreeを消す前に「使われていない」を証明する

『Worktree and simulator cleanup』は、マージ済みや放棄されたgit worktreeと古いiOSシミュレーターを消して、ディスクの空き容量を増やすPlaybookです。

6つの手順

手順は次のとおりです。

  1. 記録して監査する
  2. 分類は助言であって、許可ではない
  3. 消す前に使用状況を確かめる
  4. 元に戻せない損失の前で止まる
  5. 確定したものを消す
  6. シミュレーターなど、ほかの回収先も片付ける

ここからは、各手順を1つずつ見ていきます。

1. 記録して監査する

今のディスク使用量を df -h / で記録し、worktree-audit.sh を実行する（原則『Build the Lever』、第17章）。

worktree-audit.sh は何も消さない読み取り専用のスクリプトとなっています。調べる項目は次のとおりです。

  • 各worktreeの大きさ
  • 各worktreeの古さ（最後に更新されてからの期間）
  • マージ済みか
  • 未コミットの編集
  • PRの状態
  • 最後に触ったチャット

スクリプトは、これらをもとに分類を提案します。

2. 分類は助言であって、許可ではない

スクリプトの分類は削除候補の提案。ピン留め中または進行中のチャット（サイドバーにでてくるエージェントとのチャット）が使っているworktreeは、削除対象から外す。スクリプトが、ピン留め中のチャットが使うworktreeをsafeと判定した例もあるため、候補をチャットの一覧と照合する。

3. 消す前に使用状況を確かめる

疑わしいものは、サブエージェントにトランスクリプト（エージェントとの会話の記録）を読ませて確かめる。

4. 元に戻せない損失の前で止まる

未コミットの作業があるものは、利用者に差分を見せて判断をもらう。

5. 確定したものを消す

git worktree remove と git worktree prune で消す。ブランチは残るので、コミットは失われない。

6. シミュレーターなど、ほかの回収先も片付ける

古いシミュレーターやランタイム、必要ならビルドのキャッシュも消す。

返答に書く項目

返答に書く項目は次のとおりです。

  • 削除前後のディスク空き容量と、増えた容量
  • 消したworktree
  • 残したものと、それぞれの理由

要点は、削除の前の関門がそのままレビューになること

worktreeやシミュレーターを削除すると、作業中の環境や未コミットの変更を失う可能性があります。そのため、削除前に、使用中でないことと未コミットの変更がないことを確認します。この確認が、誤削除を防ぐ関門（削除の前に通す確認）としての役割を果たします。

ほかのPlaybookではコードレビューが誤りを見つけますが、このPlaybookは、コードレビューを通さずに利用者の手元のworktreeやシミュレーターを消す唯一のPlaybookです。そのため、手順2〜4で使用中のものや未コミットの作業を確かめる関門が、そのままレビューになります。

依頼の書き方：「安全に消せるworktreeを消して」と頼む

同梱ガイドの依頼例は、何がディスクを使っているかを尋ね、安全に消せるworktreeだけを消すよう頼んでいます。

/poteto-mode what's eating my disk? prune the worktrees that are safe to prune.
// 何がディスクを食っている？ 安全に消せるworktreeを消して。

まとめ

  • 4つのPlaybookの役割・・・ 『Autonomous run』は1つのタスクを最後まで進め、『Pause safely』と『Session pickup』は作業を止めて再開し、『Worktree and simulator cleanup』は後片付けを受け持ちます。
  • Autonomous run・・・ 確かめられる終了条件を決め、それが満たされるまで止まらずに作業を続けます。
  • Pause safely・・・ エージェントの頭の中にしかないものを wip: コミットと再開メモに出して止まります。
  • Session pickup・・・ 前の記録を信頼して、やり直すことをせず、引き継いだ主張は実際に確認します。
  • Worktree and simulator cleanup・・・ 使われていないことを証明してから消します。削除前の関門がそのままレビューになります。
