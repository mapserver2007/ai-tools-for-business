poteto氏は『The Complete Guide to pstack』Part 1（この章では「記事」と呼びます）で、pstackを使い始めた利用者が最初に作るものとして、検証スキルを挙げています。

検証スキル（verification skill）は、エージェントが、利用者の開発しているアプリを起動して操作し、変更が動いたことを確かめて証拠を残すための、プロジェクト専用のSkillです（第26章）。

たとえば、設定画面を変更したなら、エージェント自身が歯車のボタンを押して設定画面を開き、変更した箇所のスクリーンショットを証拠として残します。

この章では、記事が勧める検証スキルの作り方と使い方を、/create-verification-skill の SKILL.md などのpstackの原文と突き合わせながら解説します。

!

/create-verification-skill と /maintain-verification-skill の SKILL.md に書かれた手順は、第26章で解説しました。

この章では、次の内容を割愛し、記事が勧めることを中心に解説します。

  • 作る前の調査・・・ エージェントは、ユーザーが触るもの、起動の方法、操作の方法、残せる証拠、アプリを2つ並べて動かせるかを、利用者に聞く前にリポジトリから調べます。
  • SKILL.md に書く中身・・・ エージェントは、起動、診断、操作、証拠、片付け、補助スクリプトの6つの見出しを、調べた事実で書きます。証拠は、ユーザーが通る実際の経路を操作し、画面だけでなく、書き込まれたファイルのような副作用も確かめて残します。
  • 手渡す前の実行・・・ エージェントは、生成した検証スキルを起動から片付けまで一度実行し、動くことを確かめてから利用者に渡します。一度も実行していないものは、下書きとみなします。
  • すべての入口の確認・・・ Feature Map が1つの機能に複数の入口（ボタン、キー操作、コマンドなど）を挙げているなら、エージェントは、すべての入口を確かめるまで、その機能の検証を終えません。
  • 保守の決まり・・・ /maintain-verification-skill を実行したエージェントは、結果を clean（直すものがない）、changed（修正を1つのPRにまとめた）、blocked（確認を終えられなかった）のどれかで報告します。保守の間は、プロダクトのコードを編集しません。

なぜ検証スキルを最初に作るのか

検証スキルを最初に作る理由は2つあります。

1つ目は、検証スキルが、チーム全体の成果を増やす重要なインフラであるためです。
2つ目は、pstackのPlaybookの多くの手順が、アプリを実際に操作する手段がなければ実行できないためです。

記事の位置づけ：重要なインフラ

記事の節『Verification is all you need』は、次の一文から始まります。

The most critical skill to have in your toolbox is a high quality verification skill.

道具箱の中で最も重要なのは、質の高い検証スキルだ。

記事の言う検証（verification）とは、エージェントが自分の仕事を自分で確かめられることです。

つまり、検証は、「コードを書いた」「ビルドが通った」ということではなく、実際のユーザーのように本物のアプリを操作し、結果を証拠として残すことを意味します。

自分の仕事を確かめられるエージェントは、失敗したら直してもう一度試すことを、作業が成功するまで繰り返せます。人間が1つずつ確かめなくて済むので、人間が作業の流れを止める存在（ボトルネック）になりません。

記事では、質の高い検証スキルを用意し、保守し続けることはとても重要なので、検証スキルを「ただのSkill」ではなく、重要なインフラのように考えている、と述べているので、本書でもそのように扱います。

さらに、質の高い検証スキルは、エンジニアでないメンバーも含めた、チーム全体の成果を増やすと続きます。

エージェントが、変更が動くかを自分で確かめられれば、エンジニアでないメンバーを含む組織の全員が、アプリに変更を加え、その変更が実際に動くことを確かめられるようになります。検証スキルを適切に作れば、チーム全体の成果が100〜1000倍になると書かれているため、検証スキルはアプリに1つ必須のものと言えるでしょう。

Playbookの前提：アプリを操作する手段

多くのPlaybookは、エージェントに、ユーザーが触る画面、CLI、APIなどを実際に動かすよう求めています。

そのときに使うのが control系Skill です。control系Skillとは、cursor-team-kit プラグインにある control-ui や control-cli のような、アプリを操作するSkillです（第8章）。/create-verification-skill で作る検証スキルも、control系Skillの一つに該当します。

次の表は、主なPlaybookが、エージェントにアプリのどんな操作を求めているかをまとめたものです。

Playbook エージェントに求めているアプリの操作
『Bug fix』（不具合の修正） 不具合を、エージェント自身が再現する
『Perf issue』（性能問題の修正） 直す前の基準となるトレースを取る
『Runtime forensics』（動いているプロセスの診断） 推測ではなく、動いているプロセスからプロファイルやトレースを実際に取る
『Prototype』（使い捨ての試作で設計を決める） 見た目を決めるときは、各案のスクリーンショットを撮り、操作して比べる
『Visual parity』（2つの実装の見た目や、移行の前後の見た目を、ピクセル単位でそろえる） コンポーネントごとに、移行前の画面を撮った基準（ベースライン）との画像差分を取る。差分が0でなければ失敗とする
『Shipping』（PRを検証してマージする） PRごとに、コードを書いていない別のエージェントが、変更前と変更後で画面やCLIを実際に動かし、PASS、PASS+NOTES、FAIL の3段階で判定する

!

  • トレース・・・ 処理ごとの実行時間などを、時間の流れに沿って記録したもの
  • プロファイル・・・ CPUの使用時間やメモリの使用量などを、関数ごとなどに集計した記録

検証スキルや control系Skillのような、アプリを操作する手段がなければ、エージェントは、表の手順を実行できません。

エージェントは、作業の初めに、Playbookの手順を写したTODOリストを作ります。飛ばす手順は、その手順の行に skip: <理由> と書いて残します（第7章）。

!

TODOリスト・・・ エージェントが作業の始めに作る、その作業でやることの一覧（計画）です。Cursorでは、チャットの画面に表示されます。利用者は、この一覧を見て、エージェントがどの手順を進め、どの手順を飛ばしたか（skip: <理由>）を確かめられます（同梱ガイド 01-setup.md）。

たとえば『Bug fix』で、操作の手段がない場合や、手段が再現したい箇所まで届かない場合、本書では、エージェントに残される選択肢として、次の2つを挙げたいと思います。

  • TODOリストに skip: <理由> を残して、その手順を飛ばす
  • 『Bug fix』が認める例外として、利用者に再現を頼む

利用者に再現を頼めるのは、次の2つを満たしたときだけです。

  • 操作の手段が、なぜ再現したい箇所まで届かないのかを、具体的に説明したとき（例：その画面は、特定の契約のアカウントでしかログインできない）
  • 操作の手段で動かせるところまでは、エージェント自身が操作したとき

手順を飛ばす場合も、利用者に再現を頼む場合も、エージェントが自分で確かめられない部分が残るため、その残った部分は人間が確かめることになります。

検証スキルは何でできているのか

検証スキルの中心は、アプリを操作する小さなCLIと、アプリの機能ごとのアクセス方法（その機能が画面やコマンドのどこにあり、ユーザーがどう操作すればたどり着けるか）をまとめた Feature Map の2つです。

本書が対象にした pstack version 0.15.15 では、エージェントは、/create-verification-skill の手順に従って、どちらも .cursor/skills/verify-<app>/ の中に作ります。

記事が例に使う架空のアプリ Atlas なら、できあがる構成は次のとおりです。

.cursor/skills/verify-atlas/
├─ SKILL.md（起動から片付けまでの手順）
├─ control-atlas.mjs（アプリを操作するCLI）
└─ features/（Feature Map）
   ├─ README.md（Feature Mapの目次。機能ごとのファイルへのリンク）
   ├─ <機能A>.md
   └─ <機能B>.md

SKILL.md に書く中身は第26章で見ました。ここでは、記事が詳しく説明している、CLIと Feature Map を見ます。

CLI

検証スキルのCLIは、アプリの操作とデバッグを、エージェントが再実行できるコマンドにしたものです。

原則『Build the Lever』の応用

記事は、アプリの操作をCLIにすることを、手作業の代わりにその作業をする道具を作る原則『Build the Lever』（第17章）の応用として説明しています。

Skillを作るときに、この原則を適用すると、Skillを作る人は、エージェントに、Markdownで書いた手順の説明だけを渡すのではなく、実行できる道具も渡すことになります。

What this means in the context of creating a skill, is that we prefer to give agents tools rather than just markdown.

Skillを作るという文脈では、これは、エージェントにMarkdownだけを渡すより、道具を渡すほうを選ぶ、という意味だ。

たとえば、検証スキルの SKILL.md に「設定ボタンをクリックして、画面を撮る」とMarkdownで書くだけだと、エージェントは、そのたびにクリックするためのスクリプトを自分で書くことになります。

検証スキルに click や screenshot のようなコマンドを持つCLIを付けておけば、エージェントはそのコマンドを実行するだけで済みます。検証スキルでは、アプリの操作とデバッグをまとめた、こういった小さなCLIが、ここでいう道具に該当します。

記事では、アプリの操作をCLIにする利点として、次のことを挙げています。

  • トークンが減る・・・ エージェントは、ボタンを1つクリックするためだけの使い捨てのスクリプトを書く代わりに、CLIのコマンドを1つ実行すれば済みます。
  • 再現しやすく、テストしやすくなる・・・ 検証スキルが、何度実行しても同じ結果になります。決まったコマンドなので、検証スキル自体が正しく動くかもテストできます。

例）架空のアプリ Atlas のコマンド

次は、記事に載っている、架空のアプリ Atlas 向けのコマンドの例の一部です。Atlas は、Electron（デスクトップアプリを構築するためのフレームワーク）で作ったアプリという設定です。

エージェントは、次のコマンドを上から順に実行して、次の3つを行います。

  1. アプリが操作できる状態かを確かめる（doctor）
  2. 新しい空の会話（スレッド）を開き、「list open tasks in this project」（このプロジェクトの未完了のタスクを一覧にして）を送る（new-session、send）
  3. その結果の画面を、証拠として /tmp/atlas-proof.png に保存する（screenshot）
# health
node .cursor/skills/verify-atlas/control-atlas.mjs doctor

# open a blank thread and send
node .cursor/skills/verify-atlas/control-atlas.mjs new-session
node .cursor/skills/verify-atlas/control-atlas.mjs send "list open tasks in this project"

# screenshot for evidence
node .cursor/skills/verify-atlas/control-atlas.mjs screenshot /tmp/atlas-proof.png

コマンドの6つの分類

どんなコマンドを用意すればよいかの目安としては、次の6つの分類が挙げられます。

  • 観察（Inspection）・・・ info、snapshot、screenshot など、画面の状態を見るコマンドです。
  • 移動（Navigation）・・・ home、new-session、scroll など、画面を移るコマンドです。
  • 操作（Interaction）・・・ send、click、type、press など、入力やクリックをするコマンドです。
  • 性能（Performance）・・・ trace、profile、perf-metrics など、性能を測るコマンドです。
  • 記録の取得（Streaming）・・・ console、network-log など、コンソールや通信の記録を取るコマンドです。
  • 診断と片付け（Health & cleanup）・・・ doctor、cleanup など、アプリが操作できる状態かを確かめたり、片付け（cleanup）をしたりするコマンドです。

エージェントが扱いやすいCLI

記事は、より高度な使い方に進む前に、まずCLIを、エラーなく動くよう仕上げることに時間を使うよう勧めています。CLIができれば、すべてのエージェントが、このCLIでアプリを操作し、デバッグできるようになるためです。

CLIを使うのは、人間ではなくエージェントです。そのため、CLIは、エージェントが扱いやすい作りにする必要があります。

記事が挙げる、エージェントが扱いやすいCLIの性質は次の6つです。

  • コマンド同士を組み合わせて使いやすい作りにする（記事は、John Ousterhout氏の著書『A Philosophy of Software Design』にある deep modules（シンプルなインターフェースの裏に多くの機能を持たせる設計）の考え方を挙げています）
  • 破壊的な副作用がありうるコマンドには、--dry-run（実際には実行せず、何が起きるかだけを示すオプション）を付ける
  • 機能を一度に見せず、サブコマンドで段階的に見せる。たとえば、--help ではサブコマンドの一覧だけを示し、各サブコマンドの詳しい使い方は、そのサブコマンドの --help で示す
  • エラーメッセージで、代わりに何をすべきかまで伝える。たとえば、「アプリが起動していません」で終わらせず、「先に起動のコマンドを実行してください」という対処方法まで記述する
  • --help を充実させる
  • JSONなど、機械が読める形で出力する

こうしたエージェントが扱いやすいCLIの設計を、利用者自身が考えるか、エージェントに頼むことが、推奨されています。

Feature Map

Feature Map は、アプリの機能ごとに、「その機能が何をするか」と、「ユーザーがどう操作すれば、その機能にたどり着けるか」、検証スキルでどう操作し、どんな結果になれば動いたと分かるか、をまとめたMarkdownのファイル群です（第26章）。

アプリが複雑になるほど、エージェントは、機能を見つけて操作するための案内を必要とします。poteto氏は、その案内として Feature Map を考え出しました。

features/README.md はFeature Mapの目次で、機能ごとのファイルへのリンクを持ちます。

エージェントは、アプリを操作する前に目次を読み、作業に関係する機能のファイルだけを開きます。

必要なファイルだけを読むので、エージェントは、コンテキストウィンドウのトークンを節約できます。

!

記事は、/create-verification-skill が references/features ディレクトリを作ると書いています。pstack version 0.15.15 の SKILL.md は .cursor/skills/verify-<app>/features/ に作るよう指示しており、置き場所が異なります。本書では、pstack version 0.15.15 の置き場所に従います。形の見本は、同梱の references/feature-map-example/ を見てください。

エージェントは、/create-verification-skill の手順に従って、機能ごとのファイルを、次の4つの見出しで書きます。

見出し 答える問い
Sub-features その機能の中で、ユーザーがどんな操作ができるか（操作ごとに短いIDを付けて並べる）
How to get to it (user POV) ユーザーはどう操作して、その機能にたどり着くか
Driving it with <harness> ハーネス（アプリを外から動かす仕組み。検証スキルのCLIなど）でどう操作するか
Gotchas 検証を無駄にしたり、無効にしたりする落とし穴は何か

表の各行を、/create-verification-skill に同梱の見本 create-note.md（メモアプリ Notes の、メモを作る機能）で1つずつ見ていきます。

Sub-features

見本は、メモを作る機能でユーザーができる操作を次の4つに分類しています。

  • 編集画面を開く
  • 保存する
  • 下書きを破棄する
  • CLIから作る
## Sub-features

- `create-open` opens a blank editor from each browser entry point.
- `create-save` persists a title and body.
- `create-cancel` discards an unfinished browser draft.
- `create-cli` creates the same note shape from the terminal.

How to get to it (user POV)

入口とは、ボタン、キー操作、コマンドなど、ユーザーがその機能にたどり着く方法のことです。見本は、ツールバーの New note ボタン、n キー、notes create コマンドの3つの入口を挙げています。

## How to get to it (user POV)

- Choose the `New note` button in the browser toolbar.
- Press `n` in the browser while focus is outside an editable field.
- Run `notes create --title <title> --body <body>` in a terminal.

Driving it with <harness>

見本の README.md は、機能ごとのファイルの書き方の決まりとして、この見出しを次のように書くよう定めています。

Driving it with <harness> starts with Preconditions: and uses labeled bullets that pair each user action with an exact command and observable result.

Driving it with <harness> は Preconditions: から始め、ラベル付きの箇条書きで、ユーザーの操作ごとに、正確なコマンドと観察できる結果を対にして書く。

前提条件（Preconditions:）とは、手順を始める前に満たしておく状態です。見本では、たとえば「Notes が http://127.0.0.1:4173 で正常に動いている」「Release checklist という題のメモがまだない」を挙げています。

前提条件の後には、手順を1項目ずつ並べます。決まりに従い、各項目には次の3つをそろえて書きます。

  • ユーザーの操作
  • その操作をハーネスで再現するコマンド
  • 操作が成功したと分かる、観察できる結果
- **Open editor.**
  Choose `New note`.
  Run `control-notes browser click --role button --name "New note"`.
  A form named `Note editor` appears with focus in the `Title` textbox.

この項目を具体化すると次のようになります。

要素 見本の記述 意味
ユーザーの操作 Choose New note. New note ボタンを選ぶ
ハーネスで再現するコマンド control-notes browser click --role button --name "New note" 役割がボタンで、名前が New note の部品をクリックする
観察できる結果 A form named Note editor appears with focus in the Title textbox. Note editor という名前のフォームが開き、Title の入力欄にカーソルが入る

エージェントは、コマンドを実行した後、表の「観察できる結果」になったかを確かめます。その結果にならなければ、エージェントは、この手順で失敗したと分かります。

Gotchas

見本は、次の落とし穴を書いています。

- Pressing `n` while a textbox has focus types the character instead of opening a new editor.
- A save status alone is insufficient proof. Reopen the note from the list.

1つ目は、「入力欄にフォーカスがあると、n キーは編集画面を開かず、文字の n を入力するだけ」という落とし穴です。

2つ目は、「保存しました」の表示だけでは値が本当に保存されたかは分からないので、「表示だけでは証拠にならず、一覧からメモを開き直して確かめる必要がある」という注意です。

また、記事のFeature Mapの例（設定画面の機能）は、Gotchas に次の注意を書いています。ここでいうタブは、設定画面の左側に並ぶ切り替えの項目（General、Appearance、Models、Plan & Usage など）です。

Some tabs are entitlement-gated. Skip with an explicit account reason.

一部のタブは、契約の状態によっては表示されない。飛ばすときは、アカウントの状態という理由を明記する。

Feature Mapにこう書いておけば、エージェントは、たとえば Plan & Usage のタブが見つからないとき、タブが出ないことを不具合と取り違えずに、「アカウントの契約状態のため表示されない」という理由を書いて、そのタブの確認を飛ばせます。

チームで共有する記憶

記事は、Feature Map を「具現化された記憶（materialized memory）」と呼んでいます（第4章）。

エージェントの記憶とは、以前の作業で得た知識を、次の作業でも使えるように残しておくものです。

この記憶の究極形はコードベースです。コードには、チームが下してきた判断が表れており、何が起き、実際にどう動いているかを示す正本だからです。

Feature Map は、コードベースという記憶を、エージェントのコンテキストウィンドウのトークンを節約するために、小さくまとめたものです。

また、Feature Map は、リポジトリの .cursor/skills/ に置かれた検証スキルの中のMarkdownなので、コードベースに関わる全員が、この記憶を共有できます。

検証スキルをどう作り、どう保つのか

検証スキルを作る手順そのものは、第26章で見たとおり、エージェントが /create-verification-skill に従って進めます。ここでは、記事が利用者に勧めている、作る前の準備と、作った後の保守の頻度を見ます。

作る前に、利用者が整えること

技術スタックの選び方

記事は、アプリを外から操作する手段を用意するうえで、技術スタックの選び方も重要になると指摘しています。技術スタックがデバッグや操作をしにくいほど、エージェントを生産的に使うのが難しくなるからです。

たとえば、エージェントは、Electron（デスクトップアプリを構築するためのフレームワーク）やWebのアプリならCDP（Chrome DevTools Protocol。ブラウザの開発者ツールと同じ機能を、外部のプログラムから使う仕組み）を、iOSのアプリならシミュレータを使って、アプリを操作できます。

一方、選んだ技術スタックに、エージェントが使えるデバッグの道具がない場合については、エージェントに道具を作ってもらう（例：lldb を使う、開発環境でアプリと一緒に動かす独自のパッケージを作る）か、今ある道具で済ませるしかありません。

しかし、poteto氏は、エージェントによる検証を非常に重要と考えているので、デバッグの道具を自作することや、別の技術スタックを選ぶことを提案しています。

I personally feel that agentic verification is so important that I would unironically suggest building your own rich debugging tools, or even choosing a different tech stack

個人的には、エージェントによる検証はとても重要なので、本気で、豊富なデバッグの道具を自作すること、さらには別の技術スタックを選ぶことさえ勧めたい。

私も、個人的には検証が非常に重要かつ有益なものであるため、選んだ技術スタックに検証の道具がない場合、poteto氏の提案を採用すると思います。

開発体験の準備

記事は、利用者に、アプリを動かす準備として、開発体験について、次の3つを考えておくよう勧めています。

  • 開発用データベースにシードデータ（開発やテストのために最初から入れておくデータ）を入れる方法
  • 認証とテストユーザーの用意の仕方、テスト環境やステージング環境へのAPIの呼び出し方
  • 開発環境を、いつも同じ手順でインストールし、立ち上げる方法

CLIとこれらの準備は、エージェントがアプリを開発するときの主な道具とみなされているため、保守し、テストしておく必要があります。

準備ができたら、利用者は /create-verification-skill を実行します。記事は、参考として、架空のアプリ向けに作った検証スキルの公開の見本 poteto/verification-skill-example を挙げています。

/maintain-verification-skill で最新に保つ

保守の結果の3種類（clean、changed、blocked）や、保守の間はプロダクトのコードを編集しない決まりは、第26章で見ました。ここでは、記事が勧める実行の頻度と、それを仕組みにする方法を見ます。

実行の頻度

/maintain-verification-skill の SKILL.md は、このSkillをどのくらいの頻度で実行するかを定めていません。/create-verification-skill を実行したエージェントも、利用者に聞かれたときだけ頻度を提案します。そのため、本書では、利用者が、アプリがどのくらいの頻度で変わるかに合わせて、実行の頻度を決めるものとして扱います。

記事は、少なくとも1日1回の実行を勧めています。

エージェントは、アプリの作業をしながら検証スキルを更新することもありますが、更新し忘れた箇所が残ることも、よくあります。

利用者が1日1回 /maintain-verification-skill を実行すれば、更新し忘れた箇所が見つかり、直されます。その結果、エージェントは、常に最新のアプリの操作方法を知ることができます。

Dr Eggbot で毎日の実行を仕組みにする

記事は、1日1回の実行を仕組みにする方法として、Dr Eggbot も紹介しています。

Dr Eggbot は、poteto氏（Lauren Tan）が作った、Grok Bot（AIのBotアプリ。第5章）を設計して作るBotです。xAI のBotのマーケットプレイスの紹介文は、Dr Eggbot を次のように説明しています。

Asks a few preference questions, then creates them with CreateAgent. Coding bots get the poteto-mode bar (one job, unslopped, verified).

いくつか好みを質問してから、CreateAgent でBotを作る。コーディング用のBotには、poteto-mode と同じ基準（1つの仕事だけを任せる、AIらしい言い回しを削る、動作を確かめる）を持たせる。

Dr Eggbot は、pstack と一緒に提供されます。
そのため、Dr Eggbot は、コーディング用のBotに pstack の使い方を教えられます。コーディングをしないBotも、同じ厳密さで作れます。

Dr Eggbotの推奨される利用方法は、次のとおりです。

  1. Dr Eggbot に、エンジニア役のBotを作ってもらう
  2. 作ったBotに、/create-verification-skill を実行してもらう
  3. 同じBotに、/maintain-verification-skill を1日1回実行するルーティンを設定してもらう

作った検証スキルを依頼でどう使い、どう広げるのか

利用者は、エージェントへの依頼に、どの検証スキルで確かめ、何を証拠にするかを書きます。

利用者が検証スキルを Grok Botのルーティンや Cursor Automations（Cursorで、決まった時刻やイベントをきっかけに処理を動かす機能）に組み込むのは、検証スキルに満足できてから行う必要があります（この章の『使い方3：ユーザーの報告を自動で再現する』）。

検証スキルの使い方

記事は、検証スキルの使い方の例を3つ挙げています。次の依頼例の /control-app は、/create-verification-skill で作った検証スキルを指す、記事での検証スキル名です。

使い方1：新しい機能を作る

新しい機能を作るとき、poteto氏は、/poteto-mode と検証スキルを一緒に使い、エージェントに自分の変更を確かめさせます。記事の依頼例は次のとおりです。

/poteto-mode build <description of feature, any useful context>. use /control-app to verify your changes and show me a video and screenshots as proof
// <機能の説明と、役に立つコンテキスト>を作って。/control-app で変更を確かめて。証拠として動画とスクリーンショットを見せて。

この依頼は、作る機能の説明に、どの検証スキルで確かめるか（/control-app）と、証拠の形式（動画とスクリーンショット）を添えています。

Grok Bot から依頼する場合、poteto氏は、Botに作業そのものをさせません。代わりに、Cloud Agents（Cursorのクラウド上でエージェントを動かす機能）のエージェントを起動するよう、Botに頼みます。次の依頼が、その例です。

spawn a cloud agent to use /poteto-mode to build <description of feature, any useful context>. use /control-app to verify your changes and show me a video and screenshots as proof
// クラウドエージェントを起動して、/poteto-mode で<機能の説明と、役に立つコンテキスト>を作らせて。/control-app で変更を確かめて。証拠として動画とスクリーンショットを見せて。

poteto氏がBotに作業をさせないのは、作業をクラウドのエージェントに任せれば、Botは別の作業を続けられ、Botのコンテキストウィンドウも作業の記録で埋まらないからです。

使い方2：性能を改善する

性能を改善するとき、poteto氏は、エージェントに、まず検証スキルで改善前の性能を測らせ、直した後に同じ検証スキルで改善を確かめさせます。記事の依頼例は次のとおりです。

spawn a cloud agent to use /poteto-mode to improve the initial loading time of our app. first use /control-app to take a trace of the status quo, and identify opportunities for improvement. then do a targeted fix and use /control-app + a /swarm to confirm the win
// クラウドエージェントを起動して、/poteto-mode でアプリの初回読み込み時間を改善させて。まず /control-app で現状のトレースを取り、改善の余地を見つけて。それから狙いを絞って直し、/control-app と /swarm で改善を確かめて。

この依頼は、直す前に、/control-app で現状のトレースを取るよう書いています。『Perf issue』Playbookも、最初の手順で改善前の基準となるトレースを取り、報告に改善前と改善後の数値とその差を書くよう求めています。

記事は、多数のWorkers（並列に動く複数のエージェント）を動かして一つの報告にまとめる /swarm（第24章）を、検証スキルと組み合わせるのに最も相性のよいSkillの一つとしています。

/swarm で多数の Cloud Agents に検証スキルを実行させれば、十分なサンプル数で性能の改善を確かめたり、ファジング（ランダムな入力や想定外の入力を大量に与えて、異常が起きないかを調べる手法）でアプリが壊れていないことを確かめたりできます。

使い方3：ユーザーの報告を自動で再現する

検証スキルに満足できたら、いよいよ利用者は、検証スキルを Grok Botのルーティンや Cursor Automations に組み込めます。どちらも、決まった時刻やイベントをきっかけに処理を動かす仕組みです。

記事の例では、Botが、Slackなどに届くユーザーのフィードバックを1件ずつ受け取り、クラウドのエージェントを起動して、報告された不具合の再現を自動で試みます。

このように、検証スキルと Feature Map の質が十分に高ければ、不具合の修正まで自動にすることも可能です。

エージェントを並列に動かす

検証スキルを使って何本かのPRをマージできるようになったら、次の段階は、エージェントをもっと並列に動かすことです。

エージェントが依頼を受けて、ほぼマージできる状態まで作業を進められるなら、利用者は、その間にほかのエージェントも動かせるからです。

worktree ではなく Cloud Agents を使う

記事は、並列に動かす方法として、worktree（1つのリポジトリに、作業ディレクトリを追加で作るgitの機能。第18章）ではなく、Cloud Agents を勧めています。本書も、Cloud Agents を勧めます。

記事が worktree を勧めないのは、worktree が、エージェントごとにリポジトリの作業ディレクトリを1つずつ増やすので、手元のマシンのストレージとリソースを多く使うからです。

リポジトリの大きさとマシンの性能次第で、worktree で並列に動かせるのは最大10体くらいだと予想できます。

私の経験でも、ローカルで並列に動かすには、worktree ごとにディレクトリを分け、アプリのポートがぶつからないよう工夫する必要がありました。作った worktree の管理や、消し忘れの手間もかかります。

一方、Cloud Agents のエージェントは、クラウドの実際のコンピュータを使えるので、依存関係をインストールしてアプリを動かし、動画やスクリーンショットを撮り、実際のユーザーと同じようにアプリを操作できます。

Cursorは、最初のビルドの後に環境のスナップショット（ある時点の状態をまるごと保存したもの）を取るので、以降の Cloud Agents のエージェントはすぐに起動します。また、エージェントは1体ずつ別のマシンで動くので、各エージェントが動かすアプリのインスタンス（起動中のアプリ1つ1つ）も、初めから分かれています。

https://x.com/poteto/status/2087977008253071816

poteto氏は、Xのポストでも、Cloud Agents を使う理由を次のように書いています。

worktrees are dead. cloud agents are the future. they've allowed me to massively orchestrate swarms of agents, all with their own computer. it's how i've been able to trust that my agents are actually doing what i want them to, because they can run their code, take videos and screenshots, and interact with UIs the same way users do.

worktree の時代は終わった。これからは Cloud Agents だ。Cloud Agents によって、それぞれが自分のコンピュータを持つエージェントの群れを、大規模に動かせるようになった。エージェントが本当に自分の望みどおりに動いていると信頼できるのも、エージェントがコードを実行し、動画やスクリーンショットを撮り、ユーザーと同じようにUIを操作できるからだ。

ただし、Cloud Agents には注意点もあります。

Cloud Agents のエージェントは、コマンドを、利用者の許可を待たずに自動で実行します。コマンドを打ち間違えても壊れるのはクラウドのマシンだけで、手元のPCは壊れません。

一方、リポジトリのコードはクラウドのマシンに渡されるので、それらが外へ持ち出される危険は残ります。
シークレット（APIキーのような秘密の情報）も同様のリスクがあります。

Cursorのドキュメントも、プロンプトインジェクション（エージェントが読む文章に、悪意のある指示を紛れ込ませる攻撃）による持ち出しの危険を、次のように書いています。

自動実行にはデータ流出のリスクがあります。攻撃者がプロンプトインジェクション攻撃を仕掛け、エージェントをだまして悪意のある Web サイトにコードをアップロードさせる可能性があります。

開発環境を整えてあれば、クラウドの環境を用意するのは大きな手間ではありません。

Cursorでは、開発環境の作り方をコード（.cursor/environment.json）で定義して（EAC: Environment as Code）、リポジトリに置けます。

検証スキルのために整えた開発環境の立ち上げ手順をこのファイルに書いておけば、どの Cloud Agents のエージェントも、同じ環境で作業を始められます。Cursorはブログで、この考え方を次のように書いています。

開発環境もそれ自体がプロダクトであり、そのユーザーはエージェントである

ちなみに、Cloud Agents のエージェントはクラウドのマシンで動くので、利用者がPCを閉じても作業は止まりません。私も、Cloud Agentsヘビーユーザーです。

https://zenn.dev/sc30gsw/articles/953334f11df507

最初の一歩として何から手を付ければよいか

最初の一歩は、利用者が、エージェントが自分のアプリを外から操作・観察できる手段があるかを確かめることです。

本書では、記事の流れにしたがって、/create-verification-skill と /maintain-verification-skill を含め、利用者が進める手順を次のように整理します。

  1. アプリを外から操作・観察できる手段（既存のハーネス、CDP、シミュレータ、自作の道具）を確かめる
  2. 開発環境を一貫した手順で立ち上げられるようにする（シードデータ、テストユーザー、テスト環境、分離）
  3. /create-verification-skill を実行し、CLIとFeature Mapを生成させる
  4. 生成物を一度、通しで動かし、証拠が残ったことを確かめる。CLIを、エラーなく動くように直す
  5. /maintain-verification-skill の頻度を決める
  6. 普段の依頼に、検証スキルの名前と証拠の形を書く
  7. 検証スキルを使って何本かのPRをマージできるようになり、検証スキルに満足できてから、Cloud Agents での並列化や、ルーティンと自動化に広げる

記事は最後に、CLIを改善し続け、検証スキルに重要なインフラと同じように投資し、当番制（oncall rotation。検証スキルが壊れたときに対応する担当者を、交代で決めておく仕組み）を置くことまで提案しています。

私は、この担当にGrok Botを置くことを提案します。
Grok Botで監査をし続け、作業自体はCloud Agentsに投げるという進め方を想定しています。

  • なぜ最初に作るのか・・・ 記事は、アプリ開発では検証スキルを最も重要なスキルとしており、pstackの多くのPlaybookも、アプリを操作する手段を前提にしているからです。
  • 何でできているのか・・・ 検証スキルの中心は、再実行できるCLIと、機能ごとのたどり着き方をまとめた Feature Map です。
  • どう作り、どう保つのか・・・ 利用者は、作る前に技術スタックと開発体験を整えます。作った後は、記事が勧めるように少なくとも1日1回 /maintain-verification-skill を実行し、Dr Eggbot のルーティンで仕組みにすることもできます。
