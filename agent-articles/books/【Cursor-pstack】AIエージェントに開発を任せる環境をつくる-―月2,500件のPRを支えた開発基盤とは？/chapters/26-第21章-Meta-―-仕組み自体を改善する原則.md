# 第21章 Meta ― 仕組み自体を改善する原則

この章では、次の1つの原則を扱います。

1. [Encode Lessons in Structure](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)

この原則は、繰り返し必要になる修正（同じ間違いを何度も直すこと）を、文章の指示ではなく仕組み（道具、コード、メタデータ、自動化）に組み込むよう求めます。

エージェントは、同じ注意を2回書くことになったら、その注意を文章で書き足すのをやめ、**lintのルールや実行時チェックにして、機械に守らせます**。

!

**実行時チェック**・・・ プログラムを動かしたときに、ルールが守られているかを確かめるコード

たとえば、日付を表示する直前に、日付が `2026/09/26` の形になっているかを確かめるコードは、次のようになります。

```
// 画面に表示する日付の文字列
declare const text: string;

// 実行時チェック：表示する直前に、日付の形を確かめる
if (!/^\d{4}\/\d{2}\/\d{2}$/.test(text)) {
  throw new Error(`日付の形が違います: ${text}`);
}
```

このコードは、プログラムが実際にこの行を動かしたときに初めて、形の違う日付に気づきます。

たとえば、エージェントは、「`internal/` のモジュールを外から import しないでください」という注意を、import を検査するlintのルールにします。

同梱ガイドのページ [`docs/guide/08-principles.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/08-principles.md) は、この原則だけを、meta（メタ）の原則として分けています。

この原則の役割は、他の23件の原則と異なります。

他の原則は、個々の作業の中での判断（例：症状ではなく原因を直す、元に戻せる作業は確認を待たずに進める）を決めます。  
一方、『Encode Lessons in Structure』は、作業で見つかった教訓を、lintのルールなど、次の作業の仕組みに変えます。

この原則は、**エラー、人間による訂正、予想外の結果のすべてを、学びのきっかけ**（原文では learning signal）と呼びます。

エージェントは、学びのきっかけを拾ったら、それを適切な場所（例：繰り返す修正ならlintのルール）へ送り、記録だけで終わらせずに、今すぐ直すか具体的なtodoを作ります（詳細は[『フィードバックのループ：訂正を仕組みに変える3段』](#%E3%83%95%E3%82%A3%E3%83%BC%E3%83%89%E3%83%90%E3%83%83%E3%82%AF%E3%81%AE%E3%83%AB%E3%83%BC%E3%83%97%EF%BC%9A%E8%A8%82%E6%AD%A3%E3%82%92%E4%BB%95%E7%B5%84%E3%81%BF%E3%81%AB%E5%A4%89%E3%81%88%E3%82%8B3%E6%AE%B5)を参照）。

[講演](https://x.com/poteto/status/2102050467505430555)でも、訂正の教訓を会話の中だけに残さず、再利用できる形でリポジトリに残すよう述べられていました（[第3章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a88ea5)、[第4章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dc9141)）。

この章では、この1件を、ルール、発火条件、pstack自身での使われ方の順に解説します。

!

本章の原則には、依頼例を載せていません。

本書では、依頼例を、pstackの同梱ガイド、[README](https://github.com/cursor/plugins/blob/main/pstack/README.md)、poteto氏のポストに記載があるものだけにとどめるものとします。原文に依頼例がない原則について本書で依頼例を作ると、pstackが想定していない使い方を示してしまうおそれがあるためです。

## ルール：繰り返す訂正を、最も強い仕組みに変えて指示を消す

原則『**Encode Lessons in Structure**』は、繰り返す注意を、文章の指示ではなく仕組みで守らせるよう求めます。

エージェントは、同じ注意を2回書いたと気づいたら、**その注意を守らせる仕組みを作り、指示の文章のほうは消します**。

原則がこれを求めるのは、**文章の指示が見落とされやすい**からです。

文章の指示は、読み手がその文に気づき、内容を覚え、そのとおりに従って、初めて守られます。

エージェントの場合、セッションが変わると、前のセッションの会話で受けた訂正は引き継がれません。エージェントが「覚えておきます」と答えても、その約束は次のセッションには残らないのです。

仕組みは、エージェントが覚えていなくても働きます。そのため、文章の指示を仕組みに置き換えれば、次のセッションのエージェントにも同じルールを守らせられます。

### 手順：仕組みにしたら指示の文章を消す

手順は次の3つです。

1. その指示を、lintのルール、メタデータのフラグ、実行時チェック、スクリプトにできるかを問う
2. 可能なら、仕組みにして、指示を消す
3. 不可能なら（機械では決められず、判断が必要なら）、指示を目立たせ、その指示を守らなかったときの失敗の例を添える

!

**メタデータのフラグ**・・・ ファイルの設定欄（frontmatter）に置く値

たとえば、pstackの各Principleの `SKILL.md` は、ファイルの冒頭の設定欄に、次の値を置いています。

```
---
name: principle-encode-lessons-in-structure
disable-model-invocation: true
---
```

このうち `disable-model-invocation: true` が、メタデータのフラグです。

このフラグは、エージェントが会話の内容から自分でこのSkillを選んで動かすことを止めます。「このSkillを自分から使わないで」と本文に文章で書く代わりに、設定欄の値で決めています。

#### 機械で判定できる指示は、lintのルールにして文章を消す

冒頭の「`internal/` のモジュールを外から import しないでください」なら、手順2に該当します。

エージェントは、ルールファイル（`AGENTS.md` など、エージェント向けのルールを書いたファイル）に次の文が書かれていたら、import を検査するlintのルールを追加し、ルールファイルからその文を消します。

AGENTS.md

```
前：ルールファイルに、文章で書いている
- internal/ のモジュールを、internal/ の外から import しない
```

eslint.config.js

```
// 後：次の設定を追加し、ルールファイルの文は消す（typescript-eslint を導入済みの前提）
import tseslint from "typescript-eslint";

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser },
    // internal/ の中どうしの import は許す
    ignores: ["src/internal/**"],
    rules: {
      "no-restricted-imports": ["error", {
        patterns: [{
          group: ["**/internal/**"],
          message: "internal/ のモジュールは、internal/ の外から import しないでください",
        }],
      }],
    },
  },
];
```

この設定があれば、`internal/` の外のファイルが `internal/` のモジュールを import すると、lintがエラーにします。そのため、ルールファイルに同じ注意を書いておく必要はなくなります。

このように、**機械で判定できる指示なら、仕組みが守らせるので、指示の文章は必要ありません**。

#### 機械で判定できない指示は、目立たせて失敗の例を添える

反対に、「エラーメッセージは、ユーザーが次に何をすればよいか分かるように書いてください」は、手順3に該当します。

機械ではメッセージの良し悪しを判定しにくいので、エージェントは、この指示を文章のまま目立つ場所に置き、悪いメッセージの例を添えます。

AGENTS.md

```
## 必ず守ること

- **エラーメッセージは、ユーザーが次に何をすればよいか分かるように書く**
  - 失敗の例：「エラーが発生しました」。ユーザーは、次に何をすればよいか分からない
```

このように、機械で判定できない指示なら、文章で残すしかないので、目立たせて失敗の例を添える必要があります。

#### 仕組みで直せるなら、仕組みだけを使う

原則は、**仕組みで直せるなら、仕組みだけを使う**よう求めます。

仕組みと指示を両方残すと、同じルールを2か所で管理することになり、片方だけが更新されたときに2か所の内容が食い違います。そのため、原則は、仕組みにしたら指示の文章を消すよう求めています。

たとえば、lintのルールだけを直し、ルールファイルの文を直し忘れると、ルールファイルを読んだエージェントは、古いルールのとおりにコードを書いてしまいます。

#### 同じ指示を何度も書くのは、仕組みが足りないことの症状である

原文は、指示の文章を「症状」（原文では symptom）と呼びます。

本書では、同じ指示を何度も書くことを、ルールを守らせる仕組みが足りないことの症状と読みます。  
この読み方に従うと、原則が求めているのは、**症状である指示を書き足すことではなく、原因である足りない仕組みを作ること**と読むことができます。

### 強さの順位：使える中で最も強い仕組みを選ぶ

複数の仕組みが使えるなら、エージェントは**状況が許す最も強いものを選びます**。

強い順に、次の4つが仕組みとなります。

1. **型で表現できない状態**（原文では unrepresentable state）・・・ ルールに反する状態を、型を用いて書けないようにします。ルール違反があると、コンパイルエラーが発生します。
2. **CIを落とすlintや禁止API**・・・ ルールに反する書き方や、使ってはいけないと決めたAPIをlintが検出すると、CIが失敗し、その変更は取り込めなくなります。
3. **正規のヘルパー**・・・ 決められた書き方をまとめた共通の関数（例：後に出てくる `formatDate()`）を用意し、コードからはその関数を呼ぶようにします。
4. **実行時チェック**・・・ 動かしたときに条件を確かめます。ルールに反するコードがあっても、その部分が実際に動くまで気づけません。

強いものを選ぶのは、**エージェントが、周りのコードがすでにしている書き方をまねてコードを書くから**です（[第4章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dc9141)）。

弱いガード（原文では guard。ルールを守らせる仕組みのうち、順位の低いもの）を置くと、その弱いガードが、次のエージェントがまねる、ひな形になります。

たとえば、弱いガードがひな形になる例として、日付の表示形式を実行時チェックだけで守っているケースを見てみましょう。

注文一覧の画面のコードは、日付を自分で整形し、表示する直前に「`2026/09/26` の形になっているか」を確かめています。次のエージェントは、発送一覧の画面を作るときにこのコードをまねて、同じように日付を自分で整形し、同じ実行時チェックを書き足します。

```
type Order = { id: string; orderedAt: Date };
type Shipment = { id: string; shippedAt: Date };

// 注文一覧の画面：日付を自分で整形し、表示する直前に形を確かめる
function orderRow(order: Order): string {
  const d = order.orderedAt;
  const mm = String(d.getMonth() + 1).padStart(2, "0");
  const dd = String(d.getDate()).padStart(2, "0");
  const text = `${d.getFullYear()}/${mm}/${dd}`;

  if (!/^\d{4}\/\d{2}\/\d{2}$/.test(text)) {
    throw new Error(`日付の形が違います: ${text}`);
  }

  return `${order.id} ${text}`;
}

// 発送一覧の画面：次のエージェントが上をまね、同じ整形と同じ実行時チェックを書き足す
function shipmentRow(shipment: Shipment): string {
  const d = shipment.shippedAt;
  const mm = String(d.getMonth() + 1).padStart(2, "0");
  const dd = String(d.getDate()).padStart(2, "0");
  const text = `${d.getFullYear()}/${mm}/${dd}`;

  if (!/^\d{4}\/\d{2}\/\d{2}$/.test(text)) {
    throw new Error(`日付の形が違います: ${text}`);
  }

  return `${shipment.id} ${text}`;
}
```

一方、正規のヘルパー `formatDate()` を用意し、ヘルパーを通さない日付の整形をlintで禁じておけば、次のエージェントがまねるのは `formatDate()` を呼ぶ書き方になります。

```
type Order = { id: string; orderedAt: Date };
type Shipment = { id: string; shippedAt: Date };

// date.ts：日付の整形は、正規のヘルパー formatDate() の一か所だけで行う
function formatDate(d: Date): string {
  const mm = String(d.getMonth() + 1).padStart(2, "0");
  const dd = String(d.getDate()).padStart(2, "0");
  return `${d.getFullYear()}/${mm}/${dd}`;
}

// 注文一覧の画面
function orderRow(order: Order): string {
  return `${order.id} ${formatDate(order.orderedAt)}`;
}

// 発送一覧の画面：次のエージェントも、上をまねて formatDate() を呼ぶ
function shipmentRow(shipment: Shipment): string {
  return `${shipment.id} ${formatDate(shipment.shippedAt)}`;
}
```

```
// eslint.config.js に次の設定を追加し、date.ts の外で日付を整形するコードを禁じる（typescript-eslint を導入済みの前提）
import tseslint from "typescript-eslint";

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser },
    ignores: ["src/date.ts"],
    rules: {
      "no-restricted-properties": ["error", {
        property: "getFullYear",
        message: "日付の整形には formatDate() を使ってください",
      }],
    },
  },
];
```

その結果、日付の整形は `formatDate()` の一か所に集まり、画面を追加するたびに同じ実行時チェックが増えることもなくなります。

このように、次のエージェントは置かれた仕組みの書き方をまねるので、使える中で最も強い仕組みを選ぶ必要があります。

### フィードバックのループ：訂正を仕組みに変える3段

エージェントが訂正を仕組みに変えるまでの流れは、次の3段です。

- **訂正を見逃さずに拾う**・・・ 人間が作業に割って入って直したときや、テストが落ちたときに、エージェントは、その訂正が一回きりか、繰り返し起きるパターンかを判断します。
- **訂正を正しいレイヤーへ送る**（原文では Route to the right layer）・・・ 一回きりのものはメモ（原文では brain note）へ、繰り返す修正はSkillかlintのルールへ、システム全体の問題はPrincipleへ送ります。
- **訂正の対応を最後まで済ませる**・・・ 記録するだけで終わらせず、今すぐ適用する（例：lintのルールを今すぐ追加する）か、具体的なtodo（例：「`internal/` の import を禁じるlintのルールを追加する」）を作ります。

3段のどこかで止まると、訂正は次の作業に反映されません。

原文は、避けるべきこと（アンチパターン）として次の3つを挙げています。

- **認めるだけで記録しない**・・・ 「覚えておきます」と答えても、その言葉は次のセッションに残りません。
- **記録するだけで正しいレイヤーへ送らない**・・・ 作るべきlintのルールをメモに書いても、lintのルールを実装しなければ、次のエージェントが同じ間違いを書いてもCIは落ちず、同じ訂正がまた必要になります。そのため、そのメモは無駄になります。
- **一件を直すだけで一般化しない**・・・ `internal/` を外から import していた1か所だけを直し、lintのルールを足さなければ、次のエージェントが別の場所で同じ import を書きます。一件を直しても、同じ間違いを生むパターンが残るからです。

## 発火条件

**同じ指示を2回目に書いている自分に気づいたとき**、または**同じ訂正が繰り返されている**と気づいたときです。

### スクリプトを作る場面で、似た2つの原則と見分ける

この原則と、『[**Build the Lever**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-build-the-lever/SKILL.md)』『[**Prove It Works**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)』の2つの原則は、どれも、エージェントがスクリプトを作るきっかけになります。

『Build the Lever』の原文は、3つの原則を次のように書き分けています。

- 『Build the Lever』は、目の前の仕事を速く、レビューしやすく片付けるための原則
- 『Prove It Works』は検証そのものをスクリプトにする
- 『Encode Lessons in Structure』は繰り返す指示を長く残るガードレールに変える

本書では、この書き分けを、作るスクリプトがどの問いに答えるかで整理します。

- **「目の前のこの仕事をどう片付けるか」**・・・ [第17章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a8e80b)の『**Build the Lever**』です（例：名前を一括で変えるcodemod）。
- **「この仕事は正しく終わったか」**・・・ [第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)の『**Prove It Works**』です（例：書き出したファイルの行を確かめるスクリプト）。
- **「同じ間違いを二度と起こさないにはどうするか」**・・・ 『**Encode Lessons in Structure**』です（例：`internal/` の import を禁じるlintのルール）。

## pstack自身が、この原則で作られている

**pstackは、自分の教訓も文章ではなく仕組みに残しています**。代表的な例は次のとおりです。

- **`/reflect`（[第34章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/f70847)）**・・・ 会話から集めた学びのうち、lintやスクリプトのほうが確実に強制できる項目は、Skillの文章に書き足さず、その仕組みを実装する仕事として、チームのバックログ（課題を管理する場所）に起票します。
- **`/correct`（[第35章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/fe17ab)）**・・・ エージェントが繰り返している間違いを、リポジトリの仕組みで起こせなくするSkillです。まず、間違いをコミットやレビューの履歴から種類ごとにまとめます。次に、種類ごとに、アーキテクチャ、型と lint、テスト、文書の順に、その間違いを止められる最も確実な手段を選びます。新しく作ったチェック（lint のルールやテスト）は、過去に実際に起きた間違いに当てて、本当に止められるかを確かめます。この原則が求める「繰り返す訂正を仕組みに変える」ことを、間違いを探すところから、仕組みが効くことを確かめるところまで、一通り行うSkillです。
- **`preferences.md`**・・・ 『[**Orchestrate**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)』Playbook（[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)）は、常設の指示（例：使うモデル、触ってはいけないパス）を1行に1つずつこのファイルに書き、すべてのサブエージェントの起動時と再開時にそのまま貼り付けます。指示は再開のたびに抜け落ちやすく、抜け落ちるたびに人間が指示し直すことになるからです。エージェントは、**同じ指示を言い直していると気づいたら、作業を続ける前に、その指示をこのファイルに1行足します**。

## まとめ

- **ルール**・・・ 同じ指示（例：「`internal/` のモジュールを外から import しないで」）を2回書いたら、lintのルールや実行時チェックのような仕組みにできないかを問い、できたら指示の文章を消します。仕組みは、使える中で最も強いもの（型、CIを落とすlint、正規のヘルパー、実行時チェックの順）を選びます。仕組みにできない指示は、目立たせて失敗の例を添えます。
- **発火条件**・・・ 同じ指示を2回目に書いたとき、または同じ訂正が繰り返されていると気づいたときです。
- **pstack自身での使われ方**・・・ `/reflect` は仕組みにできる学びを起票し、`/correct` は繰り返す間違いを仕組みで起こせなくし、『Orchestrate』Playbookは `preferences.md` の常設の指示をサブエージェントに毎回貼り付けます。

講演では、信頼は会話の量ではなく、リポジトリに残した検証方法、作業手順、制約の量で増える、と述べられていました。『**Encode Lessons in Structure**』は、そのうちの制約（例：lintのルール、型）を、訂正のたびに増やしていく原則です。
