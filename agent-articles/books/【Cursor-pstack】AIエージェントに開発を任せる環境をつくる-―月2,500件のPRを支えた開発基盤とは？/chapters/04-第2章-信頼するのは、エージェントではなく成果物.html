エージェントに仕事を任せるとき、信頼すべきなのはエージェントの報告ではなく、エージェントが作った成果物です。

これは、poteto氏が講演の最初のテーマ「信頼」で示した考えです。

この章では、成果物を信頼するとはどういうことか、そしてpstackがそれをどう形にしているかを解説します。

この章の構成

この章の構成は次のとおりです。

  • なぜ報告ではなく成果物を信頼するのか
  • 成果物を確かめるとは、何をどう確かめることなのか
  • 返答の何を見れば、任せてよいと判断できるのか
  • 安心して任せられる状態に、どう近づけばよいのか
  • まとめ：信頼の置き場所を、報告から成果物へ移す

なぜ報告ではなく成果物を信頼するのか

成果物を信頼するのは、報告は正しさの証明にならないからです。

エージェントの「直しました」「動くはずです」は、エージェントがそう判断した、という情報でしかありません。判断の材料がテストの合格なのか、コードを読んだ印象なのか、実際に動かした結果なのかは、報告だけでは分かりません。
人間が正しさを確かめるには、結局、自分で差分を読み、アプリを触るしかなくなります。

この状態のまま仕事を増やすと、確かめていない変更が増えるだけです。講演でも、検証できないまま処理量だけを増やせば、増えるのは成果ではなく不具合だと述べられています。人間が隣で見張っている間しか品質を保てないなら、それは任せたことにはなりません。

反対に、成果物を確かめられる状態になっていれば、人間は報告を信じる必要も、自分で全部を確かめ直す必要もなくなります。

pstackではこれを、検証機構（仕組み）として提供しています。poteto氏は『The Complete Guide to pstack』Part 1で、検証（verification）を「エージェントが自分の仕事を確かめられること」と定義しています。

成果物を確かめるとは、何をどう確かめることなのか

成果物を確かめるとは、実物を、エージェント自身が、証拠が残る形で確かめることです。
これを具体的に言い換えると、次の3つの条件になります。

  1. 実物を相手にする・・・ ビルドの成否やテストの件数ではなく、動いているアプリ、実際に書き込まれた値、実際に出力されたファイルを確かめる
  2. エージェント自身が実行する・・・ 人間が手でアプリを触るのではなく、エージェントが操作し、観察する
  3. 証拠が残る・・・ スクリーンショット、動画、トレース、コマンドの出力など、あとから人間が見て判断できるものが残る

pstackのファイルでどう支えられているか、条件ごとに見ていきます。

実物を相手にする

1つ目の条件は、原則『Prove It Works』が定めています。冒頭は次の一文です。

Verify every task output by checking the real thing directly. Do not infer from proxies, self-reports, or "it compiles."

すべての作業結果を、実物を直接確かめて検証する。代わりの指標、自己申告、「コンパイルが通った」から推測しない。

この一文は、ビルドやテストを禁じてはいません。禁じているのは、「コンパイルが通った」ことを、動いている証拠として扱うことです。ビルドやテストに加えて、実物を動かして確かめる必要があります。

SKILL.md の description は、確かめ方の例として、以下の3つを挙げています。

  1. 機能を実際に動かす
  2. 実際の値を読む
  3. 差分を見る

また、この原則は、避けるべき間接的な確かめ方の例として、キャッシュされたスクリーンショットを挙げています。スクリーンショットは成果物に見えますが、今回の変更を反映した画面かどうかが分からなければ、検証の根拠としては弱いということです。ここから、成果物を見るときはその成果物が今回の変更のあとに作られたものかまで確かめるのがよい、と読み取ることができます。

同じ考えは、エージェントがサブエージェントに仕事を任せる場面にも当てはめられています。/poteto-mode では、主エージェントがサブエージェントの報告をそのまま渡さず、差分を見てから返答するので、人間が受け取る返答は、その時点ですでに一度、成果物で確かめられたものになります（第8章）。

エージェント自身が実行する

2つ目の条件は、不具合の修正に使う『Bug fix』Playbook（playbooks/bug-fix.md）が支えています。このPlaybookでは、担当エージェントがアプリを操作する道具（Playbookは control系Skill と呼んでいます）を使い、不具合が起きたのと同じ環境で自分で再現し、修正も同じ環境で確かめます（第11章）。

アプリを操作する道具は、pstack本体には含まれていません。ブラウザやElectron（デスクトップアプリを構築するためのフレームワーク）向けの control-ui と、CLIやTUI向けの control-cli は、別のプラグイン cursor-team-kit に入っています。自分のアプリ専用の道具を作る方法は、第3章と第39章で扱います。

利用者に再現を頼めるのは、操作の手段が対象に届かない具体的な理由を述べ、しかも手段で行けるところまで操作したあとだけです。

たとえば、ログインの途中で実機の二要素認証が要り、道具ではその先に進めない場合なら、エージェントはそこまで操作したことと、止まった理由を添えて、利用者に再現を頼むことになります。

私は、この限定が大事だと考えます。人間に頼む道を残しつつ、頼むには理由が要る形にしているので、エージェントが手間を理由に確認を人間へ戻しにくくなります。

証拠が残る

3つ目の条件は、『Prove It Works』の節『Script the check when you can』が支えています。

The strongest proof is a deterministic script that re-runs the same comparison, not a one-time eyeball.

最も強い証拠は、一度きりの目視ではなく、同じ比較を再実行できる決定的なスクリプトである。

この節は、同じ比較を再実行できるスクリプトを作り、その実行結果を人間が見られる形に残すよう勧めています。再実行できるのはスクリプトで、人間が読むのは実行結果です。

証拠をリポジトリにコミットまでするのは、大規模な移植や移行のように、あとから履歴を監査する必要がある場合に限られます。確かめ方をスクリプトにする方法は第3章で扱います。

私が一番見落とされやすいと感じるのは、この3つ目です。1つ目と2つ目の条件を満たしていても、証拠が残らなければ、人間の手元に届くのは「確かめました」という報告だけで、この章の出発点に戻ってしまいます。

実際に検証の仕組みを作るときは、エージェントが確かめられるかだけでなく、確かめた結果が人間の見られる場所に残るかまで決めておくのがよいと思います。

返答の何を見れば、任せてよいと判断できるのか

返答を見るときは、「〜しました」という主張のそれぞれに、確かめた証拠が付いているかを見れば判断できます。

たとえば「不具合を直しました」とだけ書かれた返答は、正しいかどうか判断できません。直す前に不具合が出ていた出力と、直したあとに出なくなった出力が付いていれば、読む人が自分で判断できます。

pstackは、主張ごとに証拠か「推測」のラベルを求める

pstackでは、作業を始めるときに使う /poteto-mode（skills/poteto-mode/SKILL.md）が、返答の書き方として次のルールを持っています。

Every claim carries its evidence or its label in the same sentence. Measured, inferred, or guess.

すべての主張は、同じ文の中に証拠か、種類のラベルを持つ。測定したのか、推論したのか、推測なのか。

エージェントは、証拠があれば証拠を付け、証拠がなければ「推論です」「推測です」と正直に書きます。pstackに同梱されているガイドの検証のページ（docs/guide/06-verify-and-ship.md）も、同じ考えで返答の良し悪しを見分けています。

If a check couldn't run, a good reply says "inconclusive", and you should treat a confident reply without evidence as a red flag.

確認を実行できなかったなら、良い返答は「結論が出ない」と言う。証拠のない自信満々の返答は、危険信号として扱うべきだ。

たとえば、テストを実行する環境がなかったのに「修正しました、問題ありません」と返ってきたら、それは危険信号です。

証拠が付いた返答なら、読む人が自分で正しさを判定できる

同ページでは、変更の種類ごとに合った確認を挙げています。それをもとに、報告だけの返答と、証拠が付いた返答を並べると次のようになります。中央の列は、比べるために私が作った例です。

変更の種類 報告だけの返答 証拠が付いた返答
CLIの変更 「フラグを追加しました」 実際のコマンドを実行した出力
UIの変更 「表示を直しました」 変更した画面の流れを、動いているアプリで操作した記録
パーサーや移行処理 「変換処理を修正しました」 保存しておいた入力を流し直した結果
性能の改善 「速くなったはずです」 変更前と変更後のプロファイルの比較
保存処理の変更 「書き込むようにしました」 書き込んだ値を読み戻した結果

中央の列は嘘ではないかもしれませんが、正しいかを判定する材料がありません。右の列は、読む人が自分で判定できます。

「テストが通りました」だけでは、不具合が直ったとは判断できない

間違えやすいのは、「テストが通りました」を右の列に入れてしまうことです。
『Bug fix』Playbookの「修正を確かめる手順（手順4）」も、単体テストに合格しただけでは不具合が直ったとは判断できないとしています。テストで用意した条件で処理が動いても、報告された不具合が起きた操作で直ったかは、同じ操作を再現して確かめる必要があります。

テストが振る舞いを確かめているかは、関数が undefined を返しても通るかで点検する

テストがコードの振る舞い、つまり、コードを使う人が実際に受け取る結果を確かめているかどうかは、原則『Test Behavior, Not Implementation』で確かめられます。

この原則は、テストとは、コードを使う人と同じ方法でコードを呼び出し、その人が受け取る結果を具体的な期待値と比べるものだとしています。テストが実際にその結果を見ているかは、次の問いで点検されます。

The check: before you keep a test, ask whether it would still pass if every function it imports returned undefined. If yes, it observes no behavior and cannot fail for a defect.

確認：テストを残す前に、テストが読み込む関数がすべて undefined を返しても、そのテストがまだ通るかを問う。通るなら、そのテストは何の振る舞いも観察しておらず、欠陥があっても落ちることがない。

たとえば、関数が呼ばれたかどうかだけを確かめるテストは、関数が undefined を返しても通ります。この原則は、こうしたテストを書き直すか消すよう求めています。

ただし、この問いに合格しても、分かるのは「コードが返す結果を確かめているテストだ」ということだけです。不具合がないことの証明にはなりません。

『Bug fix』Playbookは、失敗時と成功時の出力を返答に並べさせる

最後に、返答に何が残るかを、不具合を直す『Bug fix』Playbookで確かめておきます。

同Playbookは、返答に書く内容を次のように定めています。ここでいう「再現」は、前の節で見たとおり、不具合が起きる操作を実際に行い、同じ不具合が起きることを確認する作業です。

Reply: what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.

返答：何が壊れていたか、根本原因、修正内容、どう確かめたか。再現が失敗していたときの出力と、通るようになったときの出力を、そのまま貼る。

不具合が出ていたときの出力と、出なくなったときの出力が、返答に並びます。

安心して任せられる状態に、どう近づけばよいのか

安心して任せられる状態へ近づくには、足りない確認を見つけ、それを一つずつ仕組みに移していくのが良いと思います。

まず、次の5項目で足りない点を探します。5項目は、この章で見てきた内容を、私が確認の形にまとめたものです。

確かめること 答えが「いいえ」なら
完了の条件は、実行して合否が出る形になっているか 依頼に「何ができたら終わりか」を追加する
エージェントは、実際のアプリや成果物を自分で動かせるか アプリを操作する手段を用意する（第3章）
動かした結果が、証拠として残るか スクリーンショット、出力、トレースを残す手順を決める
確かめられなかったとき、そう正直に返ってくるか 「結論が出ない」を許し、証拠のない成功報告を受け取らない
人間が席を外しても、上の4つが回るか 回らない部分を仕組みに置き換える（第3〜5章）

1つ目の「完了の条件」は、同梱ガイドの検証のページ（docs/guide/06-verify-and-ship.md）が、『State the finish condition up front』で扱っています。

Put what done means in the first prompt, in whatever words fit:

何をもって終わりとするかを、最初の依頼に、合う言葉で書く。

例として挙がっているのは次の依頼です。

/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
// このコマンドにJSON出力を加えて。テキスト出力は1バイトも変えない。JSONはパースできる。どちらもサンプルプロジェクトで実行する。証拠を見せて。

ガイドは、こう書くことで、エージェントは、満たしたかを感覚で決めるしかない目標ではなく、実行して確かめられる3つの確認を持つことになる、と説明しています。

完了の条件を書くと、2つ目以降の確認項目も一緒に決まります。「テキスト出力は1バイトも変えない」と書けば、変更前後の出力を比べる手順が要ります。「サンプルプロジェクトで実行する」と書けば、エージェントがそのプロジェクトを動かせる必要があります。

完了の条件を、実行して合否が出る形で書けないときは、仕様が決まっているか、合否を判定する手段があるかを見直すきっかけになります。

表の右の列にある仕組みの多くは、依頼文だけでは用意できません。アプリを動かす道具、証拠を残す手順、人間が席を外しても回る仕組みが要ります。これが第3章以降のテーマです。

まとめ：信頼の置き場所を、報告から成果物へ移す

  • なぜ報告ではなく成果物を信頼するのか・・・ 報告は正しさの証明にならず、見張っている間しか品質を保てない状態では任せたことにならないからです。
  • 成果物を確かめるとは何か・・・ 実物を、エージェント自身が、証拠が残る形で確かめることです。pstackでは、原則『Prove It Works』、/poteto-mode、『Bug fix』Playbookがこの条件を支えています。見落とされやすいのは、証拠が残ることです。
  • 返答の何を見るか・・・ 「〜しました」という主張のそれぞれに、確かめた証拠が付いているかを見ます。テストの合格は、そのテストがコードの振る舞いを確かめているときの判断材料の一つにすぎず、不具合がないことの証明にはなりません。
  • どう近づくか・・・ 5つの確認項目で足りないところを見つけ、それを一つずつ仕組みに移します。

『Prove It Works』をはじめとするVerificationグループの原則は、第19章で詳しく扱います。

信頼の対象がはっきりしたら、次は信頼を増やす方法です。一度だけ成果物を確かめても、次の変更で同じ確認ができなければ、信頼は積み上がりません。第3章では、信頼を高める3つの方法と、訂正した教訓を仕組みに残す方法を解説します。
