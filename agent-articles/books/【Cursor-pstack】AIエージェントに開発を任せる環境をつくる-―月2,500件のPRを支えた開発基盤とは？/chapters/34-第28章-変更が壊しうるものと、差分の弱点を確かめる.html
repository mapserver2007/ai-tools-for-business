この章では、次の2つのSkillを扱います。

  1. /blast-radius
  2. /interrogate

2つとも、書き終えた変更を調べるためのSkillです。どちらを使うかは、知りたいことで決まります。

選び方は次のとおりです。

  • 変更したファイルの外で何が壊れうるか（例：キャッシュに書く値の形を変えたら、同じキャッシュを読む別のサービスが壊れないか）・・・ /blast-radius
  • 差分のコードそのものに弱点がないか（例：空の入力や、2回実行したときに正しく動くか）・・・ /interrogate

この章では、2つのSkillを一覧にしたうえで、1つずつ、使いどき、手順、出力の3つの観点で解説します。原文に依頼例があるSkillには依頼例も示します。

最後に、2つの使い分けをまとめます。

この章の構成

この章の構成は次のとおりです。

  • 2つのSkillの一覧
  • /blast-radius は、変更が安全だと言える根拠を、コードを実行して示す
  • /interrogate は、別々のモデルのレビュアーが差分の弱点を探し、主エージェントが指摘を仕分ける
  • /interrogate は差分の中を、/blast-radius は差分の外を疑う
  • まとめ

2つのSkillの一覧

Skill 一言でいうと 主な問い
/blast-radius 変更したファイルの外で壊れるものを探し、変更が安全だと言える根拠を、本物のコードを実行して証明する この変更は何を壊しうるか
/interrogate 別々のモデルのレビュアーが同じ差分の弱点を探し、主エージェントが指摘を「対応する」「退ける」などの4つに仕分ける この差分の問題点を厳しく指摘してほしい

2つは、どちらも名前で呼ばれたときだけ動くSkillです。

2つの SKILL.md はどちらも、エージェントが会話の内容から自分で選んで動かすことを止める設定（disable-model-invocation: true）を持っています。そのため、2つが動くのは、利用者が名前で呼んだときか、/poteto-mode やほかのSkillが手順の中で名前を指定して呼んだときだけです。

2つを誰が呼ぶかは、次のように分かれます。

  • /interrogate・・・ /poteto-mode が、Playbookの手順と、節『Non-negotiables』の規則に従って呼びます。/architect も、手順の中で呼びます。利用者が名前で直接呼ぶこともできます。
  • /blast-radius・・・ /poteto-mode の『Non-negotiables』の規則にも、Playbookの手順にも、ほかのSkillの手順にも出てこないので、利用者が名前で呼んだときだけ動きます。

/blast-radius は、変更が安全だと言える根拠を、コードを実行して示す

/blast-radius は、小さく見える変更が、変更したファイルの外で何を壊しうるかを探し、「安全だ」と言える根拠を、コードを実行して確かめるSkillです。

もっともらしい影響範囲の説明は、正しくても間違っていても同じように説得力があるので、説明だけでは価値がありません。そこで、/blast-radius を使うエージェントは、「影響は小さいはずです」という文章ではなく、安全の根拠になる事実を、コードを実行して確かめた結果を返します。

使いどき：小さく見えて信用しきれない差分

小さく見えるのに信用しきれない差分について、ほかに何を壊しうるかを知りたいときです。

手順：変更が安全である根拠を実行で証明する

/blast-radius の仕事は、呼び出し元を並べることではありません。呼び出し元なら、エージェントが grep ですぐに一覧にできるからです。

grep では見えない壊れ方を見つけることが仕事です。たとえば、同じキャッシュを別の言語のサービスが読んでいれば、その壊れ方は呼び出し元の一覧には出てきません。

そのため、エージェントは、ライブラリのソース、実行のタイミング（例：非同期の処理がいつ動くか、画面を閉じるときの後片付け）、APIが返すJSON、DBの列、フィーチャーフラグのような、grep では追えない先まで見ます。

!

フィーチャーフラグ・・・ コードを書き換えずに、設定の切り替えで機能の有効・無効を切り替える仕組み（例：新しい画面を一部のユーザーにだけ表示する）

ただし、エージェントが時間をかけるのは、こうして見つけた「壊れるかもしれない」可能性を長く並べることではありません。変更が安全だと言える根拠を1つ見つけることです。

根拠が1つで足りるのは、危なく見える変更の多くが、ある一つの事実さえ成り立てば安全だと言えるからです。

たとえば、キャッシュを捨てる処理を変えた場合、「この呼び出しは、すでに無効になったキャッシュ項目を捨てるだけで、ほかには何もしない」という事実が成り立てば、まだ使う項目まで消えてしまう、といった心配の多くを一度に除外できます。

そこでエージェントは、その事実を見つけ、本物のコードを実行するスクリプトやテストで証明します。

大きな変更や広い範囲に及ぶ変更は、エージェントが /arena（第24章）で複数のモデルに調べさせます。モデルが違えば、見つける不具合も違うからです。

出力：安全の根拠と確かめた深さ、マージ前の最も手軽な確認

出力の5項目は次のとおりです。

  • 変わったこと（差分からは読み取りにくい変化も含める）
  • 変更を安全にしている一つの事実と、その証明
  • リスク（壊れ方、実在する file:line（ファイル名と行番号）、起きやすさと起きたときの損害、確かめ方）
  • 確かめて問題なしとしたものと、その理由
  • マージする前に実行すれば、実際に起きうる不具合を見つけられる、最も手軽なテストや再現の手順（書いたスクリプトを含む）

また、エージェントは、安全の根拠ごとに、どこまで確かめたかを5段階で示します。読み手が、その根拠をどこまで信用してよいかを判断できるようにするためです。

5段階は次のとおりで、番号が大きいほど確かになります。エージェントは、手間をかけすぎない範囲で、できるだけ大きい番号の段階まで確かめます。

  1. エージェントが、根拠を文章で述べただけ（それだけでは価値がない）
  2. エージェントが、根拠を裏づけるコードの行（file:line）や、呼んでいるライブラリのソースの該当行を示した
  3. エージェントが、心配している壊れ方（例：まだ使うキャッシュ項目が消える）に至る処理の流れを1段ずつたどり、その壊れ方まで届かないことを示した
  4. エージェントが、本物のコードを呼ぶスクリプトやテストを実行した（根拠が間違っていれば、はっきり失敗する）
  5. エージェントが、動いているアプリで実際に操作し、根拠どおりに動くことを確かめた

5段階の例として、先に挙げた「この呼び出しは、すでに無効になったキャッシュ項目を捨てるだけで、ほかには何もしない」という事実を確かめるケースを見てみましょう。各段階では、エージェントは次のことをします。

  • 1段目では、「無効な項目だけを捨てるはずです」と書くだけです。
  • 2段目では、項目を捨てる関数の file:line や、呼んでいるライブラリのソースの該当行を示します。
  • 3段目では、まだ使う有効な項目が渡った場合の処理の流れを1段ずつたどり、その項目が捨てる処理まで届かないことを示します。
  • 4段目では、アプリと同じライブラリを読み込んでその関数を呼び、有効な項目が残ることを確かめるスクリプトを実行します。根拠が間違っていれば、スクリプトははっきり失敗します。
  • 5段目では、動いているアプリでキャッシュを捨てる操作を実際に行い、有効な項目が残ることを確かめます。

このように、確かめた深さによって根拠を信じてよい度合いが変わるので、エージェントは根拠ごとにどの段階まで確かめたかを示す必要があります。

証明できなければ、エージェントは unproven（未証明）と書きます。

/interrogate は、別々のモデルのレビュアーが差分の弱点を探し、主エージェントが指摘を仕分ける

/interrogate は、/setup-pstack（第36章）で設定したレビュー用のモデルごとに1体のレビュアーを起動し、各レビュアーが「この差分はどこで壊れるか」を探しながらレビューし、主エージェントがその指摘を仕分けるSkillです。

モデルが違えば死角も違います。そのため、2つのモデルが独立に同じ指摘を挙げたなら、その指摘は本物の問題である見込みが高いと言えます。

使いどき：差分の弱点を複数のモデルに探してほしいとき

「敵対的にレビューして」「死角を見つけて」のように、厳しいコード品質の観点も含めて、差分がどこで壊れるかを探してほしいときです。

手順：レビュアーは、意図は受け入れたうえで、それを実現するコードの弱点を探す

主エージェントは、レビューする範囲（指定がなければ git diff main...HEAD）を決め、変更の意図を1段落で書き出します。意図は、利用者の依頼、コミットメッセージ、PRの説明から読み取り、確信が持てなければ利用者に聞いてから進めます。

そのうえで、既定では Opus と Grok の2モデルのレビュアーを読み取り専用で起動します。どのレビュアーにも同じ指示と評価の観点を渡すのは、指摘の違いが、役割の違いではなくモデルの違いから生まれるようにするためです。

主エージェントは、2つ以上のモデルが独立に挙げた指摘を最も重く見て、1つのモデルだけが挙げた指摘は、重みを下げて扱います。

レビュアーは、変更の目的（意図）は正しいものとして受け入れ、その目的をコードがうまく実現できているかを厳しく調べます。

たとえば、意図が「実行をキャンセルするとき、1件ずつ取得していた実行をまとめて取得し、N+1をなくす」なら、レビュアーは「まとめて取得するべきか」は問いません。代わりに、「まとめて取得するクエリが、キャンセルしてはいけない実行まで拾わないか」を調べます。

レビュアーに渡す評価の観点は次のとおりです。

  • 正しさ・・・ コードが意図どおりに動くかを見ます（例：空の入力、2回実行したとき、前回の実行が途中で止まっていたとき）。
  • 根本原因・・・ 根本原因を直しているか、症状を隠しているだけかを見ます（例：壊れた前提を、リトライで隠していないか）。
  • 構造の健全さ・・・ 変更がシステムの形になじんでいるかを見ます（例：検証が境界に集まっているか、新しいAPIを入れたのに古いAPIを残していないか）。
  • 検証・・・ コードが動くことを確かめる手段があるかを見ます（例：不具合の修正に、その不具合を再現するテストがあるか）。
  • 複雑さの予算・・・ その複雑さが、コードが果たす役割に見合っているかを見ます（例：呼び出し元が1つしかない抽象、まだない場合のための設定）。
  • セキュリティ・・・ 危ない入力の通り道がないかを見ます（例：ユーザーの入力が、確かめられないままSQLやシェルに渡っていないか）。

レビュアーは、これらの観点に加えて、外から見た動作を変えずに実装を大きく単純にする方法（例：条件分岐や補助関数を丸ごと不要にする書き換え）も探します。

このように、レビュアーは指摘を広く挙げます。その中から、好みの書き直しや、実際には起こらない仮定の話（例：呼び出し元がnullを渡せないのに「nullが来たら落ちる」と指摘する）を退けるのは、全体のコンテキストを持つ主エージェントの仕事です。レビュアーが見たのは差分と1段落の意図だけで、すでに試して退けた案や、コードの外にある制約を知らないからです。

出力：指摘を Act on、Consider、Noted、Dismissed に仕分ける

主エージェントは、中立の集計役ではなく実務的な上級エンジニアとして、すべての指摘を4つに仕分けます。例は、先のN+1をなくす差分をレビューした場合です。

分類 意味 例
Act on（対応する） 正しさ、セキュリティ、保守性に影響する本物の問題。実際のPRなら、マージを止める問題 まとめて取得するクエリが、キャンセルしてはいけない完了済みの実行まで拾う
Consider（検討する） 妥当だが、今対応するコストに見合うか判断しきれないもの 取得した結果をキャッシュすれば速くなるが、今の件数で必要かは分からない
Noted（記録にとどめる） 技術的には正しいが、今は対応しないもの 変数名を、もっと具体的にできる
Dismissed（退ける） 間違っている指摘、細かすぎる指摘、コンテキストを知らないために出た指摘。退ける理由を短く添える 「件数が多いと遅い」という指摘。件数はすでに呼び出し元で上限を決めているので退ける

Dismissed に理由を残すのは、主エージェントが何を、なぜ退けたかを利用者が読んで、納得できない指摘を自分の判断で拾い直せるようにするためです。

主エージェントが返すのは仕分けた結果だけで、指摘された変更を自動で適用することはしません。

依頼の例：意見の分かれる設計には、マージする前に使う

/poteto-mode の『Non-negotiables』は、意見の分かれる設計をマージする前に /interrogate を使うと定めています。また、/interrogate は、『Feature』Playbook、PRを作る『Opening a PR』Playbook、第24章の /architect からも呼ばれます。

同梱ガイドの 04-design.md には、次の依頼例があります。

/interrogate the whole branch, but skeptically. no nitpicks unless it's an actual bug or regression.
// ブランチ全体を懐疑的に見て。本物のバグやリグレッションでない限り、細かい指摘は必要ない。

敵対的なレビュアーは、重大な問題が見つからないと、細かい指摘で報告を埋めがちです。利用者がこの依頼例のように細かい指摘を禁じると、Act on に入る指摘が本物の問題に絞られ、読む価値のあるものになります。

/interrogate は差分の中を、/blast-radius は差分の外を疑う

どちらも「この変更は大丈夫か」を調べますが、/interrogate は差分の中を複数モデルにレビューさせ、/blast-radius は差分の外を見て安全の根拠を実行で証明します。

まとめ

  • /blast-radius・・・ 変更を安全にしている一つの事実（例：この呼び出しは、すでに無効なキャッシュ項目を捨てるだけ）を見つけ、本物のコードを呼ぶスクリプトやテストを実行して証明します。
  • /interrogate・・・ 既定では Opus と Grok のレビュアーが同じ差分の弱点を探し、主エージェントが指摘を Act on、Consider、Noted、Dismissed の4つに仕分け、退けた指摘にも理由を残します。
  • 使い分け・・・ /interrogate は差分の中を、/blast-radius は差分の外を疑います。
