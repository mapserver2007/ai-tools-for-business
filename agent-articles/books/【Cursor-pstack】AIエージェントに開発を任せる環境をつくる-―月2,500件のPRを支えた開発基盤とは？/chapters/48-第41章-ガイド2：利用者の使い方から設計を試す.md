## 「計画を信じない」は、「コードで計画する」という意味

pstackのREADMEは「計画を信じない」と書いていますが、これは、計画を捨てるという意味ではなく、**コードで計画する**という意味です。

[README](https://github.com/cursor/plugins/blob/main/pstack/README.md)の節『why are there no planning skills?』には、次の文があります。

> personally, i don't believe in planning. the best spec is code.
>
> 個人的には、計画を信じていない。最良の仕様はコードだ。

!

**プランモード**・・・ コードを書く前に、エージェントが計画を書くモードです。

記事の節『Working backwards』で、poteto氏は、プランモードを持つほとんどのツール（原文では harness）について、次のように書いています。

「**計画に実装の細部を書きすぎ、それ以外のことは書き足りない傾向がある**」

しかし、poteto氏は次のようにも書いており、計画そのものは立てています。

> The truth is that I do plan, but I do so through code.
>
> 実のところ、私も計画は立てている。ただし、それをコードで行っている。

**異なるのは、計画の方法です**。

本書では、**コードで計画するとは、何も考えずに実装を始めるのではなく、「作って確かめながら設計上の疑問を解いていくこと**」と考えます。

コードで計画する方法には、「使い方を書いたチュートリアル（[要点5](#%E8%A6%81%E7%82%B95%EF%BC%9A%E4%BD%BF%E3%81%84%E6%96%B9%E3%82%92%E5%85%88%E3%81%AB%E6%9B%B8%E3%81%8F)）」や、「実際に動かして比べるプロトタイプ（[要点7](#%E8%A6%81%E7%82%B97%EF%BC%9A%E8%A4%87%E6%95%B0%E6%A1%88%E3%81%AE%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%81%A7%E6%AF%94%E3%81%B9%E3%82%8B)・[要点8](#%E8%A6%81%E7%82%B98%EF%BC%9A%E7%96%91%E5%95%8F%E3%81%AF%E3%80%81%E5%AE%9F%E9%A8%93%E3%81%A7%E7%A2%BA%E3%81%8B%E3%82%81%E3%81%95%E3%81%9B%E3%82%8B)）を作って確かめること」などが該当します。

## 要点5：使い方を先に書く

人間は、実装の前に、エージェントに**READMEやチュートリアルで使い方を書かせ**、そこからAPIや内部設計を逆算させます。

### 記事の考え：READMEから書き始める

poteto氏は、使い方を先に書く開発手法として、「**README駆動開発**」を、記事の中で紹介しています。

!

**README駆動開発**・・・ 想定するユーザーに使い方を説明するREADMEから書き始め、実装とアーキテクチャへ逆算する開発の方法です。

READMEから書き始めると、開発者は、作るもの（APIなど）を使う側の立場で、使いやすさ（原文では developer experience）を考えざるをえなくなります。

たとえば、poteto氏は、Cursor社内のデスクトップアプリ用フレームワークであるDuneを作ったとき、まずエージェントにチュートリアルを書かせ、Duneでアプリを作るとどうなるかを確かめようとしたそうです。

実装の前に書いた使い方は、**人間にとっては完成形を理解する材料になり、エージェントにとっては実装後に動作を確かめる具体的な基準になります**。

ちなみに、当初は、エージェントに読みやすいチュートリアルを書かせるのは難しく、先に `/technical-writing` を作ることになった、とも書かれています（[要点6](#%E8%A6%81%E7%82%B96%EF%BC%9A%2Ftechnical-writing%E3%81%A7%E3%80%81%E6%96%87%E6%9B%B8%E3%82%92%E7%94%A8%E9%80%94%E3%81%94%E3%81%A8%E3%81%AB%E5%88%86%E3%81%91%E3%82%8B)）。

### pstack：/architect の出力も、使い方を先に書く

[`/architect`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md)（[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）の `SKILL.md` も、節『Outputs』で、**呼び出し側の使い方を先に書き、骨組みはその使い方から導く**と定めています。

> The caller's usage is written first and the type sketch derived from it.
>
> 呼び出し側の使い方を先に書き、型の骨組みはそこから導く。

!

- **骨組み**・・・ 型と関数の形だけを書き、中身はまだ書かないコードです。
- **webhook**・・・ 指定したURLにHTTPリクエストを送って、別のシステムにイベントを知らせる仕組みです（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）。

使い方から骨組みを導く例として、外部から届く webhook にレート制限（一定時間に受け付ける要求の数の上限）を設ける機能を考えてみましょう。

この機能は、記事の節『The workflow in practice』の例2の依頼（`we need to add rate limiting for external webhooks`）にも出てきます（[第42章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/166acb)の「例2）設計の依頼」）。

ここでは、同じ送り手（webhook を送ってくる外部のシステム）から受け付ける webhook を、1分あたり60件までに制限する例を見ていきます。

`/architect`に従って、エージェントが使い方を先に書き、そこから骨組みを導くと、次のようになります。

```
// 1. 先に、呼び出し側の使い方を書く
const limiter = createRateLimiter({ perMinute: 60 });

function handleWebhook(webhook: { senderId: string }): Response {
  if (!limiter.tryAcquire(webhook.senderId)) {
    return new Response("Too Many Requests", { status: 429 });
  }
  return new Response("OK");
}

// 2. 使い方から骨組みを導く：型と関数の形だけを書き、中身はまだ書かない
type RateLimiterOptions = { perMinute: number };
type RateLimiter = { tryAcquire(senderId: string): boolean };

function createRateLimiter(options: RateLimiterOptions): RateLimiter {
  throw new Error("not implemented");
}
```

1の使い方で `createRateLimiter` に `{ perMinute: 60 }` を渡すと書いたので、2の `RateLimiterOptions` の形が決まります。

また、1で `limiter.tryAcquire(webhook.senderId)` の結果によって「受け付けるかどうか」の条件分岐を書いたので、2の `RateLimiter` は、送り手のID（文字列）を受け取って真偽値を返す `tryAcquire` を持つ形に決まります。

関数の中身（`throw new Error("not implemented")` の部分）は、骨組みが決まった後の実装の段階で書きます（骨組みに沿って実装する段階について、記事が説明していることは、[第42章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/166acb)の要点9で見ます）。

このように、**使い方を先に書けば、型と関数の形は使い方から決まります**。

## 要点6：/technical-writingで、文書を用途ごとに分ける

エージェントは、`/technical-writing` で文書をチュートリアル、ハウツー、リファレンス、解説の4つに分け、**1つの文書に用途を混ぜません**。

### 記事の考え：用途の混ざったREADMEは読みにくい

poteto氏が `/technical-writing` なしでエージェントに書かせた、Duneの最初のREADMEは、読みにくいものだったそうです。

**チュートリアル、ハウツー、解説、リファレンスの役目が1つの文書に詰め込まれていた**うえに、AIらしい、もったいぶった文章で書かれていたからです。

そこでpoteto氏が作ったのが `/technical-writing` です（[第33章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)）。

!

- **[Diátaxis](https://diataxis.fr/)**・・・ 文書を、読み手の目的によって4つの種類（モード）に分ける考え方です。
- **`/unslop`**・・・ エージェントが、自分の書いた文章から、AIらしい癖（読み手に「機械が書いた」と気づかせる言い回しや書式。例：「お役に立てば幸いです」のような決まり文句）を、規則に沿って削るSkillです（[第33章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)）。

`/technical-writing` は、Diátaxis に沿って文書を分類します。  
また、`/technical-writing` は `/unslop` も使うので、**作る文書が読みやすくなります**。

### 記事の考え：/technical-writing をほかのSkillと組み合わせる

`/technical-writing` を含むpstackの多くのSkillは、組み合わさって効果を高め合います。

記事は、それが起こる場面として、利用者が自分のアプリの設計を考える段階（原文では design phase）を挙げています。

pstackのSkillを組み合わせて、豊富なコンテキストを引き出すことで、**エージェントは、問題の小さな一部分だけを見るのではなく、人間と同じように問題の本質的な部分を見られるようになります**。

!

- **検証スキル**・・・ エージェントがアプリを起動・操作して証拠を取るための、プロジェクト専用のSkillです（[第39章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)）。
- **仮想化**・・・ 長いリストのうち、画面に見えている部分だけを描画する仕組みです（[第40章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b4b9a1)）。

Skillを組み合わせる例が、3つの部分からなる次の依頼です。

```
(1) /recall my work fixing virtualization bugs and perf issues from the past 7 days. use /how and /why to understand how our current virtualization implementation works.
// 過去7日間に仮想化の不具合と性能問題を直した作業を思い出して。/how と /why を使って、今の仮想化の実装がどう動いているかを理解して。

(2) then use /poteto-mode planning and /technical-writing to come up with a new virtualization engine that categorically eliminates flickering and jittering. let's start by writing a tutorial on how i would use this new package to virtualize a React app
// 次に、/poteto-mode で計画を立て、/technical-writing を使って、ちらつきとガタつきを根本からなくす新しい仮想化エンジンを考えて。まずは、私がこの新しいパッケージでReactアプリを仮想化する方法のチュートリアルを書くところから始めて。

(3) after you write the plan, /teach me and prove to me why this new approach is superior to our current engine
// 計画を書いたら、/teach で教えて。この新しい方法が今のエンジンより優れている理由を、私に証明して。
```

`/technical-writing` は (2) に出てきて、新しいパッケージのチュートリアル、つまり[要点5](#%E8%A6%81%E7%82%B95%EF%BC%9A%E4%BD%BF%E3%81%84%E6%96%B9%E3%82%92%E5%85%88%E3%81%AB%E6%9B%B8%E3%81%8F)の「使い方」を書く役目を受け持ちます。

3つの部分の内容は、次のとおりです。

- **(1)**・・・ `/recall` で過去7日間の作業を思い出し、`/how` と `/why` で、今の仮想化の実装がどう動いているかを理解するよう頼みます。
- **(2)**・・・ (1) で集めた内容（以前に直した不具合など）を使って、ちらつきとガタつきを根本からなくす新しい設計を考えるよう頼みます。
- **(3)**・・・ 計画を書いた後で、`/teach` で説明し、新しいパッケージのほうが今のエンジン（今使っている仮想化を受け持つ部品）より優れていることを証明するよう頼みます。  
  （ここで、検証スキルのような質の高い道具が重要になります）

このように、**依頼の狙いは、過去の作業や今の実装についての豊かなコンテキストをエージェントに引き出させ、それを設計と証明に使わせることです**。

### pstack：1つの文書に1つのモード

[`/technical-writing`](https://github.com/cursor/plugins/blob/main/pstack/skills/technical-writing/SKILL.md) の `SKILL.md` は、節『Pick the mode first (Diátaxis)』で、**1つの文書に1つのモード**と定めています。

> One document, one mode.
>
> 1つの文書に、1つのモード。

エージェントは、文書の内容が読み手の何に役立つかを確かめる、次の2つの問いでモードを選びます。

- 行動のためか、理解のためか
- 学習のためか、仕事のためか

組み合わせごとのモードは次のとおりです（各モードの説明は記事に沿っています）。

- **行動と学習**・・・ チュートリアル。初めての人が、手順に沿って目に見えるものを作りながら学ぶ文書です。
- **行動と仕事**・・・ ハウツー。使い慣れた人が、実際に抱えている特定の問題を解くための手順を書いた文書です。
- **理解と仕事**・・・ リファレンス。APIや設定項目を、正確に漏れなく説明する文書です。
- **理解と学習**・・・ 解説。背景、設計上の選択、トレードオフを説明する文書です。

前述した、2つの問いは、文書全体にも、1つの文にも、使うことができます。

また、この `SKILL.md` は、チュートリアルの中にリファレンスの表を入れることを禁じており、分類してリンクするよう定めています。

たとえば、チュートリアルの途中に設定項目の一覧表を入れようとしたら、その表は理解のためのリファレンスなので、エージェントは、表を別の文書に分け、チュートリアルからその文書へリンクします。

詳しいルールは[第33章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)で解説したとおりです。

## 要点7：複数案のプロトタイプで比べる

人間は、エージェントの最初の設計をそのまま採用せず、**エージェントに複数の案を実際に作らせ、操作や測定の結果で採用する案を選択します**。

### 記事の考え：複数案のプロトタイプを作って比べる

poteto氏は、節『Measure a hundred times, cut once』で、**計画でよく見る失敗**として、次の2つを挙げています。

- エージェントの最初の設計をそのまま受け入れる
- 動かして確かめた結果（経験的な証拠）なしに、計画を作り込みすぎる

本書では、1つ目への対処をこの要点7、2つ目への対処を[要点8](#%E8%A6%81%E7%82%B98%EF%BC%9A%E7%96%91%E5%95%8F%E3%81%AF%E3%80%81%E5%AE%9F%E9%A8%93%E3%81%A7%E7%A2%BA%E3%81%8B%E3%82%81%E3%81%95%E3%81%9B%E3%82%8B)で解説します。

1つ目について、poteto氏の説明は次のとおりです。

人間がコードを書いていたころは、設計書を互いにやり取りし、設計が固まるまで何度も書き直すのが普通でした。

一方、エージェントとの作業では、人間が設計書を書くという手続きを、省略することができ、エージェントに設計書を書かせることが普通になっています。

問題は、「**エージェントが最初に返した設計を、人間がそのまま受け入れてしまう**ことがよくある」ということです。

poteto氏は、これを失敗と呼んでいます。

> With agents, while we can skip the ceremony of the design doc, I often see the mistake of accepting the first thing the agent gives back to you.
>
> エージェントとの作業では、設計書という手続きは省けるが、エージェントが最初に返してきたものをそのまま受け入れる、という失敗をよく目にする。

これがなぜ失敗と呼ばれるのか、という理由について、記事には言及がないものの、これは直感的にも経験的にも正しいと言えるのではないでしょうか。

実際に、**比べていない設計は、良いかどうかを判断できない**と私は考えています。

人間が設計書に、検討した別の案まで書き、何度も書き直していたのは、案を比べて、より良いものを選ぶためでした。  
最初の設計をそのまま受け入れると、この比べる作業がまるごと抜け落ちてしまいます。

この失敗に対処するのが、複数の案を作って比べる『[**Prototype**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)』Playbookです。

依頼例は次のとおりです。

```
/poteto-mode prototype a few options for <feature request>. use /control-app* and take videos/screenshots for me to review and choose from
// <機能の要望>の案のプロトタイプをいくつか作って。/control-app* で動画とスクリーンショットを撮って、私が見比べて選べるようにして。
```

記事の注釈（\*）は、`/control-app` が、『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)で作った検証スキルを指すと説明しています（[第39章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)）。

見た目を変えるプロトタイプでは、エージェントは使い捨ての試作を、アプリの中か作業用のディレクトリに作ります。

UIの操作を比べるときは、エージェントは2〜3の案を作り、簡単な切り替えスイッチで、表示する案を入れ替えられるようにします。

たとえば、メニューの開き方を3つの案で比べるなら、画面に「案A」「案B」「案C」のボタンを並べ、押したボタンの案でメニューが開くようにします。  
こうすると、同じ画面のまま、案を切り替えて見比べられます。

そのうえで、エージェントは、`/control-app` で各案を操作してスクリーンショットを撮り、実際のタイミングやレイアウトを測定します。

また、『**Prototype**』Playbookは、見た目の案だけでなく、機能や不具合修正の案を比べるのにも使えます。

### pstack：プロトタイプは、設計を決めるための使い捨ての道具

『**Prototype**』Playbookは、**プロトタイプを、設計を決めるための使い捨ての道具**と定めています。

始める前に、エージェントは、プロトタイプで「何を決めるのか」を明確に決めます。

決めるのは、次の3つです。

- どのレイアウトにするか
- どの操作方法にするか
- 画面の要素をどれくらい詰めて並べるか

動かして観察すれば、どれがよいかがわかる選択の場合は、次のようなことを決めます。

- どの挙動にするか
- どのタイミングにするか
- どの方法にするか

プロトタイプで決めることがなければ、エージェントはプロトタイプを作らず、新機能を作る『[**Feature**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/feature.md)』Playbookへ作業を回します。

人間が案を選んだ場合も、エージェントは、その案を、『**Feature**』Playbookへ渡します。

型やモジュールの形から決める必要があれば、`/architect` へ渡します。

## 要点8：疑問は、実験で確かめさせる

人間は、作って動かせば答えが出る疑問について、自分で答えたり、エージェントに人間の返事を待たせたりせず、**エージェントに実験で確かめさせます**。

計画が抽象的なうちは、レビューを重ねて作り込むこともしません。

!

- **実験**・・・ 小さく作って動かし、結果を確かめることです。
- **抽象的な計画**・・・ まだコードで形にしていない、文章だけの計画です。実装の細部まで書き込んだ長い計画でも、コードで形にしていなければ、抽象的な計画です。

### 記事の考え：疑問はプロトタイプで答え、抽象的な計画は敵対的にレビューしない

> 動かして確かめた結果（経験的な証拠）なしに、計画を作り込みすぎる

[要点7で挙げた2つ目の失敗](#%E8%A8%98%E4%BA%8B%E3%81%AE%E8%80%83%E3%81%88%EF%BC%9A%E8%A4%87%E6%95%B0%E6%A1%88%E3%81%AE%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%82%92%E4%BD%9C%E3%81%A3%E3%81%A6%E6%AF%94%E3%81%B9%E3%82%8B)への対処も、プロトタイプです。

poteto氏は、節『Measure a hundred times, cut once』で、**プロトタイプを作ることは、コードで計画すること**だと書いています。

**プロトタイプがあれば、エージェントは、人間の返事を待たずに、動かして確かめた結果で自分の疑問に答えられます**。

たとえば、エージェントは、「AとBのどちらが速いか」なら両方を動かして時間を測り、「この操作で画面が崩れるか」ならプロトタイプを操作して確認します。

節『Architecting bigger changes』の終わりで、poteto氏は、**プロトタイプと `/architect` を使ってコードで計画することが、はるかに効果的だ**と書いています。  
これが、抽象的な計画を敵対的にレビューしない理由でもあると続けています。

!

**敵対的なレビュー**・・・ 欠陥を探す立場で、エージェントに批判させることです。

抽象的な計画を敵対的にレビューしないのは、レビューさせると、エージェントが、**根拠のない、理屈の上だけのリスクを事実のように作り出す**からです。  
そして、起こりもしない問題に備えて、複雑な例外ケースを考え出します。

たとえば、エージェントは、計画に出てくる関数について「この関数に null（値がないことを表す値）が渡されたら、処理が落ちる」と指摘し、null が渡されたときの処理を計画に足すよう求めます。

コードがあれば、呼び出し元をたどって、実際に「null が渡されることがあるか」を確かめられます。

null を渡す呼び出し元がなければ、この指摘が求める処理は、起こりもしない問題への備えだとわかります。

しかし、**抽象的な計画には、たどれる呼び出し元がありません**。  
そのため、指摘は確かめられないまま事実のように扱われ、計画には、起こりもしない問題に備える例外ケースの処理が積み重なっていきます。

以上のことから、記事では、**計画が抽象的なうちは作り込まず、未解決の疑問は、エージェントにプロトタイプを作らせ、その結果を確かめさせて、エージェント自身に答えを出させる**ことが勧められています。

### pstack：エージェントは、人間に聞く前に、実験で答えが出る疑問かを見分ける

[`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md) の節『[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)』は、どのPlaybookの作業でも守る決まりを並べた節です（[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)）。

この節には、エージェントが人間に質問しそうになったときの決まりもあります。

対象は、次のような、進め方がいくつかに分かれる場面での質問です。

- どの方法にするか
- どう作るべきか
- これは何をすべきか

『Non-negotiables』は、こうした質問をする前に、**その答えが、実行して観察すればわかる事実かどうかを見分ける**よう、エージェントに求めています（[第38章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f8911)）。

回答が、実行すれば観察できる事実なら、人間が答えるべきことではありません。

観察できる事実には、次のようなものが該当します。

- 挙動
- タイミング
- レイアウト
- 出力
- 性能

回答がこうした事実になる疑問は、**エージェントが人間に聞かずに、『Prototype』Playbookで試して決めます**。

ただし、『Non-negotiables』は、作業が読み取りのみの調査（『[**Investigation**](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)』Playbook）で、成果物が根拠つきの回答である場合を例外としています。

この場合、エージェントはプロトタイプを作らずに、集めた証拠から答えます。

**エージェントが人間に聞くのは、試しても答えが出ない、プロダクト上の判断や好みです**。

次の2つの疑問で、この分類を確かめてみましょう。

「この操作で画面が崩れるか」は、プロトタイプを操作すれば観察できるので、エージェントが試して決めます。

一方、「2つのレイアウトのうち、どちらをこのプロダクトで採用するか」は、試しても答えが出ない、好みで決まる疑問です。画面がどう配置されるか（レイアウト）は観察できますが、どちらを選ぶかは観察しても決まりません。

そのため、エージェントは、画面を並べて見せたうえで、選択を人間に委ねます。

### pstack：/interrogate にかけるのは骨組みと差分

抽象的な計画を敵対的にレビューしないなら、pstackは何を敵対的にレビューするのでしょうか。

pstackには、複数のモデルに、変更を敵対的にレビューさせるSkill、[**`/interrogate`**](https://github.com/cursor/plugins/blob/main/pstack/skills/interrogate/SKILL.md) があります（[第28章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)）。

`/interrogate` は、レビュアーへの指示文で、レビュアーを「敵対的なコードレビュアー」と呼び、手助けや励ましではなく、本物の問題を探させるよう定義しています。

この `/interrogate` を使う場面は『Non-negotiables』で決まっており、**意見の分かれる設計は、マージする前に `/interrogate` にかける**ことになっています。

!

**意見の分かれる設計**・・・ 見る人によって、良い・悪いの判断が分かれる設計です（原文では contested design）。  
本書では、どれを選んでも正しく動く作り方が複数ある設計が、これに当たると考えます。たとえば、エラーの扱い方です。失敗を例外で知らせるか、戻り値で知らせるかは、どちらでも正しく動くため、意見が分かれます。

pstackの2つの `SKILL.md` を見ると、`/interrogate` にかける設計は、どちらも**コードの形になったもの**です。

- **差分**・・・ `/interrogate` の `SKILL.md` は、レビューする対象を、コードの変更（差分）としています。
- **骨組み**・・・ `/architect`（複数のモデルの設計案を、1つの骨組みに統合するSkill。[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）の `SKILL.md` は、実装を始める前に、統合した骨組み（型と関数の形だけを書き、中身はまだ書かないコード）を `/interrogate` にかけられると記載しています（節『Phase C: Agree (opt-in)』）。

コードの形になっていれば、レビューで出た指摘を、実物と照らして確かめられます。

`/interrogate` では、全体のコンテキストを持つ主エージェントが、レビュアーの指摘を確かめます。

先ほどの null の例のような、実際には起こらない仮定の話は、呼び出し元をたどれば問題ではないとわかるので、対応しなくてよい指摘として仕分けます（[第28章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)）。

このことから、本書では、「抽象的な計画を敵対的にレビューしない」を、「レビューをしない」という意味ではなく、**根拠を用意してからレビューする**という意味として読みます。

ここでいう根拠とは、骨組みや差分、利用例、プロトタイプ、測定結果のように、レビューする側が実物を見て確かめられるものを指します。

## まとめ

- **「計画を信じない」の意味**・・・ 計画を捨てるのではなく、コードで計画するという意味です。本書では、コードで計画するとは、作って確かめながら設計上の疑問を解いていくことだと考えます。
- **要点5：使い方を先に書く**・・・ 人間は、エージェントにREADMEやチュートリアルを先に書かせ、その使い方からAPIや内部設計を考えさせます。
- **要点6：/technical-writingで、文書を用途ごとに分ける**・・・ エージェントは、`/technical-writing` で文書をチュートリアル、ハウツー、リファレンス、解説の4つのモードに分け、1つの文書に用途を混ぜません。AIらしい癖は、`/technical-writing` が使う `/unslop` で削られます。
- **要点7：複数案のプロトタイプで比べる**・・・ 人間は、エージェントの最初の設計をそのまま採用せず、複数案のプロトタイプを作らせ、スクリーンショットや測定値で比べます。プロトタイプは、設計を決めるための使い捨ての道具です。
- **要点8：疑問は、実験で確かめさせる**・・・ 人間は、実験で答えられる疑問をエージェント自身に確かめさせます。人間が答えるのは、原則として、試しても答えが出ない、プロダクト上の判断や好みで決まる疑問だけです。本書では、「抽象的な計画を敵対的にレビューしない」を、骨組みや差分、利用例、プロトタイプ、測定結果のような根拠を用意してからレビューするという意味として読みます。

- 要点11：小さく検証できる作業に分ける
