# 第35章 繰り返す間違いを、リポジトリの仕組みで起こせなくする

この章では、[`/correct`](https://github.com/cursor/plugins/blob/main/pstack/skills/correct/SKILL.md) を扱います。

`/correct` は、エージェントが繰り返している間違いを、コミットの履歴やレビューのコメントから見つけ、その間違いを止める仕組み（例：型、lint のルール、テスト）をリポジトリに追加するSkillです。

poteto氏は、pstack の `0.15.9` を告知する[ポスト](https://x.com/poteto/status/2106542593656111276)を、次の1文で始めています。

> it's easy to fall into the trap of micromanaging your agents instead of correcting the environment that shapes its behavior.
>
> エージェントの振る舞いを形づくる環境を正すのではなく、エージェントを細かく管理するという罠に陥りやすい。

前の[第34章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/f70847)の `/reflect` は、学びをSkillの文章として残し、lint などの仕組みで守らせられる学びは、課題管理のツールに回しました。`/correct` は、その仕組みを、実際にリポジトリに追加するSkillです。

`/correct` は、間違いを止める手段を、次の4つの段に分けます。上の段ほど、間違いを確実に止められます。

1. **アーキテクチャ**・・・ 間違った書き方そのものができない構造にする
2. **型と lint**・・・ 間違った書き方を、コンパイルやCIで止める
3. **テスト**・・・ 間違った振る舞いを、テストで止める
4. **文書**・・・ 文書やエージェント向けのルールに書く。エージェントが読み飛ばすと、間違いを止められない

!

- **アーキテクチャ**・・・ コードの全体の構造。どのモジュールに何を置き、モジュール同士がどうつながるか
- **型**・・・ 変数や関数の引数が、どんな値を取れるかを決めたもの。型に合わない値を書くと、コンパイルが失敗する
- **lint**・・・ コードの書き方を、決めたルールに沿っているか自動で点検する道具（例：ESLint）
- **CI**・・・ 変更をpushするたびに、ビルド、lint、テストなどを自動で実行する仕組み。どれかが失敗すると、その変更は失敗として表示される（設定によっては、マージできなくなる）

**エージェントは、間違いの種類ごとに、止められる最も上の段を選びます**。

この章では、`/correct` について、役割、使いどき、手順、依頼の書き方の4つの観点で解説します。

## この章の構成

この章の構成は次のとおりです。

- 役割：同じ間違いを、次のエージェントが起こせないようにする
- 使いどき：同じ間違いを、繰り返し訂正しているとき
- 手順：間違いの種類を見つけ、止められる段のうち、最も上の段で直し、本当に止まるかを確かめる
- 依頼の書き方：`/correct` 単体で呼ぶか、`/architect` と組み合わせて呼ぶ
- まとめ

## 役割：同じ間違いを、次のエージェントが起こせないようにする

`/correct` の目的は、同じ間違いを、次のエージェントが起こせないようにすることです。そのために、**指示ではなく、仕組みをリポジトリに追加します**。

ルールファイル（`AGENTS.md` など、エージェント向けのルールを書いたファイル）に「〜しないでください」と書いても、エージェントが読み落とせば、同じ間違いが起きることがあります。一方、CIや型など、決定論的に（同じコードなら、毎回必ず同じ結果で）失敗させられる仕組みがあれば、エージェントが気づかなくても、間違いは止まります。

### エージェントは、開いたファイルしか見ず、近くの例をまね、最短の道を選ぶ

`/correct` は、前提を次のように書いています。

> Assume every contributor is an agent that sees only the files it opened, copies the nearest example, and takes the shortest path that compiles. Design the repo so a change that looks right from one file is right for the whole repo.
>
> このリポジトリのコードを変更するのは、自分が開いたファイルしか見ず、いちばん近くにある例をまね、コンパイルが通る最短の道を選ぶエージェントだと想定せよ。1つのファイルだけを見て正しく見える変更が、リポジトリ全体にとっても正しくなるように、リポジトリを設計せよ。

つまり、**リポジトリ全体を見ないエージェントでも、正しい変更しかできないようにする**、ということです。

この前提に含まれるエージェントの性質は、次の3つです。

- **開いたファイルしか見ない**・・・ 同じデータを別のファイルでも書き換えていても、気づきません。
- **いちばん近くにある例をまねる**・・・ 古い書き方が残っていれば、それをまねます（[第4章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dc9141)）。
- **コンパイルが通る最短の道を選ぶ**・・・ モジュールの内部を外から import できるなら、外向けの関数を使わずに、内部を直接 import します。

同じ前提は、`/architect`（[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）にも書かれています。第24章では、この3つの性質から起きる間違いを、コード例で示しています。

### 価値の高い順に、間違いをなくす手段を選ぶ

poteto氏は、以前のポストで、エージェントを訂正したときの考え方を、次のように書いています（[ポスト](https://x.com/poteto/status/2089067865098113024)）。

> every time you intervene and correct your agent, you should think about how to eliminate it entirely.
>
> in order of value:
>
> 1. categorically eliminate the problem through better architecture or choice of data structures
> 2. turn it into a lint rule or test so CI catches it
> 3. turn it into a skill or rule
> 4. have humans review the code to catch it (ngmi)
>
> エージェントに割って入って訂正するたびに、その訂正を完全になくす方法を考えるべきだ。
>
> 価値の高い順に：
>
> 1. より良いアーキテクチャやデータ構造を選んで、問題を根本からなくす
> 2. lint のルールかテストにして、CIで捕まえる
> 3. Skillかルールにする
> 4. 人間がコードをレビューして捕まえる（ngmi）

「ngmi」は、「not gonna make it」（うまくいかない）の略です。**人間のレビューは、価値が最も低い手段**です。

`/correct` の4つの段は、このポストの順番と、次のように対応します。

| ポストの順番 | `/correct` の段 |
| --- | --- |
| 1. アーキテクチャやデータ構造で、問題をなくす | 1. アーキテクチャでなくす |
| 2. lint のルールかテストにして、CIで捕まえる | 2. 型で書けなくする。書けてしまうなら、lint かCIのチェックを足す 3. 振る舞いをテストする |
| 3. Skillかルールにする | 4. 文書かエージェント向けのルールを、最後に書く |
| 4. 人間がレビューして捕まえる | （`/correct` は手段として挙げていない） |

[第21章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dd2d9f)の原則『[**Encode Lessons in Structure**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)』も、繰り返す間違いを止める仕組みを、強い順に次の4つと定めていました。文章で残すのは、仕組みにできない指示だけです。

1. 型
2. CIを落とす lint
3. 正規のヘルパー（決められた書き方をまとめた共通の関数。例：日付を整形する `formatDate()`）
4. 実行時チェック（プログラムの実行中に、値が正しいかを確かめる処理）

`/correct` は、この4つの上に、アーキテクチャの段を置いています。

私は、`/correct` を、この原則をそのまま実行できる手順にしたSkillだと考えます。履歴から間違いを探し、仕組みを作り、効くことを確かめるまでを、一続きの手順にしているからです。

### `/reflect` はSkillの文章を、`/correct` はリポジトリの仕組みを変える

`/reflect` と `/correct` は、どちらも、繰り返さないための学びを残すSkillです。違いは、残す先です。

| 項目 | `/reflect`（[第34章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/f70847)） | `/correct` |
| --- | --- | --- |
| 何を材料にするか | 今の会話のトランスクリプト（エージェントとの会話の記録） | 最近のコミット、取り消し（revert）、レビューのコメント、エージェント向けの指示のファイル、回避策を説明するコメント |
| 何を残すか | 既存のSkillへの追記や書き直し | アーキテクチャ、型、lint、CIのチェック、テスト。文章のルールは最後の手段 |
| lint などで守らせられる学び | Skillの文章にせず、課題管理のツールに回す | 自分で実装し、その仕組みが過去の間違いを本当に止めるかを確かめる |
| 利用者の承認 | Skillの編集の前に、利用者の明示の承認を待つ | 承認を待つ手順は書かれていない。ただし、仕組みに例外を設けるときは、人間の承認を得て、そのことを書き残す |

## 使いどき：同じ間違いを、繰り返し訂正しているとき

[README](https://github.com/cursor/plugins/blob/main/pstack/README.md) は、`/correct` の使いどきを、「同じ間違いについてエージェントを訂正し続けているとき」と説明しています。

`/correct` は `disable-model-invocation: true` の設定を持つので（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）、エージェントが自分でこのSkillを選ぶことはありません。`/poteto-mode` やPlaybook（作業の種類ごとの進め方を定めた手順書）の手順からも呼ばれません。このSkillを使うには、利用者が `/correct` と名前で呼びます。依頼の文の中に名前を書いても使われます（[依頼の書き方](#%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%2Fcorrect-%E5%8D%98%E4%BD%93%E3%81%A7%E5%91%BC%E3%81%B6%E3%81%8B%E3%80%81%2Farchitect-%E3%81%A8%E7%B5%84%E3%81%BF%E5%90%88%E3%82%8F%E3%81%9B%E3%81%A6%E5%91%BC%E3%81%B6)の例を参照）。

`/correct` の説明（description）は、利用者に訂正されるたびに、このSkillを使うよう求めています。**訂正のたびに使い、リポジトリを少しずつ間違えにくくしていくSkill**です。

poteto氏は、告知のポストで、コードベースを適切な制約で整えていく考え方を、盆栽にたとえています。

> i like to imagine that commits rapidly flowing into the codebase are like a bonsai tree rapidly growing in whatever direction it pleases. what you want to do is not to give in to the chaos, but tame it intentionally with the right constraints
>
> コードベースに次々と流れ込むコミットは、好き勝手な方向へ急速に伸びていく盆栽の木のようなものだと、私は想像している。すべきなのは、その混沌に身を任せることではなく、適切な制約で、意図して整えることだ。

## 手順：間違いの種類を見つけ、止められる段のうち、最も上の段で直し、本当に止まるかを確かめる

手順は次のとおりです。

1. 間違いの種類を見つける
2. 種類ごとに、止められる段のうち、最も上の段で直す
3. 直して、新しいチェックが過去の間違いを本当に止めるかを確かめる
4. ルールの表（ルールと、それを守らせる仕組みを対にした表）を保つ

ここからは、各手順を1つずつ見ていきます。例には、次の間違いを使います。

- リポジトリには、日付を表示用の文字列にする関数 `formatDate()`（`src/date.ts`）がある
- それなのに、エージェントが、画面のコードで日付を自分で整形してしまう

### 1. 間違いの種類を見つける

エージェントは、まず、次の5つを読みます。

- 最近のコミット
- 取り消し（revert）
- レビューのコメント
- エージェント向けの指示のファイル（`AGENTS.md` など）
- 回避策を説明しているコメント

そして、見つけた間違いを、種類（原文では class）ごとにまとめます。**扱うのは、2回起きた種類だけです**。1回だけでは、繰り返すかどうかが分からないからです。

たとえば、レビューで次の2つの指摘があったとします。

- 「注文一覧の画面で、`formatDate()` を使わずに、日付を自分で整形している」
- 「請求書の画面で、`formatDate()` を使わずに、日付を自分で整形している」

エージェントは、この2つを、「`formatDate()` を通さずに日付を整形する」という1つの種類にまとめます。

### 2. 種類ごとに、止められる段のうち、最も上の段で直す

エージェントは、種類ごとに、次の4つの段のうち、止められる最も上の段を選びます。

| 段 | 手段 | 間違いを止める時点 |
| --- | --- | --- |
| 1 | アーキテクチャで、間違いそのものをなくす | 間違った書き方が、そもそもできない |
| 2 | 型で、不正な状態を書けなくする。書けてしまうなら、lint かCIのチェックを足す | コンパイルか、CIで止まる |
| 3 | 振る舞いをテストする | テストで止まる |
| 4 | 文書やエージェント向けのルールを、最後に書く | 止める時点はない（読み飛ばされると止まらない） |

#### 1段目：アーキテクチャで、間違いそのものをなくす

`/correct` は、アーキテクチャでなくす方法として、次の5つを挙げています。

1. **状態の持ち主を1つにする**・・・ 1つの状態（例：ログイン中のユーザーの情報）を書き換えてよいモジュールを、1つだけにする
2. **作業のやり方を1つにする**・・・ 1つの作業（例：日付の整形）には、やり方を1つだけ用意する
3. **内部実装を隠す**・・・ モジュールの内部実装を外から見えなくし、外から import するとビルドが失敗するようにする
4. **一覧を1か所だけに置く**・・・ 同じ項目を並べた一覧を、何か所にも手動で書いてそろえるのをやめる。一覧は1か所だけに置き、ほかはそこから作る（例：言語を選ぶセレクトボックスの選択肢を、設定画面と登録画面のそれぞれに書くのをやめ、1つの一覧から両方の選択肢を作る）
5. **古いやり方と、使われていないコードを消す**・・・ エージェントがまねないように消す

1〜4は、`/architect` の8つの設計の危険信号（[`references/design-red-flags.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/references/design-red-flags.md)）のうち、次の4つに対応します。コード例は[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)にあります。

| `/correct` の方法 | `/architect` の危険信号 | エージェントが起こす間違い |
| --- | --- | --- |
| 状態の持ち主を1つにする | 持ち主が複数いる（Split ownership） | 書き換える場所の1つだけを直し、ほかの場所とルールが食い違う |
| 作業のやり方を1つにする | 1つの作業に2つのやり方（Two ways to do one task） | 最初に見つけたやり方をまねるので、どのやり方も呼び出し元が増え続ける |
| 内部実装を隠す | 外から import できる内部実装（Importable internals） | 内部実装を直接 import し、内部実装がインターフェースの一部になってしまう |
| 一覧を1か所だけに置く | 手動で同期する一覧（Hand-synced list） | 見えている一覧だけを更新し、ほかの一覧を更新し忘れる |

5は、`/correct` だけが挙げている方法です。

日付の例なら、古い整形の関数 `toDisplayDate()` が残っていれば、消して `formatDate()` だけにします（作業のやり方を1つにする）。

```
 // src/date.ts
 export function formatDate(date: Date): string {
   return date.toLocaleDateString("ja-JP");
 }
-
-// 古い整形の関数。エージェントがまねるので消す
-export function toDisplayDate(date: Date): string {
-  throw new Error("not implemented");
-}
```

ただし、JavaScript に最初からある `toLocaleDateString()` は消せません。エージェントは、これで日付を直接整形できてしまいます。そのため、2段目も必要です。

#### 2段目：型で書けなくする。書けてしまうなら、直し方を示す lint を足す

アーキテクチャでなくせないなら、不正な状態を型で書けなくします。たとえば、注文の状態を3つの文字列だけを取る型にすれば、ほかの文字列はコンパイルが通りません。

```
type OrderStatus = "pending" | "paid" | "shipped";

// つづりを間違えた "payed" は、OrderStatus の値ではないので、コンパイルが失敗する
const status: OrderStatus = "payed";
```

それでもコンパイルが通ってしまうなら、lint かCIのチェックを足します。このとき、**エラーメッセージには、代わりに使うファイル、型、関数のどれかの名前を書きます**。エージェントが、メッセージだけで直し方を分かるようにするためです。

日付の例なら、ESLint のルールは次のように書けます。

eslint.config.js

```
// 例：日付を toLocaleDateString() で直接整形するコードを禁じ、代わりの関数をエラーメッセージで示す
export default [
  {
    // formatDate() 自身は toLocaleDateString() を使うので、src/date.ts だけは対象から外す
    ignores: ["src/date.ts"],
    rules: {
      "no-restricted-syntax": [
        "error",
        {
          selector: "CallExpression[callee.property.name='toLocaleDateString']",
          message: "日付の表示には、src/date.ts の formatDate() を使ってください。",
        },
      ],
    },
  },
];
```

`no-restricted-syntax` は、指定した書き方を禁止する、ESLint の標準のルールです。エージェントが `toLocaleDateString()` を使うと、lint が、`formatDate()` を使うようエラーで示します。`src/date.ts` は、`formatDate()` の中で使うので、対象から外しています。

また、`/correct` は、**間違った書き方がすでに多く使われているなら、それが増えたときだけ失敗させる**よう求めています。既存の箇所がすべて直るまで待つと、チェックを入れるのが遅れるからです。

たとえば、`toLocaleDateString()` の呼び出しが、今のリポジトリに30か所あったとします。上の ESLint のルールをそのまま入れると、30か所すべてがエラーになり、CIが通らなくなります。

そこで、既存の30か所を記録し、増えた分だけをエラーにします。こうすれば、既存の30か所を直す前から、新しい間違いを止められます。

ちなみに、ESLint には、既存の違反を `eslint-suppressions.json` に記録し、増えた違反だけをエラーにする機能があります（`eslint --suppress-all` で記録します）。

#### 3段目：振る舞いをテストする

型や lint で止められない間違いは、テストで止めます。

このとき、**呼んだ関数が何も返さなくても通るテストは、直すか消します**。振る舞いを何も確かめていないからです。たとえば、次のように直します。

```
 test("注文の合計を計算する", () => {
-  // calcTotal が何も返さなくても、このテストは通る
-  calcTotal([100, 200]);
+  // 返した値を、期待する値と比べる
+  expect(calcTotal([100, 200])).toBe(300);
 });
```

この考え方は、[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)の原則『[**Test Behavior, Not Implementation**](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-test-behavior-not-implementation/SKILL.md)』と同じです。

#### 4段目：文書やエージェント向けのルールは、判断が必要なものだけ、最後に書く

**文書やルールは、最後の手段**です。読み飛ばされる可能性があるためです。読み飛ばされれば、ルールは守られません。

そのため、文書やルールに書くのは、機械では判定できないものだけにします。たとえば、「エラーメッセージは、利用者が次に何をすればよいかが分かる言葉で書く」のようなルールです。

### 3. 直して、新しいチェックが過去の間違いを本当に止めるかを確かめる

エージェントは、よく起きている種類から順に、すぐに直します。コミットは、種類ごとに分けます。

直したら、次の3つを行います。

- **新しいチェックが、過去の間違いを本当に止めるかを確かめる**・・・ たとえば、過去のコミットで日付を自分で整形していたコードに、新しい lint を実行し、エラーが出ることを確かめます。一度もエラーを出していないチェックは、効くかどうかが分からないからです。
- **手元とCIで、同じコマンドを実行する**・・・ 手元とCIで結果が食い違わないようにします。
- **例外は、違反している行に書く**・・・ ルールに従えない行には、ルールを無効にするコメントを書き、理由、期限、承認した人を添えます。

たとえば、次のように書きます。`eslint-disable-next-line` は、次の1行だけ、指定したルールを無効にするコメントです。

```
// 例：例外を、違反している行に、理由・期限・承認者とともに書く
declare const invoice: { issuedAt: Date };

// eslint-disable-next-line no-restricted-syntax -- 理由：外部の請求書の書式に合わせるため。期限：2026-12-31。承認：@reviewer
const issuedOn = invoice.issuedAt.toLocaleDateString("en-US");
```

### 4. ルールの表を保つ

最後に、エージェントは、エージェント向けの指示のファイルに、**ルールと、それを守らせる仕組みを対にした表**を作り、保ちます。

表は、たとえば次のようになります。

AGENTS.md

```
<!-- 例：ルールと、そのルールを守らせている仕組みの表 -->
| ルール | 守らせている仕組み |
|---|---|
| 日付の表示には `formatDate()` を使う | ESLint の `no-restricted-syntax` |
| `internal/` のモジュールを外から import しない | `package.json` の `exports`（外から import できるファイルを決める設定）で、内部を公開しない |
| エラーメッセージは、利用者が次に何をすればよいかが分かる言葉で書く | （機械では判定できないので、文章だけ） |
```

表の運用は、次のとおりです。

- **利用者に訂正されたら**・・・ エージェントは、間違いを直し、ルールを表に足します。
- **訂正された間違いのルールが表にあり、守らせる仕組みがなかったら**・・・ 「ルールを文章で書いただけでは、間違いを止められなかった」ということを意味します。エージェントは、今回の修正と同じ変更の中で、[手順2](#2.-%E7%A8%AE%E9%A1%9E%E3%81%94%E3%81%A8%E3%81%AB%E3%80%81%E6%AD%A2%E3%82%81%E3%82%89%E3%82%8C%E3%82%8B%E6%AE%B5%E3%81%AE%E3%81%86%E3%81%A1%E3%80%81%E6%9C%80%E3%82%82%E4%B8%8A%E3%81%AE%E6%AE%B5%E3%81%A7%E7%9B%B4%E3%81%99)をやり直し、その間違いを、止められる最も上の段で直します。
- **間違いが起こり得なくなったら**・・・ ルールを表から消します。

### 報告：種類ごとに、根拠、選んだ段、上の段を選べなかった理由を書く

エージェントは、間違いの種類ごとに、次の3つを報告します。

- 間違いが起きていた根拠
- 選んだ段
- それより上の段では直せなかった理由

日付の例なら、「レビューで2回指摘された（根拠）。2段目の lint で止めた（選んだ段）。`toLocaleDateString()` は JavaScript に最初からある関数なので、1段目では消せない（上の段を選べなかった理由）」のように報告します。

この理由を書かせることが、**エージェントが文章を書くなど、簡単な方法に逃げることを抑止するハーネスになっている**と言えます。

## 依頼の書き方：`/correct` 単体で呼ぶか、`/architect` と組み合わせて呼ぶ

[README](https://github.com/cursor/plugins/blob/main/pstack/README.md) は、`/correct` の依頼例として、Skillの名前だけを挙げています。

```
/correct
```

`/correct` は、履歴から間違いを探すので、**利用者は間違いの内容を説明しなくて構いません**。

一方で、**繰り返している間違いが分かっているなら、`/correct` の後にその間違いを書くこともできます**。同梱ガイドの[`09-make-it-yours.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/09-make-it-yours.md)は、次の例を挙げています。

```
/correct agents keep calling the database client directly instead of going through the repository layer
// エージェントが、リポジトリ層を通さずに、データベースのクライアントを直接呼び続けている
```

同梱ガイドの[`10-recipes-and-pitfalls.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md)も、次の例を挙げています。

```
/correct agents keep adding new config flags without registering them in the schema
// エージェントが、新しい設定のフラグを、スキーマに登録しないまま足し続けている
```

poteto氏は、告知の[ポスト](https://x.com/poteto/status/2106542593656111276)で、コードベースの設計を見直す依頼の例を挙げています。Grok Bot（[第5章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b6ac2d)）に渡す依頼です。

```
/poteto-mode create a new Project agent to refactor and rearchitect my repo so that our architecture is more agent friendly. it should use both the /correct and /architect skill to look through past commits and find the most common pitfalls that agents fall into, whether its with code quality, performance, or bugs. if relevant you can also use the /recall skill to find past conversations for context. it should make a high level plan for me to review. it should also answer its own open questions by prototyping rather than defer to me. come back to me with a plan backed by real data. once i approve the plan, use either the stack or full autopilot playbook (ask me which i want) to execute
// 新しい Project のエージェントを作って、アーキテクチャがエージェントにとってもっと扱いやすくなるよう、私のリポジトリをリファクタリングし、設計し直して。
// /correct と /architect の両方のSkillを使って過去のコミットを調べ、コードの品質でも、性能でも、不具合でも、エージェントが陥りやすい落とし穴のうち、最もよくあるものを見つけること。
// 関係があれば、/recall のSkillで過去の会話を探して、文脈をつかんでもよい。
// 私がレビューするための、大まかな計画を作ること。
// 自分の未解決の疑問には、私に任せずに、プロトタイプを作って答えること。
// 実際のデータに裏づけられた計画を持って戻ってきて。
// 私が計画を承認したら、stack か full autopilot のPlaybookを使って実行して（どちらにするかは私に聞いて）。
```

この依頼は、ほかの章で扱ったものを組み合わせています。

- **`/correct` と `/architect`**・・・ 過去のコミットから、エージェントが陥りやすい落とし穴を見つけさせます。`/correct` は、間違いの種類を見つけ、直す段を選びます。`/architect`（[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）は、エージェントにとって扱いやすい設計の候補を比べます。
- **`/recall`（[第22章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746)）**・・・ 過去の会話から、作業の経緯を集めます。
- **プロトタイプで疑問に答える**・・・ 実験で答えが出る疑問は、人間に尋ねずに確かめます。[第20章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/c155cc)の原則『Never Block on the Human』と同じ考え方です。
- **『Autopilot-stack』か『Autopilot-full』**・・・ 承認された計画を、多数のPRとして実行するPlaybookです（[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)）。どちらを使うかは、利用者に尋ねるよう指示しています。

利用者が行うのは、計画の承認と、Playbookの選択だけです。間違いを探すことと、疑問を確かめることは、エージェントに任せています。

## まとめ

- **役割**・・・ エージェントが繰り返す間違いを、文章の指示ではなく、リポジトリに追加した仕組みで起こせなくします。前提にあるのは、エージェントが「開いたファイルしか見ず、近くの例をまね、コンパイルが通る最短の道を選ぶ」という動きをすることです。
- **使いどき**・・・ 同じ間違いを繰り返し訂正しているときに、利用者が `/correct` と呼びます。訂正のたびに使います。
- **手順**・・・ 2回以上起きた間違いを、種類にまとめます。種類ごとに、次の4つの段のうち、止められる最も上の段で直します。

  1. アーキテクチャ
  2. 型と lint
  3. テスト
  4. 文書

  そのうえで、新しいチェックが過去の間違いを止めるかを確かめ、ルールと仕組みを対にした表を保ちます。

次の[第36章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8487f0)では、pstackを導入し、役割ごとに使うモデルを決める [`/setup-pstack`](https://github.com/cursor/plugins/blob/main/pstack/skills/setup-pstack/SKILL.md) を扱います。
