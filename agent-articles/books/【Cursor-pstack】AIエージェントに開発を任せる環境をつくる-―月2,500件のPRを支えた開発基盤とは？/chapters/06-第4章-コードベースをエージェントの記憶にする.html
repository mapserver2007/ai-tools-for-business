エージェントが前回までの判断を引き継ぐための記憶は、モデルの中ではなくコードベースに置きます。

これは、poteto氏が講演の3つ目のテーマで示した考えです。

この章では、知識をリポジトリに置く理由と、残した記憶を選び、メンテナンスし続ける方法を解説します。

この章の構成

この章の構成は次のとおりです。

  • なぜ知識をモデルではなくリポジトリに置くのか
  • 残した記憶はどう古くなり、どうメンテナンスするのか
  • 何を消せば、次のエージェントの手本を汚さずに済むのか
  • メンテナンスの仕事を、どう続けるのか
  • まとめ：記憶は増やすものではなく、選んでメンテナンスするもの

なぜ知識をモデルではなくリポジトリに置くのか

知識をリポジトリに置くのは、エージェントが一度に扱えるコンテキストには限りがあり、必要な知識を毎回プロンプトに詰め込むことはできないからです。

過去の判断、既知の問題、再現手順、回避策を、毎回すべて依頼に含めることはできません。

そこで知識をリポジトリに置けば、エージェントは毎回ゼロから考えるのではなく、そこに残された情報を読みながら仕事を続けられます。

ここでいう記憶は、コードだけではありません。以下も、過去の判断を次のエージェントへ伝える記憶として機能します。

  • Feature Map（アプリの機能ごとに、何ができるか、ユーザー視点での機能への到達手順、検証スキルでの操作方法と確認できる結果をまとめた文書。次の節で詳しく見ます）
  • 再現手順
  • 設計上の制約
  • テスト
  • lintルール

poteto氏は『The Complete Guide to pstack』Part 1でも、同じ考えを書いています。

Personally, I think your codebase is the ultimate form of memory.

個人的には、コードベースこそ究極の記憶だと考えている。

poteto氏は、その理由を、エージェントの記憶によく使われるMarkdownのメモなどと違い、コードはチームが下してきた判断そのものを映していて、実際に何が起き、どう動くのかについて信頼できる情報源だから、と説明しています。

残した記憶はどう古くなり、どうメンテナンスするのか

残した記憶のうち、メンテナンスが必要となるのは、Feature Mapのように、アプリ側が変わっても何も知らせずに古くなる記憶です。

テストやlintは、アプリと食い違えばCIが落ちるので、古くなったことに気づけます。一方、Feature MapのようなMarkdownの文書は、アプリが変わっても何も起きません。

pstackに同梱されているガイドの検証のページ（docs/guide/06-verify-and-ship.md）も、次の一文でメンテナンスの説明を始めています。

Apps change and feature maps rot.

アプリは変わり、Feature Mapは腐っていく。

古くなったFeature Mapを渡されたエージェントは、書かれていることを信じて操作し、もう存在しない画面を探して時間を使うことになります。

この節では、Feature Mapが何か、そしてpstackがFeature Mapをどうメンテナンスするかを見ていきます。

Feature Mapは、機能ごとの使い方と確かめ方をまとめた地図

Feature Mapは、アプリの機能ごとに、何ができるか、ユーザーが機能にどうたどり着くか、検証スキルでどう操作し、どんな結果を確かめるかをまとめた文書です。

Feature Mapがあれば、エージェントはコードベース全体を読まなくても、必要な機能のファイルだけを読めば済みます。『The Complete Guide to pstack』Part 1は、Feature Mapを、コンテキストのトークンを節約できる記憶の形の一つと説明しています。

pstackでは、/create-verification-skill が検証スキル（第3章）を作るときに、Feature Mapも一緒に作ります。ファイルの形式や書く内容は、第39章で扱います。

Feature Mapは、/maintain-verification-skill で最新に保つ

Feature Mapは、/maintain-verification-skill で、今のアプリと合っているかを繰り返し確かめます。実行する頻度などの詳細は、第39章で扱います。

同梱ガイドの検証のページ 06-verify-and-ship.md によると、/maintain-verification-skill は次の順で動きます。

  1. 機能ごとに、ソースを読むだけの担当（サブエージェント）を並列に走らせる
  2. 地図に載った全機能を、実際に動かして確かめる
  3. 結果を、以下のどれか1つで返す - clean・・・ 地図に載った機能をすべて確かめ、直すところがなかったこと - changed・・・ 食い違いを直し、確かめた修正を1つのPRにまとめたこと。修正は検証スキルのディレクトリの中に限られる - blocked・・・ 確かめを続けられず、何が妨げになったかを報告すること

同ページは、さらに次のように書いています。

It never edits product code. If the live pass catches a product regression, it reports the regression instead of papering over it in docs.

製品のコードは決して編集しない。実際に動かす確認で製品の不具合が見つかったら、文書で取り繕わずに、不具合として報告する。

アプリと記憶が食い違ったとき、/maintain-verification-skill は、記憶のほうを書き換えて辻褄を合わせることはしません。

食い違いには、2つの場合があります。

  • アプリが変わった場合・・・ 記憶のほうが古いので、記憶を直すこと
  • アプリが壊れた場合・・・ アプリのほうが間違っているので、記憶は直さずに不具合として報告すること

2つ目の場合に記憶のほうを直してしまうと、壊れた挙動が正しい挙動として記憶に残ってしまいます。

Feature Mapの作り方とメンテナンスの手順は、第26章と第39章で扱います。

何を消せば、次のエージェントの手本を汚さずに済むのか

消すべきなのは、場当たり的な回避策と、同じことをする2本目の書き方です。

どちらもコードとして残り、次のエージェントに手本として読まれるからです。次に、回避策、2本目の書き方の順に見ていきます。

残した回避策は、次のエージェントの手本になる

回避策は、残せば次のエージェントにコピーされるので、原因を直したら消します。

何でも記憶として残せばよいわけではありません。場当たり的な回避策を残すと、次のエージェントがそれを正しい実装例だと思ってコピーし、そのコピーがまた次のコピーを生んで、望ましくないパターンが静かに広がっていきます。

pstackの原則にも、同じ危険に触れた記述が2つあります。

  • 『Encode Lessons in Structure』・・・ 第3章で見たとおり、同原則は、エージェントは周りのコードがしていることを真似するので、弱い仕組みがそのまま次のコードの手本になる、と説明しています。
  • 『Fix Root Causes』・・・ 同原則は、症状への対処は積み重なるとし、次のように書いています。

If a workaround needs a paragraph-long comment to justify it, the code is wrong.

回避策を正当化するのに段落ほどのコメントが要るなら、間違っているのはコードのほうだ。

pstackは、回避策が残らないよう、手順の中でも防いでいます。不具合の修正に使う『Bug fix』Playbook（playbooks/bug-fix.md）は、手順の前に次のように書いています。

Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated.

「効くかもしれない」念のための対処は、修正ではなく仮説である。それは入れない。証拠が仮説を否定したら、その仮説のために入れた変更を元に戻す。

本書では、この規則は、試しに入れた変更が回避策としてそのまま残るのを防ぐものだと読みます。

推奨される実装方法を一つに絞り、「舗装された一本の道」を作る

同じ目的の書き方が2つ以上あるなら、推奨する1つを残して古いほうを消し、それ以外の書き方はlintで止めます。

技術的負債を取り除いて推奨する実装方法を一つに絞り、アンチパターンはlintなどで機械的に見つけます。そうすれば、エージェントは複数の方法から毎回選ぶ必要がなくなります。

講演では、この標準的な実装方法を「舗装された一本の道」と表現しています。エージェントが毎回独自の近道を探さずに、整備された経路を進める状態を意味しています。

pstackの原則にも、この道を舗装するためのものがあります。READMEの原則の一覧では、以下の2つが次のように要約されています。

  • 『Subtract Before You Add』（principle-subtract-before-you-add）・・・ 不要なもの、重複した検証、中身のない参照を先に取り除き、単純になった土台の上に作る
  • 『Migrate Callers Then Delete Legacy APIs』（principle-migrate-callers-then-delete-legacy-apis）・・・ 外部との互換性を保つ必要がないなら、古いAPIを使うコードを新しいAPIに切り替え、古いAPIも同じ変更の中で削除する。互換レイヤー（古いAPIを使うコードが動き続けるように残すレイヤー）として古い方法を支えるコードは残さない

互換レイヤーを残すと、コードベースには同じことをする道が2本残り、エージェントにとってはどちらも手本になります。それぞれの原則は第17章と第18章で詳しく扱います。

本書では、どの書き方を一本の道にするかは、人間が決めることだと考えます。人間の役割は方針を決め、最終的な責任を持つことで（第5章）、一本の道を決めるのは、この「方針」に当たると読めるからです。

メンテナンスの仕事を、どう続けるのか

メンテナンスの仕事は、pstackの部品を使って続けます。

講演では、この環境を維持する仕事が「庭師」にたとえられています。庭は植物を増やすだけでは保てず、不要な枝や雑草を取り除き、望ましいものが育つようメンテナンスし続ける必要があります。

コードベースも同じで、知識を追加するだけでなく、古い回避策や悪い実装例を取り除き続けなければなりません。

pstackには、こうしたメンテナンスを助ける部品があります。

メンテナンスの仕事 助けるpstackの部品
同じ指摘を2回したら、仕組みにする 原則『Encode Lessons in Structure』（第3章、第21章）
lintや型のチェックを止めるコメントが増えていないかを見る /no-comments （不要なコメントを取り除くSkill）。「サブエージェントの報告と差分を点検する手順（手順2）」で、見落とされたlintやTypeScriptのチェックの抑制を点検するよう求めている（第32章）
「消すな」「変えるな」と書かれたコメントを、型やテストやlintに置き換える /no-comments の「制約を書いたコメントを扱う手順（手順5）」。型、実行時チェック、テスト、CIのlintのうち、最も手軽なものへの置き換えを提案する
同じ目的の書き方が2つ以上ないかを探し、一本にする 原則『Subtract Before You Add』、原則『Migrate Callers Then Delete Legacy APIs』（第17章、第18章）
Feature Mapや再現手順が、今のアプリと合っているかを確かめる /maintain-verification-skill（第26章）
長い作業で学んだ手順を、次回のために残す /reflect。READMEでは、終わった長い作業の手順をSkillの編集として残すSkillとされている（第34章）

このように、pstackには、コードを書くためのSkillだけでなく、回避策やチェックを止めるコメント、古いAPIを取り除いたり、制約を書いたコメントを型やlintに置き換えたりするための部品もそろっています。

まとめ：記憶は増やすものではなく、選んでメンテナンスするもの

  • なぜリポジトリに置くのか・・・ コンテキストには限りがあり、必要な知識を毎回プロンプトに詰め込めないからです。poteto氏はコードベースを「究極の記憶」と呼んでいます。
  • どう古くなり、どうメンテナンスするのか・・・ テストやlintは古くなればCIが知らせますが、Feature MapのようなMarkdownは何も知らせずに古くなります。/maintain-verification-skill で繰り返し確かめ、アプリが壊れているときは記憶のほうを直さずに報告します。
  • 何を消すのか・・・ 場当たり的な回避策と、同じことをする2本目の書き方です。どちらも次のエージェントの手本になります。試しに入れた変更は、『Bug fix』Playbookに従い、証拠で否定された時点で元に戻します。推奨する書き方は1つに絞り、それ以外はlintで止めます。どの書き方にするかは人間が決めます。
  • どう続けるのか・・・ コードベースを保つ仕事は、庭のメンテナンスと同じく、追加するだけでなく取り除き続ける仕事です。pstackには、同じ指摘を仕組みにする原則や、チェックの抑制を点検する /no-comments など、メンテナンスを助ける部品があります。

ここまでで、信頼の対象（第2章）、信頼を増やす方法（第3章）、信頼を引き継ぐ記憶（第4章）がそろいました。第5章では、講演の最後のテーマである自動化を扱います。自動化を最後に置く理由、どの仕事から自動化してよいのか、何を自動化できるのか、そして自動化したあと人間に何が残るのかを解説します。
