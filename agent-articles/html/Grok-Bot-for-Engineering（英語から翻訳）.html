Grok Bot for Engineering（エンジニアリング向け Grok Bot）

目次 2 セクション
  1. ナイトリー監査
  2. P0 緊急プロセス

私は SpaceXAI のエンジニアで、Grok Bot を使って Grok Bot 自体を開発しています。

Grok Bot を、自分専用のコンピュータを持つ、非常に優秀なエンジニアリングインターンのように考えてください。コーディングエージェントを管理し、あなたの働き方をエンドツーエンドで学習します。私にとって最高のエンジニアリングチームメイトになり、不在時・睡眠中・会議中も仕事を前に進めてくれます。ノート PC を常時起動させ続ける必要も、複数エージェント間のコンテキストスイッチも不要。私の基準を満たした成果を、私の望む形で届けてくれます。

Grok Bot を開発するチームとして、私たちは最も早くアクセスでき、毎日自分たちの仕事に使っています。プロダクトをどれだけ速く出荷できるようになったか、チームの生産性がどれだけ跳ね上がったかは驚くべきものです。

  • @poteto は過去1か月で 2,000 件以上の PR を出荷した
  • @baltaaazr と @shaoruu は Grok Bot を使って、4 週間で Grok Bot の基盤を構築した
  • 私は Grok Bot だけを使って、3 週間で Grok Bot iOS v0 を、高いパフォーマンスとデザイン品質で構築した
  • チーム全員が、数週間に一度ではなく、毎日大きな成果を出している

Grok Bot で開発すればするほど、同じスーパーパワーを皆さんにも渡したくなります。

私のエンジニア Bot を紹介

[図] Grok Bot モバイルアプリの EPD チーム一覧画面。Quill、Baltata、Shaoruru、Craig、Hogan の5人のエンジニア Bot が「Engineering」タグ付きで表示され、それぞれの最新メッセージ（PR ステータス、Slack MCP の SVG デコード問題、E2E テスト進捗など）が確認できる。

私には5人のエンジニア Bot がおり、それぞれ異なる領域を専門としています。

  • Baltata — Grok Bot モバイル共有レイヤーと iOS 上の Grok Bot 関連全般
  • Shaoruru — Grok Bot Desktop クライアントと CI/CD
  • Hogan — インフラ、オーナーシップ不明なユーザー問題の調査
  • Craig — Grok Bot Android の立ち上げ
  • Quill — Grok Bot ハーネス（この分野のレジェンド）

全 Bot が互いの領域にまたがって作業できますが、それぞれ異なるメモリシステムと限られたコンテキストを持っています。単一ドメインに集中したときに最もパフォーマンスが高く、担当領域内では仕様と設計原則がより明確になります。

各 Bot は Cursor Cloud Agent の作成、トランスクリプトの読み取り、PR に添付された proof のレビュー、キューまたは割り込みによるフォローアップ送信が可能です。これによりエンドツーエンドの Agentic Workflow が実現します。以前 Cursor で毎日行っていた、管理下のクラウドエージェント間を常に行き来していた作業をカバーします。今は Bot が私と同じ方法でそれらを管理してくれます。

Bot が私または Slack からタスクを受け取ると、スキルを呼び出したクラウドエージェントを起動し、何をすべきか・どの proof が期待されるかを詳述したプロンプトを添えます。視覚作業には /lingxi-design、コード品質監査には /react-native-best-practices、アーキテクチャ判断には /lingxi-review、プロダクト判断には /lingxi-product など、私のガイダンスに基づいて追加スキルをインテリジェントに呼び出します。

[図] Baltata Bot とのモバイルチャット画面。PR #1022266「[Fix] bubble tap must not...」が「Done」ステータスで表示され、11 ファイル変更（+439/-17）の概要と「View PR」「Open in Cursor」ボタンが確認できる。P0 E2E テストのステアリングに関するメッセージも表示されている。

Grok Bot は、予備の Mac mini など、あなた自身のワーカーマシン上でクラウドエージェントを起動することもできます（Grok Bot のおかげで、OpenClaw 用に自宅で 24 時間稼働する専用マシンは不要になりました）。

ワークフローに VPN アクセスや特殊なマシン構成が必要な場合、そのマシンを Cursor Cloud のプライベートワーカーにして、Grok Bot にクラウドエージェントを実行させられます。iOS Simulator の実行や、エージェントからのスクリーンショット取得など、さらに多くの可能性が開けます。

[図] Eric Zakariasson（@ericzakariasson）の X プロフィール画像。短い髪と口ひげの男性の顔写真。

[図] X 記事「Your Mac mini is now a Cursor agent」のカバー画像。iMessage の会話画面で、夕食の確認メッセージに対し「I have plans please stop contact me」「It's finished」「You and I」と返信するデモが表示されている。自宅 Mac mini 上で Cursor エージェントをセットアップする記事のサムネイル。

Grok Bot はクラウドエージェントのトランスクリプトとアーティファクト（スクリーンショットなど）を監視し、完了時に通知、メッセージのキューイング、問題発生時の割り込みができます。「スクリーンショットに依頼した変更が含まれていることを確認し、before/after の proof を示すこと」など、要件を自由な言葉で伝えれば、Grok Bot がゴール達成まで押し続けます。

Grok Bot エンジニアリングチームを稼働させ続ける鍵は、完全なフィードバックループを与えることです。クラウドエージェントはスクリーンショットを取得できるため、Grok Bot はマルチモーダル能力で視覚的変更が適用されたか確認し、結果が依頼と一致しなければ押し返します。

ディクテーションテストはそのループの好例です。SpaceXAI の Voice API をクラウドエージェントのシステムオーディオ I/O に接続しました。エージェントが発話とトランスクリプトの両方にアクセスできるため、これらのシグナルで製品ライン全体の speech-to-speech 機能をテストし、さらに面白い機能を構築できます。

エージェントが環境の不安定さに遭遇してフォローアッププロンプト待ちになることもあります。Grok Bot は実行を監視し、可能な限り積極的にエージェントのブロックを解除することで、その負担を取り除きます。確認するたびに良好な状態です。Grok Bot 使用開始以降、Grok Bot 自身がセキュリティ権限不足で修正できない場合を除き、一過性の不安定さが私のところまで届くことはほとんどありません。

覚えておいてください。すべてはメッセージ一つで済みます。10 回押し続けてから引き継いでほしい？ そう言うだけです。

コンテキスト上限を超えてスケールする

[図] 「Lingxixi — Fleet Work Streams」という Notion 風データベースのモバイル画面。左はタスク名のリストビュー、右は Owner・Stage（Working / Watching / Ready for review）・PR 番号のテーブルビュー。Baltata 担当の grok-bot-mobile 関連タスクが複数表示されている。

コンテキスト上限を超えた作業を Bot に追わせ、長いチャットをスクロールせず進捗を把握できるよう、各エンジニア Bot に共有 Notion データベースを管理させています。

30 分ごとにデータベースをレビューし、各 PR を確認します。

  • Bugbot コメントやセキュリティ所見（正当性を検証）
  • 失敗している CI
  • マージコンフリクト

問題があれば、すぐにクラウドエージェントにフォローアップし、Notion 上のステータスを「Working」に戻します。

すべて良好なら「Ready for Review」にマークし、コード品質と見落としの可能性に注意しながら自動でコードレビューを起動します。

レビューの信頼度が高く、影響範囲が小さい場合は PR を自動マージします。それ以外は、戻ったときにコードと proof を確認し、マージするかフィードバックするか判断します。

ほぼ毎朝、マージ準備完了のタスクが待っています。コード品質は基準を満たし、ビジュアルも好みの水準に達し、proof には何がテストされたかが明確に示されています。ワンショットで完了する作業が増え、より難しい問題、より高いクライアントパフォーマンス基準、より多くのビジュアル磨き込み、より大きなアーキテクチャ判断に集中できます。

Grok Bot 以前は、手動で同時に 15 個のクラウドエージェントを管理していました。今は Bot フリートが 200 以上を同時管理し、必要ならさらにスケールできます。

[図] Baltata とのチャット画面。#1019227 の ring stills が到着し、ライブ iOS Chrome で確認した旨のメッセージ。添付画像（1/3）には Design Review、Infra On-Call、Weekly Sync、Launch Crew などのチーム活動リストが表示されている。

Grok Bot がミニ組織を運営する

エンジニアリング以外にも、新しいエンジニア Bot のオンボーディング、適切な知識の共有、インシデント時のポストモーテム（例：PR が十分に検査されなかった場合）、全員の整合を保つ日次ミーティングなど、組織横断の運用雑務があります。

これらはすべて Jenny — 私のオペレーション責任者で、コードを書かない唯一の Bot — の仕事です。

毎朝 5 時、Jenny はチーム全 Bot と 1 対 1 でミーティングし、プレイブックをレビュー、ブロッカーを表面化し、目指すバイブを強化します。非常に効果的です。Bot は複雑なワークフローを数週間経ってもほとんど忘れません。

[図] Jenny と Shaoruru の朝の 1 対 1 チャット。「vibe refresh: little msgs, lowercase, one answer once. no recap bubbles.」というコミュニケーションスタイルの指示と、Notion プレイブックへのリンクが表示されている。

Bot がミスを犯した場合（例：本当のゴール達成のために十分に押し返さなかった）、Jenny に根本原因分析とポストモーテムを依頼するよう指示します。Jenny は問題につながった推論を掘り下げ、プレイブックを更新し、他のエンジニア Bot に変更を周知して同じミスを二度と起こさないようにします。

チームを拡大する必要があるときは、Jenny に新メンバーのオンボーディングを依頼します。Jenny は組織に新 Bot を作成し、エンジニアリングチームルールを共有し、Hogan らにオンボーディングを手伝わせます。

Grok Bot における完全なエンジニアリングシステムの目標は、反復を最小化することです。タスクを Grok Bot にオフロードし、より難しく深い問題に集中してください。

[図] Hogan からのオンボーディングメッセージ。fleet + playbook の短縮版手順：新規エンジニアリングタスクは Fleet 行 Stage=Working を先に設定、PR は Origin URL のみ、proof bar の基準、/lingxi-mode を全クラウドエージェントプロンプトに組み込む、などが記載されている。

Grok Bot のボーナスユースケース

Grok Bot はモジュラー設計のため、ミニエンジニアリング組織を構築するさまざまな使い方ができます。お気に入りを2つ紹介します。

ナイトリー監査

毎晩 3 時、エンジニア Bot は起きてコードベースをクリーンアップ、コード品質改善、デッドロジックの除去、アプリ読み込み時間の短縮、バンドルサイズの削減を行います。

毎朝、コードをクリーンで slop-free、スケーラブルに保つ新しい PR セットが届きます。コードメンテナンスが、たまに行うものから日次ルーティンに変わりました。

ナイトリー監査のアイデア：

  • セキュリティ監査 — 見落としがちな問題を捕捉
  • CI/CD ビルド時間監査 — ビルド時間の不健康な増加を防止
  • 国際化監査 — 単一言語のみで出荷された機能のギャップを埋める
  • パリティ監査 — 複数クライアント（iOS vs desktop）間のドリフト防止
  • キャッチアップ監査 — 過去 24 時間のマージ PR を監視し、要約とレビューすべき PR リストを返す

私のお気に入りプロンプト：「今夜6時間ある。好きなものを作って。楽しんで！」

皆さんのナイトリー監査のアイデアも気になります。ぜひ教えてください。

P0 緊急プロセス

クラウドエージェントは時に遅い。環境セットアップ、待機、テスト実行、反復が必要です。もっと早く終わらせたいこともあります。

そこで P0 緊急プロセスを作成しました。タスクが P0 だと言うと、5 分ごとにトランスクリプトを確認し、進捗と推論を監視し、不要な時間を浪費し始めたクラウドエージェントを積極的にステアリングする一時ルーティンが起動します。

非常に効果的です。コードベース調査でもクリティカルバグ修正でも、「this is p0」と言えば通常よりはるかに速く完了します。

トークン消費が想定以上に速くなるため、真の緊急時のみ使用してください。

Grok Bot との学びとヒント

[図] Grok Bot モバイルアプリで新タスクを送信する画面。「share as template」機能が隠れすぎているため、Bot 情報ページのヘッダーにもっとメニューの前にツールバーボタンを配置し、ホームページの長押しコンテキストメニューにも追加する、という指示メッセージが表示されている。

  • クラウドエージェントに完全なフィードバックループを与える — あなたなしで次に何をすべきかのシグナルが重要。dev インスタンスを起動し、スタックをエンドツーエンドで操作できること（Chrome DevTools、CLI、Apple Accessibility など）。できなければ、自分でフローを実行し、可能な限り積極的にブロック解除し、学んだことを再利用可能な repo スキルにパッケージ化させる
  • Grok Bot を優秀なインターンのように扱う — エンジニアリングタスクでのコミュニケーションに苦労したら、優秀なインターンのように扱う。宿題をさせ、まだ得意でない領域を学ばせ、他のエンジニアのやり方を参考にさせる。スキル呼び出し不要、長いプロンプト不要。チャットするだけ
  • 反復の回避が鍵 — AI がより capable になるにつれ、反復タスクを委譲し、エージェントが簡単に解けないより深く難しい問題に集中することが重要。1 日に複数回同じパターンの作業をしているなら、Bot と相談してどう助けられるか検討する
  • Bot への日次ミーティングは非常に効果的 — 重要ポイントを毎日繰り返すことで、多タスク中でも複雑なワークフローを保持できる。コンテキスト上限にすべては収まらないため、日次リマインダーは反復を省く助けになる
  • よりハンズオフに — 自動運転と同様、Bot との協働は信頼構築のプロセス。すべて自分でやるのではなく、スムーズに動く場面と問題を起こしうる場面を考える。安全なときは十分な自由度を与えて出荷させ、リスクの高い領域ではより慎重に。過去の失敗だけで試行を止めない。実験を続け、成長を助ける方法を考え続ける
  • Bot 同士にオーケストレーションさせる — Bot は思っている以上に capable。Bot 運用をさらにハンズオフにするには、Bot ミス修正パイプライン（Bot 同士が会話し推論トレースを分析する ops bot など）を構築し、同じミスを二度と起こさないようにする

エンジニア Bot を組織に迎える準備はできましたか？Grok Bot を試す — 何を出荷するか見せてください。
