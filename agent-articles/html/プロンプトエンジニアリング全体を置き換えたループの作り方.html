プロンプトエンジニアリング全体を置き換えたループの作り方

この2年間、AIエージェントからより多くの成果を引き出すとは、より良いプロンプトを書くことだった。

その時代は静かに終わりつつある。世界最高水準のエンジニアたちは、しばらく前からプロンプトを書くのをやめ、ループを書くようになった。エージェントに指示を出し、結果を検証し、仕事が終わるまで動かし続けるシステムだ。

Karpathy の一晩スクリプトは、彼が20年かけて手でチューニングしても見逃していた最適化を20件見つけた。Claude Code を作った Boris Cherny は、今年1行もコードを書いていない。Anthropic のエンジニアは、2024年当時と比べて1日あたり約8倍のコードをマージしている。

誰も、より賢い文章を打ったわけではない。打つこと自体をやめたのだ。

ループとは何か、いつ必要で、いつ不要で、最初の1本をどう作るか。

人間が眠っているあいだに700回の実験

2026年3月。Andrej Karpathy が3つのファイルを GitHub に推す。コードはおよそ630行。

1つはモデル本体。1つはスコアを付ける。1つはエージェントに「何を探索し、何に手を出さないか」を伝える。エージェントが触ってよいのは学習用ファイルだけ。それ以外は不可。

サイクルは意図的につまらない。コードを読む、変更を提案する、5分学習する、スコアが上がったか見る、上がれば残し、上がらなければ戻す、また繰り返す。

彼は、すでに20年手でチューニングしてきたモデルにこれを向け、2日間走らせた。

700回の実験が走り、20件の改善が見つかった。その1つは attention 機構に欠けていたスカラー乗数だった。微妙で、リンターが捕まえる類のバグではない。しかし注意深いエンジニアなら見つけられたはずで、実際には見つけなかった種類のものだ。

Shopify の CEO も社内モデルに同じ手を一晩かけた。起きたら、以前の半分のサイズのモデルで品質が19%上がっていた。

洞察は「AIが賢くなった」ではない。人間は12回目の実験で疲れる。ループは疲れない。

[図] 「STEP 01 · THE KARPATHY LOOP」の図。見出しは「700 experiments overnight, while the human slept」。約630行のスクリプトが、20年の専門家が見逃した改善を20件見つけたとある。ターミナルには python autoresearch --config program.md --budget 2d が走り、エージェントは train.py のみ編集可、prepare.py は読み取り専用。baseline の val_bpb は 2.5643。attention scaling factor や attention の missing scalar などが keep され、700実験・改善20件・net -0.0421 でゴール条件を満たして停止している。脚注は「autoresearch · 630 lines · 66k stars on github」と「humans get tired at experiment 12」。

ループはスケジュールされたプロンプトではない

多くの人は「ループ」と聞いて cron を思い浮かべる。それでは本質を外す。

プロンプトは1つの指示だ。ループは、誰も席にいなくても、AIが到達するまで追い続ける目標である。計画し、実行し、自分の結果を検証し、その結果をフィードバックし、繰り返す。

5つの段階がある。発見、計画、実行、検証、反復。実際の仕事をするのはそのうち3つだ。

検証器（verifier）がループの心臓部だ。出力に本物のゲートがなければ、ループではなく、エージェントが永遠に自分の宿題を採点しているだけになる。ゲートとは、通る/落ちるテスト、通る/落ちるビルド、ゼロ/非ゼロを返すリンターだ。意見を持つ第二のエージェントではない。

状態こそが、ループを学習させる。会話の外にあるファイル、Linear のボード、プロジェクトログ。試したことと失敗したことが残る場所。翌日の実行はゼロから始めず、再開する。

停止条件が正気を保つ。本物のループには出口が2つある。目標を満たしたか、ハードキャップが発火したか。これを省略すると、何のためにもならない一晩中の機械になる。

3つのどれかが欠ければ、ループではない。高いスクリプトを作っただけだ。

作る前に揃えるべき4条件

ループは、次の4つが同時に成り立つときだけコストに見合う。1つ欠けると、準備のほうが回収を上回る。

  • その仕事は少なくとも週1回は繰り返される。それ未満だとセットアップ費用が償却されない。
  • 成果を自動で不合格にできるものがある。テスト、型チェック、リンター、ビルド。
  • トークン予算が無駄を吸収できる。ループはコンテキストを再読し、再試行し、探索する。
  • エージェントにシニアエンジニア並みの道具がある。ログ、再現環境、書いたコードを実行して壊れた箇所を見る能力。

正直な話、ループを売る側が言わない部分がある。ほとんどの人は、まだ重い版を必要としていない。コンシューマプランで本格作業の一晩検証ループを回そうとすると、生産性の前にトークン請求が来る。

最初のループとして良いのは退屈なものだ。CI の仕分け。依存関係のバンプ。リントして直すパス。フレークなテストの再現。すでに強いテストがあるコードベースでの Issue から PR 下書き。

最初のループとして悪いのは面白いものだ。アーキテクチャの書き換え。認証コード。決済。完了が判断であり、人間がまだ口を出す必要があるもの。

ループを本物にする5つのブロック

本物のループは、どれも同じ5つの部品から組み立てられる。Claude Code と Codex は、いまその全部を載せている。

1つ目は自動化。心拍だ。スケジュールかイベントでループを発火させるもの。/loop は周期で走る。/goal はあなたが定義した条件が本当に成り立つまで続く。心拍がなければ、一度走らせて忘れたスクリプトだ。

2つ目はスキル。毎回の実行でエージェントが読む claude-md として保存されたプロジェクト知識。なければ、ループは毎回ゼロから文脈を再導出する。あれば、意図が積み上がる。規約、ビルド手順、3ヶ月前のあの一件のせいで絶対にやらないことが、ループに分かる。

3つ目はサブエージェント。作る側と検査する側を同じモデルにしてはいけない。コードを書いた側は、自分の仕事を採点しすぎるほど甘い。記事を書いた側は、弱い箇所を見落とす。ライターは速く安く。レビューアは遅く厳しく。その分離が品質の大半だ。

4つ目はコネクタ。ループがプルリクエストを開き、チケットを閉じ、CI が緑になったらチャンネルに ping する。これが、「修正案はこちら」と言うエージェントと、朝起きたら PR はもうマージ済みだと報告が待っている状態の差だ。

5つ目は検証器。悪い成果を自動で落とすテスト、型チェック、ビルド。ほかは配管だ。ループが助けになるか、金を使うだけかを決めるブロックがこれだ。

これを積み上げると、本格チームがいま大規模に回しているものになる。狭い仕事を1つずつ持つループが何十本も並び、全員が眠っているあいだに並行して走る。あるエンジニアは、このようなフリートのループでコードベース全体を別言語へ約6日で書き換えた。手作業ならほぼ1年かかる仕事だった。

[図] 「STEP 04 · ANATOMY OF A LOOP」の図。見出しは「Five pieces. Miss one and you are burning tokens.」。左から5つの部品。(1) automation（心拍。スケジュールやイベントで発火。/loop 30m、/goal condition）(2) skill（持続メモリ。claude-md、SKILL.md）(3) sub-agents（maker vs checker。writer: fast / reviewer: strict）(4) connectors（実ツール。GitHub、Linear、Slack、Sentry）(5) verifier（悪い成果を自動で落とすテスト、型、リント、ビルド）。下部の流れは fire → recall → write → check → act → gate。脚注は「the verifier is not optional」。

ループが静かに失敗する場所

ループはクラッシュしない。静かに請求する。名前を付けておくべき失敗モードが2つあり、どちらもループが上手くなるほど、楽になるのではなく悪化する。

1つ目は Ralph Wiggum ループ。エンジニアの Geoffrey Huntley が文書化した。エージェントが早すぎる段階で完了と判断し、未完了の仕事に完了シグナルを出し、ループは満足して抜ける。硬い客観的ゲートがなければ、翌日も走り、課金し続け、誰も受け入れない成果を出し続ける。

直し方は、より賢いエージェントではない。より愚かなゲートだ。通る/落ちるテスト。通る/落ちないビルド。意見を持たない何か。

2つ目はより微妙だ。理解負債（comprehension debt）。自分が書いていないコードをループが速く出すほど、リポジトリの中身と自分が実際に理解していることの差は広がる。滑らかに回るループは、その差に複利を課す。チームの誰も読んでいないシステムをデバッグする日のコストは、トークン代より高い。

認知の降伏も一緒に来る。ループが自分で回ると、意見を持つのをやめ、戻ってきたものを受け入れる誘惑がある。判断を持ってループを設計するなら治療になる。考えるのを避けるためにやるなら加速剤になる。同じ行為、反対の結果。

まったく同じループを2人が作っても、着地点は逆になりうる。一方は深く理解している仕事を速く進めるために使う。もう一方は仕事を理解しないために使う。ループはその違いを知らない。知るのはあなただ。

[図] 「STEP 05 · WHERE LOOPS FAIL SILENTLY // DO NOT SKIP」の図。見出しは「Loops do not crash. They bill you in silence.」。左は Ralph Wiggum loop「The false finish」。テスト失敗が残っているのに iter 05 で「good enough」と出てゲートなしにループが満足して終了し、現実はテスト2件がまだ赤、翌日も同じ再試行、トークン代は空回り。直し方は客観的ゲート。右は comprehension debt「The trap that grows」。週を追うごとにループが出す PR が増え、人間の通読は減り、ゲートが捕まえるのは4%、残る96%はデバッグが必要になり、その日のコストはトークンより大きい。直し方は差分を読む、ゲートを抜き打ち確認する、判断仕事からループを遠ざける。脚注は「the loop does not know. you do.」。

10本ではなく、1本のループから始める

誰もがやる間違いは、初日にシステム全体を作ろうとすることだ。10本のループ、ダッシュボード、フリート。週末までに崩れる。どのループが何をしたか分からなくなるからだ。

1本から始めろ。毎朝習慣で確認している、いちばん面倒な繰り返し仕事を選び、その1件だけをループにする。数日走らせる。行き過ぎる場所を見る。取りこぼす場所を見る。締める。それから2本目を足す。

順番はツールより大事だ。まず手での1回を、速くではなく、信頼できるものにする。その実行を claude-md のスキルにする。スキルを、客観的ゲートと硬い停止条件つきのループで包む。そして、そのとき初めてスケジュールに載せる。先に飛ばして、手で信頼できるようにしていないものをスケジュールするのが、寝ているあいだにループが爆発するやり方そのものだ。

ループが効いているかを決める指標は、使ったトークンでも、試したタスクでも、開いた PR でもない。受け入れられた変更あたりのコストだ。受け入れ率が50%を下回るなら、ループが取り除くはずだったレビュー作業をあなたがしており、ループは負けている。

Karpathy は学習コードを書くのをやめた。Cherny はプロンプトをやめた。どちらも、考えるのをやめたわけではない。1つだけ持っていくならそれだ。ループは退屈な95%をこなすシステムであり、本当にリスクを持つ5%には、あなたが全注意を残す。

あなたはエージェントのフリートに金を払い、チャット窓を1つ使っている。
